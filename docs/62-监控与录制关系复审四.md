# 62 监控与录制关系复审四

> 状态：v1.1（2026-11-07，[61](61-监控录制联动修复五.md) 修复之后的复审；**F1/F2/F4/F6 已在 [63](63-监控录制联动修复六.md) 修复并真机验收**，F3/F5/F7 仅文档化）｜对象：monitor.rs、recorder.rs、broker.rs、disk.rs 与前端事件订阅｜上游：[54 v3.5](54-监控与录制关系审查.md)、[60](60-监控与录制关系复审三.md)、[61](61-监控录制联动修复五.md)｜测试环境：macOS 27.0.1 arm64、ffmpeg 9.0.2、真实 bilibili 在播房间
>
> 本轮方法：不引用前几轮结论，重新按「谁能在一条录制跑起来之后改变它」把代码过一遍，再用真机验证。共 4 组测试：T1 间隔 30→3600（2 路真实录制）、T1b 间隔 3600 下断流续录、T2 interval=1 + 并发上限 1 面 3 路、T3 软删除房间 + 伪造 ffmpeg 冷退出。测试数据已清理，产物只在临时目录，未改动业务代码。

一句话结论：**检测间隔和失败退避只决定「什么时候去看一眼」，不会碰已开录的会话；但它们也不只是「更新状态」——监控仍握着三条能改录制的开关（两次确认离线后停录、磁盘红线停录、自动开录），还带两个每拍发生的副作用（写 `touch_room`、推 `rooms://changed`）。本轮新发现 3 条问题：检测失败每拍无条件推事件（F1）、被删除的房间仍会续录 3 次并记成「自然结束 + 满足结束通知条件」（F2）、非限流失败完全不退避（F6）；另有 3 条观察/取舍（F3–F5）。**

## 1. 结论先行

### 1.1 四个问题的判定

| 问题 | 判定 | 证据 |
| --- | --- | --- |
| 正在录制的房间会不会被检测间隔影响 | **不会** | T1：间隔从 30 改成 3600 后，92 秒内 `last_checked_at` 冻结在 1793986900 / 1793986897，同期两个分片 1,310,720 → 19,398,656 与 5,505,024 → 12,320,768 字节 |
| 会不会被「失败退避」影响 | **不会** | 退避只改下一拍的 `next_at`（[monitor.rs:227](../src-tauri/src/monitor.rs#L227)）；已开录会话由 recorder 自己的 1 秒 watcher 驱动，与 monitor 的排期无关 |
| 监控是不是「只更新状态」 | **不是** | 它还能结束录制（离线确认 → `stop("stream_ended")`、磁盘红线 → `stop("disk_full")`）、能开始录制（`start_checked`）；另外每拍写库 `touch_room`、推 `rooms://changed` |
| 是不是只有「直播源真没数据」才影响录制 | **不是** | T3：源还在播、房间被软删，仍续录 3 次、记成 `finished/stream_ended`，并满足 `emit_notice("ended")` 的条件；F1/F6 则在源健康时造成 UI 全量重拉与请求不退避 |

### 1.2 真正能结束一条录制的入口（本轮复核）

只有这 4 类，加上「ffmpeg 自己退出」这条自愈路径：

| # | 入口 | 触发者 | 落点 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 用户停录 | 前端 / 托盘 / 删除房间 | `stop("stopped")` | `finished/stopped` |
| 2 | 磁盘红线 | monitor 每拍 | `stop("disk_full")` | `aborted/disk_full` |
| 3 | 平台两次确认离线且文件不增长 | monitor 每拍 | `stop("stream_ended")` | `finished/stream_ended` + 结束通知 |
| 4 | 应用退出 | SIGTERM / quit | `shutdown_all` | `aborted/app_exit` |
| — | ffmpeg EOF / 崩溃 | 进程自己 | watcher → respawn ×3 → 平台判定 → `finalize` | 取决于平台状态与确认凭据 |

第 3 条有两道保险，本轮复核仍然成立：两次确认（[recorder.rs:405](../src-tauri/src/recorder.rs#L405)）+ 文件仍在增长就按误报处理（[recorder.rs:438](../src-tauri/src/recorder.rs#L438)）。

### 1.3 间隔 / 退避相关参数

| 参数 | 默认 | 范围 | 作用对象 | 影响已开录会话？ |
| --- | --- | --- | --- | --- |
| `monitor.interval_sec` | 30 | 0–86400 | 每个房间的网格间隔 | 否 |
| `monitor.backoff_cap_sec` | 120 | 60–3600 | 限流退避上限 | 否 |
| `BACKOFF_MAX_SHIFT` | 5 | — | 退避倍数 `base*2^streak` 的封顶指数 | 否 |
| 全局 / 每平台并发 | 12 / 4 | — | 同时进行的检测请求 | 否（录制并发另有 `record.max_concurrent`） |
| `STALL_TIMEOUT` | 60s | — | 无增长看门狗 | 是（会杀进程重启） |
| `EARLY_EXIT` | 12s | — | 秒退门槛 | 是（决定续录还是探测平台） |
| `MAX_RESTARTS` | 3 | — | 续录预算 | 是（用尽即收尾） |
| `MAX_EOF_RETRIES` | 2 | — | 干净 EOF 的复核次数 | 是 |
| `ENDED_BLOCK` | 600s | — | 自然结束后的静默 | 是（期间不重开） |
| 磁盘红线 | 2 GiB 起 / 1 GiB 守 | — | 开录与续录 | 是（低于红线停录） |

## 2. 真机测试

### 2.1 T1：间隔 30 → 3600，两路真实录制

- 01:41:06 与 01:41:11 分别开始录 bilibili 6（主播甲）与 545068（主播乙），quality 为「超清 · FLV · H.264」「高清 · FLV · H.264」。
- epoch 1793986872 把 `monitor.interval_sec` 改成 3600。
- 最后一次检测：1793986900（甲）、1793986897（乙）——这是改动前已经排上的那一拍，属预期内的「残留一拍」。
- epoch 1793986992（距最后一次检测 92 秒、距改动 120 秒）再看：`last_checked_at` 一点没动；分片在这段时间里从 1,310,720 → 19,398,656（乙）、5,505,024 → 12,320,768（甲）。

**结论：间隔只影响「下一次去问平台的时间」，与 ffmpeg 是否继续写盘完全无关。**

### 2.2 T1b：间隔 3600 时断流续录照常

01:34:03 对主播甲的 ffmpeg `kill -9`（pid 68111）。01:34:04.878 取流请求 `ok=true`，01:34:04.967 打出「断流后续录 room_id="rm-t1a" start_number=1 restarts=1」，生成 part0001.ts，会话仍是同一条 `recording`，DB 里没有多出第二条会话。

**结论：续录是 watcher 的行为，不经过监控排期；把间隔调到 1 小时也不会让断流续录失效。**

### 2.3 T2：interval=1 + 并发上限 1，面对 3 路在播

3 个真实在播房间、`record.max_concurrent=1`、`monitor.interval_sec=1`：

- 25 秒后只有 1 条会话、1 个 ffmpeg、1 条「开始录制」。
- 被挡的两路各只有 1 条 WARN「自动开录失败 err=同时录制已达上限（1 路）…」（17:34:37.293 / .314，均在原因首次出现时），之后 40 秒 WARN 数不再增长——C7 的去重生效。
- 但 DEBUG「自动开录仍失败」40 秒里 89 条（≈ 每拍每路 1 条），随房间数线性增长（F7，见 §3）。
- 预检查在发网络请求之前就拦住了，所以本轮没有走到「并发已满」的插入复查分支。

### 2.4 T3：软删除房间 + 伪造 ffmpeg 冷退出（F2 复现）

测试媒体目录用 `HIVECAST_MEDIA_DIR` 指到临时目录，`post.auto_remux=false`，`interval=1`。假 ffmpeg 识别 `-version`，按输出参数里的 `%04d` 写 part0000.ts，先写 120,000 字节、每秒追加 40,000 字节，9 秒后 `exit 0`（< `EARLY_EXIT` 12 秒）。

- 01:39:13.219 开始录制；同一秒用 sqlite3 把 `room.removed_at` 置为当前时间（模拟「房间被删除，但没有经过 room_remove 的 stop」）。
- 9 秒后 ffmpeg 干净退出 → 三次「断流后续录 restarts=1/2/3」（01:39:26.319 / 01:39:39.414 / 01:39:52.514）→ 01:40:02.547「续录次数用尽 restarts=3」。
- 01:40:02.551「录制结束 status="finished" reason="stream_ended" file_size=480000」，DB：`finished|stream_ended|480000|duration_ms=49000`。
- 全程没有「未能确认平台已下播」的 WARN，说明 `confirmed_end=true`——来源是 `platform_state` 把「房间查不到 / 已移除」直接当离线（[recorder.rs:543](../src-tauri/src/recorder.rs#L543)）。

**后果**：给一个用户已经删掉的房间记「自然结束」，并且满足 `mark_ended`（[recorder.rs:1381](../src-tauri/src/recorder.rs#L1381)）与 `emit_notice("ended")`（[recorder.rs:1458](../src-tauri/src/recorder.rs#L1458)）的条件，会弹「直播已结束」；同时白白续录 27 秒、留下空分片。

## 3. 本轮新发现

| 编号 | 级别 | 症结 | 证据 |
| --- | --- | --- | --- |
| F1 | P2 | 检测失败时每拍无条件 `emit(EVENT_ROOMS_CHANGED)`，前端收到就全量重拉房间列表 + 会话列表；间隔调到 1 秒、平台又持续报错时，就是每秒 N 次全量刷新 | [monitor.rs:555](../src-tauri/src/monitor.rs#L555)；前端 [MonitorPage.tsx:321](../src/features/monitor/MonitorPage.tsx#L321) `onRoomsChanged(() => load())`、[WatchPage.tsx:161](../src/features/watch/WatchPage.tsx#L161) `roomsList()` |
| F2 | P2 | 被删除（软删）的房间：`respawn` 只判「行不存在」不判 `removed_at`（[recorder.rs:1231](../src-tauri/src/recorder.rs#L1231)），会继续续录到预算用尽；收尾又被 `platform_state` 的「已移除 → Offline」当成确认下播，记 `finished/stream_ended` 并满足结束通知条件 | 真机 T3（§2.4）；代码 [recorder.rs:543](../src-tauri/src/recorder.rs#L543) |
| F3 | P4 | 调大间隔后会多跑一拍「已经排上的检测」（T1 的 1793986897/1793986900），属排期语义而非缺陷；文档化即可 | T1 |
| F4 | P3 | 把间隔改成 0（关闭自动检测）会 `schedule.clear()`（[monitor.rs:116](../src-tauri/src/monitor.rs#L116)），在途检测的结果回不来（`drain` 找不到 entry），重新开启时该房间会立即再查一次，同一房间可能同时有两次检测 | 代码 |
| F5 | P3 | 平台侧「已下播」的确认依赖检测节奏：间隔 86400 时两次确认要两天，实际停录只能靠 ffmpeg EOF；大间隔下这条停录入口形同关闭（设计取舍，需要文档化） | 代码 |
| F6 | P2 | 非限流失败（房间不存在、解析失败）走 `Outcome::Failed`，网格直接 `now + base`，完全不退避；配合 F1 就是每个间隔一次请求 + 一次 UI 全量刷新 | [monitor.rs:200](../src-tauri/src/monitor.rs#L200) 分支与 [monitor.rs:227](../src-tauri/src/monitor.rs#L227) |
| F7 | P4 | interval=1 且多路被并发上限挡住时，每路每拍 1 条 DEBUG（实测 40 秒 89 条 / 2 路），日志量随房间数线性增长（WARN 已去重） | 真机 T2 |

### 3.1 F2 的可达性与定级

正常删除房间会先 `stop("stopped")`（commands.rs 的 room_remove），watcher 拿到 `stop_reason` 后走 `finished/stopped`，不会弹结束通知。F2 成立的条件是「房间行消失 / 被软删，但没有 stop 到达 watcher」：

- 删除请求与 watcher 的平台探测并发（删除设置 `removed_at` 后、`stop` 生效前，ffmpeg 恰好干净退出）；
- 进程崩溃恢复后残留会话，而房间已被删除；
- 外部直接改库（本轮测试用的就是这条）。

三种都窄，但后果是「给不存在的房间弹通知 + 白录」，所以定 P2；修法只需在续录与收尾两条路径上看一眼 `room_removed`。

## 5. 修复建议

1. **F2（先修）**：`respawn` 开头加 `if db.room_removed(room_id) { return false; }`；watcher 每拍先查 `room_removed`，命中就 `finalize(..., Some("stopped"), true)` 并 return——这样既不再续录，也不会弹结束通知（`stopped` 不满足 `emit_notice("ended")` 的条件）。
2. **F1 + F6**：失败分支复用 C7 的「错误文案变化才 emit / 告警」，其余降为 debug；非限流失败也走 `backoff_wait`（或对 `RoomNotFound` 单独用更长间隔），避免坏房间每拍一次请求。
3. **F4**：`base == 0` 时不要 `clear` 排期，只把 `next_at` 推到很远的将来；或在 `drain` 里记录「结果回来但排期已清」并忽略，重新开启时按正常网格重排，不做立即补考。
4. **F3 / F5 / F7**：只写文档，不改代码；F7 可在日志层面对同类失败做 1 分钟折叠。
