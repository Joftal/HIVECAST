# 抖音关注导入与关注池

> 2026-11-16。范围：监控页「导入关注」新增抖音来源、全量分页选择、离线关注进入待开播池、开播后自动转成正式房间并录制，以及真实接口分页/房间数据解析的两个修正。

## 1. 要解决的问题

抖音关注列表里只有正在直播的项才带可用的房间入口。离线关注没有 `web_rid`，不能直接建房，也不能像已建房那样每 30 秒单房轮询。原先「导入关注」只支持哔哩哔哩和斗鱼，抖音关注只能手动挑正在直播的房间，离线主播开播后不会被发现。

这次把导入拆成两条路：

- 在播且拿得到 `web_rid`：和普通导入一样，立即创建房间，按用户选择决定是否监控、是否自动录制。
- 暂未开播或暂时拿不到 `web_rid`：写入 `douyin_follow` 关注池，不建房、不轮询；后台每 120 秒翻一次关注列表，开播后自动转正。

## 2. 真实接口与数据形态

关注列表接口：

```text
GET https://www.douyin.com/aweme/v1/web/user/following/list/
  ?device_platform=webapp&aid=6383&channel=channel_pc_web
  &user_id=<自己的 uid>&sec_user_id=<自己的 sec_uid>
  &offset=0&min_time=0&max_time=<上一页 min_time>
  &count=20&source_type=2&gps_access=0&address_book_access=0&is_top=1
```

2026-11-16 用真实账号实测：1490 个关注、75 页、每页 20；不需要 `a_bogus`，带登录 Cookie 即可。响应结构的关键点是：

- `followings`、`has_more`、`min_time` 都在**响应根上**，没有 `data` 包裹。
- 在播项的 `live_status=1`，`room_data` 是 JSON 字符串；里面有 `status=2`、`owner.web_rid`、`user_count`、`stream_url`，但**没有 `id_str` / `id` / `room_id`**。
- 内部 19 位房间号只在关注项外层的 `room_id` 上；`web_rid` 只在 `room_data.owner.web_rid` 上。
- 离线项的 `room_data` 为空，外层 `room_id` 仍可能有值。

实测 75 页中有 42 个在播关注。例如：

```json
{
  "uid": "3250618555442916",
  "nickname": "偷心九月天",
  "live_status": 1,
  "room_id": 7708405304424041000,
  "room_data": "{\"status\":2,\"user_count\":5957,\"owner\":{\"web_rid\":\"205048140143\"}}"
}
```

## 3. 数据模型

`src-tauri/src/db.rs:23` 新增 `douyin_follow`：

```sql
CREATE TABLE IF NOT EXISTS douyin_follow (
    uid TEXT PRIMARY KEY,
    sec_uid TEXT NOT NULL DEFAULT '',
    uname TEXT NOT NULL DEFAULT '',
    avatar_url TEXT,
    web_rid TEXT,
    internal_room_id TEXT,
    is_live INTEGER NOT NULL DEFAULT 0,
    title TEXT NOT NULL DEFAULT '',
    cover_url TEXT,
    area_name TEXT,
    online INTEGER,
    started_at INTEGER,
    monitor INTEGER NOT NULL DEFAULT 1,
    auto_record INTEGER NOT NULL DEFAULT 0,
    promoted_room_id TEXT,
    last_checked_at INTEGER,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);
```

- 主键是关注 `uid`，重复导入只更新，不会产生两行。
- `promoted_room_id` 指向已转正的房间；为空表示仍在池里。
- `monitor` / `auto_record` 保存导入时用户的选择，转正时沿用；自动录制必须同时勾选监控。
- `last_checked_at` 只用于巡检排序和观测，不参与冷却判断。

相关方法：`upsert_douyin_follow`（`db.rs:613`）、`list_douyin_follows`（`db.rs:666`）、`pending_douyin_follows`（`db.rs:685`）、`update_douyin_follow_status`（`db.rs:705`）、`mark_douyin_follow_promoted`（`db.rs:745`）、`release_douyin_follow_room`（`db.rs:763`，删除房间时把关注放回池）。

## 4. 导入链路

后端：

- `commands.rs:318 douyin_follow_page(cursor)`：取一页并给每项补 `in_pool` / `promoted_room_id`，前端据此禁选已入池或已建房的关注。
- `commands.rs:337 douyin_pool_add(items, monitor, auto_record)`：批量写池，返回 `added` / `updated`；空 `uid` 跳过。
- `lib.rs:322` 注册两个命令；`src/lib/ipc.ts:152/157` 对应 `douyinFollowPage` / `douyinPoolAdd`。

前端 `src/features/monitor/ImportFollowsDialog.tsx`：

- `Source` 扩为哔哩哔哩 / 斗鱼 / 抖音，三平台共用同一张表。
- `douyinStatus`（:45）把关注项映射成 `LiveStatus`：`roomId=webRid`、`shortId=internalRoomId`。
- 抖音加载循环（:193）每页 `douyinFollowPage(cursor)`，游标取 `page.nextCursor`；`hasMore` 为假、游标为空或与上一页相同就停，页间等 180ms。
- 全量加载后，只有 `isLive && webRid` 的项走 `roomsImport`；其余走 `douyinPoolAdd`（:427），成功后本地把 `inPool` 置真，行上显示「待开播」。
- 已入池或已转正的关注显示「已添加」并禁用复选框；同时保留「未添加 / 在播 / 待开播」计数。
- 导入结果同时展示建房结果和入池结果；部分失败不清空选择，便于重试。

## 5. 关注池转正

后台任务在 `state.rs:151` 启动，逻辑在 `douyin_follow.rs`：

- `pool_loop`（:479）：启动后等 25 秒，之后每 120 秒跑一次；失败只 warn，不退出。
- `refresh_pool`（:314）：
  1. 只取 `promoted_room_id IS NULL` 的项；池空直接返回。
  2. 没有登录 Cookie 直接跳过，不报错。
  3. 从第一页开始翻关注列表；每页只处理池里存在的 `uid`，并写回最新昵称、头像、在播状态、标题、在线人数、封面、开播时间。
  4. 在播且拿到 `web_rid` 才调 `promote`。离线、缺 `web_rid`、房间信息请求失败都留在池里，下一轮再试。
  5. 所有池项都匹配到，或关注列表翻完，就停止；不为了池里一个靠后的关注无条件翻完 75 页。
- `promote`（:382）：
  - 先按 `web_rid` 请求一次房间信息，确认真的在播；平台说离线就不转。
  - 已有同 `web_rid` 的房间：只更新房间信息并标记已转正，不重复建房。
  - 没有房间：用导入时的 `monitor` / `auto_record` 建 `room`，写 `platform_uid=关注 uid`、`batch_follow=1`、`internal_room_id`，再标记已转正并广播房间变化。
  - 建房失败（网络/风控）只 warn，关注仍留在池里，下一轮重试。
- 转正后的房间进入普通监控：状态、录制、画质、线路、弹幕都按单房链路走；关注池本身不参与录制。

## 6. 这次修掉的两个真实解析缺陷

第一次用真实关注做端到端验证时，池扫描只跑了 1 页、匹配 0 项。定位到两个独立问题：

### 6.1 分页字段只在根上，代码只读 `data`

`parse_follow_page`（`douyin_follow.rs:163`）原来只在 `root.data` 里找 `has_more` / `min_time`。真实响应没有 `data`，于是 `has_more=false`、游标为空，永远只加载/扫描第一页 20 个关注。

修复（:186）：`pick(key)` 先读 `data`，没有再读根；`min_time` 缺失时回退 `max_time`。单测 `parses_root_level_page_from_real_api`（:600）固定真实根结构。

### 6.2 `room_data` 没有房间号，`parse_room` 整项丢弃

`parse_follow_item` 原来直接把 `room_data` 交给 `douyin_batch::parse_room`。真实 `room_data` 没有 `id_str`，`parse_room` 第一行就拿不到房间号并返回 `None`，结果 `web_rid` 永远为空——关注在播也永远不会转正（日志会显示 `matched=1 promoted=0`）。

修复（:255）：如果 `room_data` 自己没有任何 id 字段，就把外层 `room_id` 注入成 `id_str` 再解析；这样 `owner.web_rid`、在线人数、开播时间都能保留。单测 `live_room_data_without_room_id_keeps_web_rid`（:569）覆盖。

这两个缺陷只有用真实关注列表才会暴露：原有单测用的是 `data` 包裹且 `room_data` 自带 `id_str` 的理想结构。

## 8. 边界与已知限制

- **首次转正有延迟**：池任务启动后 25 秒首扫，此后 120 秒一次；导入后最晚约 2 分钟才会发现刚开播的关注。没有做「导入即扫」，避免和正在跑的全量扫描叠加请求。
- **关注列表可能被风控**：401/403 映射为「登录态已失效」，412/429 映射为限流；池任务只 warn，等下一轮。不会把限流误判成离线。
- **隐藏关注/私密关注**：接口不返回的项无法进池；这是平台边界。
- **在播项也可能拿不到 `web_rid`**：例如 `room_data` 只有 `additional_stream_url`；这类项会留在池里，等后续页面补齐。
- **内部房间号精度**：外层 `room_id` 是 19 位整数，serde 按 i64 解析；注入 `id_str` 后按字符串保存，不用浮点。真实响应中若平台给出超过 i64 的值，仍以字符串字段优先。
- **转正只做一次**：房间建好后不再依赖关注池；用户手动删除房间时才会通过 `release_douyin_follow_room` 放回池里。
- **不改变录制并发**：池转正只是新增房间，录制仍由用户/自动录制开关控制；本项目已移除录制并发上限。
