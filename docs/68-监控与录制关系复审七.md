# 68 监控与录制关系复审七

> 状态：v1.1（2026-11-07，第十一轮；I1–I4 已在 [69](69-监控录制联动修复九.md) 修复并复验）｜对象：monitor.rs、recorder.rs、db.rs、segment.rs、retention.rs、state.rs、commands.rs｜上游：[54 v4.1](54-监控与录制关系审查.md)、[66](66-监控与录制关系复审六.md)、[67](67-监控录制联动修复八.md)

一句话结论：**这一轮没有发现能改变「录制是否继续」的新问题——检测间隔、退避、暂停监控与已开录会话仍然互不干涉，前几轮修掉的停录入口也没有回归。** 新发现集中在「收尾之后」：崩溃恢复把会话时长按「重启时刻」结算（实测 32 KB 的分片被记成 5 小时 00 分 04 秒）、合并失败在媒体目录留下 `.concat.txt`、保留策略删掉 mp4 与 .jsonl 却把同名 `.ass` 留在盘上。四条都是低优先级的数据/目录整洁问题，不影响录制本身。

## 1. 四个判定（本轮复核）

| 说法 | 结论 | 本轮依据 |
| --- | --- | --- |
| 已开录的直播间不受检测间隔影响 | **成立** | T2：把间隔改成 0（关闭自动检测）后杀掉 ffmpeg，12 秒内按「平台仍显示在播」续录（restarts=1，同一 session id）；T5：间隔 0 期间磁盘红线照常停录 |
| 不受失败回退影响 | **成立** | 退避只改 `Schedule.next_at`（[monitor.rs:177](../src-tauri/src/monitor.rs#L177)），错误分支只写 room.error 与事件，不碰 recorder；本轮所有停止都来自磁盘/退出/删除房间，没有一条来自检测失败 |
| 监控只是更新主播状态、房间状态 | **不完全对** | 它还会自动开录、磁盘红线停录、两次确认离线后停录；另有移除房间、退出应用、手动停录等入口（§3、§4） |
| 只有直播源真没数据才会影响录制 | **不成立（老结论不变）** | 源健康时仍可被停：磁盘 <1 GiB（T4/T5）、移除房间（T3）、退出（T6）。这些是设计内的安全动作，但确实与「源」无关 |

这一轮额外确认了一件事：**「崩溃」不会让正在录的 ffmpeg 立刻停**。T1 里 kill -9 应用后，两个 ffmpeg 被 launchd 收养（ppid=1）继续往分片里写；是下一次启动的 `reap_orphans` 才把它们杀掉。这段时间的录像没有丢，恢复时被合并进 mp4。

## 3. 新发现（I 系列）

| 编号 | 级别 | 症状 | 根因 | 落点 |
| --- | --- | --- | --- | --- |
| I1 | P4 | 崩溃后隔一段时间才重启，恢复出来的录像时长按「重启时刻」结算：实测 32 KB 的分片显示 5 小时 00 分 04 秒 | `close_orphan_sessions` 统一 `ended_at = now`、`duration_ms = (now - started_at) * 1000` | [db.rs:244](../src-tauri/src/db.rs#L244) |
| I2 | P3 | 崩溃恢复在窗口出现前同步合并分片：按本轮 35 MB / 0.75 秒（≈46 MB/s）外推，一条 10 GB 的录像要等约 3–4 分钟才看到主窗口（未做大文件实测，属外推） | `recover_parts` 在 `state.rs` 的启动路径上 `await` | [state.rs:64](../src-tauri/src/state.rs#L64)、[recorder.rs:2025](../src-tauri/src/recorder.rs#L2025) |
| I3 | P4 | 合并失败时在媒体目录留下 `[片名].concat.txt`，每次失败一个，媒体库里看不到 | 清单在 `merge` 开头写入，只在成功分支删除 | [segment.rs:69](../src-tauri/src/segment.rs#L69) |
| I4 | P4 | 保留策略删掉录像后，同名 `.ass` 字幕（以及遗留的 `.part*.ts` / `.concat.txt`）仍在盘上，容量统计与目录对不上 | 删除只覆盖 `file_path` 与同名 `.jsonl` | [retention.rs:65](../src-tauri/src/retention.rs#L65)、[postprocess.rs:340](../src-tauri/src/postprocess.rs#L340) |

### 3.1 I1 为什么会离谱

`recover_parts` 先合并分片，再 `close_orphan_sessions` 收尾；收尾用的 SQL 是「`ended_at = 现在`，`duration_ms = (现在 - started_at)`」。应用崩溃的那一刻录制就停了，但数据库只有下次启动才知道——中间隔多久，就会多算多久。

用户看到的是：昨天下午崩的，今天早上打开应用，历史里那条约 1 分钟的录像显示 18 小时，按「时长」排序直接冲到最前面。文件本身没问题（合并后的 mp4 可播），只是统计字段错了。

建议改法：`ended_at` 取「分片文件 mtime 的最大值」，取不到再退回 `now`，并把 `duration_ms` 夹到不小于 0、不大于 `now - started_at`。分片 mtime 就是 ffmpeg 最后一次写入的时间，误差在秒级。

### 3.2 I2 是启动路径上的同步等待

`recover_parts` 在 `AppState::init` 里被 `await`，之后才 `app.manage(state)`、建窗口。合并本身是 `ffmpeg -c copy`，很快，但再快也是整文件 I/O：本轮两个 30 MB 级文件各约 0.75 秒，日志时间戳 `11:58:02.78` → `11:58:03.53`。按这个吞吐外推，几 GB 级的录像会让窗口延后几十秒到几分钟，用户会以为应用「打不开」。

可行改法（二选一）：恢复改成后台任务，窗口先出来、媒体库先显示「恢复中」；或先按 `parts_total` 把大小写回库、让人能看见，合并挪到后台，完成后替换路径。

### 3.3 I3 / I4 是「目录比媒体库脏」

- `merge` 先写清单再调 ffmpeg；失败时 `return Err`，清单没人删。正常路径下清单在成功分支被删（`segment.rs` 末尾），所以只有失败会漏。
- 保留策略按数据库行删除：`path` 与 `path.with_extension("jsonl")`。而弹幕导出会额外生成 `path.with_extension("ass")`，它不进数据库，也就永远不会被清理；`.part*.ts` 与 `.concat.txt` 同理。
- 后果不是「空间爆掉」，而是「媒体库显示 0 条、目录里还有一堆小文件」，用户排查磁盘占用时会对不上账。

建议：收尾/保留策略统一走一个「同名兄弟文件」清单（`.mp4`/`.ts`/`.jsonl`/`.ass`/`.concat.txt`/`.part*.ts`/`.ffmpeg.pid`），合并失败时 `finally` 删清单。顺带把保留策略的容量口径改成「数据库 file_size 与目录实际大小取大」，避免 file_size=0 的失败会话不计入容量。

## 5. 没覆盖到的

- 真实 429 / 平台限流（本机造不出来，前几轮也没复现）；
- 真实自然下播（两位主播整轮都在播）；
- 系统睡眠/唤醒后的续录；
- 4 路以上并发收尾；
- 合并到一半再崩溃（时间窗太窄）；
- Windows 平台；
- I2 的大文件实测（只有 35 MB 级数据与外推）。

## 6. 结论

前几轮反复出现的「间隔/退避把录制搞停」在这轮一次都没出现；这次所有停录都能对应到一个明确动作（压盘、删房间、SIGTERM），且都在预期时间内完成。**建议不动录制主链路**；如果要收拾，按 I4 → I3 → I1 → I2 做一个小补丁即可（I2 改动稍大，放最后）。
