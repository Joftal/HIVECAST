# 任务中心历史增量加载与部分完成

> 状态：实现、单测与真机验收完成（2026-11-21）。承接 [184-任务中心全链路复查](184-任务中心全链路复查.md) 第 5 节的剩余项。
> 本轮范围：补齐历史「加载更多」、把 `partial` 的入库阶段文案改为「部分完成」、给收尾重试锁补并发单测；不改数据库 schema。后续全链路复查见 [186-任务中心复查与边界收口](186-任务中心复查与边界收口.md)。

## 1. 背景

docs/184 明确了三个待完善项：

1. 任务中心固定请求最近 100 场，后端最多接受 500 场，超过 100 场的历史无法从界面访问；
2. `partial` 的入库阶段中文写作「部分失败」，但实际语义是「有产物、未完整入库」；
3. 收尾重试锁只有代码审查，没有测试覆盖。

本轮逐项处理。历史不再固定 100 条，而是按 100 场一页递增，最多 1000 场；页面底部提供「加载更多历史」，达到上限后改为提示。

## 2. 历史增量加载

### 2.1 后端契约

`/Library/dshproject/HIVECAST/src-tauri/src/task_center.rs`：

- `build(..., history)` 的上限由 `clamp(1, 500)` 改为 `clamp(1, 1_000)`（:35）。
- 历史分组循环新增 `closed_group_count`（:173）：每遇到一个已结束且不含 `recording` 成员的分组先加一（:187），再判断是否已经收满 `history`。多读到的这一组不返回，只用于回答「后面还有没有」。
- `TaskCenter.history_has_more = closed_group_count > history`（:399）。
- `/Library/dshproject/HIVECAST/src-tauri/ipc-types/src/lib.rs` 的 `TaskCenter` 增加 `pub history_has_more: bool`；`pnpm run gen:bindings` 生成 `src/lib/bindings/TaskCenter.ts` 的 `historyHasMore: boolean`。

这样后端不需要额外 count 查询：多读一组就能区分「刚好 100 场」和「还有第 101 场」。`load_sessions` 原有的完整分组分页、5000 行硬上限与告警继续生效。

### 2.2 前端加载更多

`/Library/dshproject/HIVECAST/src/features/tasks/TasksPage.tsx`：

- 常量 `HISTORY_PAGE = 100`、`HISTORY_MAX = 1_000`（:23）。
- 状态 `historyLimit`（:868）与 `historyLimitRef`（:870）。`load(limit = historyLimitRef.current)`（:883）把当前上限传给 `taskCenter`；2 秒轮询继续调用 `load()`，因此加载到 200 场后不会被轮询缩回 100。
- `loadMore()`（:917）：`next = min(current + 100, 1000)`，先更新 ref 与 state，再请求；`loadingMore` 防止重复点击。
- 历史表/空态之后（:1358）：
  - `center.historyHasMore` 且未到上限时显示「加载更多历史」按钮；
  - 加载中显示「正在加载…」并禁用；
  - 达到 `historyLimit >= 1000` 时显示「最多显示最近 1000 场」。
- 删除了上一轮固定在标题右侧的「最多显示最近 100 场」提示。

i18n 删除 `tasks.historyLimit`，新增：

| key | zh-CN | en-US |
| --- | --- | --- |
| `tasks.loadMore` | 加载更多历史 | Load older runs |
| `tasks.loadingMore` | 正在加载… | Loading… |
| `tasks.historyMax` | 最多显示最近 {{n}} 场 | Showing up to the latest {{n}} runs |

### 2.3 交互语义

- 第一次进入任务中心仍只请求 100 场，首屏速度和之前一致。
- 点一次加载更多变成 200 场；每次追加 100，直到 1000 场。
- 只有后端确认「还有更多」时才显示按钮；131 场时点一次就加载完全部，按钮消失，不会出现空按钮。
- 轮询、手动刷新都使用当前上限，不会把用户已经展开的历史又折叠回去。

## 3. partial 文案

`partial` 是「同组既有成功片段又有失败片段」或「aborted 但有产物」的入库阶段状态。旧文案「部分失败」容易被理解成整条 Run 失败，实际上整条 Run 可能已经是 `failed`，而入库阶段是「部分完成」。

本轮把 `tasks.statePartial` 与 `tasks.stagePartial` 统一改为：

- 中文：**部分完成**
- 英文：**Partially completed**

整体状态 Chip 不变：磁盘满等异常中断仍显示「失败」，详情链路里的入库阶段显示「部分完成」。这样「整条 Run 失败」与「有产物但未完整入库」不再混用同一个词。

## 4. 收尾重试锁测试

`/Library/dshproject/HIVECAST/src-tauri/src/recorder.rs` 把锁逻辑抽成 `acquire_finalize_retry(manifest)`（:3895），`retry_finalize` 通过 `let _lease = acquire_finalize_retry(&manifest)?;` 持有（:3929）。锁仍以 `split_manifest` 字符串为键，分组录制的多个片段共用清单时不会并发重试。

新增单测 `finalize_retry_lock_is_per_manifest_and_released_on_drop`（:6132）：

- 同一 manifest 第二次获取失败；
- 不同 manifest 可以同时获取；
- lease drop 后同一 manifest 可以再次获取。

## 7. 边界

1. 真机只验证到 131 场，未构造 1000 场或 5000 行；1000 上限的「最多显示最近 1000 场」提示没有在真机触发，逻辑由 `HISTORY_MAX` 和 `historyMax` 条件覆盖。
2. 「加载更多」一次追加 100 场，没有做虚拟滚动；几千行时 DOM 仍然全部渲染。后端有 5000 行/1000 组上限，但前端大列表性能未单独量化。
3. 收尾锁本轮补了单测，仍没有真机同时点两个片段「重试收尾」；多实例同时重试不在进程内锁的覆盖范围。
4. `partial` 只改文案，整体 Run 状态机不变：异常中断仍可能是 `failed`，只有入库阶段显示「部分完成」。
5. 历史数量包含失败/中断/取消的已结束场次，不只是「完成」；因此「最近完成 131」里的 131 是已结束 Run 总数，其中可能有失败行。
