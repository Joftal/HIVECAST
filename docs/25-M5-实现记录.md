## 2. 抖音适配器

### 2.1 房间号解析

与另外三个平台一样实现 `PlatformAdapter` 的 `resolve`；抖音的输入形态比 B 站多：

| 输入 | 处理 |
| --- | --- |
| `douyin:362845039857` | 去前缀，余下按纯数字规则校验 |
| `362845039857` | 全数字且长度 ≥ 3，直接当 `web_rid` |
| `https://live.douyin.com/362845039857` | 取最后一段，允许 `[A-Za-z0-9_-]{1,32}` |
| `https://v.douyin.com/xxxx/` | 短链原样存 `canonical_url`，`real_room_key` 再跟随 302 取最后一段 |

`real_room_key` 的存在是为了短链：界面上显示的仍是用户粘贴的短链，但取流、去重、DB 主键都用真实 `web_rid`。

### 2.2 进入房间：预热 + 签名

抖音的 `webcast/room/web/enter/` 校验 `a_bogus`，且**必须有 `ttwid` Cookie**。所以流程固定三步：

1. `GET https://live.douyin.com/{rid}`，UA 用签名模块里的 `SIGN_UA`（必须完全一致，UA 参与 RC4 密钥流），把响应里所有 `Set-Cookie` 收进 map，**读完整个 body**（相当于浏览器行为预热），只留 `name=value` 拼 Cookie 头。
2. `abogus::sign(query, "", SignOptions::now())` 生成 `a_bogus=...` 追加到查询串。
3. `GET ENTER`，带同一 UA、`Referer: https://live.douyin.com/{rid}`、Cookie。

查询参数**顺序参与签名**，改动顺序会导致签名失效：

| # | 参数 | 值 |
| --- | --- | --- |
| 1 | `aid` | 6383 |
| 2 | `live_id` | 1 |
| 3 | `device_platform` | web |
| 4 | `language` / `browser_language` | zh-CN |
| 5 | `enter_from` | web_live |
| 6 | `cookie_enabled` | true |
| 7 | `screen_width` / `screen_height` | 1920 / 1080 |
| 8 | `browser_platform` | MacIntel |
| 9 | `browser_name` | Chrome |
| 10 | `browser_version` | 131.0.0.0 |
| 11 | `web_rid` | 房间号 |
| 12 | `Room-Enter-User-Login-Ab` | 0 |
| 13 | `is_need_double_stream` | false |

失败表现很反直觉：**签名不对时抖音返回 HTTP 200 + 空 body**，不是 4xx。因此 `douyin.rs` 里把「2xx 但 body 为空」单独映射成 `PlatformError::Upstream { code: 0, message: "抖音房间 {rid} 返回空响应" }`，并在消息里点明「通常是签名或 ttwid 失效」，避免用户看到「房间不存在」的误导。

### 2.3 ABogus 签名

实现对齐参考项目 `biliLive-tools/packages/DouYinRecorder/src/sign.ts`（其源头是 rust-srec），为了少一个依赖，SM3 与 RC4 都手写，不引 crate。

常量（改动任何一个都会让签名全废）：

| 名称 | 值（截断显示） | 用途 |
| --- | --- | --- |
| `SALT` | `cus` | 参与两次 SM3 的盐 |
| `ALPHA_ABOGUS` | `Dkdpgh2ZmsQB80/MfvV36XI1R45-WUAlEixNLwoqYTOPuzKFjJnry79HbGcaStCe` | 输出用的自定义 base64 字母表 |
| `ALPHA_BASE64` | `ckdp1h4ZKsUB80/Mfvw36XIgR25+WQAlEi7NLboqYTOPuzmFjJnryx9HVGDaStCe` | 中间态编码字母表 |
| `TABLE` | 256 字节置换表 | 末段逐字节换表 |
| `SORT1` / `SORT2` | 各 44 个索引 | 从 `dir[72]` 里挑字节与做异或校验 |
| `SIGN_UA` | `Mozilla/5.0 (Windows NT 10.0; Win64; x64) ... Chrome/130.0.0.0 ... Edg/130.0.0.0` | 与请求 UA 必须一致 |
| `SIGN_FP` | `1920\|1080\|1944\|1170\|0\|30\|0\|0\|1920\|1080\|1920\|1080\|1920\|1080\|24\|24\|Win32` | 设备指纹串 |
| `options` | `[0, 1, 14]` | 写进 `dir` 的固定字节 |

算法五步：

1. `salt` 与查询串双拼后两次 SM3，得到 `arr1`/`arr2`（64 字节）。
2. `rc4([0x00, 0x01, 0x0e], UA)`，结果用 `ALPHA_BASE64` 编码后再 SM3，得 `arr3`。
3. 把时间戳字节、`options`、`arr1[21..22]`、`arr2[21..22]`、`arr3[23..24]`、`aid=6383`、指纹长度、时间戳高低位依次填进 `dir[72]`。
4. 按 `SORT1` 取 44 个字节，接指纹字节，再按 `SORT2` 做异或得到校验和。
5. 用 `TABLE` 逐字节换表，前面拼 12 字节前缀，最后用 `ALPHA_ABOGUS` 做 base64。

**12 字节前缀必须是浏览器位模式**，否则一样 200+空体。每 4 字节来自一个 `0..10000` 的随机数 `rd`：

```
let low = (rd & 0xff) as u8;
let high = (rd >> 8) as u8;
chunk[0] = (low & 170) | 1;
chunk[1] = (low & 85) | 2;
chunk[2] = (high & 170) | 5;
chunk[3] = (high & 85) | 40;
```

单元测试 `random_prefix_follows_browser_pattern` 跑 64 轮断言这四条位运算，防止以后「优化」成纯随机。

### 2.4 档位映射

抖音的档位 key 与其它平台都不同，映射表写在 `douyin.rs` 顶部：

| `quality_key` | qn | 显示名 |
| --- | --- | --- |
| `origin` | 10000 | 原画 |
| `uhd` | 400 | 蓝光 |
| `hd` | 250 | 超清 |
| `sd` | 150 | 高清 |
| `ld` / `md` | 80 | 标清 / 极速 |

旧版 `flv_pull_url` 的 key 没有 `quality_key`，另有一套：`FULL_HD1`=400、`HD1`=250、`SD2`=150、`SD1`=80、`ORIGION`/`ORIGIN`=10000（抖音自己拼错了，两种都收）。

主路径是 `live_core_sdk_data.pull_data`：`options.qualities` 给 `sdk_key` → 名称，`stream_data` 是**字符串化的 JSON**，解析出 `data{ sdk_key: { main: { flv, hls, sdk_params } } }`。解析时跳过 key 为 `ao`/`hls`/`flv` 的聚合项，只取 `main`；`sdk_params` 里拿 `resolution`（`WxH`）、`vbitrate`（除以 1000 得 kbps）、`fps`、`v_codec`（264/h264、265/hevc、av1）。SDK 数据缺失时退回 `flv_pull_url` 与 `hls_pull_url_map`。

排序：先按 qn 降序，再按码率降序，保证「原画」永远在最前。`pick_quality`：请求 qn=0（原画/自动）取码率最高；否则取 qn 差最小、同差取码率高者——与 B 站适配器的策略一致。

### 2.5 线路组

每个档位最多两组，走 `StreamGroup`：

| 组名 | priority | weight | 说明 |
| --- | --- | --- | --- |
| `{cdn} FLV` | 0 | 码率 kbps | 录制与观看默认走这条 |
| `{cdn} HLS` | 1 | 码率 - 0.5 | 仅当 FLV 全挂时的兜底 |

`cdn` 从主机名取：`pull-flv-c13.douyincdn.com` → `c13`；没有 `c-` 前缀就取首段主机名。candidate 的 `attrs` 带 `qn`/`sdkKey`/`bitrateKbps`，`id` 为 `{sdkKey}-{flv|hls}`，`name` 为 `{档位名} · FLV`（观看页徽标直接显示这个字符串）。

## 3. 本地后处理

设计取向：**全部本地、全部 ffmpeg、全部失败可读**。不引入 ffmpeg 之外的依赖，不做重编码（除截图外都是 `-c copy`），产物与源文件同目录同 stem，避免用户找不到文件。

### 3.1 命令与类型

```rust
pub struct PostResult {
    pub kind: String,        // mp4 | screenshot | ass | merge
    pub path: String,
    pub size: i64,
    pub message: Option<String>,
}
```

| 命令 | 入参 | 产物 |
| --- | --- | --- |
| `session_remux` | `session_id` | `{stem}.mp4` |
| `session_screenshot` | `session_id`, `at_secs?` | `{stem} 截图-{n}s.jpg` |
| `session_export_danmaku` | `session_id` | `{stem}.ass` |
| `room_merge_sessions` | `room_id` | `合并-YYYYmmdd-HHMMSS.mp4` |

两个守卫写在 `commands.rs` 里而不是 `postprocess.rs`：`session_video` 遇到 `status == "recording"` 直接返回 `AppError::User("这段还在录制，先停下再处理")`；`session_export_danmaku` 没有 `danmaku_path` 时返回 `User("这场没有弹幕存档")`。合并只取「已结束 + 有文件 + 文件还在磁盘上」的会话，按 `started_at` 升序。

所有命令都跑在 `tokio::time::timeout(600s)` 里。ffmpeg 失败时取 stderr 末 4 行、用 ` | ` 连接后塞进 `AppError::Ffmpeg`，前端 `describeError` 原样展示——比「退出码 1」有用得多。

### 3.2 转封装

```
-c copy -movflags +faststart -avoid_negative_ts make_zero
```

- `-c copy`：FLV 的 H.264/AAC 直接搬进 MP4，不重编码，速度取决于磁盘。
- `+faststart`：moov 前移，边下边播与分享都友好。
- `-avoid_negative_ts make_zero`：直播流起播时间戳常为负，不归零会让部分播放器显示异常时长。
- 源已经是 `.mp4` 时直接返回 `User("源文件已经是 mp4")`，不生成 `.mp4.mp4`。

### 3.3 截图

```
-ss {at} -i {src} -frames:v 1 -q:v 2 {dst}
```

默认 `10.0` 秒：避开开播瞬间的黑帧/绿帧（B 站起播约 1–2 秒才有画面）。`-ss` 放在 `-i` 前是快速定位（关键帧跳转），比解码到指定时间快一个量级。产物名带秒数，同一个录像截多张不会互相覆盖。

### 3.4 合并

用 concat demuxer，不重编码：

```
file '/abs/path/a.flv'
file '/abs/path/b.flv'
```

`-f concat -safe 0 -c copy -movflags +faststart`。路径里的单引号按 ffmpeg 规则转义成 `'\''`。临时的 `.txt` 用 `sibling()` 生成、结束后删除，不污染媒体目录。

限制写进文档也写进代码注释：**只有编码参数一致（同平台同画质同分辨率）的片段能这样拼**；跨画质合并会得到时间轴错乱的产物。M6 若需要跨画质，得改成重编码路线。

### 3.5 弹幕 ASS

输入是 M3 落盘的 JSONL（`{"c":"文本","t":毫秒,"col":十进制颜色,...}`），输出标准 ASS v4.00+。

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `PlayResX` / `PlayResY` | 1280 / 720 | 与观看端默认档一致，播放器按比例缩放 |
| 字体 | `PingFang SC` 42px | macOS 默认中文字体；Windows 缺字时播放器回退 |
| 颜色 | `&H00BBGGRR&` | ASS 是 BGR，`col=16777215`（白）→ `&H00FFFFFF&` |
| 移动 | `\move(1280,y,-width,y)` | 从右边缘进、完全移出左侧后结束 |
| 速度 | 190 px/s | 与 B 站网页端观感接近 |

车道算法：每条弹幕选「已释放的车道」，否则选最早释放的；释放时间 = 到达时间 + min(自身停留时长, 4 秒)。停留时长 = `(1280 + 估算宽度) / 190 * 1000` 毫秒；宽度估算 CJK 每字 42px、ASCII 每字 23.1px、下限 40px——不测字体度量，宁可略宽也不重叠。

安全：`escape_text` 把反斜杠、左右花括号换成全角 `＼`/`｛`/`｝`，并压掉换行。否则一条带 `\pos` 或 `}` 的弹幕就能改写整份字幕。

## 4. 前端交互

- **入口在历史行**：每条已结束会话右侧三个按钮「转 MP4 / 截图 / 弹幕 ASS」；「弹幕 ASS」只在 `danmakuPath` 存在且 `danmakuCount > 0` 时出现（空 jsonl 打开后只会报错）。
- **合并**：一个房间有 ≥2 条已结束且有文件的会话时，历史框顶部出现 `mergeHint`（「把 N 段按时间合并为一个 mp4」）与「合并」按钮。
- **单飞**：页面级 `postBusy` 用 `postKey(roomId, kind, sessionId)` 标识正在跑的任务，按钮显示 `…` 并禁用，避免连点起一堆 ffmpeg。
- **结果提示**：成功在列表下方显示绿色条「大小 · 文件名」并刷新会话列表；失败走同一个位置的红条。
- 文案全部走 i18n（`monitor.post.*`），中英各一套，`check-i18n` 校验 123 个 key 对齐。

## 6. 踩坑

1. **抖音签名错 = 200 + 空 body**，不是 4xx。一开始以为是网络问题，加日志才定位到 `a_bogus`。
2. **`random_prefix` 不能纯随机**。第一版用 `rand::random::<u8>()` 填前缀，签名 100% 失败；换成位模式立刻通。
3. **B 站「预告」房间不是 bug**：`live_status=2` 的轮播房里没人发弹幕，jsonl 0 字节是正常的。UI 因此加了 `danmakuCount > 0` 的门控。
4. **截图默认 10 秒**：0 秒截出来是黑帧（B 站起播有约 1–2 秒黑场）。
5. **合并要求编码参数一致**：FLV 直拼在跨画质时会音画不同步，代码里不阻止但文档写明。
6. **强杀 dev 会留孤儿 ffmpeg**：`pnpm tauri dev` 被 kill 时 `SIGTERM` 收尾跑不到，ffmpeg 继续写文件。本轮出现的孤儿已手动清理，M6 要把「启动时清理残留 ffmpeg」做进 `close_orphan_sessions`。
7. **端口 1420 被占**：旧 dev 实例没退干净时新实例 `beforeDevCommand` 直接失败，先 `pgrep -fl hivecast` 再起。
8. **macOS 的 `ls` 没有 `--time-style`**，排查产物时间要用 `stat`。

## 7. 已知缺口

| 缺口 | 影响 | 计划 |
| --- | --- | --- |
| 抖音弹幕未接入 | 抖音录像没有 JSONL，因此没有 ASS | M6 或后续版本（抖音弹幕走 protobuf WS，工作量与 B 站同级） |
| 抖音 HLS 线路未实测 | 只有 FLV 组经过真机验证 | 观察；FLV 不可用时再验 |
| 合并未在真机多段验证 | 只有单元测试（合成 3 段） | M6 补一次两段真机 |
| 后处理没有进度 | 大文件转封装期间只有 `…` | M6 接 ffmpeg `-progress` 输出 |
