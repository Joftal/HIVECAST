## 2. 从 web_rid 到 room_id

三个编号不能混用：

| 编号 | 例子 | 来源 | 用在哪 |
| --- | --- | --- | --- |
| web_rid | `25278854644` | 用户输入 / 地址栏 | 页面地址、日志、房间键 |
| room_id | `7704639507076844342` | enter 接口 `data.id_str` | WS 参数 `room_id`、签名 |
| ttwid | `1%7CH76...` | 打开房间页的 `Set-Cookie` | WS 请求头 `Cookie` |

流程（`douyin_ws::open`）：

1. `resolve_web_rid`：纯数字直接用；否则请求 `https://v.douyin.com/{key}/` 跟随跳转，取末段数字。
2. GET `https://live.douyin.com/{web_rid}`：收集 `Set-Cookie` 里的 `ttwid`（缺失直接报「页面没有下发 ttwid」）。
3. 真实 room_id 走 `crate::platform::douyin::live_room_id`（enter 接口），失败才回退页面里的 `roomIdStr`。
4. 拼连接串、签名、连 WS。

**页面 SSR 里的 `roomIdStr` 现在是 `$undefined`**，所以第 3 步不能省；保存下来的页面 HTML 里能看到这个字面量，不是抓取姿势问题。

## 3. 签名：md5 拼串 + 官方 JS

服务端确实校验签名，而且校验失败的表现很容易被误读成网络问题：把签名换成 4 个字符的假值，握手直接得到

```
WebSocket 连接失败：HTTP error: 200 OK
```

HTTP 200 + 握手失败，而不是 401/403。看到这条先怀疑签名，不要怀疑 TLS 或 UA。

签名分两步：

1. **X-MS-STUB**：13 个字段按固定顺序拼 `k=v,k=v` 再取 md5，顺序错了签名就废：

```
live_id=1,aid=6383,version_code=180800,webcast_sdk_version=1.0.15,
room_id={room_id},sub_room_id=,sub_channel_id=,did_rule=3,
user_unique_id={uid},device_platform=web,device_type=,ac=,identity=audience
```

2. **签名**：把这段 32 位 hex 喂给 `douyin_sign::sign`，内部执行官方 `webmssdk` 的 `get_sign`，返回形如 `6Q9CP+1cah1nU/1G` 的串（base64 字符集，不是 hex）。

rquickjs 侧的三个要点：

- sign.js 是浏览器脚本，开头就 `document = {}``window = {}``navigator = {...}`；Rust 侧要先注入 `window/document/navigator/location/screen/history/localStorage/sessionStorage/crypto/performance` 以及 `Image/WebSocket/XMLHttpRequest/fetch/setTimeout/setInterval/clearTimeout/clearInterval` 这些桩，再 `eval` 脚本。
- 每次签名新建 `Runtime::new() + Context::full()`，耗时 20–40ms。这个开销只在建连时出现，不进热路径，不做池化是对的。
- 不要在 JS 里传中文或 URL 转义后的 stub；传 32 位 hex 字符串，Rust 侧先校验长度与字符集。

连接串里的 `signature` **原样拼接**（`&signature=xxx`），不要 URL 编码，否则服务端签名比对不通过。

## 4. 连接串与帧格式

参数集对齐 biliLive-tools 的 DouYinDanma：`webcast_sdk_version=1.0.15`、`tz_name=Etc/GMT-8`、host 用 `webcast100-ws-web-hl.douyin.com`，**不带** `cursor` / `internal_ext`。bililive-go 的参数集（1.0.14-beta.0 + `cursor` + `internal_ext`）在本机实测同样能连、能收到消息，两套都行；选短的那套。

其余固定参数：`app_name=douyin_web`、`version_code=180800`、`compress=gzip`、`device_platform=web`、`screen_width/height=1920/1080`、`browser_platform=Win32`、`browser_name=Mozilla`、``endpoint=live_pc`、`im_path=/webcast/im/fetch/`、`need_persist_msg_count=15`、`heartbeatDuration=0`。

帧结构（全部手写 wire，没有引 prost，避免 `protoc` 依赖）：

```
PushFrame:  1 seqId(varint) 2 logId(varint) 7 payloadType(string) 8 payload(bytes)
Response:   1 messages(repeated Message) 5 internalExt(string) 6 fetchType 9 needAck
Message:    1 method(string) 2 payload(bytes)
ChatMessage: 2 user.message 3 content         // user.message 2 是昵称
GiftMessage: 5 repeatCount 7 user 15 gift     // gift 16 是礼物名
```

- `payloadType == "hb"` 的是心跳回包（约 101 字节），直接跳过。
- `Response.needAck == true` 时回一帧：field2 = logId、field7 = `"ack"`、field8 = internalExt。
- 心跳每 **5 秒**一帧：field1 = 递增 seq、field2 = 毫秒时间戳、field7 = `"hb"`。心跳和读帧在同一个 `select!` 里，共用一个 sink，不另开任务。

## 5. 消息映射

| method | 处理 | 输出 |
| --- | --- | --- |
| `WebcastChatMessage` | 解 user.nickname + content | `kind=chat`，白色 `0xFFFFFF` |
| `WebcastGiftMessage` | 解 user.nickname + gift.name + repeatCount | `kind=gift`，内容 `{礼物} x{n}`，颜色 `0xFFB027` |
| 其它 | 忽略 | — |

抖音一帧里可能有几十条消息，所以 `danmaku.rs` 的 `douyin_session` 用 200ms 超时读一批，再走与另外三家共享的 `accept` / `flush`：1 秒窗口最多 200 条、200ms 批量广播、同名 JSONL 落盘。前端没有平台分支。

## 6. 排障关键：0 观众房间会伪装成「协议不通」

这轮最大的时间坑。现象：连接成功、心跳正常、ACK 正常，能解出 `WebcastRoomStatsMessage` / `WebcastBackupSEIMessage` / `WebcastRoomUserSeqMessage`，但 60 秒内一条 `WebcastChatMessage` 都没有。

排查顺序与结论：

1. 先怀疑签名。用假签名对照，确认服务端会拒绝 → 我们的签名是有效的。
2. 再怀疑参数集。换成 biliLive-tools 的 1.0.15 / `-hl` / `Etc/GMT-8`，能连、仍然没有聊天。
3. 怀疑实现。把 biliLive-tools 的 `DouYinDanma` 原样跑（Node + tsx + 它自己的 webmssdk），**同样 0 条**。
4. 怀疑环境。用真 Chrome 开同一房间，CDP 抓 WS 二进制帧解码，**同样只有 SEI/榜单**；页面右侧显示「在线观众 0」「需先登录，才能开始聊天」。
5. 换房间。`enter` 接口的 `user_count` 排序后挑 26 人的房间，30 秒内聊天刷屏。

结论：协议没问题，房间没观众。以后验收抖音弹幕，先看 `live_counts`：

```
DOUYIN_ROOMS=25278854644 cargo test --lib douyin_ws::tests::live_counts -- --ignored --nocapture
```

输出 `25278854644 live=true online=Some(26) title=27年高考来了`。在线人数为 0 的房间不要用来判断弹幕链路。分类页拿到的房间多为个位数观众，这也是最初 20 多个房间全都「没有弹幕」的原因。

## 8. 踩坑

1. **0 观众房间 = 假故障**：见 §6。判断链路好坏先看在线人数，再看消息类型。
2. **页面 `roomIdStr` 是 `$undefined`**：必须走 enter 接口的 `id_str`；页面解析只作兜底。
3. **假签名返回 HTTP 200 而不是 4xx**：握手阶段的 200 + 失败优先查签名，别在 TLS/UA 上打转。
4. **signature 不能 URL 编码**：原样追加，编码后签名比对失败。
5. **rquickjs 0.9 没有 `bundled` feature**：直接 `rquickjs = "0.9"`，它会编译 rquickjs-sys，不需要额外开关。
6. **心跳与读帧抢 sink**：放在同一个 `select!` 分支里发心跳，另开任务会 `borrow` 冲突或丢帧。
7. **ACK 的 payloadType 有两种写法**：我们按 bililive-go 用 `"ack"` + payload=internalExt；biliLive-tools 用 payloadType=internalExt + 空 payload。两种都能被接受，选定一种后不要混。

## 9. 已知缺口

- `WebcastGiftMessage` 只取「昵称 + 礼物名 + 数量」，礼物等级、连击、价值没取。
- `WebcastAudioChatMessage`、`WebcastScreenChatMessage` 未消费（普通房间以 `WebcastChatMessage` 为主）。
- 没有用 `cursor` / `internalExt` 做断点续传：断开即重连，重连窗口内的消息丢失。
- 不带登录 Cookie：匿名连接可用，但「需登录才能发言」的房间只能看不能说（我们也不需要发言）。
- 每次签名新建 Runtime，冷启动多 20–40ms；量级可接受，暂不池化。
