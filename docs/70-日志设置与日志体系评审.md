# 70-日志设置与日志体系评审

> 状态：v0.1 评审稿（2026-11-07），**已实施并验证**，实现见 [72-日志功能实现](72-日志功能实现.md)。本文保留需求评审、可行性分析与缺陷预判，作为决策依据。
> 范围：日志输出目录、日志保留天数、全功能日志捕获、日志分类、跨天滚动、Windows/macOS 兼容。
> 结论：两项设置都可行，但「默认放安装目录」这一条不建议照做；真正的工作量不在设置，而在全链路日志补齐。

## 0. 结论速览

| 需求 | 判定 | 说明 |
| --- | --- | --- |
| 日志输出目录可配置 | 可行，默认值需改 | 目录可创建、可切换；但 macOS 的 .app 包内和 Windows 的 Program Files 默认不可写，不能作为默认值 |
| 日志保留天数（0=不清理，默认 7） | 可行，口径需定 | 按文件名日期清理最稳；需明确「7 天」是含今天 7 个自然日还是 7×24 小时 |
| 检测并补齐全功能日志 | 必要，缺口大 | 46 个 Tauri 命令 0 条日志、后处理 0 条、ffmpeg stderr 默认被过滤、前端错误不落盘 |
| 日志分类 | 可行 | 用 tracing target = 模块路径 + 固定 event 名，文件里保留 target，控制台不显示 |
| 跨天/连续跨天 | 当前没有文件日志，等于未实现 | tracing-appender 的 DAILY 按 UTC 零点切，东八区会在 08:00 换文件，不能直接用 |
| 设置入口 | 放「设置 → 存储」，不新增一级分类 | 媒体目录、媒体保留已在该页，日志目录/日志保留是同一类心智；新增分类会造成两个「保留」入口 |
| Windows/macOS 兼容 | 可行 | 路径、文件占用、打开目录、权限四处差异要专门处理；Windows 需要真机验收 |

三个最重要的判断：

1. **默认目录不要用安装目录**。用户原话是「安装后的应用程序目录下的 log」。macOS 的 .app 是签名包，包内写入会破坏签名，升级/公证也会替换包；Windows 的 Program Files 需要管理员权限，普通用户会被 UAC 虚拟化到 VirtualStore，日志「看起来写了，实际找不到」。默认应使用平台标准日志目录，安装目录只作为用户显式选择时的候选，并在不可写时拒绝或回落。
2. **保留天数不是删文件那么简单**。用户可以把日志目录选到任意位置，清理必须只匹配自家文件名（如 hivecast-2026-11-07.log），只删普通文件，跳过当天/当前文件，删失败不能影响应用；否则一个手滑选到桌面就会误删用户文件。
3. **跨天必须自己写 writer**。已核对 tracing-appender 0.2.5：RollingFileAppender 用 OffsetDateTime::now_utc() 判定切分，Rotation::DAILY 在 UTC 零点切；东八区每天 08:00 换文件、文件名是 UTC 日期，不满足「自然日/跨天」的直觉。自写 writer 还能同时解决「运行中改目录」「同一天重启追加」「单日上限」三件事。

### 1.3 前端与命令层

- 46 个 #[tauri::command] 全部没有日志；命令返回 AppError 后，前端大多只 toast，关闭应用后无法回看。
- src/lib/ipc.ts 是每个命令直接 invoke，没有统一 wrapper；要记录「哪个命令失败」最省事的做法是加一个 call() 包装并替换所有 invoke。
- 前端没有 window.onerror、unhandledrejection、React ErrorBoundary；白屏/渲染异常目前只能靠用户口述。
- 134 处 let _ = 吞错。不是每一处都要改成日志，但「用户能感知的失败」必须有至少一条 WARN。

### 1.4 跨天现状

当前没有文件日志，所以「跨天记录」实际上没有实现：控制台时间戳带日期，但 Finder 启动没有 stdout；用户用终端重定向到文件时，切分与清理由 shell 决定，应用完全不知道。新增文件日志后，跨天、连续跨天、同日重启追加、运行中换目录都必须由 writer 自己保证。

## 2. 参考项目与平台惯例

### 2.1 bililive-go 的日志实现

配置在 /Library/dshproject/bililive-go/config.yml:11-15：log.out_put_folder（默认 ./）、save_last_log、save_every_log、rotate_days（默认 7）。实现在 /Library/dshproject/bililive-go/src/log/log.go：

- logrus + os.Stderr 双写；目录不存在时 log.Fatalf 直接退出（不可照搬，桌面应用不能因为日志目录不可写就退出）。
- newDailyRotatingWriter 用本地 time.Now() 的 YYYY-MM-DD 切文件，O_CREATE|O_WRONLY|O_APPEND，同一天重启是追加而不是覆盖。
- 保留清理：rotateDays<=0 不清理；cutoff = now.AddDate(0,0,-rotateDays)，Glob "bililive-go-*.log"，解析文件名日期，早于 cutoff 的删除。
- 清理只在切天时跑；没有单日大小上限；save_last_log 分支还会在启动时把旧日志全删，和 rotate_days 语义冲突。

可借鉴：本地日期切分、append、按文件名日期判断保留、0=不清理。要改进：目录不可用自动创建/回落而不是退出；单日大小上限；只删自家文件；运行中也能每日清理；清理失败不阻塞；不要把 save_last_log 那套「启动清空」带进来。

### 2.2 Tauri 的平台日志目录

Tauri 2.12.5 的 app_log_dir()：macOS 为 ~/Library/Logs/<identifier>，Windows 为 %LOCALAPPDATA%/<identifier>/logs，Linux 为 ~/.local/share/<identifier>/logs；identifier 是 com.hivecast.desktop。这个位置符合各平台习惯，不需要管理员权限，也不会被应用升级替换，适合作为默认值。

开发环境则用工程目录：src-tauri 的 CARGO_MANIFEST_DIR 上跳一级就是 HIVECAST，默认 HIVECAST/logs（.gitignore 已忽略 logs/ 与 *.log）。这样开发时日志就在手边，不污染用户目录。

### 2.3 tracing-appender 的日切语义

已核实 0.2.5 源码：RollingFileAppender 的 from_builder/now 用 OffsetDateTime::now_utc() 判定日期，Rotation::DAILY 在 UTC 零点切。东八区会在每天 08:00 换文件，文件名也是 UTC 日期。对「自然日」「跨天」来说这是错的。可以只用它的 non_blocking 通道（避免写盘阻塞调用线程），但不用它的 Rotation，日期判断自己做。

### 2.4 结论

采用「自写 DailyWriter + tracing-appender::non_blocking」：non_blocking 负责把写盘从调用线程剥离，DailyWriter 负责本地日期切分、追加、单日上限、换目录、清理。不要为了省事直接 Rotation::DAILY，否则第一天就会被用户发现「日志日期不对」。

## 3. 逐条评审

### 3.1 日志输出目录

需求拆解与判定：

| 子需求 | 判定 | 说明 |
| --- | --- | --- |
| 保存位置可自行选择 | 合理 | 目录选择器 + 手输路径都支持；空值表示跟随默认 |
| 默认在安装目录/log | 不建议 | 见下方平台表；macOS 基本不可行，Windows 取决于安装方式 |
| 没有就自动创建 | 合理 | create_dir_all；父目录不可写则回落并提示 |
| 开发环境在工程目录 | 合理 | debug 构建默认 HIVECAST/logs；可用 HIVECAST_LOG_DIR 覆盖 |
| 运行中可切换 | 合理 | 设置保存后立即切；旧文件关闭，新文件从当天开始 |
| 打开日志目录 | 合理 | 设置页放「打开目录」按钮；不要复用只支持文件的 media_reveal |

默认目录平台对照：

| 平台/场景 | 安装目录/log 是否可写 | 风险 |
| --- | --- | --- |
| macOS .app（/Applications） | 通常不可写（包内只读） | 写包内会破坏代码签名；公证/更新会替换整个 .app，日志丢失 |
| macOS 未签名/ translocation | 不可写或路径随机 | Gatekeeper 路径隔离，用户找不到日志 |
| Windows 每用户安装（%LOCALAPPDATA%\Programs） | 通常可写 | 升级/卸载可能清目录；不是标准排错位置 |
| Windows 每机器安装（Program Files） | 普通用户不可写 | 旧式/无 manifest 场景可能被 UAC 虚拟化到 VirtualStore，资源管理器看不到；需管理员 |
| 便携版 exe 同目录 | 可能可写 | 放 U 盘/只读目录时失败；仍应回落 |
| 开发环境 cargo run | 工程目录可写 | 推荐 HIVECAST/logs |

因此建议：默认 = Tauri app_log_dir()（macOS ~/Library/Logs/com.hivecast.desktop，Windows %LOCALAPPDATA%\com.hivecast.desktop\logs）；开发 = HIVECAST/logs；设置里允许用户选安装目录，但保存时做可写探测，macOS 检测到路径在 .app/Contents 内直接拒绝并提示。这样既满足「可自行选择」，又不会把默认值设在一个大多数用户不可写的位置。

启动期还有一个细节：设置存在 DB 里，而日志要在读设置之前就开始记录。做法是 subscriber 先初始化，文件 writer 进入「待定目录」状态，把启动期日志放进有界内存队列；拿到 AppHandle 并 load 设置后再 set_dir，队列一次性写入正确目录。这样不会出现「前 200 毫秒日志落在默认目录、之后落在自定义目录」的分裂。

### 3.2 日志保留天数

| 子需求 | 判定 | 说明 |
| --- | --- | --- |
| 自动清理超过指定天数的日志 | 合理 | 启动时、保存设置时、每天本地 00:05 后各清理一次 |
| 0 表示不清理 | 合理 | 0 时完全跳过按天清理；单日大小上限仍生效（防止一天写爆） |
| 默认 7 天 | 合理 | 与 bililive-go 的 rotate_days 默认一致 |
| 清理最旧的文件 | 合理 | 按文件名日期判断，不按 mtime（mtime 会被复制/同步工具改） |
| 只清日志、不碰其他文件 | 必须 | 白名单正则 + 只删普通文件 + 跳过当前文件；用户选到桌面也不能误删 |
| 与媒体保留的关系 | 需说明 | 日志不计入 media.max_total_gb，也不受 media.retention_days 影响；两个「保留」在 UI 上要写清楚 |

「7 天」建议定义为含今天 7 个自然日：今天 11-07，保留 11-01 至 11-07，删除 10-31 及更早。另一种是 7×24 小时，边界会落在一天中间，用户更难理解。这个口径需要裁决（见 §8 Q2）。

清理时机：启动完成后一次；设置保存后一次；长跑应用每天一次。不要只在启动时清理——用户可能几周不重启。每日任务用 30 分钟一次的轻量检查（记录 last_cleanup_date），跨过本地日期就清理；这样睡眠唤醒、DST、系统时间被改都能兜住。切天时 writer 也会换文件，但清理不依赖写入，避免「没有日志就不清理」。

单日上限：必须有。否则某个模块进入错误循环（例如每秒重连）会把磁盘写满。建议单文件 16 MiB，超出后依次写 hivecast-YYYY-MM-DD.1.log 到 .3.log；四个都满就丢弃并计数，状态里显示 dropped，下一次切天恢复。上限只约束当天，不影响历史保留。

清理实现要点：列出目录，匹配 ^hivecast-(\d{4}-\d{2}-\d{2})(\.\d+)?\.log$；解析日期；日期早于 cutoff 的删除；跳过 current_path；删除失败只 WARN 一次并计入 skipped；不递归子目录。日志目录如果被用户选到媒体库根目录，也不会碰到录像文件（录像名不匹配）。

### 3.3 全功能日志捕获

这一项是本次需求的主体，不是「加两行 info」能完成的。建议先定义验收口径，再按模块补：

1. 用户能感知的失败，至少一条 WARN/ERROR，包含模块、操作、房间/平台（有则带）、错误链；不能只有前端 toast。
2. 关键状态变化一条 INFO：开播/下播、开始/停止录制、续录、收尾、掉盘、进入/退出冷却、登录失效、转封装开始/结束。
3. 外部请求一条完成日志：成功 DEBUG（默认不落文件也可以），失败 WARN；字段含 platform、room、qn、line、status、elapsed_ms、attempt；绝不带 Cookie/Authorization/完整 query。
4. ffmpeg/ffprobe 非 0 退出时，WARN 带退出码、信号、最后 N 行 stderr（环形缓冲，N=20）；正常运行不逐行落盘。
5. 前端异常：全局 error、unhandledrejection、ErrorBoundary、命令失败（命令名 + 错误）都能落盘。
6. 不允许每个 tick 一条 INFO；高频成功日志用 DEBUG，并做去重/限流。

| 开录 | record.start（platform/room_key/qn/line/quality/pid/session/file） | INFO |

| 通知 | notice.send_fail（kind/err） | WARN |
| panic | panic（thread/location/message） | ERROR |

P0 是「错误可追踪」的底线：启动、设置、录制、ffmpeg、后处理、平台 HTTP、前端、panic。P1 是「问题可定位」：监控、取流、观看、弹幕、磁盘、保留、账号、平台解析、生命周期、通知。P2 是锦上添花：缩略图成功耗时、DB 慢查询、demo。

### 3.4 日志分类与格式

分类不靠「中文标题里写模块」，靠 tracing 的 target。默认 target 就是模块路径，例如 hivecast_lib::recorder、hivecast_lib::monitor、hivecast_lib::postprocess；需要跨模块归类时用显式 target，例如 hivecast_lib::ffmpeg、hivecast_lib::ui、hivecast_lib::panic。

建议文件格式（控制台保持现在的简洁格式，文件里带 target 和字段）：

```text
2026-11-07 14:25:37.123 +08:00  INFO hivecast_lib::recorder event=record.start room_id=... platform=bilibili room_key=... qn=10000 line=... pid=4242
2026-11-07 14:31:02.004  WARN hivecast_lib::recorder event=ffmpeg.exit room_id=... code=1 signal=- tail="... last 20 lines ..."
2026-11-07 14:31:02.010  INFO hivecast_lib::recorder event=record.finalize room_id=... status=failed reason=error duration_ms=... file_size=... restarts=3 confirmed=false
```

约定：

- 时间统一 chrono::Local，含毫秒和本地时区偏移（如 +08:00）；不要用 UTC 伪装本地时间。
- 文件 UTF-8 无 BOM，LF 换行；Windows 记事本/VS Code 都能正常打开。
- 字段用 key=value，值含空格时加引号；event 名固定，便于 grep/统计。
- 中文消息给用户看，字段名用英文给脚本看；两者都保留。
- 高频成功日志用 DEBUG；默认文件过滤器建议 info,hivecast_lib::recorder=debug,hivecast_lib::monitor=debug,hivecast_lib::postprocess=debug，既能看到状态机，又不会被每 30 秒一次的请求刷爆。RUST_LOG/HIVECAST_LOG 可临时开到 debug 排障。
- 日志级别设置本身本次不做（避免新增入口）；docs/19 已规划「日志级别」，将来放到全局设置或诊断页，本期先用 HIVECAST_LOG 环境变量兜底。

安全与隐私：

- URL 只记录 scheme://host/path，query 只留 key（sign=***&expires=***）；直播流 URL 建议只留 host + url_redacted=true，因为 token 可能藏在 path。
- Cookie、Authorization、Set-Cookie、token、password、secret、wsSecret、phone、email 永不记录；错误信息里出现也要先脱敏。
- 房间标题、主播名、文件路径可以记录（排错需要），但设置页要提示「日志会包含房间标题与录像路径，不包含账号凭据」。
- 平台错误串现在把完整 URL 拼进 AppError（platform/http.rs:40），monitor 的 warn 会把 hint 原样写进日志；这是上传日志时最现实的泄漏点，必须在落日志前统一脱敏。

### 3.5 跨天与连续跨天

| 场景 | 目标行为 |
| --- | --- |
| 同一天重启 | 打开同一个 hivecast-YYYY-MM-DD.log，O_APPEND，不截断 |
| 跨过本地午夜 | 午夜后第一条日志触发换文件；文件名用新日期；旧文件关闭 |
| 连续运行多天 | 每天一个基名文件；单日超限才有 .1/.2/.3 段；不把多天写进一个文件 |
| 连续多天没运行 | 启动时直接开今天；清理任务按文件名日期删旧文件 |
| 运行中改目录 | 旧目录文件关闭；新目录开当天文件；保留天数对新目录同样生效 |
| 系统睡眠跨天 | 唤醒后第一次写入检查日期并换文件；每日清理任务在 30 分钟内补跑 |
| DST/改系统时间 | 每次写入重新取 Local 日期；不缓存「今天」到进程生命周期 |
| 跨天时正好在写 | 单 writer 互斥，先完成当前行再换文件；不会把一行拆到两个文件 |
| 单日写满 | 切到 .1/.2/.3；都满则丢弃并计数，不阻塞业务 |
| 清理正在被查看的旧文件 | macOS 可 unlink；Windows 删除会失败，跳过并下次重试；当天/当前文件永不删 |

文件命名与匹配：

- 基名：hivecast-2026-11-07.log
- 分段：hivecast-2026-11-07.1.log、.2.log、.3.log
- 清理白名单：^hivecast-\d{4}-\d{2}-\d{2}(\.\d+)?\.log$
- 不匹配的文件一律不碰；不递归；不删目录；不删符号链接目标（只删链接本身或跳过）。

### 3.6 设置入口整合

两项都是全局设置，只保留一份，不按房间/平台覆盖；房间字段只作为日志内容，不作为配置。现有设置页是左栏分类 + 内容：账号 / 录制与观看 / 存储 / 通知 / 外观与语言 / 关于。存储页已有「目录」（媒体根目录 + 选择）、「命名」、「保留」（录像保留天数 + 容量上限）。日志设置应放在「存储」页，顺序建议：

1. 目录（媒体根目录）
2. 日志文件（新增：日志目录 + 打开目录 + 恢复默认；日志保留天数）
3. 命名
4. 保留（录像）

理由：日志目录和媒体目录都是「文件放哪」，日志保留和录像保留都是「旧文件清多久」，放在一起用户不需要学新分类；不新增一级入口，符合「不要有多余的功能入口或差异」。缺点是两个「保留」相邻，必须用标题和说明区分：「录像保留」与「日志保留」。

交互细节：

- 日志目录输入框：占位显示实际默认路径（只读提示），空值 = 跟随默认；右侧「选择」「打开」「恢复默认」三个按钮。
- 选择目录复用现有 @tauri-apps/plugin-dialog 的 open({directory:true})；chooseFolder 目前写死 mediaRoot，需要改成可传目标。
- 「打开目录」新增 logs_open 命令，只能打开当前生效的日志目录，不接受任意路径参数；不要复用 media_reveal（它只接受 session_id，且 macOS 用 open -R 是「在 Finder 中显示文件」）。
- 日志保留天数：数字输入 0–3650，单位「天」，0 的说明写「不按天清理（单日大小上限仍生效）」。
- 状态行：显示「当前目录：…；保留：7 天；今日文件：…；已丢弃：N 行」；读取失败显示错误，不要让页面空白。
- 搜索索引加两条：日志目录/打开日志、日志保留/清理；关键词包含 log、日志、排错、诊断。
- i18n 中英各约 12–14 个键，check-i18n 必须过。
- Settings 结构体加 logDir、logRetentionDays；ts-rs 重新生成 bindings；DB 键用 log.dir、log.retention_days，空串表示跟随默认，便于以后改默认值。

### 3.7 Windows/macOS 兼容

| 关注点 | macOS | Windows | 处理 |
| --- | --- | --- | --- |

## 4. 建议设置键与接口

## 7. 验收标准

1. 安装包启动（Finder/开始菜单，非终端）后，默认目录出现 hivecast-YYYY-MM-DD.log；开发构建出现在 HIVECAST/logs。
2. 同一天重启追加，不覆盖；跨天（可用测试时钟/改系统时间）生成新日期文件；连续 3 天模拟不混写。
3. 日志目录选到自定义路径后立即生效：旧文件关闭、新文件产生、状态行显示新路径；重启后仍使用新路径。
4. 目录不可写/盘拔出：应用不崩溃、不阻塞；回落默认目录并通知；设置里的值不被静默改写（或明确提示已改写）。
5. 保留 0：不按天删；保留 7：含今天 7 个自然日，旧日期删除，当前文件与无关文件保留。
6. 单日超过上限：出现 .1/.2/.3；全满后 dropped 增长，应用继续工作。
7. 伪造 ffmpeg 失败：日志有 ffmpeg.exit、退出码、stderr 尾部；后处理失败有 stage/input/output。
8. 前端触发一个命令失败：日志有 command.error + 命令名；白屏/未处理 Promise 有 ui.error。
9. 全量 grep 日志：不出现 Cookie、Authorization、sign=、token=、wsSecret 的值；URL 只到 host/path。
10. Windows：默认路径正确、文件可写、打开目录可用、占用中的旧文件不导致清理崩溃、跨天正常。
11. 日志写入不阻塞 UI：录制/监控正常，磁盘满时只 dropped 增长。
12. node scripts/check-docs.mjs、check-i18n、tsc -b、vite build 全过。
