# 65 监控录制联动修复七（G 系列）

> 状态：v1.0（2026-11-07，第八轮；修复 [64 复审五](64-监控与录制关系复审五.md) 的 G1–G5，G6 只文档化；验收过程中新发现并修复 G7）｜对象：monitor.rs、recorder.rs、disk.rs、db.rs、App.tsx、i18n｜上游：[64](64-监控与录制关系复审五.md)、[54 v3.8](54-监控与录制关系审查.md)

一句话结论：**G1–G5 五条全部改完并用真机复验：外接卷拔掉后 1 秒内按 `disk_lost` 停录并进入 `aborted/disk_lost`（以前是守卫失明、由 ffmpeg 报错兜底）；失败会话遗留的分片在下次启动时自动合并并回写文件大小；长间隔重启后的首次检测最多等 30 秒；开录连续失败 3 次进入 5 分钟冷却；检测成功但平台信息没变时写库从每秒一次降到 10 秒一次。验收还挖出一个比 G1 更严重的调度问题 G7：`+10%` 抖动会让长间隔被误判成「旧排期太远」，interval=1800 实际约 20 秒查一次；已改成记录排期时的基础间隔，只在间隔真的变小时重排。**

### 1.1 G3：先判「目录还在不在」，再判「还剩多少」

旧实现的顺序是「按卷算容量 → 容量为 `None` 就放行」。外接卷拔掉后，`volume_key` 会一路往上找到系统盘，容量于是变成「系统盘还有空间」，守卫完全失明；录制继续写一个已经不存在的目录，最后由 ffmpeg 的退出码收尾，记成 `failed/error`，用户看不到任何磁盘告警。

现在先做目录可用性检查：`root_ready(path)` 要求 `create_dir_all` 成功、路径是目录、权限不是只读。不可用直接 `Missing`，不再看剩余空间。监控每拍按**目录**汇总（不是按卷），`Missing` 与 `Low` 分开处理：

- `Missing` → `stop("disk_lost")`，WARN「录制目录不可用，停止录制」；
- `Low` → `stop("disk_full")`，沿用原来的红线文案。

收尾侧新增 `Some("disk_lost") => ("aborted","disk_lost",None)`，通知侧新增 `("aborted","disk_lost")` 分支；前端把 `disk_lost` 映射到 `notice.diskLost`，中英文各补一条文案（「录制目录不可用」/「Recording folder unavailable」）。这样用户看到的是「盘/目录没了，请接回后手动开录」，而不是一条笼统的「录制失败」。

另外把「自动开录被拒」的日志前缀拆开了：目录不可用时写「录制目录不可用，暂不自动开录」，只有真的容量不足才写「空间不足，暂不自动开录」。

### 1.2 G4：失败会话也要认领自己的分片

G3 修好之后，掉盘那一刻的分片还在卷上：DB 行已经是 `failed/disk_lost`（或 `aborted/disk_lost`），旧 `recover_parts` 只查 `status='recording'`，于是这些分片永远没人合并。

新逻辑在原有「恢复崩溃遗留的录像」之后加一轮：取最近 200 条 `failed`/`aborted` 会话，逐条找同名前缀的 `.partNNNN.ts`；有分片就 `finish_file(path, true)` 合并，大小 >0 时更新 `record_session.file_path/file_size`，记 INFO「恢复失败会话遗留的分片」，并计入 `recovered/recovered_bytes`。没有分片、或分片都被删掉的会话直接跳过，不会产生空文件。

限制：只处理 DB 里还有行的会话；纯目录孤儿（DB 行已被删、只剩文件）本轮不扫，避免误合并用户手工放进媒体库的 `.ts`。

### 1.3 G1 + G7：首检封顶 30 秒，长间隔不再被抖动打回

G1 的改法很直接：`spread` 原来是 `hash % base`，interval=1800 时首个排期可能落在 29 分钟之后；现在 `cap = base.min(30)`，任何间隔下首次检测都在 30 秒内发生，后续仍严格按 interval 推进。

验收 T1 时先看到「interval=1800，rm-g1 的 `last_checked_at` 却每 20 秒左右变一次」，才挖出 G7。原因是 tick 里判断「间隔是否被调小」用的是：

```rust
if !entry.backoff && entry.next_at > now + interval { /* 重排 */ }
```

而成功排期是 `grid + jitter(id, ±10% base)`。当抖动为正时，`next_at` 必然大于 `now + interval`，于是每一拍都被判定成「旧排期太远」：

1. 重置为 `now + spread(id, base)`，最多 30 秒；
2. 到点检测，又得到一个正抖动；
3. 下一拍再次重置。

结果 interval=1800 实际变成「每 20 秒左右查一次」，正好和 G1 的 30 秒上限撞在一起。负抖动的房间不受影响（`next_at < now+interval`），所以现场表现是「有的房间疯狂检测、有的房间正常」，很容易被误判成平台抖动。

修法是把「排期时用的基础间隔」记进 `Schedule.interval_secs`（成功、限流、Retry、Failed 四个分支都写当前 `base`），重排条件改成 `base > 0 && base < entry.interval_secs && entry.next_at > now`。间隔调大不重排（让当前这拍按旧节奏走完），退避中的排期也不跟着收缩，与 C6/F4 的语义一致。

### 1.4 G5：哪些失败才值得冷却

不是所有 `start_checked` 失败都该计数：并发已满、房间已删、应用正在退出、上一场正在收尾、用户手动停录，这些重试也不会变好，计数只会把「等用户操作」误伤成「冷却 5 分钟」。所以 `start_failure_is_counted` 明确排除：

- `AppError::Db` / `AppError::Internal`（不是源或路径的问题）；
- `AppError::User` 且消息以「房间已移除」「房间不存在」「应用正在退出」「上一场正在收尾」「同时录制已达上限」「该房间连续录制失败」「连续开录失败」开头。

其余（平台鉴权/取流失败、ffmpeg 缺失/启动失败、路径不可写等）计入。达到 3 次记 WARN「连续开录失败，暂停自动重试 5 分钟」；冷却期内 `start_checked` 直接拒绝，监控侧也加了 `!in_start_cooldown` 条件，不再每拍调用。手动开录同样受冷却限制——这是有意的：坏路径下手动连点也只会刷同样的错误。

### 1.5 G2：结构性变化立即写，其余 10 秒一次

监控页要看到「是否在播、标题、主播、头像、分区、开播时间」的变化，这些字段任一变化仍然立刻 `update_room_info` + 推事件。只有全都没变时才走 `touch_room_throttled`：一条条件 UPDATE，只在 `last_checked_at` 为空或已超过 10 秒时写 `online/last_checked_at/updated_at`，返回是否真的落库。

在线人数仍然会更新，只是最多延迟 10 秒；前端每秒重绘用的 `now` 不受影响。10 秒是常量 `ROOM_TOUCH_INTERVAL`，和检测间隔无关——interval=1 时收益最大，interval=60 时本来就一拍一写，没有额外开销。

## 4. 行为变化与边界

| 项 | 变化 |
| --- | --- |
| 外接盘/录制目录消失 | 1 秒内按 `disk_lost` 停录，会话记 `aborted/disk_lost`，通知「录制目录不可用」；盘接回后自动重开 |
| 失败/中止会话 | 启动时最多扫 200 条，有分片就合并并把大小写回 DB |
| 重启后的首次检测 | 最多等 30 秒（不再随 interval 放大） |
| 长间隔 + 正抖动 | 不再被误重置；interval 只影响检测节奏，不会再退化成 30 秒 |
| 开录连续失败 | 3 次后冷却 5 分钟；用户意图类失败不计入 |
| 检测写库 | 结构没变时最多 10 秒写一次；标题/在播/开播时间变化仍然立即写并推事件 |
| 掉盘时的收尾 | `file_size` 可能是 0（文件已不可访问），以 DB 的 `aborted/disk_lost` 为准 |
