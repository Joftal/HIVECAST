# 09 · 弹幕子系统

> 参考实现：`bililive-go/src/recorders/danmaku/`（baseRecorder + bilibili/douyin/douyu 三套客户端 + ass_writer）、`src/recorders/danmaku/bilibili/{api,client,handler,packet,pb}.go`、`configs.DanmakuConfig`。
> 目标：把直播弹幕实时落成 **与视频同名的 .ass 字幕文件**，可选后续烧录进视频。

## 1. 总体结构

```text
平台 WS ──▶ DanmakuClient（每平台一个实现）
              │  统一消息
              ▼
        DanmakuRecorder（生命周期/开关/计数/广播）
              │
      ┌───────┴────────┐
      ▼                ▼
  AssWriter        UI 实时推送（SSE/事件）
  (.ass 文件)
```

三层职责：

| 层 | 职责 | 不该做的事 |
| --- | --- | --- |
| Client | 连接、解包、重连、心跳 | 不写文件、不管开关 |
| Recorder | 过滤（礼物/SC/舰长开关）、计数、广播、写 ASS | 不解析协议 |
| AssWriter | 样式、排版、时间轴、落盘 | 不关心消息来源 |

## 2. 统一消息模型

```rust
enum DanmakuKind {
    Chat,        // 普通弹幕
    Gift { name: String, num: u32, price: u64, coin: String },
    SuperChat { price: u64, duration_secs: u32 },
    Guard { level: String },   // 舰长/提督/总督
    System,                    // 进场/关注/公告
}

struct DanmakuMessage {
    kind: DanmakuKind,
    /// 相对录制开始的毫秒偏移——这是唯一正确的时间基准
    offset_ms: i64,
    user: Option<String>,      // 关闭"显示用户名"时为 None
    content: String,
    color: u32,                // 0xRRGGBB
    raw_ts: i64,               // 平台原始时间戳（用于排查）
}
```

**时间基准是最大的坑**，见 §6。

## 3. B 站弹幕客户端

### 3.1 连接

```text
1. room_init 拿真实 room_id
2. getDanmuInfo?id=<real>&type=0 → { token, host_list[{host, wss_port}] }
3. 依次尝试 wss://<host>:<wss_port>/sub
4. 全失败 → wss://broadcastlv.chat.bilibili.com/sub
5. 发送认证包（op=7）
6. 启动心跳（30s，op=2）
```

认证体：

```json
{"uid":0,"buvid":"","roomid":123456,"protover":3,"platform":"danmuji","type":2,"key":"<token>"}
```

- `buvid` 从 cookie 的 `_uuid` 提取（正则 `_uuid=(.+?);`），没有就空串。
- JSON 体里的 `protover: 3` 表示接受 brotli 压缩；但 **16 字节包头里的 protover 字段填 `1`**（`ProtoPopularity`），bililive-go 就是这么发的，照抄即可，不要「顺手改成 3」。
- **WS 握手不要带 Cookie**（bililive-go 只带 UA），带 Cookie 反而可能被拒。

### 3.2 包格式（16 字节头，大端）

```text
0..4   packet_len  u32
4..6   header_len  u16 = 16
6..8   protover    u16  0=plain 1=popularity 2=zlib 3=brotli
8..12  operation   u32
12..16 sequence    u32 = 1
```

| op | 含义 |
| --- | --- |
| 2 | 心跳 |
| 3 | 心跳回复（人气值） |
| 5 | 业务消息 |
| 7 | 认证 |
| 8 | 认证回复（`code=-101` 表示 token 过期） |

- `protover=2/3` 的 body 是**压缩后的多个子包**，解压后要按同样格式循环切分。
- 连续 5 次失败（`refreshThreshold=5`）要重新 `getDanmuInfo` 换 token。

### 3.3 消息解析

| cmd | 提取 |
| --- | --- |
| `DANMU_MSG` | `info[1]`=文本，`info[2][0]`=uid，`info[2][1]`=用户名，`info[0][3]`=颜色 |
| `SEND_GIFT` | `data.giftName`/`num`/`price`/`coin_type` |
| `SUPER_CHAT_MESSAGE` | `data.message`/`price`/`user_info.uname` |
| `GUARD_BUY` | `data.gift_name` |

cmd 可能带后缀（`DANMU_MSG:4:0:2:2:2:0`），用前缀匹配。

## 4. 斗鱼 / 抖音客户端

### 4.1 斗鱼（TCP，不是 WebSocket）

斗鱼弹幕走**裸 TCP**，这一点和 B 站/抖音都不同：

```text
地址：danmuproxy.douyu.com:8601（可通过接口拿服务器列表，含 ip/port）
帧头：12 字节，小端
      length(4) + length(4) + type(4)
      body 长度 = length - 8（重复的 length 是历史遗留）
type：689 = 客户端消息，690 = 服务端消息
结尾：body 以 \x00 结束，读取后要去掉
```

消息体是 `key@=value/` 形式的 STT 序列化串（value 中的 `/` 和 `@` 要转义）。

流程：

```text
1. TCP 连接（超时 10s）
2. 登录：  type@=loginreq/roomid@=<rid>/
3. 读一帧登录响应
4. 加房间：type@=joingroup/rid@=<rid>/gid@=-9999/
5. 启动读循环 + 心跳循环
6. 心跳：  type@=keeplive/tick@=<unix_ms>/     每 45s
7. 读超时 60s；断线后重新解析服务器地址并重连
```

弹幕消息在 `chatmsg` 类型里：`nn`=昵称、`txt`=内容、`col`=颜色（十进制 RGB）、`uid`=用户 id。

### 4.2 抖音

- 依赖 `bililive-tools` 或自研签名（见 07 文档）。
- WS 消息为 protobuf（`dy.pb.go` 里有完整 message 定义），需要 `sign.js` 生成的签名参数建立连接。
- 消息类型多（`WebcastChatMessage`/`WebcastGiftMessage`/`WebcastMemberMessage`），需要按 `method` 分发。

> 三个平台的共同点：**连接层差异大，消息层可以统一**。所以 Client 实现要独立，Recorder 以上全部复用。

## 5. ASS 生成

### 5.1 为什么用 ASS 而不是 SRT

| 能力 | ASS | SRT |
| --- | --- | --- |
| 颜色 | ✅ 逐条 | ❌ |
| 描边/阴影 | ✅ | ❌ |
| 定位（顶部/底部/滚动） | ✅ | ❌ |
| 字号/字体 | ✅ | ❌ |
| 播放器兼容 | 好 | 好 |

弹幕需要"彩色 + 描边 + 滚动"，只有 ASS 能做到。

### 5.2 结构

```text
[Script Info]
ScriptType: v4.00+
PlayResX: 1920
PlayResY: 1080
WrapStyle: 2
ScaledBorderAndShadow: yes

[V4+ Styles]
Format: Name, Fontname, Fontsize, PrimaryColour, ...
Style: Danmaku,Microsoft YaHei,36,&H00FFFFFF,&H00000000,...

[Events]
Format: Layer, Start, End, Style, Name, MarginL, MarginR, MarginV, Effect, Text
Dialogue: 0,0:00:01.23,0:00:11.23,Danmaku,,0,0,0,,{\c&H00FF00&}这是一条弹幕
```

### 5.3 配置项（对齐 bililive-go `DanmakuConfig`）

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `font_size` | 36 | 相对 1080p 的字号 |
| `font_name` | Microsoft YaHei | 跨平台建议回退到 `Noto Sans CJK SC` |
| `scroll_area` | full | `full`（全屏滚动）/ `top`（上半）/ `bottom`（下半） |
| `scroll_time` | 10 | 单条弹幕停留秒数 |
| `resolution` | 1920x1080 | `PlayResX/Y`，影响字号换算 |
| `outline` | 1 | 描边宽度 |
| `opacity` | 128 | 透明度（0–255，ASS 的 alpha 是反的：0=不透明） |
| `record_gift` | — | 是否记录礼物 |
| `record_guard` | — | 是否记录上舰 |
| `record_super_chat` | — | 是否记录醒目留言 |
| `guard_position` | bottom-left | 舰长消息位置 |
| `sc_position` | bottom-left | SC 位置 |

### 5.4 颜色转换

ASS 颜色是 `&HAABBGGRR`（**BGR 顺序 + alpha 在前**），平台给的是 `0xRRGGBB`：

```text
ass = &H00 | BB | GG | RR
```

透明度：ASS 的 `00` 是完全不透明，`FF` 是完全透明。用户配置 `opacity=128`（半透明）要转成 `&H80`。

### 5.5 滚动定位（避免重叠）

最简单的做法是"固定轨道轮转"：

```text
lane_count = 可用高度 / 行高
lane = next_lane(); next_lane = (next_lane + 1) % lane_count
\move(1920, y, -text_width, y)
```

更精细的做法是记录每条弹幕的"离场时间"，选最早空出的轨道。**先用简单方案**，重叠在弹幕稀疏时几乎不可见。

### 5.6 特殊消息的排版

| 类型 | 样式建议 |
| --- | --- |
| 礼物 | 底部固定行，`{\c&H00D7FF&}赠送 xxx × N` |
| SC | 底部块状，带背景框（`{\bord}...` 或 `{\p1}` 绘图） |
| 舰长 | 左下角，带等级色 |

## 6. 时间轴对齐（最关键）

### 6.1 问题

弹幕消息自带的是**平台服务器时间**，而视频文件从"ffmpeg 收到第一个包"开始计时。两者有几十毫秒到几秒的偏差。

### 6.2 正确做法

```text
1. 录制开始时记录 t0（本地单调时钟，ffmpeg 启动前）
2. 每条弹幕到达时记录 t_arrive（本地单调时钟）
3. offset_ms = t_arrive - t0
4. ASS 时间 = offset_ms
```

**不要用平台时间戳做基准**，除非你能拿到服务器时间同步（B 站的心跳回复里有人气值但没时间）。

### 6.3 已知偏差与修正

| 偏差来源 | 量级 | 处理 |
| --- | --- | --- |
| 网络延迟 | 50–500ms | 可忽略（弹幕本身就是"实时"的） |
| ffmpeg 启动耗时 | 0.5–3s | `t0` 应在 ffmpeg 进程启动**之后**、收到首包**之前**取 |
| 分段录制 | 每段独立 | 每段重新取 `t0`，ASS 文件名与视频同名 |
| 录制开始前的弹幕 | — | 丢弃（offset < 0） |

### 6.4 与视频时长校验

结束时对比 `ASS 最后一条时间` 与 `视频时长`：

- 差 > 10s → 记录警告（可能漏录或时间基准错了）；
- 差 > 60s → 标记该 ASS 不可信，不参与烧录。

## 7. 性能与稳定性

| 问题 | 对策 |
| --- | --- |
| 高并发弹幕（万人直播间） | 批量写（每 100 条或每 500ms flush 一次） |
| 内存增长 | 不缓存全量消息，只保留"最近 N 条"给 UI |
| ASS 文件过大 | 单场 > 50 万条时建议截断或降采样 |
| 磁盘 IO | 独立线程写，不阻塞 WS 读循环 |
| WS 断线 | 指数退避重连（1s→2s→…→30s），重连后重新认证 |
| token 过期 | 连续 5 次失败刷新 `getDanmuInfo` |

**限流策略**：单房间每秒最多处理 200 条，超出部分丢弃并计数（UI 显示"已丢弃 N 条"）。丢弃比卡死好。

## 8. 与录制/后处理的衔接

```text
录制开始 → 启动 DanmakuRecorder（若开启）
         → ASS 路径 = 视频路径去掉扩展名 + ".ass"
录制结束 → 停止 recorder → flush → 关闭文件
         → 若开启 burn_subtitles：pipeline 的 burn 阶段把 ASS 烧进视频
         → 若开启 burn_delete_ass：烧录成功后删 ASS
```

**命名必须严格同名**，否则后处理找不到（bililive-go 的 `findAssFile` 就是按同名找的）。

### 8.1 烧录参数

```bash
ffmpeg -i video.flv -vf "ass=/path/to/file.ass" \
  -c:v libx264 -crf 18 -preset medium -c:a copy out.mp4
```

- ASS 路径要转义（空格、冒号、单引号），Windows 下尤其麻烦。
- `-crf 18` 是 bililive-go 默认值，画质与体积平衡点。
- 烧录是**重编码**，耗时 ≈ 视频时长的 0.3–1×，必须放在后台队列。

## 9. 可选：原始弹幕存档

除了 ASS，建议同时落一份 `JSONL`（每行一条消息）：

```json
{"t":12345,"kind":"chat","user":"xxx","content":"哈哈","color":16777215}
```

好处：

- 可重新生成不同样式的 ASS（改字号/颜色不用重录）；
- 可做统计（发言数、礼物总额）；
- 出问题时能对比"原始 vs ASS"定位 bug。

体积很小（1 万条 ≈ 1MB），默认开启。

## 10. 反模式

1. ❌ 用平台时间戳直接当 ASS 时间 → 整体偏移。
2. ❌ ASS 与视频不同名 → 后处理找不到。
3. ❌ 在 WS 读循环里同步写磁盘 → 消息堆积、连接被踢。
4. ❌ 弹幕无限缓存 → 长时间直播 OOM。
5. ❌ 颜色直接 `0xRRGGBB` 塞进 ASS → 红蓝颠倒。
6. ❌ 关闭"显示用户名"时仍写 `Name` 字段 → 隐私泄露。
7. ❌ 分段录制时复用同一个 ASS → 后段弹幕跑到前段文件里。
