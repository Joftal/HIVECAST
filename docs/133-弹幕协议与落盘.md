# 133 · 弹幕协议与落盘

> 适用范围：连接、心跳、消息解析、去重、落盘、ASS 导出。
> 参考：bililive-go（四平台协议 + ASS）、biliLive-tools（重连/去抖）、streamlink（**没有弹幕**，不要在这找）。
> 结论先行：**视频断了可以重连，弹幕客户端必须独立重连；弹幕绝不能阻断录制。**
> 2026-11-12 全链路复查与修复见 [147-B站弹幕全链路复查](147-B站弹幕全链路复查.md)。

---

## 1. 总体结构

```text
RecordSession
  ├── video: ffmpeg 进程
  └── danmaku: DanmakuHub
        ├── BilibiliConnector   WS + WBI + brotli
        ├── DouyuConnector      TCP + STT
        ├── HuyaConnector       WS + Tars/JCE
        └── DouyinConnector     WS + protobuf + gzip
              │
              ▼
        DanmakuEvent { t, kind, uid, name, text, color, ... }
              │
              ├──▶ RecordWriter → danmaku.jsonl（每 50 条或 1s flush）
              └──▶ 实时 UI（可选，失败不影响录制）
```

HIVE 当前实现：

- `src-tauri/src/danmaku.rs`：`DanmakuHub` 按房间扇出，引用计数归零才断开；同一房间多个消费者（录制 + 预览）共用一条连接。
- `src-tauri/src/douyin_ws.rs`：抖音独立 protobuf/gzip/ACK/5s 心跳。
- `RecordWriter`：JSONL，字段 `t/k/u/c/col`，每 50 条或 1 秒 flush；空文件在收尾时删除。

## 2. B 站

### 2.1 连接

1. `GET https://api.live.bilibili.com/xlive/web-room/v1/index/getDanmuInfo?id={rid}`
   - 需要 WBI 签名（见 2.4）；失败时退回旧 `getConf` 接口。
   - 返回 `token` 与 `host_list[]`（`host/port/wss_port`）。
2. 选第一个可用 host，连 `wss://{host}:{wss_port}/sub`。
3. 发送认证包（Op=7），body 为 JSON：

```json
{"uid":0,"buvid":"","roomid":123,"protover":3,"platform":"web","type":2,"key":"<token>"}
```

   - WS 本身不发送 Cookie；`uid=0`、`buvid=""` 是匿名身份。
   - `platform` 固定为 `web`（旧版文档写的 `danmuji` 与当前实现不符）。
   - 弹幕 REST（`room_init` / `getDanmuInfo` / `getConf` / `nav`）也走匿名 GET，不注入登录 Cookie，见 `src/platform/http.rs` 的 `get_json_anon`。

4. 收到 Op=8 认证回复后开始收包；每 30 秒发 Op=2 心跳（body 为 `[object Object]`）。

> `getDanmuInfo` 常因出口 IP 风控返回 `-352`，此时回退 `getConf` 取 token；两者都失败才进入重试。详见 [147](147-B站弹幕全链路复查.md)。

### 2.2 包格式

16 字节头，全部大端：

```text
offset 0  : packet_len   u32
offset 4  : header_len   u16 (=16)
offset 6  : protover     u16
offset 8  : operation    u32
offset 12 : sequence     u32 (=1)
body      : packet_len - 16 字节
```

- `protover=0`：body 是 JSON。
- `protover=1`：body 是 popularity（4 字节整数），可忽略。
- `protover=2`：body 是 zlib 压缩的**多个完整包**，解压后要循环再解析。
- `protover=3`：body 是 brotli 压缩的多个完整包（HIVE 用 brotli crate）。

Op 含义：

| Op | 方向 | 含义 |
| --- | --- | --- |
| 2 | C→S | 心跳 |
| 3 | S→C | 心跳回复（popularity） |
| 5 | S→C | 通知（普通消息） |
| 7 | C→S | 认证 |
| 8 | S→C | 认证回复 |

### 2.3 消息映射

Op=5 的 JSON 里 `cmd` 决定类型：

| cmd | 映射 | 关键字段 |
| --- | --- | --- |
| `DANMU_MSG` | chat | `info[1]` 文本、`info[2][0]` uid、`info[2][1]` 昵称、`info[0][3]` 颜色、`info[0][4]` 时间戳(ms) |
| `SUPER_CHAT_MESSAGE` | super_chat | `data.message`、`data.price`、`data.user_info.uname` |
| `SEND_GIFT`（旧） | gift | `data.giftName`、`data.num`、`data.uname` |
| `SEND_GIFT_V2`（当前真实主路径） | gift | `data.pb` base64 protobuf：顶层 2 用户名、10.2 礼物名、10.3 数量 |
| `GUARD_BUY` | guard | `data.gift_name`、`data.num`、`data.username`（舰长/提督/总督） |
| `INTERACT_WORD` / `INTERACT_WORD_V2` | enter | 可丢弃，量大 |
| `ROOM_CHANGE` | room_change | 标题变更，用于分段 |

> 真实直播礼物现在主要走 `SEND_GIFT_V2`；只处理旧 `SEND_GIFT` 会把礼物全部丢掉。protobuf 字段与真实样本见 [147 §5.2](147-B站弹幕全链路复查.md)。

**不要**把所有 `cmd` 都落盘；进入/关注类消息会迅速膨胀 JSONL。HIVE 当前只保留 chat/gift/guard/super_chat 等有价值类型。

### 2.4 WBI 签名

`getDanmuInfo` 需要 `w_rid` 与 `wts`：

1. `GET https://api.bilibili.com/x/web-interface/nav` 拿 `wbi_img.img_url/sub_url`。
2. 取文件名（去掉路径与扩展名），拼成 64 字符。
3. 按 `mixinKeyEncTab` 取前 32 位得到 `mixin_key`。
4. query 参数按 key 排序，拼 `k=v&...`，末尾加 `wts={unix}`。
5. `w_rid = md5(query + mixin_key)`。

注意：

- `mixinKeyEncTab` 是固定表，但 B 站改过；建议做成常量并写单测。
- 签名只用于 API，不用于 WS。
- `nav` 未登录也能拿 key；登录后不要复用匿名 key 的缓存超过 1 小时。

## 3. 斗鱼

### 3.1 连接

- TCP `danmuproxy.douyu.com:8601`（也有 8602/8603）。
- 先发登录包：`type@=loginreq/roomid@={rid}/`。
- 再发加入分组：`type@=joingroup/rid@={rid}/gid@=-9999/`。
- 每 45 秒发 `type@=keeplive/tick@={unix}/`；超过 90 秒无响应应重连。

### 3.2 包格式

12 字节头，全部**小端**：

```text
offset 0 : 包总长（含头） u32
offset 4 : 包总长（重复） u32
offset 8 : 消息类型      u16（689 = 弹幕）
offset 10: 加密标志      u8（0）
offset 11: 保留          u8（0）
body     : 包总长 - 12
```

body 是 STT 序列化：

- 键值对 `key@=value/`。
- 值里的 `@` 转义为 `@A`，`/` 转义为 `@S`。
- 解析时先反转义，再按 `/` 分割。

### 3.3 消息映射

| `type` | 映射 | 关键字段 |
| --- | --- | --- |
| `chatmsg` | chat | `nn` 昵称、`txt` 文本、`uid`、`col` 颜色、`level` |
| `dgb` | gift | `gfid`、`gfcnt`、`nn` |
| `uenter` | enter | 可丢弃 |
| `rss` | room_status | 开播/下播 |
| `ssd` | super_chat | 特殊礼物 |

斗鱼有 `mrkl`（排行榜）等大包，解析时要限制单包最大长度（如 1MB），防止恶意长度导致 OOM。

## 4. 虎牙

### 4.1 连接

- `wss://ws.api.huya.com`。
- 先发注册包（Tars/JCE 编码）：`tars_mp.register` 或 `userInfo.register`，携带 `uid/roomid`。
- 再发加入分组：`tars_mp.joinGroup`，`gid` 为房间组。
- 心跳：WUP 包，60 秒一次；不同 `iUri` 对应不同消息（8006 弹幕、1400 礼物、6501 心跳回复）。

### 4.2 编码

- 外层是 WUP/Tars 结构，不是 JSON；字段按 JCE 顺序编码。
- 解析需要维护 schema（字段 id + 类型），不能靠字符串猜。
- HIVE 当前在 `danmaku.rs` 内有虎牙命令帧解析；新增字段时要兼容「未知字段跳过」。

### 4.3 消息映射

| iUri | 映射 | 关键字段 |
| --- | --- | --- |
| 8006 | chat | `sContent`、`lUid`、`sNickName` |
| 1400 | gift | `sGiftName`、`iGiftCount` |
| 6501 | heartbeat_reply | 忽略 |

虎牙对连接频率敏感：同一 IP 短时间大量重连会触发验证码/断连；重连必须退避。

## 5. 抖音

### 5.1 连接

1. 先取房间信息与签名（见 130 §7），拿 `room_id` 与 `ttwid`。
2. 连 `wss://webcast5-ws-web-lf.douyin.com/webcast/im/push/v2/...`，参数含 `app_name/did/ttwid/room_id/...` 与签名。
3. 消息是 protobuf；部分帧 gzip 压缩；收到后要回 ACK。
4. 心跳 5 秒一次（HIVE `douyin_ws.rs`）；100 秒无消息视为假死，主动重连。

### 5.2 消息映射

| method | 映射 | 关键字段 |
| --- | --- | --- |
| `WebcastChatMessage` | chat | `content`、`user.id`、`user.nickname` |
| `WebcastGiftMessage` | gift | `gift.name`、`repeat_count`、`user.id` |
| `WebcastMemberMessage` | enter | 可丢弃 |
| `WebcastLikeMessage` | like | 可聚合，不逐条落盘 |
| `WebcastRoomUserSeqMessage` | online | 在线人数，低频采样 |

抖音礼物有连击：同一 `groupId_userId_giftId` 在 5 秒内会重复推送。参考实现做 5 秒去抖合并；HIVE 至少要去重，否则 JSONL 会爆炸。

## 6. 重连与健康

| 平台 | 心跳 | 判定假死 | 重连策略 |
| --- | --- | --- | --- |
| B 站 | 30s | 90s 无包 | 指数退避 1s→30s（0–400ms jitter）；token 连续失败 5 次才重新取 token |
| 斗鱼 | 45s | 90s 无包 | 5s 起退避，最多 8 次 |
| 虎牙 | 60s | 120s 无包 | 10s 起退避，避免风控 |
| 抖音 | 5s | 100s 无消息 | 3s 起退避，重新取签名 |

当前实现（`src/danmaku.rs`）：B 站每 30 秒心跳，`IDLE_TIMEOUT=90s`、每 15 秒检查一次 `last_rx`；超过 90 秒没有任何事件就主动断开重连。退避 1s→30s，每次加 0–400ms jitter。

原则：

1. **退避带 jitter**，避免同一时刻所有房间重连。
2. **重连不换房间 ID**，但要重新取 token/签名（可能已过期）。
3. **弹幕失败只记录，不影响视频**；UI 显示「弹幕连接中断」而不是「录制失败」。
4. **引用计数**：录制与预览共用连接；最后一个消费者退出才断开（HIVE `DanmakuHub` 已实现）。
5. **认证失败不是永久停止**：B 站 `run_once` 返回 Err 后按退避重试；token 连续失败 5 次才丢弃并重新请求 `getDanmuInfo/getConf`。这样偶发风控不会让弹幕永久停摆。

## 7. 落盘格式

HIVE 当前 JSONL，一行一条：

```json
{"t":265062,"k":"chat","u":"绪方理奈-w-","c":"[空之轨迹1st表情包_对不起]","col":16777215}
```

字段：

| 字段 | 含义 |
| --- | --- |
| `t` | 相对该 RecordWriter 启动时刻的毫秒偏移，不是服务端时间戳 |
| `k` | chat / gift / guard / super_chat |
| `u` | 昵称（当前实现写昵称，不写 UID） |
| `c` | 文本内容；礼物为 `赠送 X × N`，SC 为 `[N 元] 文本` |
| `col` | 十进制颜色整数；B 站聊天几乎都是 `16777215` |

写入策略：

- 每 50 条或 1 秒 flush；`flush` 每 200ms 额外调 `flush_pending()`，慢速房间最后一条最多滞留 200ms。
- 先写录制、再做 200 条/秒的 UI 限流，爆发时不会因为限流丢盘。
- 进程崩溃最多丢约 200ms–1 秒；可接受。
- 空文件在收尾时删除；不要留下 0 字节 `danmaku.jsonl`。
- 文件编码 UTF-8，不转义中文（便于 grep）。
- 昵称就是 `u`，没有单独的 UID 字段；需要去重请用 `u + c + t`。

## 8. ASS 导出

bililive-go 的 ASS 时间轴规则（`src/pkg/danmaku/ass.go:419-458`）值得直接借：

```text
startCS     = (recvAt - startAt) / 10ms，负数钳 0
textWidth   = 估算（中文 1em，英文 0.5em）
durationCS  = travelCS(resX + textWidth)，最小 200cs
lane        = 找空闲车道；全满时复用「最早离开」的车道，允许重叠
scrollMs    = round(scroll_time_ms / resX)，<1 取 1
```

原则：

1. **宁可重叠，不推迟时间戳**。推迟会让整场弹幕越来越晚，最后完全对不上。
2. 顶部/底部弹幕单独车道，不与滚动混用。
3. 颜色从 `col` 转 ASS `&HBBGGRR&`。
4. 字号/描边/分辨率要与视频一致；导出前读视频分辨率，不要写死 1920×1080。
5. 时间基准用「录制开始」而不是「文件创建」，否则分片合并后偏移。

HIVE 当前已有 ASS 导出命令；本节作为校验清单，不要求重写。

## 9. 去重与顺序

- 去重键：`(platform, room, uid, ts, kind, text)`；礼物用 `(uid, gift_id, group_id)` + 5 秒窗口。
- 不要用「文本相同」去重：同一人连发「666」是正常的。
- 不要用「接收顺序」当时间：多分片/重连会乱序；落盘前按 `t` 稳定排序（或至少保证单文件内追加顺序）。
- 重连后可能收到重复的历史消息；用「最后一条 `t`」做水位，丢弃 `t` 明显倒退且内容重复的包。

## 10. 实测清单

用 ego-browser + Cookie.txt：

1. B 站：进一个高人气房间，确认 30 秒内收到 chat；断网 10 秒恢复，是否自动重连。
2. B 站：确认 brotli 包能解出多条消息（不是只解第一条）。
3. 斗鱼：确认小端长度正确、STT 转义正确（含 `@` 与 `/` 的文本）。
4. 虎牙：确认 WUP 心跳与 8006 消息；连续重连 5 次是否被风控。
5. 抖音：确认 gzip 解压、ACK、5 秒心跳；礼物连击是否合并。
6. 录制 10 分钟：JSONL 行数是否合理、空文件是否删除、ASS 是否与视频对齐。
7. 同时开录制与预览：是否只有一条 WS 连接（引用计数生效）。

## 11. 反模式

- 弹幕连接失败导致整场录制失败。
- 每个消费者各建一条 WS（被平台限流/封 IP）。
- 心跳用固定间隔但重连后不重置计时器（刚连上就发心跳）。
- 把 `INTERACT_WORD/uenter` 全量落盘。
- 用接收时间当弹幕时间（延迟/重连会整体偏移）。
- ASS 车道满了就推迟时间（时间轴越推越歪）。
- 解压后只解析第一个包（B 站 zlib/brotli 是多包）。
- 不限制单包长度（恶意/异常包导致 OOM）。
