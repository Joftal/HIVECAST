# 12 · 数据模型与持久化

> 参考实现：`bililive-go/src/livestate/`（store.go 748 行、types.go 66 行、migrations 000001–000003）、`src/pipeline/` 的 `SQLiteStore`、`src/metadata/`。
> 桌面端同样需要持久化：房间、场次、文件、任务、账号、配置。SQLite 是唯一合理选择。

## 1. 为什么是 SQLite

| 方案 | 评价 |
| --- | --- |
| JSON 文件 | 并发写会损坏；查询要全量加载；不适合 1000+ 场次 |
| SQLite | 单文件、零部署、支持事务/索引/WAL、Rust 生态好（`rusqlite`/`sqlx`） |
| 嵌入式 KV（sled） | 无 SQL，统计查询要自己写 |
| 外部数据库 | 桌面端不可接受 |

**决策**：SQLite + WAL 模式。

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

WAL 让"读不阻塞写"，对"UI 持续查询 + 后台录制写状态"的场景是刚需。

## 2. 数据库布局

```text
<app_data>/
  ├─ hivecast.db          # 主库：房间/场次/文件/任务/账号
  ├─ hivecast.db-wal
  └─ hivecast.db-shm
```

单库即可，不需要分库。备份 = 复制三个文件（或用 `VACUUM INTO`）。

## 3. 表结构

### 3.1 live_rooms（房间）

```sql
CREATE TABLE live_rooms (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    live_id         TEXT NOT NULL UNIQUE,   -- 稳定标识，如 "bilibili/123456"
    url             TEXT NOT NULL,          -- 用户原始 URL
    platform        TEXT NOT NULL,          -- "bilibili"
    host_name       TEXT NOT NULL DEFAULT '',
    room_name       TEXT NOT NULL DEFAULT '',
    avatar_url      TEXT,
    last_start_time INTEGER,                -- unix 秒
    last_end_time   INTEGER,
    is_recording    INTEGER NOT NULL DEFAULT 0,
    is_listening    INTEGER NOT NULL DEFAULT 1,
    notify_only     INTEGER NOT NULL DEFAULT 0,
    last_heartbeat  INTEGER,                -- 监听器最后活跃时间
    last_error      TEXT,
    created_at      INTEGER NOT NULL,
    updated_at      INTEGER NOT NULL
);

CREATE INDEX idx_live_rooms_platform ON live_rooms(platform);
CREATE INDEX idx_live_rooms_recording ON live_rooms(is_recording) WHERE is_recording = 1;
```

要点：

- `live_id` 是业务主键（`platform/room_key`），`id` 只是自增。外部引用一律用 `live_id`。
- `last_heartbeat` 用于崩溃检测：应用启动时心跳过期的 `is_recording=1` 记录要修复。
- `last_error` 让 UI 能显示"上次失败原因"，而不是只显示一个红点。

### 3.2 live_sessions（场次）

一次"开播 → 下播"= 一个 session；一个 session 可对应多个物理文件（分段）。

```sql
CREATE TABLE live_sessions (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    live_id     TEXT NOT NULL,
    host_name   TEXT NOT NULL DEFAULT '',
    room_name   TEXT NOT NULL DEFAULT '',
    start_time  INTEGER NOT NULL,
    end_time    INTEGER,
    end_reason  TEXT,              -- normal | user_stop | crash | error | unknown
    created_at  INTEGER NOT NULL,
    FOREIGN KEY (live_id) REFERENCES live_rooms(live_id) ON DELETE CASCADE
);

CREATE INDEX idx_sessions_live ON live_sessions(live_id, start_time DESC);
CREATE INDEX idx_sessions_open ON live_sessions(end_time) WHERE end_time IS NULL;
```

`end_reason` 枚举：

| 值 | 含义 | UI 展示 |
| --- | --- | --- |
| `normal` | 主播下播 | 正常结束 |
| `user_stop` | 用户手动停止 | 手动停止 |
| `crash` | 应用崩溃后恢复 | 异常中断（已修复） |
| `error` | 录制错误 | 失败 |
| `unknown` | 未知 | 未知 |

### 3.3 recording_files（文件）

```sql
CREATE TABLE recording_files (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  INTEGER NOT NULL,
    live_id     TEXT NOT NULL,
    path        TEXT NOT NULL,
    size        INTEGER NOT NULL DEFAULT 0,
    duration_ms INTEGER,
    kind        TEXT NOT NULL DEFAULT 'video',  -- video | cover | danmaku | other
    status      TEXT NOT NULL DEFAULT 'recording', -- recording | completed | failed | deleted
    started_at  INTEGER,
    ended_at    INTEGER,
    created_at  INTEGER NOT NULL,
    FOREIGN KEY (session_id) REFERENCES live_sessions(id) ON DELETE CASCADE
);

CREATE INDEX idx_files_session ON recording_files(session_id);
CREATE INDEX idx_files_status ON recording_files(status);
```

- 分段录制时一个 session 对应多行。
- `status=deleted` 用于"文件已被清理但记录保留"（历史列表仍能看到）。
- **不要**在 DB 里存文件的绝对路径之外的东西；文件系统是唯一真相，DB 只是索引。

### 3.4 name_history（改名历史）

```sql
CREATE TABLE name_history (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    live_id     TEXT NOT NULL,
    field       TEXT NOT NULL,   -- host_name | room_name
    old_value   TEXT NOT NULL,
    new_value   TEXT NOT NULL,
    changed_at  INTEGER NOT NULL
);

CREATE INDEX idx_name_history_live ON name_history(live_id, changed_at DESC);
```

用途：分段依据、UI 展示"这个主播改过几次名"、排查"为什么文件名叫旧名字"。

### 3.5 pipeline_tasks（后处理任务）

```sql
CREATE TABLE pipeline_tasks (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    record_id     TEXT NOT NULL,           -- 对应 recording_files.id 或逻辑记录
    live_id       TEXT NOT NULL,
    status        TEXT NOT NULL,           -- pending | running | completed | failed | canceled
    current_stage TEXT,
    stage_index   INTEGER NOT NULL DEFAULT 0,
    files_json    TEXT NOT NULL DEFAULT '[]',
    error         TEXT,
    attempts      INTEGER NOT NULL DEFAULT 0,
    created_at    INTEGER NOT NULL,
    started_at    INTEGER,
    finished_at   INTEGER
);

CREATE INDEX idx_pipeline_status ON pipeline_tasks(status, created_at);
```

- `files_json` 存 `FileInfo` 数组（含 `deletable`、`source_path`），用于 `retry_from_stage`。
- 重启时 `UPDATE ... SET status='pending' WHERE status='running'`。

### 3.6 accounts（账号）

```sql
CREATE TABLE accounts (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    platform     TEXT NOT NULL,
    account_id   TEXT NOT NULL,        -- 平台用户 ID
    display_name TEXT NOT NULL DEFAULT '',
    avatar_url   TEXT,
    cookies_json TEXT NOT NULL DEFAULT '{}',   -- 加密存储
    tokens_json  TEXT NOT NULL DEFAULT '{}',
    device_id    TEXT,                 -- 斗鱼 dy_did 等，必须固定
    status       TEXT NOT NULL DEFAULT 'unknown', -- valid | expired | unknown
    updated_at   INTEGER NOT NULL,
    UNIQUE(platform, account_id)
);
```

**加密**：`cookies_json` 用 OS keychain 派生的密钥做 AES-GCM 加密（Tauri 可用 `keyring` crate）。至少要做到"不以明文躺在磁盘上"。

### 3.7 settings（键值配置）

```sql
CREATE TABLE settings (
    key        TEXT PRIMARY KEY,
    value      TEXT NOT NULL,
    updated_at INTEGER NOT NULL
);
```

存 UI 偏好（主题、列宽、上次选中的标签页）、`config_version`、schema 版本等。**业务配置仍用 YAML**（用户可手改），这里只存"应用内部状态"。

### 3.8 schema_migrations

```sql
CREATE TABLE schema_migrations (
    version    INTEGER PRIMARY KEY,
    applied_at INTEGER NOT NULL
);
```

迁移用**递增编号的 SQL 文件**（`000001_init.sql`、`000002_add_sessions.sql`），启动时按序执行未应用的。禁止"改已发布的迁移文件"。

## 4. 关键查询

### 4.1 房间列表（带当前状态）

```sql
SELECT r.*,
       (SELECT COUNT(*) FROM live_sessions s WHERE s.live_id = r.live_id) AS session_count,
       (SELECT MAX(start_time) FROM live_sessions s WHERE s.live_id = r.live_id) AS last_session
FROM live_rooms r
WHERE r.is_listening = 1
ORDER BY r.is_recording DESC, r.updated_at DESC;
```

### 4.2 某房间的场次历史

```sql
SELECT s.*, COUNT(f.id) AS file_count, SUM(f.size) AS total_size
FROM live_sessions s
LEFT JOIN recording_files f ON f.session_id = s.id AND f.status != 'deleted'
WHERE s.live_id = ?
GROUP BY s.id
ORDER BY s.start_time DESC
LIMIT ? OFFSET ?;
```

### 4.3 崩溃恢复

```sql
-- 1) 找未结束的场次
SELECT * FROM live_sessions WHERE end_time IS NULL;

-- 2) 心跳过期的录制房间
SELECT * FROM live_rooms
WHERE is_recording = 1 AND (last_heartbeat IS NULL OR last_heartbeat < ?);

-- 3) 重置运行中的任务
UPDATE pipeline_tasks SET status = 'pending' WHERE status = 'running';
```

### 4.4 统计

```sql
-- 按平台统计录制时长（近 30 天）
SELECT r.platform,
       COUNT(DISTINCT s.id) AS sessions,
       SUM(COALESCE(s.end_time, strftime('%s','now')) - s.start_time) AS total_seconds
FROM live_sessions s JOIN live_rooms r ON r.live_id = s.live_id
WHERE s.start_time > strftime('%s','now') - 30*86400
GROUP BY r.platform;
```

## 5. 写入策略

| 场景 | 频率 | 策略 |
| --- | --- | --- |
| 录制状态（is_recording） | 状态变化时 | 立即写 |
| 心跳（last_heartbeat） | 每 30s | 批量/节流写（每 60s 一次） |
| 文件大小 | 每 5s | **不写 DB**，只在内存 + UI 推送；结束时写一次 |
| 房间信息（标题/主播名） | 变化时 | 立即写 + 记 name_history |
| 任务进度 | 每阶段 | 立即写 |

**原则**：高频、可推导的数据不落库。文件大小随时可 `stat` 得到，DB 里存了反而会不一致。

## 6. 数据保留

```text
retention:
  sessions_days: 0      # 0 = 永久
  files_days: 0
  name_history_days: 90
  pipeline_tasks_days: 30   # 已完成的任务定期清理
```

清理策略：

- 只删 DB 记录，**不删磁盘文件**（删文件必须是用户显式操作）。
- `VACUUM` 定期执行（每月或记录数变化 > 20% 时）。

## 7. 一致性

### 7.1 文件与 DB 的关系

```text
文件系统 = 真相（source of truth）
DB       = 索引（可重建）
```

- 扫描功能：遍历输出目录，发现 DB 里没有的文件 → 提示"导入"。
- 修复功能：DB 里有但文件不存在 → 标记 `status=missing`（不要直接删记录）。

### 7.2 事务边界

| 操作 | 事务范围 |
| --- | --- |
| 开播 | 更新 room + 插入 session |
| 分段 | 插入 file + 更新 session 的 end_time（可选） |
| 下播 | 更新 session.end_time + room.is_recording |
| 后处理完成 | 更新 task + 更新 file.status |

单条 `INSERT` 不需要显式事务（SQLite 自动），但"多表一致"必须显式 `BEGIN ... COMMIT`。

## 8. 备份与恢复

```sql
VACUUM INTO '/path/backup-2026-11-05.db';
```

- 比复制文件安全（WAL 模式下直接复制可能不一致）。
- 建议每天一次，保留 7 份。
- 恢复 = 关闭应用 → 替换 `.db` → 删除 `-wal`/`-shm` → 启动。

## 9. 性能

| 数据量 | 表现 |
| --- | --- |
| 100 房间 / 1 万场次 | 无压力 |
| 1000 房间 / 100 万文件记录 | 需要索引（已建）+ 分页查询 |

- 所有列表查询**必须分页**（默认 50）。
- 避免 `SELECT *` 返回大字段（`files_json` 单独查）。
- UI 不要每次刷新都全量查询，用增量推送（见 13 文档）。

## 10. 反模式

1. ❌ 用自增 id 做业务主键 → 换库/同步就乱。
2. ❌ 把文件大小/时长当权威数据 → 与磁盘不一致。
3. ❌ 一个巨大 JSON 存所有房间 → 并发写丢失。
4. ❌ 迁移文件发布后还改 → 老用户库结构错乱。
5. ❌ 明文存 cookie → 任何能读文件的人都能盗号。
6. ❌ 高频写 DB（每秒） → WAL 膨胀、IO 打满。
7. ❌ 删除 DB 记录时顺手删文件 → 用户数据丢失且不可恢复。
8. ❌ 不用 WAL → UI 查询阻塞录制写入。
