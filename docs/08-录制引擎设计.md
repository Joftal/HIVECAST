# 08 · 录制引擎设计

> 参考实现：`bililive-go/src/recorders/recorder.go`（2163 行）、`src/recorders/manager.go`（421 行）、`src/listeners/listener.go`（250 行）、`streamlink/src/streamlink/stream/segmented/segmented.py`（361 行）、`stream/hls/hls.py`（954 行）、`buffers.py`（163 行）。
> 这是整个应用最核心、最容易出线上问题的部分。本文按"一个录制任务的生命周期"组织。

## 1. 两个循环，不要合并

初学者常把"检测开播"和"下载流"写在一个循环里，结果是：下载阻塞时检测不到下播，检测频繁时又干扰下载。正确做法是**两个独立循环 + 事件解耦**：

```text
监听循环（每房间一个）              录制循环（每任务一个）
  loop:                              loop:
    info = adapter.room_info()         if !should_record: break
    diff(prev, info) → 事件            try_record()  // 阻塞直到本轮结束
    sleep(interval ± jitter)           sleep(retry_interval)
```

事件：

| 事件 | 发布者 | 订阅者动作 |
| --- | --- | --- |
| `LiveStarted` | 监听器 | 创建录制任务（`notify_only` 房间跳过） |
| `LiveEnded` | 监听器 | 停止录制任务 |
| `RoomNameChanged` | 监听器 | 若开启"标题变化分段"则重启录制 |
| `ListenStopped` | 监听器 | 停止录制任务 |
| `RecordStopRequested` | 录制器自身 | 从管理器移除 |

> bililive-go 用 `events.Dispatcher`（`AddEventListener`/`DispatchEvent`/`DispatchEventSync`）做这件事。**同步派发只用在初始化交接**（替换监听器），其余都是异步。

## 2. 状态机

```text
        ┌────────┐  room_info.is_live    ┌───────────┐  ffmpeg 启动成功  ┌───────────┐
        │  Idle  │ ────────────────────▶ │ Preparing │ ────────────────▶ │ Recording │
        └────────┘                       └───────────┘                   └───────────┘
            ▲                                  │                              │
            │ 失败/超时                         │ 下播/停止/错误                │
            └──────────────────────────────────┴──────────────────────────────┘
                                                                              ▼
                                                                        ┌───────────┐
                                                                        │ Finalizing│
                                                                        └───────────┘
```

各状态对外暴露的字段（参考 bililive-go `Info`）：

| 状态 | UI 显示 | 内部标志 |
| --- | --- | --- |
| Idle | 未开播 | `status=false, listening=true` |
| Preparing | 准备录制 | `recording_preparing=true` |
| Recording | 录制中 | `recording=true` |
| Finalizing | 处理中 | `recording=false`，任务在 pipeline 队列 |

**关键**：`Preparing` 必须有超时（建议 60s），否则取流卡死会让房间永远显示"准备中"。

## 3. 录制循环（tryRecord）

一次 `try_record()` 的完整步骤（对应 `recorder.go:tryRecord`）：

```text
1. 解析该房间的有效配置（全局 → 平台 → 房间三级覆盖）
2. 快照录制选项（画质、仅音频、cookie、昵称）
   —— 快照后本轮内不再变化；若录制中选项变了，本轮作废重取
3. 取流候选
   a. 优先"懒解析"接口：只列元信息
   b. 选中目标档位后再 resolve 出真实地址
   c. 无懒解析则一次性取全部
4. 失败 → 退避重试（见 §4），或直接结束
5. 渲染文件名模板（见 §5）
   —— 模板渲染失败 → 直接停止任务，不要重试（否则死循环）
6. 按用户偏好选流（见 §6）
7. 按格式改扩展名：hls → .ts，audio_only → .aac，flv → .flv
8. 检查外部依赖（ffmpeg 是否可用）
   —— 未就绪 → 每 2s 轮询，不发平台请求
9. 探测流头（可选）：FLV 读头部拿分辨率/码率；HLS 异步探测
10. 启动下载器/解析器，阻塞直到结束
11. 结束后：清理空文件 → 登记产物 → 提交后处理流水线
```

### 3.1 为什么"选项快照"很重要

录制中途用户改了画质，如果直接读最新配置，会出现"文件名说 1080p 但内容是 720p"。正确做法：

- 开始时快照；
- 每轮结束检查"当前配置 vs 快照"，不一致则本轮作废、重取；
- 文件名用**快照时的值**渲染。

bililive-go 用 `RetainRecordingVersion` / `SameRecordingOptions` 实现。

## 4. 失败与退避

### 4.1 秒退检测

如果一次 `try_record` 在 `5s` 内就结束（`fastFailThreshold = 5s`），说明"取流成功但立刻断"，这是典型的被风控或地址失效。此时**逐步拉长重试间隔**：

```text
retry_interval = base * 2^(consecutive_fast_fail)   // 上限 5min
```

成功录制超过阈值则重置计数。

**biliLive-tools 的同一套机制（可直接对照实现）**：

| 参数 | 值 | 行为 |
| --- | --- | --- |
| 短录制阈值 | 12 s | 录制时长 < 12s 视为"秒退" |
| 连续次数 | 2 | 连续 2 次秒退 → 下一次 **优先切换备用线路**（`preferAlternativeStream`，主要给抖音） |
| 恢复条件 | ≥ 12s | 时长达到阈值即清零计数 |
| 立即重查 | 录制 ≥ 60s 且非手动停止 → 1s 后重查，最多 10 次 | 主播短暂断流后快速续录 |
| 停止原因黑名单 | `manual stop` / `remove recorder` / `直播间标题包含关键词` / `标题变更分段` | 这些原因**不计入失败**，不触发重试 |

两个细节值得抄：**"秒退计数"与"线路选择"联动**（不是单纯拉长间隔，而是换一条路走），以及**黑名单过滤停止原因**（用户主动停止不该被当成故障）。


### 4.2 分类处理

| 情况 | 动作 |
| --- | --- |
| 未开播 | 正常结束，回到监听循环 |
| 取流接口失败 | 退避重试（1s→2s→4s…5min） |
| 取到地址但立刻断 | 秒退检测，拉长间隔 |
| 外部工具未就绪 | 2s 轮询工具状态 |
| 房间被封 | 标记不可用，10× interval 后再试 |
| 磁盘满 | **立即停止所有录制**，告警（不要继续写坏文件） |

## 5. 文件命名

### 5.1 默认模板（bililive-go）

```text
{{ .Live.GetPlatformCNName }}/{{ .HostName | filenameFilter }}/[{{ now | date "2006-01-02 15-04-05" }}][{{ .HostName }}][{{ .RoomName }}].flv
```

产物示例：

```text
哔哩哔哩/某某主播/[2026-11-05 20-30-00][某某主播][今天的直播].flv
```

### 5.2 模板能力

| 变量/函数 | 说明 |
| --- | --- |
| `.Live.GetPlatformCNName` | 平台中文名 |
| `.HostName` | 主播名 |
| `.RoomName` | 房间标题 |
| `.Live.GetOptions.NickName` | 用户自定义昵称（优先于 HostName） |
| `now` / `date "layout"` | 当前时间与格式化 |
| `filenameFilter` | 过滤非法字符（`/ \ : * ? " < > \|` 与控制字符） |
| `replace` / `trim` / `lower` 等 | 通用字符串函数 |

### 5.3 命名规则（HIVECAST 建议）

1. **必须先过滤再拼接**：标题里的 `/` 会创建意外目录。
2. **长度限制**：单段 ≤ 100 字符，总路径 ≤ 240 字符（Windows 兼容）。
3. **重名处理**：同名文件已存在时追加 `_1`、`_2`，不要覆盖。
4. **模板预览**：UI 提供"输入示例 → 实时预览"，避免用户写出坏模板。
5. **渲染失败**：立刻停止任务并报错，**绝不重试**。

## 6. 选流策略

```text
score(candidate) =
      quality_match      // 用户指定档位命中 → 最高
    + weight             // 归一化权重（分辨率/码率/fps）
    + format_pref        // flv > hls（省 CPU、可断点续传性更好）
    + codec_pref         // 兼容性优先时 h264 > h265
    - placeholder_penalty// 需要二次解析的候选略降权
```

用户偏好支持**列表回退**：`["原画", "蓝光", "best"]`，逐个尝试。

> 参考 streamlink 的 `stream_weight` 与 `best`/`worst` 同义词生成机制：排序后动态生成别名，用户配置 `best` 永远指向当前最优。

## 7. 下载器选型

| 方式 | 适用 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 外部 `ffmpeg` 子进程 | FLV/HLS/任意 | 稳、兼容一切、可转封装 | 进程管理复杂、错误信息需解析 |
| 内置 HLS 下载器 | HLS | 可控重试、可过滤分片、可去广告 | 需自己做 AES/字节范围/时间戳 |
| 内置 FLV 解析 | FLV | 无外部依赖、可精确切分 | 需处理时间戳回绕、tag 校验 |

**HIVECAST 建议**：

- 默认 **ffmpeg 子进程**（最稳），把 stderr 解析成结构化进度。
- HLS 增加内置下载器作为备选（ffmpeg 对某些带鉴权的 HLS 支持不好）。
- 两者都实现 `Downloader` trait：`start() / progress() / stop(graceful) / wait()`。

### 7.1 ffmpeg 参数基线

```bash
ffmpeg -hide_banner -loglevel warning \
  -headers "Referer: https://live.bilibili.com/123\r\nUser-Agent: ..." \
  -user_agent "..." \
  -i "<url>" \
  -c copy -f flv "<output>.flv"
```

- `-c copy` 不转码（CPU 几乎为零）。
- `-headers` 用 `\r\n` 分隔，**末尾也要有**。
- 输出 `-f flv` 显式指定，避免扩展名推断错误。
- 需要限时/限大小时用 `-t` / `-fs`，但更推荐应用侧主动 stop（可控性更好）。

**fmp4 输出基线（biliLive-tools 的默认值，强烈建议照抄）**：

```bash
ffmpeg -hide_banner -i "<url>" \
  -c copy -movflags +frag_keyframe+empty_moov+separate_moof \
  -fflags +genpts+igndts -min_frag_duration 10000000 \
  "<output>.mp4"
```

- `+empty_moov`：moov 写在文件头 → **录制中就能播放**，而不是等收尾；
- `+frag_keyframe` + `-min_frag_duration 10000000`：每 10s（关键帧对齐）一个 fragment → 进程被强杀最多丢最后一个 fragment，文件仍可播；
- `-fflags +genpts+igndts`：直播流时间戳常跳变，让 ffmpeg 重新生成 PTS；
- 该组合的代价是文件不再"标准 mp4 索引"，某些老播放器 seek 稍慢——可接受。

**选 `-f segment` 分段时**追加 `-reset_timestamps 1` 与 `-segment_format mp4`，否则第二段起时间戳从上一段延续，播放器会显示异常时长。

**输出格式默认值的选择顺序**（biliLive-tools `FFmpegDownloader`）：`videoFormat=auto` 时，无分段 → `m4s`（若源是 ts 流则仍用 `ts`），有分段 → `ts`。即"**不分段用 fmp4 抗损坏，分段用 ts 便于拼接**"。

**失败判定（比"进程退出"更早）**：ffmpeg 对坏流往往不退出，只是持续输出 warning。biliLive-tools 用 `createFFmpegInvalidStreamChecker` 统计 stderr 连续无效行数：**HLS 35 行、FLV 18 行**即判定流坏，主动杀掉重试。配合 30s 超时检查（3 × 10s）双保险。

### 7.2 优雅停止

```text
SIGTERM → 等待 5s 让 ffmpeg 写完尾部 → 仍未退出则 SIGKILL → 检查文件完整性
```

- **不要直接 SIGKILL**：FLV 尾部元数据会丢，文件可能无法 seek。
- 停止后要校验：文件大小 > 0、时长 > 0、可被 ffprobe 解析。

## 8. 分段（Split）

三种触发：

| 触发 | 配置 | 说明 |
| --- | --- | --- |
| 时长 | `max_duration` | 到时优雅停止并立即开新段 |
| 大小 | `max_file_size` | 支持 `500MB`/`1GB` 可读格式；负数非法 |
| 标题变化 | `on_room_name_changed` | 房间改名即切段（常用于区分"场次"） |

### 8.1 分段时的状态交接（重要）

分段不是"停一个再起一个"那么简单，有两类状态要传递：

1. **共享状态**（`pipelineSharedState`）：待处理计数、已上传明细、摘要是否已发送。否则每段都会发一次"录制完成"通知。
2. **文件累积**（`initial_recorded_files`）：一个"逻辑录制"可能产出多个物理文件，后处理要能看到全部。

bililive-go 通过 `redirect` 链把旧 recorder 的状态交给新 recorder。HIVECAST 里建议用 `RecordingSession`（逻辑场次）+ `Segment`（物理文件）两级模型：

```text
RecordingSession { id, room_id, started_at, ended_at, segments: Vec<Segment> }
Segment { path, started_at, ended_at, size, status }
```

## 9. 断流检测

仅靠"进程退出"不够——ffmpeg 有时会挂着但不再产出数据。需要**看门狗**：

```text
每 5s 检查：
  - 输出文件大小是否增长（或 mtime 是否更新）
  - 连续 3 次无增长（≈15s）→ 判定断流 → 优雅停止并重试
```

阈值参考：

| 场景 | 无数据超时 |
| --- | --- |
| FLV 直播 | 20s |
| HLS 直播 | `max(5, targetduration * 3)`（streamlink 的 `queue_deadline` 默认 3 倍目标时长） |
| 低码率纯音频 | 60s |

> streamlink 的实现：`check_queue_deadline`，日志 `"No new segments for more than X s. Stopping..."`。这个日志文案值得照抄，排障时一眼能定位。

**补充：文件增长检测对 ffmpeg 不可靠。** fmp4 每 10s 才落一个 fragment，文件大小在 fragment 之间是不变的；而 ffmpeg 挂死时进程也不会退出。所以对 ffmpeg 后端要**以 stderr 为第一信号源**：

| 信号 | 含义 | 动作 |
| --- | --- | --- |
| `time=` 长时间不前进 | 没有数据在流 | 超时阈值（30s）后杀掉重开 |
| 连续无效行（HLS 35 / FLV 18） | 流已坏但 ffmpeg 还在重试 | 立即杀掉，判为失败 |
| 进程退出码 ≠ 0 | 连接/鉴权失败 | 按 §4.2 分类处理 |
| 进程退出码 = 0 且时长 < 12s | 秒退 | 计入秒退计数（§4.1） |

自研下载器（`segmented`）则相反：**以"最后一个成功分片的时间"为准**，文件增长只是副产品。

## 10. 并发与资源

| 资源 | 建议上限 | 说明 |
| --- | --- | --- |
| 同时录制数 | 3（可配，默认对齐 `task_queue.max_concurrent`） | 每个 ffmpeg 约占 20–50MB 内存 |
| 同平台并发请求 | B 站 4 / 斗鱼 2 / 抖音 1 | 见 04 文档 |
| 磁盘写入 | 单文件顺序写，不要多线程写同一文件 | |
| 句柄 | 每个任务 1 个输出文件 + 1 个 ffmpeg 进程 + 1 个日志 | 50 房间监听不应持有 50 个文件句柄 |

**监听 ≠ 录制**：监听只发 HTTP 请求，不持有文件。50 个房间监听 + 3 个录制是合理配置。

## 11. 崩溃恢复

应用重启后要能回答："上次是不是在录？"

```text
启动时：
  1. 查 sessions 表，找 end_time IS NULL 的记录
  2. 对每条：检查对应文件是否存在、是否可解析
  3. 可解析 → 标记 end_reason = "crash"，提交后处理（修复 FLV）
  4. 不可解析 → 标记失败，保留文件供人工检查
  5. 清理孤儿临时文件（.part / .tmp）
```

> bililive-go 的 `pipeline` 用 `ResetRunningTasks` 把"运行中"的任务重置为"待处理"，思路相同。

## 12. 与后处理的衔接

录制结束后**不要在主流程里做转码**，而是：

```text
录制结束 → 写 DB（segment 完成）→ 提交 pipeline 任务（入队）→ 立即返回，可以开下一段
```

后处理在独立线程池执行（详见 10 文档）。这样：
- 录制不会被转码阻塞；
- 转码失败可重试，不影响录制；
- 应用退出时后处理任务可恢复。

## 13. 关键指标（用于 UI 与排障）

| 指标 | 采集方式 |
| --- | --- |
| 录制时长 | 开始/结束时间差 |
| 文件大小 | 定期 stat |
| 实际码率 | Δsize / Δt |
| 丢帧/断流次数 | 看门狗触发计数 |
| 重连次数 | try_record 调用次数 |
| ffmpeg 退出码 | 进程 wait 结果 |

UI 上"录制中"卡片至少显示：已录时长、文件大小、当前码率、健康状态（绿/黄/红）。

## 14. 反模式清单

1. ❌ 在 UI 线程做取流/下载 → 界面卡死。
2. ❌ 用固定 sleep 等 ffmpeg 退出 → 关机慢、文件损坏。
3. ❌ 录制中途读实时配置 → 文件名与内容不一致。
4. ❌ 失败立即无限重试 → 被封 IP。
5. ❌ 只判断进程存活，不看数据增长 → "假录制"。
6. ❌ 转码放在录制循环里 → 后续分段延迟。
7. ❌ 文件名不过滤非法字符 → 随机创建目录。
8. ❌ 分段时不传递状态 → 重复通知、重复上传。
