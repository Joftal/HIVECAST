# 斗鱼单房批量与三平台登录态降级

> 2026-11-16。范围：斗鱼批量门槛、B 站/斗鱼/抖音批量返回登录态异常时的处理、抖音关注页「不返回离线房」的显示语义。
> 基线：`9aee8cd`（抖音导入与批量边界修复）之后的本地修改；362 个 Rust 单测。

## 1. 结论

这次只改监控的批量调度，不动取流、录制、画质、弹幕和账号存储：

1. **斗鱼不再要求 3 个房间**。只要斗鱼登录态为 `ok`，1 个斗鱼房间也走关注列表批量；未登录仍然逐房匿名 `betard`。
2. **登录态失效降级单房，风控仍然整平台冷却**。批量返回明确的「未登录/登录态失效」时，这一拍把该平台全部房间降级为并发单房检查；批量返回明确风控时暂停整个平台 120 秒，避免把 N 个请求变成新的风控证据。
3. **抖音离线房会显示离线**，不是“接口不返回就看不出”。`follow/feed` 确实只返回在播房间，但监控用「上一轮已离线 + 本批 `unresolved==0`」合成离线状态，所以表格照常显示离线；只有上一轮在播、或本批存在解析失败时才单房确认。

## 2. 斗鱼：1 个房间也批量

文件：`/Library/dshproject/HIVECAST/src-tauri/src/monitor.rs`

- 删除 `DOUYU_BATCH_MIN_ROOMS = 3`。
- `monitor.rs:259 douyu_batch_ready(logged_in)` 只判断登录态，不再数房间。
- `monitor.rs:561` 调用变为 `douyu_batch_ready(crate::credential::is_ok("douyu"))`。
- `batchable_platform` 仍要求 `platform == "douyu"`、`room_key` 非空；不再有数量条件。

为什么 1 个也值得批量：

- 关注列表一次返回标题、主播、分区、人气、头像、封面、`videoLoop`，比单房 `betard` 字段更全；
- 监控表的人气和封面会随批次更新，单房 `betard` 没有同样的展示字段；
- 缺失房间仍会逐房回退，不会因为“关注列表没返回”把房间误判离线。

真机（release bundle，DB 只放 1 个斗鱼房 `9999`，登录态有效）：

```text
13:01:43.424 INFO 批量状态检查开始 platform="douyu" rooms=1 interval_sec=30
13:01:43.751 INFO 批量状态检查完成 platform="douyu" authed=true rooms=1 keys=1 returned=1 live=1 missing=0 unresolved=0 elapsed_ms=318
```

成本：1 个房间每 30 秒一次关注列表请求，约 0.3 秒；相比单房 `betard` 多拿到完整状态字段，且不会因为房间少就跳过批量。

## 3. 登录态失效：降级，不是冷却

文件：`/Library/dshproject/HIVECAST/src-tauri/src/platform/mod.rs`、`monitor.rs`

原来的 `is_auth_or_risk()` 把「登录失效」和「风控」混在一起，抖音统一 120 秒冷却。现在拆成两个判断：

| 判断 | 命中条件 | 监控动作 |
| --- | --- | --- |
| `is_auth_expired()` | 抖音 8、B 站 -101、斗鱼 -1；message 含「未登录」「登录态失效」或小写 `not login` | 本拍降级为并发单房检查，不暂停平台 |
| `is_risk_blocked()` | 抖音 10011/10012/10013；message 含 `blocked`、"风控"、"频繁" | 整平台 `not_before = now + 120s`，所有房间 `Outcome::Retry(120)` |
| `is_rate_limited()` | 已有 429 / 412 / -352 限流 | 仍按平台 `retry_after` 整平台冷却 |

`monitor.rs:890-928` 的分支顺序是：限流 → 登录失效 → 风控 → 普通失败。登录失效与普通失败共用 `monitor.rs:943 fallback_single_checks`，用 `join_all` 并发跑 `run_check`，再把每个房间的结果逐条回传，不会串行拖住整批。

这样做的原因：

- **登录失效不等于不能监控**。B 站房间信息、斗鱼 `betard`、抖音房间页在匿名态通常仍可读；降级单房能让离线/开播状态继续更新，只是自动录制会用匿名可用的画质。
- **缓存在拍点之间必须继续**。若登录失效也整平台冷却，房间会在冷却窗口里停止状态更新；用户会看到“直播中”却迟迟不触发录制。
- **风控不能降级**。逐房请求只会把 1 个被拦截的批量请求放大成 N 个单房请求，反而延长风控；所以风控保留 120 秒整平台暂停。

需要说明的边界：批量门槛仍要求账号状态为 `ok`。如果账号维护循环已经把凭据标成 `expired`，下一拍根本不会进批量，直接走单房；上面的降级主要覆盖「状态还是 ok、服务端已经开始拒绝」的窗口。这个窗口里每拍会先发一次失败的批量请求，再降级单房，直到维护循环写入过期或 Cookie 恢复。

## 4. 抖音「关注页不返回离线房」到底是什么问题

`follow/feed` 是“正在直播的关注”列表，不是完整关注列表：

- 在播房间：返回 `web_rid`、标题、封面、人气、`room_data`；
- 离线房间：**不出现**，没有 `is_live=false` 这样的显式字段；
- 已注销/私密/地区限制：可能以不可解析项出现，计入 `unresolved`。

监控不是“没返回就判离线”，而是按房间上一轮状态分三种：

| 情况 | 处理 | 结果 |
| --- | --- | --- |
| 本批返回了该房间 | 用批量字段更新，必要时开录/停录 | 显示直播中 |
| 没返回，上一轮已离线，且 `unresolved==0` | 合成 `offline_room_info`，清掉 `started_at` | 显示离线，不再逐房请求 |
| 没返回，上一轮在播，或本批有 `unresolved>0` | 单房 `run_check` 确认 | 真离线才停录，避免漏项误停 |

对应代码：`monitor.rs douyin_missing_keeps_only_known_offline_follow_rooms`、`offline_room_info`。所以“接口只返回在播房间”不会导致离线房一直显示直播中；代价是已离线房间在批量里天然缺失，不能靠批量接口主动发现“某个关注刚刚开播”，要靠下一轮关注池扫描/批量重新出现。

## 5. 三平台当前矩阵

| 项目 | B 站 | 斗鱼 | 抖音 |
| --- | --- | --- | --- |
| 批量门槛 | 有 UID 即可 | 登录，1 个房间也批量 | 登录 + 关注来源 + 内部 room_id |
| 批量键 | `platform_uid` | 页面 `room_key` | 19 位内部 room_id |
| 登录失效 | 降级并发单房 | 降级并发单房 | 降级并发单房 |
| 风控 | 120 秒整平台冷却 | 120 秒整平台冷却 | 120 秒整平台冷却 |
| 限流 | `retry_after` 整平台冷却 | 同左 | 同左 |
| 离线房 | 批量显式返回 | 关注列表缺失则单查 | 已知离线 + unresolved=0 合成离线 |

三个平台仍共用 `monitor.rs` 的调度器，但 `BatchState`、`not_before`、房间筛选条件各自独立；一个平台的登录失效不会把另一个平台拖进单房。
