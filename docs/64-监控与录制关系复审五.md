# 64 监控与录制关系复审五

> 状态：v1.1（2026-11-07，G1–G5 已在 [65](65-监控录制联动修复七.md) 修复；验收中新发现 G7 并当场修复；G6 仍只文档化）｜对象：monitor.rs、recorder.rs、broker.rs、disk.rs、db.rs 与媒体目录生命周期｜上游：[54 v3.7](54-监控与录制关系审查.md)、[62](62-监控与录制关系复审四.md)、[63](63-监控录制联动修复六.md)｜测试环境：macOS 27.0.1 arm64、ffmpeg 9.0.2、真实 bilibili 在播房间（6 / 545068 / 7734200）、APFS 稀疏卷 3 GiB
>
> 本轮方法：不引用前几轮结论，按「一条录制到底依赖哪些外部量」重新切：平台排期（检测间隔、退避）、媒体目录（容量、可写性、挂载）、时间线（重启、退出、暂停）。共 12 项真机测试（T1–T12），产物只落在 /tmp 与临时卷，测试数据已清理，未改动业务代码。

一句话结论：**检测间隔、退避、暂停依然碰不到已开录会话；但把「媒体目录」单独拉出来测之后，发现了 4 条新的真问题：外接卷被拔掉时磁盘守卫完全失明，录制以 failed/error 收尾（G3）；失败会话留下的分片成了永久孤儿（G4）；重启后首次检测被 spread 拖到 0 到 interval 之间（G1）；媒体目录不可写时开录失败不退避（G5）。另有 2 条观察（G2 写放大、G6 测试坑）。**

## 1. 结论先行

### 1.1 四个老问题的判定（本轮重新验证）

| 问题 | 判定 | 本轮证据 |
| --- | --- | --- |
| 正在录制的房间会不会被检测间隔影响 | **不会** | T1：间隔 30 改 3600 后 101 秒内 last_checked_at 冻结在 1794007182，同期两个分片 3,407,872 增到 22,282,240、2,097,152 增到 13,631,488 字节 |
| 会不会被失败退避影响 | **不会** | T4/T6：坏房间的失败间隔按 22.06、48.17、55.12 秒拉长时，健康房间仍按 2 秒节拍前进 |
| 监控是不是只更新状态 | **不是** | 它仍能开录（start_checked）、停录（离线两次确认、磁盘红线）、写库与推事件；本轮新增一条：媒体目录不可写时它每个周期都在重试开录（G5） |
| 是不是只有直播源没数据才影响录制 | **不是** | T10：源一直在播，只是外接卷被拔掉，录制照样以 failed/error 收尾，且磁盘红线全程没有告警 |

### 1.2 本轮新增的问题

| 编号 | 级别 | 一句话 | 证据 |
| --- | --- | --- | --- |
| G1 | P3 | 重启后首次检测用 spread 散在 0 到 interval 之间，interval 很大时自动续录可能被推迟近一个间隔 | T11：interval=900 重启，25 秒内 last_checked_at 仍为 0、没有开录；改成 5 秒后 18 秒内检测并开录 |
| G2 | P4 | 每次检测成功都整行 UPDATE room，房间多、间隔小时写放大线性增长 | T12：interval=1、3 个房间，30 秒 WAL 增长 206,000 字节，CPU 0.8% |

## 2. 测试与证据

### 2.1 T1 间隔与并发上限都改不动已开录会话

两路真实录制（rm-r8-a = 6，rm-r8-b = 545068）在 07:19:12 与 07:19:14 开录（超清 FLV H.264 / 高清 FLV H.264）。07:19:31 把 monitor.interval_sec 改成 3600、record.max_concurrent 改成 1：

- last_checked_at 最后停在 1794007182，101 秒后（1794007283）没有变化；
- 分片继续增长：3,407,872 到 22,282,240 字节，2,097,152 到 13,631,488 字节；
- 两路会话仍是 recording，调低并发上限不会停掉已有录制。

### 2.2 T2 间隔 3600 下断流续录照常

07:21:28 对 rm-r8-a 的 ffmpeg（pid 75789）执行 kill -9，07:21:42.538 出现「断流后续录 start_number=1 restarts=1」，生成 part0001.ts（1,572,864 字节），会话 id 34b18f04-56dd-493a-9726-2002a32003e7 未变，DB 没有多出会话。

### 2.3 T3 退出收尾

07:22:09.315 pkill -TERM：rm-r8-b 在 .614 收尾为 aborted/app_exit（27,975,206 字节），rm-r8-a 在 .885 收尾为 aborted/app_exit（16,995,522 字节）；无残留 hivecast/ffmpeg，mp4 与 ass 均已生成，没有新会话。

### 2.4 T4 失败退避的节奏与上限

坏房间 rm-r8-bad = bilibili 999999999（平台返回解析失败），interval=10、backoff_cap_sec=60、backoff_enabled=true。失败时刻：

| 次数 | 时刻（UTC） | 与上一次的间隔 | 期望 |
| --- | --- | --- | --- |
| 1 | 23:23:11.654（WARN） | - | 首次 |
| 2 | 23:23:33.712 | 22.06 秒 | 20 秒正负 20% |
| 3 | 23:24:21.886 | 48.17 秒 | 40 秒正负 20% |
| 4 | 23:25:17.008 | 55.12 秒 | 封顶 60 秒正负 20% |
| 5 | 23:26:12.156 | 55.15 秒 | 同上 |
| 6 | 23:27:07.353 | 55.19 秒 | 同上 |

同一条失败文案只 WARN 一次（F1 的去重生效），后续都是 DEBUG「刷新房间仍失败」。健康房间在同一时段仍按 10 秒节拍更新 last_checked_at。

### 2.5 T5 运行中改间隔会立刻改变退避的基数

23:26:26 新增 rm-r8-bad2 = 999999998，首次失败 23:26:37.229（距加入约 11 秒，落在 spread 内）。第一次等待按旧基数 10 秒算出 23.07 秒。23:26:51 把间隔改成 2 秒后，后续两次失败为 23:27:10.334 与 23:27:28.385，间隔 10.04 与 18.05 秒，正好是 2 乘 2 的平方等于 8、2 乘 2 的三次方等于 16，再加正负 20% 抖动。说明 apply 用的是当前设置，而不是建排期时的快照。

### 2.6 T6 坏房间的退避不拖累健康房间

间隔改成 2 秒后，两路健康房间的 last_checked_at 在 6 秒内从 1794007695 前进到 1794007701，仍是 2 秒一拍。

### 2.7 T7 重启后并发上限生效

重启应用（内存上限从设置加载为 1）、3 个真实在播房间都开了自动录制：只有 rm-r8-c（7734200）进入 recording，另外两路各一条 WARN「同时录制已达上限（1 路），先停掉一路或到设置里调高上限」，随后转 DEBUG；ffmpeg 只有 1 个，会话只有 1 条。

### 2.8 T8 间隔 0 暂停监控不影响录制

把 interval 改成 0 后 22 秒：last_checked_at 冻结在 1794008187，录制分片从 8,126,464 增到 12,320,768 字节，会话仍是 recording。

### 2.9 T9 保留策略（造数据）

造 3 条 5 天前完成的会话，各配一个 10 MiB 的 mp4（共 30 MiB），设置 media.retention_days=1 后启动应用：

```
INFO 媒体库保留策略：已清理旧录像 deleted=3 freed=31457280
```

目录清空，DB 中 3 条旧会话被删；正在录制的会话不在清理范围内（retention_rows 只取 status 不为 recording，db.rs:785）。

### 2.10 T10 外接卷被拔掉（G3、G4、G5）

3 GiB APFS 稀疏卷挂在 /Volumes/HIVECASTR8C，媒体目录指到卷内 Recording。23:29:28 开录，23:29:58 强制 detach（此时分片 5,767,168 字节）：

| 时刻 | 事件 |
| --- | --- |
| 23:29:59.7 | ffmpeg 因写入失败退出，exit status 254 |
| 23:30:02.9 / 06.99 / 11.09 | 平台仍显示在播，按断流续录 restarts=1/2/3（每次都因目录不存在失败） |
| 23:30:12.097 | WARN 续录次数用尽 restarts=3 |
| 23:30:12.757 | WARN 续录失败，按平台状态收尾 confirmed=false |
| 23:30:12.759 | 录制结束 status=failed reason=error file_size=0 |
| 23:30:18 起 | 每 10 秒一次「自动开录失败」，错误为 path is not accessible ...（Permission denied (os error 13)）；首条 WARN，其后 DEBUG |
| 23:33:27 | 卷重新挂载后自动恢复录制（新会话 e91ac801，part0000.ts 重新长到 5,242,880 字节） |

关键点：

- 磁盘红线全程没有触发。disk.rs:88 的 can_start 在 free_bytes 返回 None 时直接放行，disk.rs:95 的 is_low 返回 false；volume_key（disk.rs:33-51）找不到目标目录时会回退到最近存在的祖先（/Volumes，根盘设备号），于是掉盘被当成「根盘还有 118 GiB」。
- 真正的失败点是 recorder.rs:751 的 create_dir_all（父目录不可写），而不是容量检查。
- 23:30:18 到 23:33:17 共 19 次自动开录尝试，说明开录失败不计入连续失败冷却（该计数只在收尾 failed 时累加，recorder.rs:1447 起）；网络请求受 broker 的 60 秒取流缓存限制，这 3 分钟里实际只有 23:31:19 与 23:32:28 两次取流请求（broker.rs:19）。
- 卷回来后旧分片没有恢复：会话 98fd13d1 已经是 failed，recover_parts 只遍历 status='recording' 的会话（db.rs:759-765），所以那份 5,767,168 字节的 .part0000.ts 与 0 字节的 .mp4、14,244 字节的 .jsonl 一直留在卷上，UI 不可见，保留策略也不会删（它按 DB 行清理）。

### 2.11 T11 重启后的首次检测被 spread 推迟（G1）

把 interval 设成 900 后重启（房间 rm-r8-a 在播、自动录制开），25 秒后 last_checked_at 仍是 0，没有开录。把间隔改成 5 秒后，18 秒内 last_checked_at 变为 1794008157，23:35:48 开始录制。

原因：新条目的首次排期是 now 加 spread(id, base)（monitor.rs:247），spread 把哈希取模到 0 到 base 之间；interval 越大，首次检测越可能被推到接近一个完整间隔之后。room_add 对在播房间会立即开录，所以主要影响「重启后自动续录」与「离线时添加、后来开播」两种场景。

### 2.12 T12 检测成功的写放大（G2）

interval=1、3 个房间、1 路在录，30 秒内：WAL 从 519,152 增到 725,152 字节（加 206,000），hivecast 进程 CPU 0.8%，RSS 约 100 MB；录制分片从 13,107,200 增到 19,660,800 字节，未受影响。每次检测成功都会整行 UPDATE room（db.rs:352-376），所以写入量随「房间数除以间隔」线性增长；3 个房间 1 秒间隔的量级仍很小，属于 P4。

## 3. 逐条说明与建议

### 3.1 G3 掉盘时磁盘守卫失明（P2）

**现象**：媒体目录所在卷被卸载后，录制不会以 disk_full 收尾，而是等 ffmpeg 写失败退出；收尾是 failed/error，file_size=0（因为文件随卷消失），没有任何磁盘相关提示。

**原因**：

- disk.rs:54 free_bytes 用 fs4::available_space，目录不存在时返回 None；
- can_start 对 None 放行（disk.rs:87-92 的注释是「网络盘不该阻塞录制」），is_low 对 None 返回 false；
- volume_key 回退到存在的祖先，掉盘被归到根盘。

**建议**：在 can_start / is_low 之前先判「媒体根目录或其挂载点是否还在」，不可用就直接拒绝开录并给出「录制目录不可用，外接盘可能已断开」的行内错误；watcher 里也可以每拍检查媒体根目录，消失就主动 stop 一个 disk_lost 原因（或复用 disk_full 文案），不必等 ffmpeg 超时。

### 3.2 G4 失败会话的分片成为孤儿（P3）

**现象**：T10 里失败会话留下的 5.7 MB 分片、0 字节 mp4、弹幕 jsonl 都还在卷上，重启后既没合并进媒体库，也没被保留策略清掉。

**原因**：recover_parts（recorder.rs:1879）按 db.recording_sessions（db.rs:759-765，status='recording'）遍历；会话已经 failed 就不再被认领。retention_rows（db.rs:785）同样按 DB 行清理，不扫目录。

**建议**：收尾失败时把分片路径记进会话（或在 finalize 时清理 0 字节产物）；启动恢复时补一轮「扫媒体目录下无主的 .part*.ts，按 mtime 合并或移到隔离目录」。至少不要让 0 字节 mp4 与孤儿分片无声堆积。

### 3.3 G1 首次检测的 spread 上限（P3）

**建议**：首次排期改成 now 加 min(spread(id, base), 30)，或第一次检测立即执行、之后才进网格；这样重启后最多 30 秒就能恢复自动录制，后续抖动仍然分散。

### 3.4 G5 开录失败没有退避（P4）

**现象**：媒体目录不可写期间每个检测周期都重试，首条 WARN 之后全是 DEBUG，共 19 次；由于 broker 有 60 秒取流缓存，网络侧大约 70 秒才真正请求一次。

**建议**：把开录失败按房间计数，连续 3 次进入 5 分钟冷却（复用 in_failure_cooldown 的语义，但不要把「房间不存在」这类永久错误也算进去）；或者至少在日志与 UI 上标出「已暂停重试」。

### 3.5 G2 写放大（P4）

**建议**：把 last_checked_at 的更新与房间内容的更新拆开，内容没变时只写一行轻量 UPDATE，或把 last_checked_at 按 10 秒节流落库；当前 3 房间 1 秒间隔的实测成本很小，可延后处理。

### 3.6 G6 测试坑（观察）

直接 sqlite3 UPDATE record.max_concurrent 不会热更新内存上限：settings::save 才会调用 recorder.set_max_concurrent（settings.rs:232），监控读设置只用于排期。所以本轮第一次并发测试（运行中直接把上限改成 1）出现 3 路全开，重启后同样的限制就正确生效。这不是产品缺陷，但后续造数据必须注意「改上限要重启或走设置页」。

## 5. 修复顺序建议

1. G3：掉盘先判目录可用性，别让 ffmpeg 用退出码兜底；顺带给用户明确提示。
2. G4：失败会话的分片与 0 字节产物要有归属或清理，否则卷回来会一直堆垃圾。
3. G1：首次检测延迟封顶 30 秒，重启后的自动续录才及时。
4. G5：开录失败计数与冷却，避免坏路径下无休止重试。
5. G2：按需再做，当前 3 房间 1 秒间隔的写放大可以接受。

> v1.1 追记：以上五条已在 65 全部落地并真机复验；验收时发现 G1 的 30 秒封顶会与「正抖动重排」叠加，长间隔被压回 20 秒级（记为 G7），65 一并修掉。
