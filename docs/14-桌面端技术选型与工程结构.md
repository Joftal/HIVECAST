# 14 · 桌面端技术选型与工程结构

> 目标：在 `HIVECAST/` 下建立一个可长期维护的桌面应用。本文给出选型结论、理由、以及可以直接照着建的目录结构。

## 1. 选型结论

| 层 | 选择 | 备选 | 理由 |
| --- | --- | --- | --- |
| 桌面壳 | **Tauri 2** | Electron | 体积 ~10MB vs ~150MB；内存占用低；Rust 后端可直接做下载/协议 |
| 后端语言 | **Rust** | Go（复用 bililive-go） | 单二进制、无 GC 停顿、并发模型适合长跑；与 Tauri 同进程 |
| 前端 | **React 19 + TypeScript + Vite** | Vue/Svelte | 生态最大，参考项目 webapp 也是 React，组件可借鉴 |
| 样式 | **Tailwind CSS + shadcn/ui** | Ant Design | 体积小、可控；shadcn 是源码级复制，不怕版本锁定 |
| 状态 | **TanStack Query + Zustand** | Redux | Query 管服务端状态，Zustand 管 UI 状态，职责清晰 |
| 数据库 | **SQLite（rusqlite/sqlx）+ WAL** | — | 见 12 文档 |
| 媒体处理 | **ffmpeg sidecar** | 纯 Rust 解码 | 兼容性无敌；sidecar 可随包分发 |
| 日志 | **tracing + tracing-subscriber** | log4rs | 结构化、可分层过滤、生态好 |
| 错误 | **thiserror（库）+ anyhow（应用层）** | — | 库要类型化错误，应用层要上下文 |

### 1.1 为什么不用 Electron

- 参考项目 bililive-go 是"Go 后端 + React 前端"，如果照搬到 Electron，等于"Node 壳 + Go 子进程 + React"，三层进程、两套 IPC，复杂度翻倍。
- 录制/协议这类 CPU + IO 密集且需要长期稳定的逻辑，放在 Rust 主进程里最省心。
- 包体积：Electron 基线 150MB+，Tauri 10MB 左右（不含 ffmpeg）。

### 1.2 为什么不复用 bililive-go 的 Go 代码

可以，但代价大：

- 需要把 Go 编译成 sidecar（cgo 依赖、跨平台交叉编译麻烦）。
- Go 的 `otto`（JS 引擎）在 ARM64 macOS 上支持一般。
- 进程间通信 + 生命周期管理又是一套东西。

**结论**：**借鉴设计，重写实现**。bililive-go 的价值在"知道哪些坑"，不在"代码能直接搬"。

## 2. 进程与线程模型

```text
┌────────────────────── Tauri 主进程（Rust）──────────────────────┐
│  tokio runtime（多线程）                                         │
│   ├─ 命令处理（IPC handler）                                     │
│   ├─ 监听任务池（每房间一个 task，HTTP 轮询）                     │
│   ├─ 录制任务池（每场一个 task，管理 ffmpeg 子进程）              │
│   ├─ 弹幕任务池（每场一个 WS 连接）                               │
│   ├─ 后处理任务池（并发 3，跑 ffmpeg）                            │
│   └─ 定时器（心跳、对账、清理）                                   │
│                                                                  │
│  阻塞操作（文件 IO、ffmpeg wait）走 spawn_blocking               │
└──────────────────────────────────────────────────────────────────┘
        │ IPC
┌───────▼──────── WebView（React）──────────────┐
│  渲染进程，只做 UI 与状态管理                   │
└────────────────────────────────────────────────┘
```

**关键约束**：

1. 任何 `await` 阻塞超过 100ms 的操作都不能在 IPC handler 里同步做（用 `spawn_blocking`）。
2. ffmpeg 子进程统一由 `ProcessSupervisor` 管理，应用退出时统一优雅停止。
3. 每个房间的监听任务有独立取消令牌（`CancellationToken`），停止监听 = cancel。

### 3.1 分层规则（强制）

```text
commands  →  service（可省）  →  domain
    │                             ▲
    └──────────► platform/recorder/pipeline ──┘
```

- `domain` **不许** `use` 任何 IO crate（rusqlite、reqwest、tokio::fs）。
- `platform` 不许依赖 `recorder`（只返回候选，不管下载）。
- `commands` 不许写业务逻辑（≤ 20 行，做参数校验 + 调用 + 错误转换）。

用 `cargo-deny` 或简单的 CI 脚本检查依赖方向。

## 5. ffmpeg 分发策略

三种方案，**推荐 B**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 用户自装 | 探测 PATH，缺失时提示 | 包小 | 新手劝退 |
| B. **随包 sidecar** | 打包进 `binaries/`，启动时优先用内置 | 开箱即用 | 包体积 +70MB |
| C. 首次运行下载 | 从 CDN 下载到 app_data | 包小 | 需要网络、要校验、要处理失败 |

### 5.1 sidecar 命名

Tauri 要求：`binaries/ffmpeg-<target-triple>`，如：

```text
ffmpeg-aarch64-apple-darwin
ffmpeg-x86_64-pc-windows-msvc.exe
ffmpeg-x86_64-unknown-linux-gnu
```

配置：

```json
{
  "bundle": {
    "externalBin": ["binaries/ffmpeg"]
  }
}
```

### 5.2 探测顺序

```text
1. 用户配置的 ffmpeg_path（显式指定优先）
2. 随包 sidecar
3. 系统 PATH（which ffmpeg）
4. 都没有 → 标记 ToolMissing，UI 提示
```

启动时**异步**探测（`ffmpeg -version`），不要阻塞 UI。

## 6. 打包与分发

| 平台 | 产物 | 注意 |
| --- | --- | --- |
| macOS | `.dmg`（universal 或分 arch） | 需公证（notarization）；`com.apple.security.network.client` 权限 |
| Windows | `.msi` / `.exe`（NSIS） | 需签名避免 SmartScreen 警告 |
| Linux | `.AppImage` / `.deb` | AppImage 最通用 |

### 6.1 自动更新

Tauri updater + 静态 JSON：

```json
{
  "version": "0.2.0",
  "notes": "修复斗鱼签名",
  "pub_date": "2026-11-05T10:00:00Z",
  "platforms": {
    "darwin-aarch64": { "signature": "...", "url": "https://.../Hivecast_0.2.0_aarch64.app.tar.gz" }
  }
}
```

- 必须配置 `pubkey`，包必须签名。
- 更新前要**停止所有录制**并等待落盘（否则文件损坏）。
- 参考 bililive-go 的 `CheckGracefulUpdate`：所有录制结束后才允许重启。

### 6.2 版本切换（不停机）

参考项目的 `version-switching` skill 提到"不停机版本切换"（Docker/独立运行）。桌面端简化版：

```text
下载新版本 → 校验签名 → 提示"将在录制结束后重启" → 
监听所有录制结束 → 启动新进程 → 旧进程退出
```

## 7. 测试策略

| 层 | 工具 | 覆盖 |
| --- | --- | --- |
| 领域/配置/模板 | `cargo test` | 纯函数，快，覆盖率要求高 |
| 平台解析 | `cargo test` + 固定 fixture（HTML/JSON 快照） | 每个平台至少 3 个 fixture（正常/下播/改版） |
| 存储 | `cargo test` + 临时 SQLite | 迁移、并发、崩溃恢复 |
| 录制 | 集成测试 + mock 服务器 | 断流、分段、优雅停止 |
| 前端 | Vitest + Testing Library | 组件与 hooks |
| E2E | Playwright（WebDriver）或 tauri-driver | 关键路径：添加房间 → 录制 → 停止 → 后处理 |

**fixture 驱动**是平台适配的关键：把真实响应存成文件，测试不依赖网络，改版时只需更新 fixture。

## 8. 性能预算

| 指标 | 目标 |
| --- | --- |
| 冷启动 | < 2s（到窗口可见） |
| 空闲内存 | < 150MB（不含 ffmpeg） |
| 100 房间监听 | CPU < 5%，内存 < 300MB |
| 3 路同时录制 | CPU < 15%（copy 模式） |
| UI 列表 1000 项 | 滚动 60fps（虚拟列表） |
| 事件延迟 | < 100ms（状态变化 → UI） |

超出预算时优先怀疑：事件频率、DB 查询、大列表未虚拟化。


## 11. 反模式

1. ❌ 在 IPC handler 里做长耗时操作 → UI 卡死。
2. ❌ 前端直接访问文件系统 → 安全漏洞。
3. ❌ 所有状态放一个全局 store → 重渲染风暴。
4. ❌ 用 Electron 却想要 Tauri 的体积 → 选型时想清楚。
5. ❌ ffmpeg 只在 PATH 里找 → 新手装不上。
6. ❌ 更新时不断录制 → 文件损坏。
7. ❌ 平台解析不写 fixture 测试 → 改版即崩。
8. ❌ 领域层依赖数据库 → 无法单测。
