# 54 监控与录制的关系审查

> 状态：v1.0（2026-11-06）｜审查对象：监控调度（53）与录制链（recorder.rs）｜结论：正在进行的录制不受检测间隔与失败退避影响，但存在 5 个边界场景会间接影响录制，其中 3 个建议尽快修。

## 0. 一句话结论

监控（monitor）只做三件事：刷新房间信息、决定「要不要开录」、决定「要不要停录」。
**已经在录的 ffmpeg 进程不归监控管**——它的存亡由 recorder 自己的 watcher 决定，与检测间隔、退避、暂停监控都无关。

监控主动停录只有两个入口：

1. 一次**成功**的房间信息请求明确返回「不在播」（`room_info` 成功且 `is_live = false`）；
2. 磁盘剩余空间低于红线（每 1 秒都检查，不受间隔与暂停影响，monitor.rs:236）。

平台请求失败（网络错误、限流、房间不存在、解析失败）**不会**停录，只在房间上写一条错误提示。

## 1. 监控的职责边界

`monitor::tick()` 每 1 秒跑一次，但每秒只是「看谁到点了」，真正请求房间信息由每个房间的排期控制（间隔 + 抖动 + 退避）：

```text
tick() 每分钟 60 次
  ├─ 磁盘红线检查（所有房间，含暂停监控的）      monitor.rs:236
  ├─ 间隔 <= 0 ？→ 直接返回（只保留磁盘检查）      monitor.rs:250
  └─ 遍历房间
       ├─ monitor_paused → 移出排期，跳过           monitor.rs:261
       └─ 到点 → check_room()
            ├─ 成功且 is_live → 更新 DB；需要时 start()
            ├─ 成功且 offline → resume_auto；录制中则 stop(stream_ended)
            └─ 失败 → touch_room + set_error，不碰录制
```

监控写库的字段：`is_live`、`started_at`、`title`、`host_name`、`avatar_url`、`cover_url`、`area_name`、`online`、`last_checked_at`。
它**不写**任何与「流是否还在传输」「文件是否在增长」有关的状态。

## 2. 录制链是独立的

`recorder.start()` 拉起 ffmpeg 后立刻 `spawn_watcher()`（recorder.rs:495）：一个独立的 tokio 任务，**每 1 秒** `try_wait()` 一次，只看进程有没有退出。整条链路不读监控排期，也不看 `monitor_paused`。

ffmpeg 退出后的判定（recorder.rs:507-524）：

| 条件 | 行为 |
| --- | --- |
| 用户/监控设了 stop_reason | 直接收尾，不续录 |
| 退出码非 0 | 续录（respawn） |
| 退出码 0 但只活了不到 12 秒（EARLY_EXIT） | 续录（地址过期常表现为「正常 EOF」） |
| 退出码 0 且活了 12 秒以上 | 收尾为 finished / stream_ended |

续录（recorder.rs:546）做四件事：丢掉旧线路缓存 → 等 3 秒 → 重新解析带时效签名的播放地址 → 用同一个会话、分片编号接着写。最多 3 次（MAX_RESTARTS），用尽才收尾为 failed。

**时间线示例（间隔 30 秒，录制中）**

```text
10:00:00  监控检查：直播中，已录制 → 什么都不做
10:00:05  CDN 踢连接，ffmpeg 退出码 1
10:00:06  watcher 发现退出 → respawn：清缓存、等 3 秒、重解析 URL
10:00:09  新 ffmpeg 起来，分片从 part_00042 继续 → 同一条历史记录
10:00:30  监控检查：直播中，已在录制 → 什么都不做
```

整个过程没有经过监控。把间隔改成 300 秒、改成 0、或者点「停止监控」，上面这段流程一模一样。

## 3. 录制会被停下的全部入口

| 入口 | 触发条件 | stop_reason | 历史状态 | 是否受间隔/退避影响 |
| --- | --- | --- | --- | --- |
| 平台明确下播 | 成功检查且 is_live=false | stream_ended | finished | 受：最多延迟一个间隔才被看到 |
| 磁盘红线 | 每 1 秒检查，低于红线 | disk_full | aborted | 不受 |
| 用户停止录制 | 按钮 | stopped | finished | 不受 |
| 关闭自动录制 | 设置开关 | stopped | finished | 不受 |
| 移除房间 | 删除房间 | stopped | finished，随后历史被级联删除 | 不受 |
| 应用退出 | 退出拦截后收尾 | app_exit | aborted | 不受 |
| 并发上限已满 | 只在「开录」时拦，不影响已在录的 | — | — | 只影响新开录 |

## 4. 场景矩阵

| 场景 | 监控行为 | 录制行为 | 最终结果 |
| --- | --- | --- | --- |
| 正常直播 + 录制中 | 按间隔刷新信息 | ffmpeg 持续写分片 | 无影响 |
| 间隔改为 0 | 停止轮询，只保留磁盘检查 | 不受影响，继续写 | 录制正常；但下播只能靠 ffmpeg EOF 发现 |
| 暂停监控 | 该房间移出排期 | 不受影响 | 录制正常；房间状态停在暂停前 |
| 断网 5 分钟 | 每次失败写 error，退避重试 | 只要 ffmpeg 连接还在就继续 | 恢复后监控看到仍直播，不做动作 |
| 平台 429 / -412 限流 | 进入 5–60 秒冷却，退避重试 | 不受影响 | 状态更新变慢，录制继续 |
| 主播真下播 | 下次成功检查看到 offline → stop | 优雅退出 | finished / stream_ended |
| CDN 断流（非零退出） | 无感知 | watcher 续录，最多 3 次 | 通常无感；3 次用尽记 failed |
| 播放地址过期（0 退出且不足 12 秒） | 无感知 | 判为断流并重解析续录 | 通常无感 |
| 流卡住、连接还在但不给数据 | 仍看到「直播中」，不停 | ffmpeg 阻塞（录制端没有读超时） | 会话可能长时间停在 recording（见 S4） |
| 磁盘低于红线 | 主动 stop(disk_full) | 收尾 | aborted / disk_full，并通知 |
| 并发上限已满 | 开录时报错，下次间隔再试 | 已在录的不受影响 | 未开录的房间最多等一个间隔 |
| 手动停录 | 本次直播内不再自动拉起 | 收尾 | finished / stopped |
| 移除房间 | 先停录再删房间 | 收尾 | finished，历史级联删除（见 S5） |
| 平台报房间不存在 | 写 error，不碰录制 | 继续到 EOF | 房间显示错误，录制照常结束 |
| 应用重启 | 重新排期，最多等一个间隔才检查 | 旧会话被标 aborted，不会自动续录 | 想继续录要等下一次检查（或手动开录） |

## 5. 需要修的风险

### S1 单次「离线」就停录（误判风险，建议 P1）

现在的判定是一次成功响应里 `is_live` 为 false 就立刻 `stop(stream_ended)`，没有二次确认，也不看分片是否还在增长。

**举例**：10:00:30 平台接口抖动/降级，返回体缺字段，反序列化默认成 `live_status = 0`；监控把正在录的健康流当成下播，录像被截断，历史写 finished，还会发一条「录制结束」通知。10:00:45 下一次检查又显示直播中，于是自动开一条新会话——一场直播变两条，中间丢十几秒。

**建议**：连续两次成功检查都判离线（间隔至少 5 秒）才停；或者停之前做一次交叉验证（最近 60 秒分片体积是否增长）。

### S2 自然结束后可能被立刻重开（噪声会话，建议 P1）

ffmpeg 正常 EOF 收尾后，`clear_failure` 会清掉失败计数，但没有任何「刚刚正常结束」的抑制；而平台的下播状态常常滞后几十秒。

**举例**：10:59 主播下播，ffmpeg 退出码 0，会话 A 收尾为 finished；11:00 监控检查，平台仍返回直播中 → 自动开录 → 新 ffmpeg 连不上流，2 秒退出 → 判为 EARLY_EXIT 续录 → 3 次全失败 → 记一条 status=failed 的会话 B，并弹「录制失败」通知。严重时同一次下播会产生两条失败记录。

**建议**：同一房间「自然结束」后 2–5 分钟内不自动开录，除非监控至少成功看到过一次离线；或者要求「先观察到离线，再观察到开播」才允许自动开录。

### S3 手动停录的抑制标记可能跨场残留（建议 P2）

`auto_suppressed` 只在监控成功看到离线时清除（monitor.rs:351）；手动开录、重新打开自动录制也会清。若主播「下播后很快又开播」，而监控在这段窗口里没有成功检查到离线，抑制标记会带进下一场。

**举例**：10:00 用户手动停录；10:05 下播、10:06 又开播；监控在 10:05:20 与 10:05:50 两次检查都恰好还看到直播中 → 没有执行 `resume_auto` → 新一场不自动录，直到这一场也结束。

**建议**：用 `room.started_at` 变化作为「新一场」的信号顺带复位抑制；或让 S2 的「观察到离线」状态机统一处理。

### S4 录制端 ffmpeg 没有读超时（建议 P0）

观看端显式加了 `-rw_timeout 10000000`（view.rs:636），录制端 `build_command()`（recorder.rs:782）没有。源「TCP 还连着但不再给数据」时，ffmpeg 会一直阻塞在读上：文件不再增长、会话仍是 recording、退出拦截一直挡着，监控此时看到的还是「直播中」，也不会停。

**举例**：20:00 某 CDN 边缘节点网络分区，连接保持但没有新数据；直到系统 TCP 超时（可能几分钟到几十分钟）才 EOF。这期间的录像时长会按墙钟继续算，实际内容为零。

**建议**：录制命令补 `-rw_timeout`（15–30 秒）；watcher 再加一条「最近 60 秒分片体积没有增长 → 判为假死」（先尝试续录，连续两次再收尾为 failed）。

### S5 移除房间会级联删除该房间的全部历史（建议 P1，独立缺陷）

`room_remove` 先停录，再 `DELETE FROM room`（commands.rs:128-140）；`record_session.room_id` 是 `REFERENCES room(id) ON DELETE CASCADE`，且连接上开了 `foreign_keys=ON`（db.rs:225）。结果是该房间所有历史记录（含已完成、已归档的）一起消失，媒体库看不到，但磁盘文件还在。

**建议**：删房间时只解除关联（`ON DELETE SET NULL` 或软删除），或至少在确认弹窗里写明「同时删除 N 条历史记录」。

## 6. 三条间接耦合

### C1 开录延迟等于检测间隔

主播 10:00:00 开播、间隔 300 秒，最坏情况下 10:05:00 才开录，前 5 分钟没有文件；退避期间还会再拉长。新添加的房间是例外：`room_add` 会当场取一次信息并在直播时直接开录（commands.rs:98-114），不用等排期。

### C2 退避会推迟「发现下播」，但几乎不影响录制

退避期间监控看不到离线，于是不会主动 `stop`；实际收尾由 ffmpeg EOF 完成，结果仍是 finished / stream_ended。只有 S4 那种「不 EOF 也不给数据」的情况，才会因为监控看不到离线而一直挂着。

### C3 共享 broker 的两套冷却 key 不一致

房间信息失败记在 `"platform:room_key"`（broker.rs:151、190），线路解析失败记在 `room_key`（broker.rs:93、126），而 `invalidate()` 只清前者（broker.rs:215）。续录会先 `invalidate` 再解析线路，于是清不掉线路侧的冷却。

**举例**：录制中断流，恰好上一次线路解析被平台 429 → 冷却 5–60 秒；respawn 里的 `groups()` 直接返回 Throttled → 续录失败 → 会话被收尾为 failed；下一轮监控又开一条新会话，于是一次直播出现「failed + 新会话」两条历史。

**建议**：统一冷却 key（都带 platform 前缀），或让 `invalidate()` 同时清 `room_key` 与 `platform:room_key`。

## 7. 修复清单

| 编号 | 问题 | 优先级 | 改动量 | 影响面 |
| --- | --- | --- | --- | --- |
| S4 | 录制 ffmpeg 缺读超时 + 死流看门狗 | P0 | 小（命令参数 + watcher 一段） | 只影响录制 |
| S1 | 离线需二次确认才停录 | P1 | 小（monitor 记一个计数） | 只影响停录时机 |
| S2 | 自然结束后短时不再自动开录 | P1 | 小（recorder 记结束时间） | 只影响自动开录 |
| S5 | 删房间不再级联删历史 | P1 | 中（迁移表结构或改删除语义） | 数据安全 |
| C3 | 统一 broker 冷却 key | P2 | 小（两处字符串） | 续录成功率 |
| S3 | 抑制标记随新一场复位 | P2 | 小 | 自动开录 |

## 8. 如何复现与验证

1. 间隔与录制无关：录制中把间隔从 30 改成 300、再改成 0，观察 ffmpeg PID 不变、分片持续增长。
2. 暂停监控不影响录制：录制中点「停止监控」，等房间状态变红后分片仍增长；再点「开始监控」恢复正常。
3. 断流续录：录制中 `kill -9` 掉 ffmpeg，1 秒内应出现「断流后续录」日志，3 秒后新 PID，分片编号接续，历史仍是一条。
4. 磁盘红线：把媒体目录挂到小容量分区，或临时把红线阈值调高，录到越线时应停录并记 disk_full。
5. 误判停录（S1）：临时让 `room_info` 返回一次 offline，观察是否立刻停录；修复后应要求连续两次。
6. 读超时（S4）：录制中用防火墙丢弃该 CDN 的出站包但保留连接，观察 ffmpeg 是否会一直挂着。
