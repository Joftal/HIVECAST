# 任务中心分组与收尾状态复查

> 状态：复审完成并真机验收（2026-11-20）。设计见 [179-任务中心全链路追踪设计](179-任务中心全链路追踪设计.md)，P1/P2 实现见 [180-任务中心全链路追踪实现](180-任务中心全链路追踪实现.md)、[181-任务中心P2阶段事件与时间线](181-任务中心P2阶段事件与时间线.md)。
> 本轮范围：重新审查任务中心的 Run 生成、分组、状态机、阶段推导、需要处理与详情展示；修掉复审确认的缺陷，未改数据库表结构（只补了 `record_session` 已有的分组列在聚合层的读取）。

## 1. 复审结论

任务中心的整体方向成立：以 Run（一次录制链路）为第一对象，把 recorder、record_session、task_history、jobs、平台健康拼成同一张页面。上一轮修复的筛选统计、详情前缀、开录中阶段、失败重试等行为在真机上仍然正常。

本轮复审发现并修复了 5 个问题：

1. **分割录制的多个片段各成一条 Run**：同一场直播被标题/大小/时长切成 s1、s2 后，历史表出现两行，体积和时长被拆开，完成状态也可能被片段顺序误导。
2. **aborted 被当成「完成」**：磁盘满、掉盘等异常收尾的 session 状态是 `aborted`，旧状态机只看 `failed`，历史行显示「完成」。
3. **收尾任务失败但阶段显示完成**：`finalize` 任务的 `state=failed` 只驱动 `finalizing`，没有驱动失败；详情里「收尾」仍是绿勾。
4. **异常中断的收尾阶段被推断成完成**：`aborted` 片段已经有 `ended_at`，旧逻辑用 `all_ended` 直接推出「收尾完成」。
5. **片段级阶段事件不会出现在 Run 时间线**：事件按 `session:<片段 id>` 落库，Run id 已改成 `session:<group>`，详情时间线查不到后续片段的事件。

## 2. 当前实现逻辑

### 2.1 分组键

- `record_session` 在创建首片段时写 `group_id = session.id`、`clip_index = 0`（`src-tauri/src/db.rs:930`）。
- 分割片段写入同一个 `group_id`，`clip_index` 从 0 递增（`src-tauri/src/db.rs:977`、`src-tauri/src/recorder.rs:2856`）。
- 聚合层 `session_group_key`（`src-tauri/src/task_center.rs:1141`）优先用 `group_id`，为空时回退到 `id`，兼容旧数据与普通录制。
- `RecordSession` 新增 `group_id: Option<String>` 与 `clip_index: i64`（`src-tauri/ipc-types/src/lib.rs:478-481`），TS 绑定同步生成。

没有改表：`record_session` 本来就有 `group_id/clip_index` 列；本轮只是让 `create_session` 也写这两个字段，并在 `SESSION_SELECT` / `map_session` 中读出来（`src-tauri/src/db.rs:2658`、`:2789`）。旧行 `group_id` 为空时按单场处理，不会报错。

### 2.2 Run 的合并

`build`（`src-tauri/src/task_center.rs`）先按 `session_group_key` 建 `group_cache`，再做四轮：

| 来源 | 处理 |
| --- | --- |
| `recorder.active_all()` | 用当前 session 的 group key 建 Run；`draft.sessions` 放入整组 |
| `status=recording` 的 session | 同组只建一次，防止进程已退出但 session 仍在收尾时 Run 消失 |
| 历史 session | 按 group 去重，`group_representative` 优先失败/aborted 片段，否则取最后结束的片段 |
| `task_history` | `task.session_id` 先映射到 group key；`finalize` 只驱动阶段，不进入任务列表 |

`group_representative`（`:1149`）的规则：

```rust
members.iter().find(|s| {
    s.status == "failed"
        || (s.status == "aborted" && s.reason.as_deref() != Some("app_exit"))
})
.or_else(|| members.iter().max_by_key(|s| s.ended_at.unwrap_or(s.started_at)))
```

这样详情里的画质、文件路径、上下文场次至少指向一个有诊断价值的片段，而不是永远指向首片段。

### 2.3 汇总口径

`finish_run`（`:443`）对整组求和：

- 体积：普通片段取 `file_size`；仍 `recording` 的片段取 `max(主文件 metadata, segment::parts_total(path))`，避免录制中只算主文件导致 0。
- 时长：普通片段取 `duration_ms`；仍 `recording` 的片段用 `(now - started_at) * 1000`。
- 开始时间取组内最小，结束时间取组内最大；只要还有片段在录制，`ended_at` 为 `None`。
- 历史行、统计卡、详情都使用汇总后的同一组数字。

真机例子：`audit-s1` 1,000,000 B / 600,000 ms + `audit-s2` 2,000,000 B / 600,000 ms，历史表显示一行 **20:00 / 2.9 MB**（3,000,000 B），而不是两行 10:00 / 976 KB + 1.9 MB。

### 2.4 状态机

`finish_run` 的失败判断从「只看 `status=failed`」扩展为：

```text
session_failed = 任一 status=failed
              或 (status=aborted 且 reason != app_exit)
session_interrupted = 任一 reason=app_exit
finalize_failed = 任一 finalize 任务 state=failed
failed = 任务失败 || session_failed || finalize_failed
```

`aborted/app_exit` 仍然记为 `interrupted`，不会被误报成录制失败。磁盘满/掉盘等 `aborted` 会进入 `failed`，并出现在「需要处理」的 `record_failed`（`src-tauri/src/task_center.rs:968`）。

### 2.5 阶段推导

`build_stages`（`:689`）现在按组内所有片段计算：

- **录制**：任一失败 → `failed`；仍有片段 `recording`（即使 recorder 已摘掉 record_task）→ `active`；全部结束 → `done`。
- **收尾**：`finalizing` → `active`；`finalize_failed` → `failed`，并把失败任务的 message 放进阶段 detail；`finalize_finished` → `done`；异常 aborted → `failed`；`app_exit` → `skipped`；全部正常结束且没有收尾任务（旧数据）→ `done`。
- **后处理**：按组内 session 的 `post_state` 与 post/remux 任务聚合；全部 source 且完成 → `skipped`。
- **入库**：后处理失败 → `pending`；组内全部 `post_state=done` → `done`；source 模式且已结束 → `done`。

真机例子：`audit-s4` 的 `finalize:audit-s4` 是 `failed/合并失败`，详情显示 **收尾 失败 / 合并失败**，不再显示绿勾；`audit-s3` 是 `aborted/disk_full`，显示 **录制失败 / 收尾失败**，不会因为 `ended_at` 存在而报「收尾完成」。

### 2.6 事件与需要处理

- 事件读取时把 `session:<片段 id>` 映射回 `session:<group>`，所以详情「阶段时间线」能看到所有片段的事件（`src-tauri/src/task_center.rs:277` 附近）。
- `record_failed` 的触发条件与状态机一致，包含 `aborted` 非 `app_exit`；同一场次有失败任务时仍用 `failed_task_sessions` 去重，避免一条失败报两次。

## 5. 仍需注意 / 未做事项

> 2026-11-21 更新：第 1–5 条已在 [183-任务中心收尾重试与历史回填](183-任务中心收尾重试与历史回填.md) 处理；本节保留当时复审的原始记录。

1. **旧数据不会自动补 group**：本轮之前产生的分割录像 `group_id` 为空，仍会按单场显示。没有做历史回填，因为无法可靠判断哪些 session 属于同一场；如需回填要另写迁移规则。
2. **收尾失败没有单独任务行**：`finalize` 任务按设计不进入「任务」列表，只在「收尾」阶段显示状态和 message；如果用户需要看到 finalize 任务的耗时/重试入口，后续要单独加一个收尾任务区。
3. **aborted 的入库语义**：磁盘满的 session 有部分文件与 `file_path`，当前「入库」仍显示完成；它表示记录已落库，不代表录像完整。若希望区分「部分入库」，需要给 commit 阶段增加 partial 状态。
4. **分组读取上限**：一次最多读 `history*4` 条 session（最少 200），极端情况下同一场片段超过上限会被截断；正常分段（几段到几十段）不受影响。
5. **收尾重试**：本轮只修状态，没有新增「重试收尾」按钮；`finalize` 失败后仍依赖录制流程或人工处理。
6. **未改数据库 schema**：没有新增列/表；`group_id/clip_index` 是既有列。
