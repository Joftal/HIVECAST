# 虎牙画质探测与重播识别

## 1. 背景

用户反馈（m71711）：虎牙的画质应像哔哩哔哩、斗鱼、抖音一样，按账号能力解锁；当前所有档位都显示可选，选了 4K 后录制几秒就中断。

第一版实现（提交 fe5579b）用“登录态 + 房间源码率 ≥ 20000”推断 4K 能力。用户随即质疑（m72416）：其他平台不是这么判断的，虎牙的探测逻辑和它们不一致。

复查后确认，第一版确实把两件事混在了一起：

1. **重播被当成直播。** 660000 页面同时有 `"isOn":true` 与 `"is_replay":"1"`、`"live_status_text":"重播中"`。旧代码只看 `isOn`，于是把回放当直播去录制；回放源不提供 4K，4K 自然 403。
2. **源码率不是账号权限。** 660000 的 `gameLiveInfo.bitRate=10000` 却列出 4K HDR/4K；chenzihao 的 `bitRate=30000` 反而没有 4K 标签。用源码率推断 4K 会误判。
3. **登录态也不改变档位表。** 匿名与登录页面都返回同样的 `vMultiStreamInfo`；虎牙没有 B 站那种 `accept_qn`/`current_qn` 授权字段，也没有稳定的 VIP/贵族字段。

实测（2026-11-18，660000 重播中）：

- 4K HDR `ratio=20100&codec=265`：TX/AL/HS 等线路均为 403。
- 4K `ratio=20000&codec=265`：同样 403。
- 1080P `ratio=10000&codec=264`：TX/TX15 返回 200，ffprobe 为 H.264 1920×1080。
- 带网页 Cookie.txt 的虎牙 Cookie 再测，4K 仍然 403，1080P 仍 200；排除“匿名才被拦”。

因此，虎牙能稳定拿到的能力信号不是账号等级，而是**实际取流是否成功**。

## 2. 与其他平台的差异

| 平台 | 当前实现 | 判断依据 |
| --- | --- | --- |
| 哔哩哔哩 | `stream_plan` 在请求 qn 低于 `QN_MAX=30000` 时额外拉一次最高档 playinfo；`granted_qn` 取所有 `codec.current_qn` 最大值，`accepted` 取 `codec.accept_qn`；`quality_available` 先看 accept 表，再看 granted | 平台真实授权 + 编码能力 |
| 斗鱼 | `authed = credential::is_ok("douyu")`；登录时信任 `multirates` 全档，匿名才用实际返回的 `rate` 封顶 | 登录态 + 平台档位表 |
| 抖音 | `available: quality.flv.is_some() or quality.hls.is_some()` | 该档位是否有可用地址 |
| 虎牙（旧） | 登录态 + `gameLiveInfo.bitRate >= 20000` | 源码率启发式，和账号无关 |
| 虎牙（现在） | 对 4K/4K HDR 构造真实签名地址，带 `Range` 取第一段数据；403/404 判不可用，200 且有字节判可用，超时/异常不隐藏 | 实际取流探测 |

虎牙没有等价于 B 站 `accept_qn` 的字段，直接照抄“读账号授权”并不可行；用实际取流探测是最接近 B 站“最高档探测”的做法。

## 3. 实现

文件：`src-tauri/src/platform/huya.rs`

### 3.1 重播识别

`parse_is_replay`：

```rust
fn parse_is_replay(body: &str) -> bool {
    // "is_replay":"1" / "is_replay":1
    // 兜底 "live_status_text":"重播中"
}
```

- `room_info`：`is_live: is_on && !banned && !replay`，并在 `extra.replay` 记录。
- `stream_plan`：`if !parse_is_on(&body) || parse_is_replay(&body) { return Err(NotLive) }`。
- 效果：重播房间在监控里显示未开播，不自动开录；即使直接调用取流也返回 `NotLive`。

### 3.2 4K 实际取流探测

`probe_quality(stream, qn)`：

- 只对 `qn=30000`（4K HDR，`ratio=20100`）与 `qn=20000`（4K，`ratio=20000`）调用。
- 从 `gameStreamInfoList` 取前两条线路，用现有 `build_stream_url` 重新签名。
- 请求带 `Referer: https://www.huya.com` 与 `Range: bytes=0-65535`；连接超时 4 秒，首块超时 3 秒。
- 返回：`Some(true)` 已出流；`Some(false)` 两条线路都 403/404；`None` 超时或状态不明。

`probed_quality_cap(stream)`：

- 档位表里没有 `iBitRate >= 20000` → `15100`（最高 2K HDR）。
- 4K HDR 探测成功 → `30000`（4K HDR + 4K 都开放）。
- 4K HDR 未成功、4K 成功 → `20000`（只开放 4K）。
- 两者都明确 403/404 → `15100`（4K/4K HDR 标不可用）。
- 探测不明 → `20000`，不因一次网络抖动隐藏 4K。

`quality_available(qn, cap_qn)` 仍是 `qn <= cap_qn`；`pick_quality` 把已保存的 4K 偏好收敛到 `cap_qn`，自动回落 2K HDR/2K，避免再次撞 403。

不可用 4K 档的提示统一为：

- `4K HDR HEVC · 20100 kbps · 当前不可用`
- `4K HEVC · 20000 kbps · 当前不可用`

不再区分“登录后可用”：登录本身并不能解锁这些 403 的档位。

### 3.3 探测开销

- 没有 4K 档的房间：0 次探测。
- 有 4K 档的房间：最多 2 个档位 × 前 2 条线路 = 4 次请求；403 通常 0.2–0.4 秒返回，实测 660000 总耗时约 1 秒。
- 探测只在 `stream_plan`（起播/开录）执行，不在 30 秒监控轮询里执行。

## 4. 验证

### 4.1 真机/联网

- release bundle 真机（2026-11-18 03:09）：添加 660000 后监控行显示「离线 / 未录制」，操作按钮禁用；日志 `房间信息请求完成 platform="huya" room=660000 live=false`，30 秒轮询持续为 `live=false`，没有开录、没有生成录像。
- 同一 bundle 添加当时正在直播的 11336726：日志 `房间信息请求完成 ... live=true` → `取流请求完成 ... groups=3 qualities=3` → `开始录制 ... quality=蓝光4M · FLV requested_qn=10000 actual_qn=10000`；录制约 200 秒后手动停止，分片合并为两段（60 秒 / 140 秒），弹幕 4 条、ASS 4 行，`post_state=done`。说明重播拦截没有影响正常直播起录。
- `cargo test --lib -- --ignored --nocapture huya::tests::live_room_probe`：
  - `room: 虎牙英雄联盟赛事 / 【预告】29日4点 S16瑞士轮第五日 live=false`
  - `probed cap_qn=15100`
  - 证明 `is_replay=1` 被识别，且 4K 探测返回不可用。
- 手工 curl（同一房间、同一签名算法）：
  - `ratio=10000&codec=264` → 200，1.9 MB，ffprobe `h264,1920,1080`。
  - `ratio=20000/20100/30000&codec=265` → 403，0 字节（TX/AL/HS 多条线路一致）。
  - 带 Cookie.txt 的虎牙 Cookie 结果相同。
- 当前没有正在直播的 4K 房间，因此“4K 探测成功 → 可选/可录”的路径未做真机闭环；只验证了“4K 失败 → 15100 → 回落 2K”的路径。这一点必须如实保留。

### 4.2 单测

`cargo fmt --check && cargo check --all-targets && cargo test --lib`：

- **386 passed / 0 failed / 19 ignored**

新增/调整：

- `replay_is_not_live`：`is_replay=1`、`live_status_text=重播中` 判重播；`0`/缺失不误判。

## 5. 限制

1. 只探前两条线路。如果某房间的 4K 只在第 3 条及以后线路可用，会被误判为不可用；目前 660000 的前两条（AL/TX）与 HS 结果一致，暂未发现反例。
2. 探测依赖 `Range` 与首块数据。CDN 若忽略 Range 但正常出流，仍会返回 200，不影响判定；若首块超过 3 秒才到，会返回 `None`，按 4K 可用处理，不会误隐藏。
3. 重播识别依赖 `is_replay`/「重播中」文案。虎牙若改字段名，需要同步调整；当前页面两种信号同时存在。
4. 4K 是否真的对某些账号/某些赛事开放，仍缺一个“正在直播的 4K 房间”样本；等 660000 或其他 4K 赛事开播后应补一次成功路径验收。
5. 本次只改 `src-tauri/src/platform/huya.rs`，不涉及 B 站/斗鱼/抖音适配器、共享 HTTP、录制器、监控器。
