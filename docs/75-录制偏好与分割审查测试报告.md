# 75 录制流偏好与视频分割审查测试报告

> 状态：v1.0（2026-11-08）。审查对象为 `docs/74` 落地的录制流画质/源流格式/编码偏好，以及标题变化/时长/大小三种分割；范围包含设置层、选流、录制、收尾、崩溃恢复、媒体库与删除命令。审查方式为代码走查 + 单元测试 + 真实平台录制 + 造数据/故障注入。

## 1. 结论

1. 录制流偏好的主链路正确：画质优先、编码次之、格式再次；平台能力不足时只降级排序，不会因为偏好没有对应候选而拒绝开录。
2. 三种分割都能真正切出文件，但**时长分割最初存在严重缺陷**：用分片 mtime 判断时长，60 秒目标在真实录制中会变成 120 秒。已改为按 `-segment_time` 标称长度推进，真实 B 站录制复验首段 60.06 秒。
3. 崩溃恢复有两个会让用户丢恢复依据的问题：收尾写库失败仍删清单、恢复遇到首个缺失片段就提前退出。均已修复并补测试。
4. 媒体库与删除命令存在一致性问题：首片段缺失时整场不可播、单删片段会留下悬空 group、整场删除中途失败会留半组、平台计数按片段而卡片按场。前四项已修，平台计数已改为按场。
5. 真实录制覆盖了画质选流、时长分割、标题分割、场次分组、弹幕/缩略图/媒体入库与优雅退出；大小分割受测试流码率限制未在 95 秒内达到 64 MiB 下限，由造数据单测覆盖边界。
6. 本轮共确认并修复 11 个实现问题，另有 2 个属于产品粒度/平台能力的已知限制，写进 `docs/74` 而不强行改语义。

## 3. 真实录制结果

统一环境：独立 `HOME`，媒体根在 `/tmp/hivecast-e2e/runN/recordings`，B 站房间 6，`record.default_qn=40000`、`record.source_format=auto`、`record.codec=auto`、`post.auto_remux=true`。未登录时平台实际最高返回超清（qn 250），应用按“最高可用”降级，没有开录失败。

| 轮次 | 设置 | 日志/产物 | 结论 |
| --- | --- | --- | --- |
| run5 | 时长 60 秒 | `start=1 reason="duration"`，clips=2；clip0 60.060 秒 / 8,897,912 B / DB 60000 ms；clip1 17.349 秒 / 2,701,030 B / DB 14000 ms | 修复后 60 秒目标不再变 120 秒 |
| run7（旧边界时间） | 标题分割 | `start=1 reason="title"`；clip0 60.062 秒，clip1 24.618 秒；DB 首段 57000 ms | 标题切在分片边界，但 DB 首段少了 3 秒 |
| run9（新边界时间） | 标题分割 | `start=1 reason="title"`；clip0 60.065 秒 / 9,649,837 B / DB 60000 ms；clip1 19.255 秒 / 1,829,182 B / DB 15000 ms | 标题分割与 DB 首段一致；末段 DB 为墙钟时间 |
| run8 | 大小 64 MiB | 95 秒只录到 14,073,721 B，未触发切分；restarts=1 后继续续录同一场 | 测试流码率约 148 KiB/s，未达到 64 MiB 下限 |

补充说明：

- run7/run9 中平台标题在开录约 5 秒后被监控更新，随后用户把房间标题改成 T1；分割仍只能落在分片边界（默认 60 秒），所以首段是 60 秒，而不是标题变化的第 5 秒。这是当前设计的粒度，不是丢帧。
- run5 的末段 DB 时长 14 秒、容器 17.3 秒，差值是 SIGTERM 后 ffmpeg 刷缓冲与容器时间戳造成的墙钟/媒体时长差；首段与总时长不受影响。该差异会保留在残余风险里。
- 真实录制的弹幕 WebSocket 已认证、ASS/JSONL 正常生成，缩略图与媒体行在收尾后入库；分片文件在合并成功后删除。

## 4. 已确认并修复的问题

| ID | 现象 | 根因 | 修法 | 回归 |
| --- | --- | --- | --- | --- |
| D1 | 时长上限 60 秒，真实首段 120 秒 | `plan_clips` 用分片 mtime 当结束时间；ffmpeg 延迟关闭文件，mtime 比真实结束早 5–6 秒，`ended + 5s >= 60` 仍不成立 | 时长边界改用标称分片数 × `segment_secs`，边界时间也用标称值；mtime 只用于匹配标题变化 | `split_plan_uses_nominal_segment_length_for_duration`、run5 |
| D2 | 标题分割 DB 首段 57 秒，容器 60 秒 | 标题/大小边界用 mtime 写 `ended_at` | 所有分割边界的 `ended_at` 都改为标称分片起点 | run9；`split_plan_honors...` |
| D3 | 合并完成但清单未更新时，崩溃恢复可能重合并并覆盖完整成品 | `merge_range` 直接写目标文件，成功后逐个删分片；崩溃窗口内成品与分片并存 | 先写同目录 staging，成功后 rename；目标已存在且非空时拒绝覆盖；恢复优先复用完整成品并清残留分片 | `merge_refuses_to_overwrite_a_complete_output`、`recovery_prefers_a_complete_clip_even_when_parts_remain`、`orphan_recovery_reuses_a_complete_file_without_remerging` |
| D4 | 收尾写库失败仍删 SplitManifest，重启后无法补历史 | `finalize` 无条件 `completed=true` 并删清单 | 跟踪 `history_ok` 与每段成品大小；任一失败保留 `completed=false` 清单 | 代码走查 + 现有恢复测试 |
| D5 | 某个早期片段缺失时，恢复直接 return，后面片段永远不恢复 | `size<=0` 分支写清单后整体返回 | 改为 continue；DB 失败也置 `db_ok=false`；只有全部片段恢复且 DB 成功才删清单 | `recovery_continues_past_a_missing_early_clip` |
| D6 | Windows 上启动失败/并发满后删占位文件可能失败，留下 0 字节录像 | `start_kill` 后立刻删文件，ffmpeg 仍持有句柄；只删 part0000 | 等待退出最多 2 秒，再用 `collect_parts` 清全部片段 | 代码走查；macOS 真机清理正常 |
| D7 | 首片段文件缺失、后续片段有文件时，媒体库封面可点但播放 404 | 封面永远用 `group.primary` | 选择第一个 `hasFile` 的片段播放；无文件时仍禁用 | 代码走查 |
| D8 | 单删分割录像首段会留下悬空 group；整场删除中途失败留半组；批量提示按片段数但实际删整组 | 删除命令缺少组校验、逐段 `?` 中断、提示数量用 `selectedItems.length` | 单删前查 `session_group_size`，多片段拒绝；整场删除记录首个错误并继续删其余片段；提示改为整场片段总和 | `session_group_size` 断言；代码走查 |
| D9 | 平台筛选条数量与卡片数不一致 | `media_platform_counts` 用 `COUNT(*)` 按片段 | 改为 `COUNT(DISTINCT COALESCE(group_id,id))` 按场 | `split_clips_form_one_session_in_library_and_host_counts` |
| D10 | 虎牙 8000 kbps 蓝光被标成 qn=10000，指定 400 时反而选 4M 档 | `qn_for_bitrate` 把 `>=8000` 全部映射原画 | `>=10000`→10000，`>=8000`→400（蓝光 8M），并同步 docs/24 | `bitrate_maps_8m_to_bluray_not_origin` |
| D11 | 手工写入 `record.split_on_title=1` 时被静默当 false | `parse::<bool>()` 只认 true/false | `parse_bool` 兼容 1/0；所有布尔设置统一 | `load_accepts_numeric_booleans` |

## 6. 设置页与周边检查

- 新安装默认“最高可用”，老配置保留原 qn；房间 0 表示跟随全局。`effective_record_qn` 有单测。
- 时长 1–59 秒、大小 1–63 MB：前端允许输入，后端保存时夹到 60 秒 / 64 MB；页面提示已补“最短 60 秒 / 64 MB，低于会按最小值保存”。
- 大小单位 MB/GB 只影响输入显示，底层统一存 MB；`1000 MB` 显示约 `0.98 GB`，切换单位不丢值。
- 空数字输入被当作 0（不限）；这是现有输入组件行为，未改，避免用户清空时突然保存失败。
- 录制开始后修改设置不影响当前会话，下一次开录生效；设置页保存后回读通过。
- 媒体库按 `group_id` 聚合，一场直播一张卡；卡片显示片段数、总大小、总时长、总弹幕；`+N` 可补齐未加载片段。
- 单片段抽屉删除已改为删整场，避免留下无首段的组；整场删除前会停本地回放并清缩略图/弹幕。
- 平台筛选数量改为按场；媒体库分页/总数仍按片段，用于保证“加载更多”不会漏掉半组。这是剩余的分页语义差异。

## 8. 残余风险与产品限制

1. **大小分割是软上限**：只能在分片边界切，分片最短 60 秒；高码率流下 64 MiB 目标可能产出约 150 MiB 的单段。真实测试流码率太低，95 秒未达到 64 MiB。
2. **标题分割最多延迟一个分片**：默认 60 秒分片，标题在第 5 秒变化也要等到第 60 秒边界；轨道内不会丢帧，但首段会包含旧标题的剩余时间。
3. **末段 DB 时长是墙钟时间**：ffmpeg 收到停止信号后还会刷缓冲，容器时长可能比 `duration_ms` 多几秒；首段与总大小不受影响。
4. **媒体库分页仍按片段**：平台计数与卡片按场，但“加载更多”和总数仍按片段，极端情况下会出现数量口径不同。
5. **Windows 未真机**：D6 的等待/清理逻辑针对 Windows 句柄问题，但只在 macOS 验证；发布前需在 Windows 做一次启动失败、并发满、删文件测试。
6. **弹幕只挂首段**：分割后后续片段没有独立弹幕文件；这是当前数据模型限制。
7. **标题检测依赖监控更新**：`track_title` 每 5 秒读一次 DB，但房间标题通常由监控每 30 秒刷新；平台标题变化到被记录可能延迟最多约 30 秒，再叠加分片边界。
8. **真实平台画质受账号能力限制**：未登录 B 站只能到 250；4K/HDR 需要登录与相应权限，代码只做“请求最高、失败逐级降”，不保证一定拿到。
