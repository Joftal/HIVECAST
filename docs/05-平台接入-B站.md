## 2. 清晰度（qn）映射

| qn | 名称 |
| --- | --- |
| 30000 | 杜比 |
| 25000 | 原画真彩 |
| 20000 | 4K |
| 15000 | 2K |
| 10000 | 原画 |
| 400 | 蓝光 |
| 250 | 超清 |
| 150 | 高清 |
| 80 | 流畅 |

- 应用层的 40000 是「最高可用」哨兵，B 站接口最高接受 `qn=30000`；`request_qn(40000)` 返回 30000。
- 全局录制默认「最高可用」；单个房间可以覆盖为具体档位。
- 用户偏好通过 `StreamPreference.Quality` 传入，反向映射到 qn。
- 注意：**qn 只是"期望值"**，实际给什么由 `current_qn` 决定；`accept_qn` 是"该路流可切换到的档位列表"。

### 2.1 能力清单必须独立高档探测

请求 qn=10000 时，平台会把 `current_qn` 封在 10000；用它判断 2K/4K/杜比会把高档全部误标不可用。HIVE 的做法：

1. base 请求按用户目标档位取线路；
2. 目标 < 30000 时，另请求一次 `qn=30000`，只取 `g_qn_desc`、`accept_qn`、`current_qn` 构造能力清单；
3. 探测失败/未开播/无 `playurl_info` 时回退 base 清单，`probed_high=false`，不把未知高档直接标灰；
4. `quality_available` 必须同时满足 `accepted.contains(qn)` 和 `qn <= granted_qn`（高档探测成功时）；
5. `granted_qn` 取高档响应所有 codec 的 `current_qn` 最大值。

实测房间 `22637261` 的高档探测 granted=25000：菜单出现「原画真彩」25000，4K/杜比标灰；2K 因该房间 `accept_qn` 不含 15000 而标灰。详见 [142](142-B站画质档位与高档探测修复.md)。

## 3. 取流响应结构与解析

```text
data.playurl_info.playurl.stream[]        // 协议层：http_stream | http_hls
  ├─ protocol_name
  └─ format[]                             // 封装层：flv | ts | fmp4
       ├─ format_name
       └─ codec[]                         // 编码层：avc | hevc | av1
            ├─ codec_name
            ├─ current_qn
            ├─ accept_qn[]                // 可切换的档位
            ├─ base_url
            └─ url_info[] { host, extra }
```

**拼 URL 规则**：`host + base_url + extra`。同一路流会给出多个 `url_info`（多 CDN 节点），要全部生成候选并按顺序尝试。

bililive-go 的产物（`bilibili.go:GetStreamInfos`）：

- 对每个 `(protocol, format, codec, url_info, accept_qn)` 组合生成一个 `StreamUrlInfo`；
- `Name = "<画质> - <format>"`，如 `原画 - flv`；
- `AttributesForStreamSelect` 带 `画质/协议/codec/format_name/index`，供前端分组；
- `IsPlaceHolder = (acceptQn != currentQn)`：非当前档位是占位，切换时需重新请求。

**格式判定**：`protocol_name == "http_hls" || format_name == "fmp4"` → `hls`；`format_name == "flv"` → `flv`。

**兜底逻辑**（主解析为空时）：优先 `stream.1.format.1.codec.1`（HEVC m3u8），否则 `stream.0.format.0.codec.0`（AVC FLV）。

## 4. streamlink 的另一条路线（更省请求）

`plugins/bilibili.py` 的策略值得借鉴：

1. 先用老接口 `room/v1/Room/playUrl` 拿 FLV 直链，**逐个 HEAD 校验**（`status_code >= 400` 就丢弃）——因为 B 站常返回"看起来正常但实际 403"的地址。
2. HLS 走页面内嵌 JSON（`__NEPTUNE_IS_MY_WAIFU__`），一次请求同时拿到：
   - `roomInitRes.data.live_status`（是否在播）
   - `roomInitRes.data.playurl_info`（流）
   - `roomInfoRes.data.room_info`（`live_id`/`title`/`area_name`）
   - `roomInfoRes.data.anchor_info.base_info.uname`（主播名）
3. 页面拿不到再退回 `_get_api_v2_playinfo`。
4. 只保留 `http_hls` + `avc` + `format in (fmp4, ts)`（客户端兼容性优先，不碰 HEVC）。
5. `stream_weight` 覆写：`httpstream` 权重 4，`hls` 权重 2（FLV 直链更省 CPU），`_alt` 后缀减 1。

> **HIVECAST 建议**：两条路线都实现，按"是否需要登录/是否要 HEVC"选择。默认走 v2 接口（信息全、支持多档），失败时降级到页面内嵌 JSON，最后降级到 v1。

## 6. 扫码登录

流程：

1. 请求 `qrcode/generate`，把 `data.url` 渲染成二维码，保留 `qrcode_key`。
2. 每 2s 轮询 `qrcode/poll?qrcode_key=...`：
   - `code=86101` 未扫码；
   - `code=86090` 已扫码待确认；
   - `code=0` 成功。
3. **成功时凭证在 `Set-Cookie`**：需要从响应头取 `SESSDATA/bili_jct/DedeUserID/DedeUserID__ckMd5/sid`；`data.url` 的 query 里也可能有 `sid`，两处合并、`Set-Cookie` 优先。
4. 只落库上述 5 个字段，埋点字段（`buvid3`/`_uuid`）丢弃。

> 实现细节见 `bililive-go/src/servers/handler.go:4108-4163`：`biliLoginCookieNames` 白名单 + `attachBilibiliLoginCookies`。注意 JSON 解析必须用 `UseNumber`，否则大整数 `room_id`/`mid` 会被 float64 截断。

## 7. 弹幕

### 7.1 连接流程

1. `room_init` 拿真实房间号。
2. `getDanmuInfo?id=<real>&type=0` 拿 `token` 与 `host_list`。
3. 依次尝试 `wss://<host>/sub`（`host_list[].host`，注意还有 `wss_port`），全失败回退 `wss://broadcastlv.chat.bilibili.com/sub`。
4. 连上后发认证包，然后开两个循环：读循环（含重连）与心跳循环。

### 7.2 包格式（16 字节头，大端）

```text
offset 0..4   packet_len   u32
offset 4..6   header_len   u16 (=16)
offset 6..8   protover     u16 (0=plain, 1=popularity, 2=zlib, 3=brotli)
offset 8..12  operation    u32
offset 12..16 sequence     u32 (=1)
body...
```

| operation | 含义 |
| --- | --- |
| 2 | 客户端心跳 |
| 3 | 心跳回复（人气值） |
| 5 | 业务消息（弹幕/礼物/SC/舰长） |
| 7 | 客户端认证 |
| 8 | 认证回复 |

- 认证体：`{"uid":0,"buvid":"","roomid":<real>,"protover":3,"platform":"danmuji","type":2,"key":"<token>"}`
- 心跳间隔 30s；连续失败 5 次刷新 `getDanmuInfo`（token 会过期，`code=-101`）。
- `protover=2/3` 的 body 是压缩的**多个子包**，需要递归解包。

### 7.3 消息类型

| cmd | 含义 | 关键字段 |
| --- | --- | --- |
| `DANMU_MSG` | 弹幕 | `info[1]` 文本、`info[2][0/1]` uid/用户名、`info[0][3]` 颜色 |
| `SEND_GIFT` | 礼物 | `data.giftName`、`num`、`price`、`coin_type` |
| `SUPER_CHAT_MESSAGE` | 醒目留言 | `data.message`、`price`、`user_info.uname` |
| `GUARD_BUY` | 上舰 | `data.gift_name`（舰长/提督/总督） |

> cmd 可能带后缀（`DANMU_MSG:4:0:2:2:2:0`），匹配要用前缀而非全等。

## 8. 坑位清单

1. **短号 vs 真实号**：URL 里的可能是短号，所有接口都要用 `room_init` 后的 `room_id`。
2. **HEVC 是 ts 不是 flv**：选 `format=1`（fmp4/ts）时文件扩展名要改成 `.ts`，否则播放器识别失败。
3. **占位候选**：非当前 qn 的 `base_url` 直接请求会 403，必须重新调接口（带新 qn）。
4. **多 CDN**：`url_info` 有多个 host，第一个失败要自动换下一个。
5. **Referer 必须对**：用房间页 URL，不是 `live.bilibili.com` 首页。
6. **风控**：短时间内大量 `getRoomPlayInfo` 会返回 `code=-412`（请求被拦截），需要退避 + 换 UA + 带 cookie。
7. **Wbi 签名**：部分接口（如 `nav`）需要 Wbi 签名，签名密钥来自 `wbi_img`，混淆表 64 元素，缓存 1 小时。
8. **原画 PRO 有时转码崩**：社区反馈 HEVC 流偶发损坏，建议保留"切回 AVC"的开关。
9. **AV1 不能直接录制**：`codec=0,1,2` 后平台可能返回 AV1。AV1 `-c copy` 进 MPEG-TS/Matroska 分片会报 `Output file does not contain any stream`，产物 0 字节；HIVE 观看可用 AV1，录制侧过滤 AV1，只给 AV1 时返回明确错误。
10. **25000 不是 4K**：「原画真彩」是独立档位，不能当成 20000/4K 或 30000/杜比的别名。
