## 1. 结论

任务中心的主链路是通的：监控开录后出现「录制中」的 Run，停止后自动进入收尾、后处理、入库，完成后落到「最近完成」；失败会进入「需要处理」，并能从异常卡跳到直播间、账号页或 Run 详情。本轮重点复核了上一轮四个修复，全部通过真机验证；另外修掉一个此前未发现的统计口径问题。

## 2. 当前实现

### 2.1 数据源与聚合入口

`/Library/dshproject/HIVECAST/src-tauri/src/task_center.rs:25` 的 `build(db, recorder, jobs, statuses, ffmpeg_path, media_root, history)` 是唯一聚合入口，把五类数据拼成页面：

- `recorder.active_all()` / `starting_rooms()`：正在录制、正在开录（还没有 session）的房间；
- `record_session`：已结束或正在收尾的场次，含 `group_id`、`split_manifest`、`post_state`、`danmaku_count`；
- `jobs.board(...)`：内存中的后处理/合并任务与最近任务历史；
- `task_event`：阶段时间线；
- `room`、`credential`、`MonitorStatusMap`：房间信息、登录失效、平台态势。

`history` 参数先 `clamp(1, 1_000)`（后续见 185；本轮复查时是 500）；`jobs.board` 取 `(history * 4).clamp(200, 1600)` 条，避免一个 Run 的多个片段任务被截断。历史场次最终还会 `truncate(history)`，所以**页面能看到的条数由调用方决定**。

### 2.2 Run 怎么分组

- 普通录制一场一个 `record_session`，Run id 形如 `session:<session_id>`。
- 标题变化、手动分段、断流续录会产生多条 `record_session`，共用同一个 `group_id`；`session_group_key` 取 `group_id`，没有则退回 `id`，整组只生成一条 Run。
- 运行中的 Run 用 `recorder` 的 session 建草稿；还没拿到 session 的「开录中」用 `starting:<room_id>` 临时 id，拿到 session 后自然归并。
- 历史 Run 从 `record_session` 的已结束分组来；分组内的 `file_size`、`duration_ms` 求和，结束时间取最大值，录制中的片段用 `parts_total(path)` 补实时体积。
- 分组后按 `ended_at` 倒序，`running` 与 `history` 分别输出；`queued` 是等待后处理槽位的任务，单独列表，不伪造队列序号。

### 2.3 状态与阶段

`finish_run`（`task_center.rs:441`）先算整组事实，再按优先级落状态：

```text
finalizing > recording > running > queued
          > failed / partial / interrupted / cancelled > done
```

- `recording`：录制进程在跑，或 session 仍是 `recording`；
- `finalizing`：收尾任务 running/queued，录制已经停止；
- `running`：后处理/合并/弹幕导出在跑；
- `queued`：只有排队任务，没有活动任务；
- `failed`：任一片段失败、收尾失败，或 `aborted` 且原因不是 `app_exit`；
- `partial`：同组既有成功片段又有失败片段，但整组不是录制失败/收尾失败；
- `interrupted`：`app_exit` 等异常退出；
- `cancelled`：用户取消；
- 其余为 `done`。

四段链路固定为「录制 → 收尾 → 后处理 → 入库」；异常中断时入库阶段区分 `done` / `partial` / `failed`。`normal_commit`（`task_center.rs:815`）的规则是：aborted 且有文件/大小 > 0 时为 `partial`，完全没有产物才是 `failed`。

### 2.4 页面结构

`/Library/dshproject/HIVECAST/src/features/tasks/TasksPage.tsx`：

- 页头 + 刷新；工具栏四个筛选（全部/运行中/排队/需要处理），平台筛选与直播间筛选可叠加；
- 五张统计卡：房间、直播中、录制中、排队、24 小时失败；
- 四平台态势卡：房间/直播/录制数、登录状态、最近错误；点卡即平台筛选；
- 系统行：ffmpeg 是否可用、磁盘剩余、媒体目录；
- 「需要处理」异常卡：录制失败、后处理失败、收尾失败、登录失效、磁盘不足等，按严重度排序；
- 「进行中」Run 卡：画质、主播、标题、时长、体积、四段轨、进度、开始时间；
- 「排队」列表：任务类型、片段序号、同 Run 其他排队任务、等待时长；
- 「最近完成」表：平台、主播/标题、时长、体积、结束时间、状态；
- 详情抽屉：Run 状态、房间/场次、四段链路、任务列表（录制→收尾→后处理）、阶段时间线、上下文、录制文件、复制诊断、重试/取消。

页面每 2 秒轮询一次；`load()` 用递增 `loadSeq` 只接受最后一次响应，避免手动刷新与轮询互相覆盖。手动刷新成功会 toast「已刷新」。

### 2.5 异常动作

`build_incidents`（`task_center.rs:969`）按异常类型返回动作：

- 录制失败 → `open_room`，前端打开对应直播间抽屉；
- 后处理失败 → `retry_post` 或 `open_task`；
- 收尾失败 → `retry_finalize`；
- 登录失效 → `open_account`；
- 磁盘不足 → 打开监控/存储相关入口。

前端 `TasksPage.tsx` 的 `retry()` 按 `task.kind` 分流：`finalize` 调 `finalizeRetry(sessionId)`，其余调 `postRetry(sessionId)`。重试前会置 `busyId`，防止重复点击。

## 3. 本轮修复

### 3.1 收尾任务只认最新一次

旧实现把同一 Run 的所有 `finalize` 任务都放进详情，重试成功后旧的 failed 记录仍会显示「收尾失败」，详情还会继续给「重试收尾」按钮。现在 `finish_run` 按 `started_at/finished_at` 排序后只保留最新一条；旧记录仍留在 `task_history`，需要排查时可以从数据库或事件里看到。

真机：`tc-review-fin` 注入 `finalize:tc-review-fin` failed，点「重试收尾」后 manifest 删除、`split_manifest` 清空、`task_history` 新增 `job:2 done 收尾完成`；刷新后详情只剩一条「收尾 完成 100%」。

### 3.2 分组后处理成功不掩盖其他片段的失败

旧实现只要 Run 里任意 session 的 `post_state == done`，就删除所有 failed post/remux 任务。分组录制 g1 成功、g2 失败时，g2 的失败会被 g1 掩盖。现在只有 `group_members` **全部** `post_state == "done"` 才删除旧失败任务。

真机：`tc-review-g1`(done) + `tc-review-g2`(post failed) 时历史行仍为失败，详情能看到 g2 的失败任务；补真实文件后点「重试后处理」，两段都 done，刷新后异常 4→3、历史该行变完成，旧失败任务不再出现。

### 3.3 收尾重试锁按清单而不是按场次

分组录制的多个片段共用一份 `split_manifest`。如果按 session_id 加锁，两个片段可以同时重试同一份清单，互相覆盖中间文件。`recorder.rs:3876` 的 `FINALIZE_RETRYING` 改为存 manifest 字符串；`FinalizeRetryLease` 也按 manifest 释放。

该修复目前只有代码审查 + 单测覆盖（185 补了同清单互斥/不同清单并行/drop 释放的用例），没有真机并发双开（两个片段同时点重试）的场景；单进程锁本身不防多实例。

### 3.4 历史分页只保留完整分组

旧 `load_sessions` 达到目标分组数就停，目标分组可能正好跨页，最后只读到半个分组；达到 5000 行上限时也可能留下半组。现在：

- 必须多读一个分组（`closed_order.len() > target`）才停；
- 未达上限时 `trim_to_target_groups` 丢掉末尾多读的不完整分组；
- 达到 `MAX_ROWS = 5000` 时 `capped = true`，丢掉最后一组并打 WARN。

单测 `trim_to_target_groups_drops_the_extra_partial_group` 覆盖「2 个完整组 + 1 个跨页组」；真机 250 片同组聚合为 41:40 / 244 KB，证明跨 `PAGE=200` 没有被截成 200 片。

### 3.5 「全部」数量不再重复计算

失败 Run 同时出现在「需要处理」和「最近完成」两个区块。旧 badge 用 `运行中 + 排队 + 历史 + 异常`，同一条失败记录被算两次，出现「历史 100 条 + 异常 4 条 = 全部 104」但页面并没有 104 条独立记录。

现在只把**找不到对应 Run 的异常**算作额外记录：有 `taskId` 的异常先在 `allRuns` 里找任务，有 `roomId` 的再找房间；找到就说明它已经由历史行/运行卡承载，不重复加。登录失效这类没有对应 Run 的异常仍然计数。

### 3.6 历史条数上限有明确提示

本轮复查时页面固定请求最近 100 场（`taskCenter(100)`），并在标题右侧提示「最多显示最近 100 场」。后续 185 已改成真正的增量加载：首屏 100 场，底部「加载更多历史」每次追加 100 场，最多 1000 场；后端新增 `history_has_more` 判断是否还有更多。本节保留为当时状态。

## 5. 仍需完善

> 以下 1–3 项已在 185 处理，保留原始记录便于对照。

1. **历史没有真正的分页/加载更多**（已由 185 完成）：前端改为 100→200→…→1000 的增量加载，后端返回 `history_has_more`，页面底部有「加载更多历史」。
2. **「部分失败」文案**（已由 185 完成）：`partial` 的入库阶段改为「部分完成 / Partially completed」，整体运行状态仍按失败/中断判断。
3. **收尾并发只验证了代码和单测**（185 已补单测，真机并发仍未覆盖）：`FINALIZE_RETRYING` 按 manifest 去重；同清单互斥、不同清单并行、lease 释放已有单测，但没有真机同时点两个片段「重试收尾」；多实例同时重试也不在锁的覆盖范围。
4. **收尾夹具的状态语义**：`tc-review-fin` 的 manifest.status 写的是 failed，所以重试成功后 session 仍是 failed、「录制失败」仍显示。真实「录制成功但收尾失败」的 manifest.status 是 finished，本轮夹具只验证重试与旧任务隐藏，不代表完整成功态回归。
5. **异常与历史重复展示**：数量已去重，但同一失败仍会在「需要处理」和历史表各出现一次；这是产品上有意的双入口，不是数据重复。
6. **大数据量性能未量化**：377 条 session、250 片同组时页面可用，2 秒轮询没有明显卡顿，但没有记录接口耗时/内存；超过 5000 行会截断并告警。
7. **B 站登录失效是环境状态**：本机 B 站 Cookie 已过期，页面显示登录失效属真实状态；测试结束会用备份恢复，不是本轮代码回归。
