## 3. 连接与鉴权

### 3.1 实际链路

```text
room_init(room_key)
  → 真实 room_id
  → 读取 credential("bilibili")
  → 有 Cookie：uid=DedeUserID，buvid=buvid3/4 或 finger/spi 动态获取
  → getDanmuInfo（WBI 签名 + Cookie + buvid3，目标：登录 token）
      ├─ 成功：auth uid/buvid 用登录身份
      └─ 失败：warn 后回退匿名 getDanmuInfo → getConf
  → getConf（匿名兜底）
  → token + host_server_list
  → wss://{host}:{wss_port}/sub
  → Op=7 auth
  → Op=8 code=0
  → Op=5 消息 / Op=2 心跳 30s
```

### 3.2 登录态优先与匿名兜底

2026-11-12 22:30 起，`src/danmaku.rs` 的 `fetch_session` 不再无条件匿名：

1. `room_init` 拿到真实房间号后读 `credential::get("bilibili")`；
2. 从 Cookie 取 `DedeUserID` 作为 uid；Cookie 没有 `buvid3/buvid4` 时请求 `https://api.bilibili.com/x/frontend/finger/spi` 的 `b_3`，进程内缓存；
3. 用 WBI 签名请求 `getDanmuInfo`，请求显式带 Cookie，并追加 `buvid3`；
4. 成功则把 `uid/buvid` 存进 `DanmuSession`，auth body 用登录身份；
5. 失败只 `warn`，回退匿名 `getDanmuInfo` → `getConf`，不影响开播。

### 3.3 为什么真实环境仍常常是匿名

**2026-11-13 已定位根因并修复**（详见 18.1）：

| 客户端 | getDanmuInfo | 结果 |
| --- | --- | --- |
| 修复前 reqwest | 带 DB Cookie、追加 buvid3、WBI 签名 | `-352` |
| 修复前 Node | 正确签名（mixin 取 32 位） | HTTP 200 + token |
| 修复后 reqwest | 同一房间、同一 Cookie | `code=0` + token 260 |

- `-352` 与 Cookie、Origin、`web_location`、TLS 指纹均无关；是签名里的 mixin key 长度错误，服务端直接判签名无效。
- 修复前“浏览器能过、Node/reqwest 不能过”的对照不成立：早期 Node 探针也用了 64 位 mixin，只是后来某一版探针修正了却没同步回应用。
- 结论：**有 Cookie 时优先走登录态 token，拿不到时才匿名；两条路径都使用同一套正确签名。**

### 3.4 登录流与匿名流的真实差距

同一房间 732、同一 60 秒窗口，自建原生 WS 探针：

| 身份 | 总事件 | DANMU_MSG | 礼物类 |
| --- | --- | --- | --- |
| 登录 token（uid 352130563） | 285 / 289 / 293 | 67 / 68 / 51 | 1–4 |
| 匿名 token | 24 / 35 / 42 / 55 | 2 / 4 / 3 / 10 | 几乎为 0 |

登录流约为匿名的 **5–12 倍总事件、7–20 倍聊天弹幕**。这不是网络抖动，是 B 站对匿名连接的降采样/过滤。
所以“Cookie 是否参与弹幕”的答案是：**有 Cookie 时优先登录 token，没有或取不到时才匿名；登录流的数据量明显高于匿名流。**

### 3.5 认证 body

`src/danmaku.rs` 实际发送：

```json
{"uid":<session.uid>,"buvid":"<session.buvid>","roomid":<真实room_id>,"protover":3,"platform":"web","type":2,"key":"<token>"}
```

- WS 握手不发送 Cookie；
- 匿名时 uid=0、buvid 为空；登录时 uid/buvid 来自 Cookie 或 finger/spi；
- `platform="web"`、`protover=3`（brotli）；
- 登录 token 配匿名 uid 会被服务端立即断开，因此 uid 必须与 token 身份一致。

## 4. 收包、心跳与假死

### 4.1 协议

16 字节大端头：

```text
packet_len u32 | header_len u16(=16) | protover u16 | operation u32 | sequence u32(=1)
```

- `protover=0`：明文 JSON；
- `protover=2`：zlib，解压后可能是多个完整包；
- `protover=3`：brotli，同样递归拆包；
- `MAX_DEPTH=3` 防止压缩炸弹/递归异常。

### 4.2 心跳与假死

- 每 30 秒发 Op=2 心跳（body `[object Object]`）。
- `src/danmaku.rs:43` `IDLE_TIMEOUT=90s`；`run_once` 每 15 秒检查一次 `last_rx`。
- 90 秒没有收到任何 WS 事件 → 返回 Err，由 `run_room` 重连。
- 真实 90 秒探测中曾在约 72 秒收到 `Connection reset without closing handshake`；正式循环会把它当 Err 重连，不会永久挂住。

### 4.3 重连退避

- 1s → 2s → 4s → ... → 30s；
- 每次再加 0–400ms jitter（`src/danmaku.rs:770` `retry_delay`），避免多房间同时重连；
- token 连续失败 5 次才丢弃并重新取 token；
- 成功认证会重置 backoff。


1. base64 解码 `data.pb`；
2. 顶层字段 2 = 用户名；
3. 顶层字段 10 = GiftInfo；
4. GiftInfo 字段 2 = 礼物名，字段 3 = 数量；
5. 缺失时回退 JSON 的 `uname/giftName/gift_name/num`。

## 6. JSONL 落盘

### 6.1 格式

`src/danmaku.rs` `RecordWriter` 写：

```json
{"t":265062,"k":"chat","u":"绪方理奈-w-","c":"[空之轨迹1st表情包_对不起]","col":16777215}
```

| 字段 | 实际含义 |
| --- | --- |
| `t` | 相对 writer 启动的毫秒偏移，不是服务端时间戳 |
| `k` | chat / gift / super_chat / guard |
| `u` | 昵称，不是 UID |
| `c` | 文本 |
| `col` | 十进制颜色，B 站聊天几乎都是 16777215 |

### 6.2 写入策略

- 每 50 条或 1 秒 flush；
- 每 200ms 批次 flush 时额外调用 `flush_pending()`，慢速房间最后一条最多滞留 200ms；
- 先 `fan_out` 给 RecordWriter，再做 200 条/秒的 UI 限流；
- 空文件在 `finish` 时删除；
- 录制中 DB 的 `danmaku_count` 仍是 0，收尾 `detach_record` 才写真实条数。  
  这是“文件已经 121 行、DB 还显示 0”的原因，不是丢数据。

## 7. 分割录制：每段独立弹幕

### 7.1 原缺陷

分割录制整场只挂一个 RecordWriter，后续 clip 的 `danmaku_path` 固定写 `None`、`danmaku_count` 固定 0；ASS 只为第一段生成。  
默认 `split_max_duration_sec=0`、`split_max_size_mb=0` 时不会触发；开启时长/大小/标题切分后必现。

### 7.2 修复

`src/recorder.rs:2604-2685`：

1. 收尾时记录 writer 的 `started_epoch_ms()`；
2. 把整场 JSONL 复制成 `.split-src`，避免原地切第一段后下一段读到已截断文件；
3. 按每个 clip 的 `started_at/ended_at` 计算相对 writer 的区间；
4. 用 `src/postprocess.rs:255` `slice_danmaku` 切出每段 JSONL，并把 `t` 重设为段内偏移；
5. 第一段切片成功才删除母 JSONL；失败保留母文件；
6. 每个 clip session 写自己的 `danmaku_path/danmaku_count`；
7. `src/recorder.rs:2831` 对每段分别 `danmaku_to_ass`。

### 7.3 真实结果

本次 5055636 在 19:03 因标题变化触发切分：

- `e60aa6a2`（clip 0，4 分钟）：0 条，无 JSONL；
- `58526ec9`（clip 1，16 分钟）：1 条，`...19-03-54.clip01.jsonl` + `...clip01.ass`，ASS 有一行「很多好东西」。

说明每段弹幕不再只挂在首段。

### 7.4 残余限制

- `split_manifest` 还没有记录每段 `danmaku_path`；崩溃恢复后的片段仍可能没有弹幕文件；
- 母 JSONL 在极端崩溃（切片前进程被杀）时可能残留，但不会丢源文件。

## 17. 2026-11-12 二次复查补充（§18 已修正 -352 结论）

> 本节覆盖第 3、6、8、9、11、13 节的旧描述；冲突时以本节为准。

### 17.1 Cookie 与匿名：有 Cookie 优先登录，匿名只做兜底（已修正）

- 当前 `fetch_session` 会先尝试登录 token：Cookie 的 `DedeUserID` 作为 uid，`buvid3/4` 缺失时调用 `finger/spi` 取 `b_3`，再带 Cookie + buvid3 请求 WBI 签名的 `getDanmuInfo`。
- 2026-11-13 定位到 `-352` 的真正原因是 WBI mixin key 取了 64 位；改为只取前 32 位后，同一 Cookie、同一房间返回 `code=0` + token 260（见 18.1）。
- 因此“风控导致登录 token 不可用”的旧结论作废；应用现在能真正走登录态，匿名路径只在没有 Cookie 或登录接口失败时启用，且不注入 Cookie。
- 登录/匿名数量差仍然存在：同房间 732、60 秒探针，登录 285/289/293 总事件、67/68/51 条 DANMU；匿名 24/35/42/55 总事件、2/4/3/10 条 DANMU。约 5–12 倍总量、7–20 倍聊天弹幕，这是平台对匿名连接的降采样。
- 登录 token 与 auth body 的 uid/buvid 必须来自同一身份；修复后 `fetch_session` 已按此传递。历史“`getConf` token 带非 0 uid 会被断开”只说明不能混用匿名 token 与登录身份。

### 17.2 落盘完整性

- `RecordWriter` 先落盘、再进 UI 限流；`MAX_PER_SECOND=200` 只影响前端 batch，不影响 JSONL。
- `run_once` 改为固定 `interval(BATCH_WINDOW)`，连续消息不会再不断重置定时器；进程正常退出/断线时会 flush 最后一批。
- `writeln`/flush 失败会 `warn`（首次及每 100 次），`finish` 汇总“本场弹幕存在写入失败，文件可能不完整”；不再静默少行。
- JSONL 仍是五字段 `t/k/u/c/col`，**不是 B 站原始 JSON 的完整副本**；uid、勋章、粉丝牌、礼物价格、服务端时间戳等没有保存。文本、昵称、颜色、事件类型可保真。
- 录制中 DB `danmaku_count` 为 0 是设计：收尾 `detach_record` 才写真实条数；文件本身已在增长。

### 17.3 分段与合并

- 分段：按 clip 的 `started_at/ended_at` 从整场 JSONL 切片，每段 `t` 归零，分别生成 JSONL 与 ASS；边界消息归下一段。
- 合并：`postprocess::merge_danmaku` 按每段 `duration_ms` 累加偏移重写 `t`，输出与合并视频同名的 `.jsonl`，再生成 `.ass`；`room_merge_sessions` / `sessions_merge` 都会调用。单测覆盖“100ms + 空段 1000ms + 50ms = 2050ms”。
- 合并登记（2026-11-13）：`commands.rs:1363 register_merged_session` 会把合并产物写成一条 `status=finished`、`reason=merge`、`post_mode=source` 的 `record_session`，并带上 `danmaku_path` 与 `danmaku_count`；`db.create_session` 同时同步 `media_file`，因此媒体库能直接看到这条合并录像和它的弹幕轨。`room_merge_sessions` 会跳过 `reason=merge` 的旧产物，避免把合并结果再次整房合并。
- `merge_danmaku_files` 现在返回合并后的 JSONL 路径；即使 ASS 导出失败也保留 JSONL 供回放。
- 残余：`split_manifest` 仍未记录每段 `danmaku_path`；崩溃恢复只补视频/DB 行时，片段可能没有弹幕文件。合并失败只 warn，不阻断视频合并。

### 17.4 前端渲染与 ASS

- Canvas `colorOf(0)` 改为白色，B 站 `col=0` 不再黑字黑边不可见。
- 轨道全满时不再 `queue.length=0` 清空整队，只丢最旧一条并 break 到下一帧；UI 仍是“尽力渲染”，长弹幕超宽或极端爆发会跳过，但不影响 JSONL。
- ASS 轨道占用从固定 4 秒改为按弹幕宽度/滚动速度计算，长弹幕不会被下一条压住；字体仍是 `PingFang SC`，Windows 缺字体时由播放器回退。
- 礼物/SC/舰长在 Canvas 与 ASS 都以“用户名：内容”加粗/独立样式显示。

### 17.5 仍存在的风险

1. 登录 token 的 `-352` 已修复；若 B 站未来调整 WBI 算法，仍需更新 `wbi_mixin_key`，失败时自动退回匿名。
2. 未保存 B 站原始 JSON，无法事后还原 uid/勋章/价格等字段；若要“完全一样”需扩展 JSONL schema。
3. `USER_TOAST_MSG`、`SUPER_CHAT_MESSAGE_DELETE` 等非聊天事件仍未解析；聊天、礼物、SC、舰长四类已覆盖。
4. 崩溃恢复片段的弹幕路径未写入 manifest；极端崩溃可能只有视频没有弹幕。
5. 前端 Canvas 有界队列，极端爆发会丢显示，不丢落盘。

### 17.6 结论

- **不会因为 UI 限流、flush 饥饿、分割、合并而丢 JSONL**；正常停止时 ASS 与 JSONL 条数一致。
- **无法保证与 B 站下发完全一致**：匿名流本身被降采样，且 JSONL 只保存五字段。
- **有 Cookie 时优先登录 token，匿名路径不注入 Cookie**；`-352` 已由 WBI 签名修正解决，登录/匿名数量差来自平台对匿名的降采样。

## 18. 2026-11-13 根因修正与合并登记

### 18.1 `-352` 的真正原因：WBI mixin key 取了 64 位

`src-tauri/src/danmaku.rs:589 wbi_mixin_key` 原先用 `MIXIN_KEY_ENC_TAB` 重排 64 位原始 key 后，把 **64 位全部**作为 mixin key。B 站算法只取**前 32 位**：

```rust
// 混入密钥只取前 32 位；取满 64 位会算出错误的 w_rid，接口固定返回 -352。
let mixin: String = MIXIN_KEY_ENC_TAB
    .iter()
    .map(|idx| raw.as_bytes()[*idx] as char)
    .take(32)
    .collect();
```

证据链：

| 请求 | w_rid 依据 | getDanmuInfo |
| --- | --- | --- |
| 修复前 Rust 探针 | 64 位 mixin（`ea1db124…cd341`） | `code=-352 message="-352"` |
| 同参数 Node 探针 | 32 位 mixin | HTTP 200，`code=0`，token 260 |
| 修复后 Rust 探针 | 32 位 mixin | `code=0`，token 260 |

- 修复前把 Rust 生成的签名 URL 拿到 curl/Node 重放，同样 `-352`，证明问题在签名本身，不在 reqwest 的 TLS/header。
- 加 `Origin`、`web_location=444.8`、buvid3/buvid4 都只是旁路变量；加不加都能过，唯一的必要修正是 mixin 截断。
- 影响范围：登录态与匿名态共用 `sign_url`，所以 Windows / macOS 双端、任何账号都会固定 `-352`，与 Cookie 是否有效无关。
- 修复后 `fetch_session` 的登录分支能拿到 token，auth body 的 uid/buvid 来自同一 Cookie 身份；匿名分支仍用 `get_json_anon`，不注入 Cookie。

### 18.2 合并录像登记为可挂弹幕的录像

- `src-tauri/src/commands.rs:1412 merge_danmaku_files` 返回合并后的 JSONL 路径（`Option<PathBuf>`）。
- 两个合并命令在视频合并成功后调用 `register_merged_session`（`commands.rs:1363`）：
  - `status=finished`、`reason=merge`、`post_mode=source`、`post_state=done`；
  - `file_path/file_size` 指向合并后的 mp4，`duration_ms` 为各段时长之和；
  - `danmaku_path` 指向合并 JSONL，`danmaku_count` 由 `count_lines` 统计非空行；
  - `db.create_session` 同步 `media_file`，媒体库详情可直接展示主文件与弹幕轨。
- `room_merge_sessions` 会过滤 `reason=merge` 的会话，避免合并产物被再次整房合并。
- 合并失败或登记失败只 `warn`，不阻断视频合并结果。

### 18.3 媒体库弹幕轨回放

- 新 Tauri 命令 `media_danmaku(session_id)`（`commands.rs:2081`）读取该会话 JSONL，解析 `t/k/u/c/col`，跳过空内容，按 `offsetMs` 排序后返回 `Vec<DanmakuMessage>`。
- `MediaItem` 新增 `danmaku_path`，媒体库详情抽屉新增「弹幕轨」行，可定位 JSONL 文件，并显示条数/无内容。
- 内置播放器复用 `DanmakuCanvas`：`Player` 新增 `onPositionChange`，播放时把当前视频位置传给 Canvas；Canvas 支持 `messages + positionMs` 回放模式，按播放位置入队，seek 时清空并重定位。直播路径仍只依赖 `roomId` 订阅实时事件，两种模式互不影响。
- 弹幕开关只在有弹幕轨时出现；没有 JSONL 的录像行为与旧版一致。
