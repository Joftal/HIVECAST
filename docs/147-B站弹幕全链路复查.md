## 3. 连接与鉴权

### 3.1 实际链路

```text
room_init(room_key)
  → 真实 room_id
  → getDanmuInfo（WBI 签名，失败 -352）
  → getConf（免签名兜底）
  → token + host_server_list
  → wss://{host}:{wss_port}/sub
  → Op=7 auth
  → Op=8 code=0
  → Op=5 消息 / Op=2 心跳 30s
```

### 3.2 本次修复：弹幕 REST 不再注入登录 Cookie

`src/platform/http.rs` 的共享 `send` 会给所有请求自动挂本地 Cookie；弹幕 REST 也走了这条路。  
真实环境里 `getDanmuInfo` 带 Cookie 更容易被风控（`-352`），而 WS 握手本身并不带 Cookie，两边不一致。

修复：

- `src/platform/http.rs:215` 新增 `send_anon`，`send_inner(request, url, inject_cookie)` 统一实现；
- `src/platform/http.rs:288` 新增 `get_json_anon`；
- `src/danmaku.rs` 的 `room_init` / `getDanmuInfo` / `getConf` / `nav` 全部改用 `get_json_anon`。

修复前真机日志：

```text
getDanmuInfo 返回空数据（code=-352 -352）
弹幕 WS 已连接
WebSocket protocol error: Connection reset without closing handshake
```

修复后：

```text
getDanmuInfo 不可用，已退回 getConf primary_err=... -352
弹幕 WS 已连接 url=wss://zj-cn-live-comet.chat.bilibili.com/sub
弹幕认证回复 code=0
```

> `-352` 仍会出现：这是当前出口 IP 对 `getDanmuInfo` 的风控，不是 Cookie 失效。  
> 兜底 `getConf` 的 token 可以正常认证，所以不再把“主接口失败”当成弹幕失败。

### 3.3 认证 body（与 docs/133 旧文不同）

`src/danmaku.rs:914` 实际发送：

```json
{"uid":0,"buvid":"","roomid":<真实room_id>,"protover":3,"platform":"web","type":2,"key":"<token>"}
```

- 不发送 Cookie；
- `uid=0`、`buvid=""`：匿名身份；
- `platform="web"`，不是旧文档写的 `danmuji`；
- `protover=3` 表示接受 brotli 压缩。

匿名身份不影响公开弹幕、礼物、SC、舰长广播；本次真实录制与观看都使用匿名 WS。

## 4. 收包、心跳与假死

### 4.1 协议

16 字节大端头：

```text
packet_len u32 | header_len u16(=16) | protover u16 | operation u32 | sequence u32(=1)
```

- `protover=0`：明文 JSON；
- `protover=2`：zlib，解压后可能是多个完整包；
- `protover=3`：brotli，同样递归拆包；
- `MAX_DEPTH=3` 防止压缩炸弹/递归异常。

### 4.2 心跳与假死

- 每 30 秒发 Op=2 心跳（body `[object Object]`）。
- `src/danmaku.rs:43` `IDLE_TIMEOUT=90s`；`run_once` 每 15 秒检查一次 `last_rx`。
- 90 秒没有收到任何 WS 事件 → 返回 Err，由 `run_room` 重连。
- 真实 90 秒探测中曾在约 72 秒收到 `Connection reset without closing handshake`；正式循环会把它当 Err 重连，不会永久挂住。

### 4.3 重连退避

- 1s → 2s → 4s → ... → 30s；
- 每次再加 0–400ms jitter（`src/danmaku.rs:770` `retry_delay`），避免多房间同时重连；
- token 连续失败 5 次才丢弃并重新取 token；
- 成功认证会重置 backoff。

## 5. 消息解析

### 5.1 当前保留的类型

| cmd | kind | 关键字段 | 文本 |
| --- | --- | --- | --- |
| `DANMU_MSG` | chat | `info[1]`、`info[2][1]`、`info[0][3]` | 原文 |
| `SEND_GIFT` | gift | `data.giftName`、`num`、`uname` | `赠送 {gift} × {num}` |
| `SEND_GIFT_V2` | gift | `data.pb` protobuf | 同上 |
| `SUPER_CHAT_MESSAGE` | super_chat | `data.message`、`price`、`user_info.uname` | `[{price} 元] {text}` |
| `GUARD_BUY` | guard | `data.gift_name`、`num`、`username` | `开通了 {gift} × {num}` |

其他 cmd（`INTERACT_WORD_V2`、`ENTRY_EFFECT`、`ONLINE_RANK_*`、`WATCHED_CHANGE`、`LIKE_INFO_*` 等）直接丢弃，不落盘、不渲染。

### 5.2 SEND_GIFT_V2（本次新增）

真实直播礼物已经不是旧 `SEND_GIFT`，而是：

```json
{"cmd":"SEND_GIFT_V2","data":{"pb":"<base64 protobuf>"}}
```

`src/danmaku.rs:1113` `parse_gift_v2`：

1. base64 解码 `data.pb`；
2. 顶层字段 2 = 用户名；
3. 顶层字段 10 = GiftInfo；
4. GiftInfo 字段 2 = 礼物名，字段 3 = 数量；
5. 缺失时回退 JSON 的 `uname/giftName/gift_name/num`。

真实样本（2026-11-12 房间 545068）：

```text
uid=6549696 uname=橘子入雨 gift=人气票 num=1 coin_type=gold
```

单测 `parses_gift_v2_protobuf` 使用这段真实 base64，断言解析为：

```text
kind=gift user=橘子入雨 content=赠送 人气票 × 1
```

## 6. JSONL 落盘

### 6.1 格式

`src/danmaku.rs` `RecordWriter` 写：

```json
{"t":265062,"k":"chat","u":"绪方理奈-w-","c":"[空之轨迹1st表情包_对不起]","col":16777215}
```

| 字段 | 实际含义 |
| --- | --- |
| `t` | 相对 writer 启动的毫秒偏移，不是服务端时间戳 |
| `k` | chat / gift / super_chat / guard |
| `u` | 昵称，不是 UID |
| `c` | 文本 |
| `col` | 十进制颜色，B 站聊天几乎都是 16777215 |

### 6.2 写入策略

- 每 50 条或 1 秒 flush；
- 每 200ms 批次 flush 时额外调用 `flush_pending()`，慢速房间最后一条最多滞留 200ms；
- 先 `fan_out` 给 RecordWriter，再做 200 条/秒的 UI 限流；
- 空文件在 `finish` 时删除；
- 录制中 DB 的 `danmaku_count` 仍是 0，收尾 `detach_record` 才写真实条数。  
  这是“文件已经 121 行、DB 还显示 0”的原因，不是丢数据。

### 6.3 本次真实结果

| 场次 | 房间 | 时长 | 视频大小 | JSONL 条数 | ASS |
| --- | --- | --- | --- | --- | --- |
| `d2412a20` | 7734200 | 32m06s | 944,347,494 B | 121 | 121 行 |
| `cac108c8` | 5055636 | 14m04s | 232,072,377 B | 5 | 5 行 |
| `e60aa6a2` + `58526ec9` | 5055636 | 4m + 16m03s | 29,272,073 + 182,671,335 B | 0 + 1 | clip01 1 行 |

## 7. 分割录制：每段独立弹幕

### 7.1 原缺陷

分割录制整场只挂一个 RecordWriter，后续 clip 的 `danmaku_path` 固定写 `None`、`danmaku_count` 固定 0；ASS 只为第一段生成。  
默认 `split_max_duration_sec=0`、`split_max_size_mb=0` 时不会触发；开启时长/大小/标题切分后必现。

### 7.2 修复

`src/recorder.rs:2604-2685`：

1. 收尾时记录 writer 的 `started_epoch_ms()`；
2. 把整场 JSONL 复制成 `.split-src`，避免原地切第一段后下一段读到已截断文件；
3. 按每个 clip 的 `started_at/ended_at` 计算相对 writer 的区间；
4. 用 `src/postprocess.rs:255` `slice_danmaku` 切出每段 JSONL，并把 `t` 重设为段内偏移；
5. 第一段切片成功才删除母 JSONL；失败保留母文件；
6. 每个 clip session 写自己的 `danmaku_path/danmaku_count`；
7. `src/recorder.rs:2831` 对每段分别 `danmaku_to_ass`。

### 7.3 真实结果

本次 5055636 在 19:03 因标题变化触发切分：

- `e60aa6a2`（clip 0，4 分钟）：0 条，无 JSONL；
- `58526ec9`（clip 1，16 分钟）：1 条，`...19-03-54.clip01.jsonl` + `...clip01.ass`，ASS 有一行「很多好东西」。

说明每段弹幕不再只挂在首段。

### 7.4 残余限制

- `split_manifest` 还没有记录每段 `danmaku_path`；崩溃恢复后的片段仍可能没有弹幕文件；
- 母 JSONL 在极端崩溃（切片前进程被杀）时可能残留，但不会丢源文件。

## 13. 覆盖边界与已知限制

1. **没有抓到本次实时 SC / 舰长**：真实房间采样窗口内没有这两种事件。  
   解析与 ASS 由单测覆盖，未做真实支付场景验收。
2. **SEND_GIFT_V2 只在探测样本中验证**：本次录制 121 条弹幕未出现礼物；解析器使用 2026-11-12 的真实礼物 pb 单测。
3. **匿名 WS**：不发送 Cookie，也不发送真实 uid/buvid；公开消息可用。  
   如果未来需要“登录用户专属弹幕/进场身份”，再单独设计，不能直接把网页 Cookie 塞进 WS。
4. **getDanmuInfo 的 -352**：当前出口 IP 常态触发，依赖 `getConf` 兜底；若两个接口同时失败，弹幕会重试并记录错误，视频录制不受影响。
5. **崩溃恢复的分割片段**：`split_manifest` 尚未保存每段 `danmaku_path`，恢复后的片段可能没有弹幕；正常收尾路径已覆盖。
6. **观看页实时渲染不读录制过滤开关**：这是产品选择，避免用户关掉礼物落盘后观看页也看不到礼物。
