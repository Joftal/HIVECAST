## 0. 结论先行

1. **v1 的核心不是“多了一个转 MP4 开关”，而是把“录制成品”和“后处理产物”拆成了两个文件。** 录制器只负责封出源封装母带；转封装、自定义命令都是派生文件，失败不影响母带，源路径永远不被派生路径覆盖。
2. **当前实现的安全顺序比三个参考项目都严格**：临时文件 → ffprobe 校验 → fsync → rename → DB 提交 → 才允许把源移入回收站。biliLive-tools 是转换成功立即删源且 DB 仍指原文件；bililive-go 的内置 Pipeline 顺序正确，但自定义命令退出 0 就删源；streamlink 则完全不删。
3. **功能完整度要分两个口径看**：
   - 按本项目 v1 目标：约 **85%**。source / convert / custom 三条主路径、临时文件、校验、DB、回收站、清单恢复、设置页、媒体库双文件、手动转封装都已落地；缺的是重试/取消、并发与磁盘预检、自定义命令真实平台验收、派生文件单独播放等边界能力。
   - 按四个项目功能并集：约 **45%–55%**。HIVECAST 目前只做“录制 + 后处理”，没有上传、压制、字幕烧录、封面、Webhook、云同步、预设管理等生态功能。
4. **最大的技术债不是“少功能”，而是“两条手动/自动链路并存”**：自动后处理走新的 `post.rs`，媒体库手动“转 MP4”仍走旧的 `postprocess::remux`，后者没有 ffprobe、回收站和失败重试。下一步应优先把手动转封装收编到统一实现，而不是继续加模式。
5. **不建议照抄任何一个参考项目的后处理模型。** 可以学 bililive-go 的阶段化和“全部成功再删源”，学 biliLive-tools 的回收站/输出占用检查/引用计数思路，学 streamlink 的抓流与后处理解耦；但不能学 shell 自定义命令、立即删源、单路径覆盖、双转换链路。

- **默认不再自动出 MP4**。新安装默认 `source`：FLV 源得到 `.flv`，HLS/HTTP-TS 得到 `.ts`，DASH 得到 `.mp4`，FLV + HEVC/AV1 得到 `.mkv`，AudioOnly 得到 `.m4a`/`.mka`。
- 设置页出现三张互斥卡片：保留源封装 / 转封装 / 自定义 FFmpeg 命令。
- `convert` 可以选择 MP4/MKV/TS，并显式选择“转换成功后把源移到回收站”；默认不删。
- `custom` 是完整的 ffmpeg argv 模板，必须含 `{input}` 和 `{output}`，不经过 shell，源永不自动删。
- 媒体库卡片显示主文件和源封装两行；源还在时可以点击定位，源已删时显示“源已删”。
- 手动“转 MP4”现在会保留母带，并把主文件切到新 mp4，媒体库立即反映；但播放器里正在放的那条流不会自动切到新文件。

## 2. 当前工作流程

### 2.1 开录

1. 解析实际线路，拿到 `StreamFormat` + `Codec`，并用当前设置快照一份 `PostConfig`。中途改设置只影响下一场。
2. 由 `post::source_extension` 决定母带扩展名，不再固定 `.mp4`。
3. 用原子占位创建母带路径，DB 同时写 `source_path=占位路径`、`post_mode`、`post_state=recording`。
4. ffmpeg 实际仍写同 stem 的 `.partNNNN.ts` 分片；母带是收尾时合并出来的，不是录制期间直接写的。

### 2.2 收尾

```
停止 ffmpeg
  → 按分片规划 clip
  → 每段合并成源封装母带（失败退化为字节拼接 .ts）
  → 对母带执行 post::run
       source  : 只 ffprobe 校验
       convert : 临时文件 → -map 0 -c copy → ffprobe → fsync → rename
       custom  : 模板分词 → 替换 {input}/{output} → 直接执行 ffmpeg → 校验 → rename
  → DB 事务提交 file_path / source_path / post_mode / post_state
  → 若 convert + delete_source：把源移入回收站，成功后 source_deleted=1
  → 全部片段与 DB 成功后清单标 completed 并删除
```

关键顺序：

- **先有母带，才跑后处理。** 母带合并失败不会进入转换。
- **先校验，再 rename。** ffmpeg 退出码 0 不等于产物完整；优先 ffprobe，缺 ffprobe 时用 ffmpeg 读 1 秒。
- **先 DB 提交，再删源。** 删除失败只 WARN，源保留，状态仍是 `done`；不会把“删源失败”误报成“转换失败”。
- **失败不丢源。** 转换失败、超时、校验失败、rename 失败都会删临时文件，返回源路径 + `failed` + `post_error`。
- **已 `failed` 的段不会在下次启动自动重跑。** 恢复只补缺失的源/最终文件，保留失败状态，避免无限重试。

### 2.3 三种模式

| 模式 | 产物 | 删源 | 自定义命令 | 适用 |
| --- | --- | --- | --- | --- |
| `source`（默认） | 母带本身 | 不动 | 不执行 | 想保留直播源封装，后续手动处理 |
| `convert` | 母带 + MP4/MKV/TS | 仅显式开启，且转换成功、DB 提交后 | 不执行 | 想直接得到剪辑软件可用的容器 |
| `custom` | 母带 + 自定义输出 | **永不自动删** | 执行 ffmpeg argv | 转码、压制、裁切等高级处理 |

互斥规则：切到非 `convert` 时设置页会把 `postDeleteSource` 置回 false；`custom` 不产生 `delete_source`，即使 DB 里误留 true 也不会删。

### 2.4 手动转封装

媒体库抽屉的“转 MP4”仍是旧链路：

1. 调 `postprocess::remux` 生成同目录 mp4，保留源。
2. 成功后 `source_path = session.source_path ?? session.file_path`。
3. 把 `file_path` 切到新 mp4，写 `convert/done/source_deleted=false`。
4. 前端用返回的 `PostResult` 立即更新卡片和抽屉，再整体刷新。

这条链路解决了“手动产物媒体库看不见”的问题，但没有接统一的 ffprobe、回收站、失败重试；这是当前最明显的一致性缺口。

## 3. 四方模型对比

### 3.1 真实模型

| 维度 | bililive-go | streamlink | biliLive-tools | HIVECAST v1 |
| --- | --- | --- | --- | --- |
| 抓流层职责 | 拉流并按源写 FLV/TS/AAC | 只把流字节写入文件 | 拉流并固定 `-c copy` 到 ts/m4s/flv | 拉流 + TS 分片 |
| 成品模型 | 源对应封装，录完可进 Pipeline | 用户指定，无后处理概念 | 录制层直接出 ts/m4s/flv，可选立即转 MP4 | **源封装母带 + 派生文件** |
| 后处理入口 | `OnRecordFinished` + 阶段化 Pipeline | 无 | 录制器 `convert2Mp4` + Webhook 转封装（两条） | 收尾时 `post::run` 单入口 |
| 内置转换 | 临时文件 + rename，`-c copy` | 无，交给外部 ffmpeg | 同目录直接输出，`-c copy` | 临时文件 + ffprobe + fsync + rename |
| 删源 | 所有阶段成功统一删；自定义成功即删 | 无 | 录制器 `unlink`；Webhook 可 `trash` | DB 提交后移入回收站，失败保留 |
| 自定义命令 | 有，shell 模板，无超时 | 无 | 无任意命令，只有 ffmpeg `extraOptions` | ffmpeg argv，不走 shell，有超时 |
| 数据模型 | 文件/通知为主 | 无 | 单 `video_file`，转换后常不更新 | 5 个后处理字段，主/源双路径 |
| 崩溃恢复 | 依赖文件系统 | 无 | 弱，无统一后处理状态机 | 清单 v2 + DB 状态 + 文件系统 |
| 扩展生态 | 烧字幕、封面、上传、通知 | 无 | 上传、弹幕压制、Webhook、预设 | 仅录制 + 后处理 |

### 3.3 各项目优缺点

#### bililive-go

**优点**

- 阶段化 Pipeline 是所有参考里最成熟的：修复 FLV、转换、封面、上传等阶段可以组合。
- 内置转换用临时文件 + rename，且**所有阶段都成功后才统一删源**，失败保留现场。
- 平台覆盖广，录制产物与源格式对应。

**缺点**

- 自定义命令走 shell，Linux `sh -c`、Windows `cmd /C`，无超时；失败只打 Debug 日志。
- 自定义命令退出 0 且勾了“转换后删除 FLV”就 `os.Remove`，**不检查输出文件是否存在、是否非空、是否真的是转换产物**。
- 自定义命令一开，内置 Pipeline 全部绕过；一个“上传/发通知”的命令也可能把源删掉。
- 没有“母带 + 派生文件”的双路径模型，媒体库无法同时展示两个产物。

**可学 / 不可学**

- 学：阶段化、全成功再删、临时文件 + rename。
- 不学：shell 模板、成功即删、失败只 Debug、自定义绕过全部阶段。

#### streamlink

**优点**

- 边界最干净：抓流层只负责拿到字节并写文件，容器、后处理、上传都是外部工具的事。
- 不偷偷改扩展名、不偷偷删文件；用户完全掌控输出路径。
- 作为 CLI/库，组合性强，适合被别的工具调用。

**缺点**

- 没有后处理、没有媒体库、没有状态机、没有删除安全语义；普通桌面用户要自己写 ffmpeg 命令。
- 不适合直接作为“桌面应用默认体验”的参考；它证明的是解耦，而不是产品完整度。

**可学 / 不可学**

- 学：抓流与后处理解耦，输出路径由用户负责。
- 不学：把容器选择完全丢给用户；HIVECAST 需要安全默认值。

#### biliLive-tools

**优点**

- 生态最完整：录制、转封装、上传、弹幕压制、Webhook、预设等串成一条工作流。
- 有输出占用检查：目标已存在时按“已完成”复用，避免重复转换，但也可能把用户手工放入的文件当成自己的产物。
- Webhook 链路用系统回收站；fileRef 式多消费者删除标记的收敛思路值得借鉴，但必须允许“保留优先”，不能任一消费者要求删就删。
- 有任务/进度/错误事件，用户可见性比 bililive-go 的自定义命令好。

**缺点**

- 不是“源封装 + 派生文件”模型，而是“录制层固定 `-c copy`，可选录完立即转 MP4 并删源”。
- 录制器链路转换成功后 `fs.unlink` 源，但 DB/历史仍指原文件；重启也不会自愈。
- Webhook 是第二条转换链路，默认删源，覆盖 `rawFilePath`，原路径直接丢失；官方 UI 自己提示两条链路不要同时开。
- 没有任意自定义命令；`extraOptions.split(" ")` 这种“伪自定义”遇到带空格路径会拆坏。
- 转换直接写目标，失败可能留下半截 MP4。

**可学 / 不可学**

- 学：回收站、输出占用检查、fileRef 式删除标记、任务可见性。
- 不学：双链路、单路径覆盖、立即 `unlink`、把 `rawFilePath` 改成转换后路径、按空格拆参数。

#### HIVECAST v1

**优点**

- **产物模型正确**：源封装母带永远保留；派生文件可重做、可删除，不影响母带。
- **顺序正确**：临时文件 → 校验 → fsync → rename → DB 提交 → 回收站；任何一步失败都不丢源。
- **自定义命令安全**：只执行 ffmpeg argv，不走 shell，必须含输入/输出占位符，有超时，源永不自动删。
- **数据一致**：`file_path` 是当前主播放文件，`source_path` 是母带，媒体库能同时展示；手动转封装也会更新 DB。
- **恢复能力**：清单 v2 记录每段源、最终文件、后处理状态；崩溃后优先复用，不重复转换，不把失败误标成功。
- **用户可见**：失败有红色徽标和 `post_error`；源可定位，源删有明确标识。

**缺点**

- 没有 `post_retry` / `post_cancel`；已失败的自动后处理只能重录或手工处理。
- 没有全局任务队列/并发上限；多房间同时收尾会同时跑 ffmpeg。
- 没有转换前磁盘空间预检；转换峰值约“源 + 临时文件”，删源进回收站也不会立即释放空间。
- 自定义模式只有单测/合成 ffmpeg，没有真实平台整场验收。
- 手动转封装仍是旧链路，缺 ffprobe/回收站/重试；与自动链路并存。
- 媒体库不能“分别播放主文件和源文件”，也没有“仅删源”“失败重试”入口。
- 没有上传、压制、字幕烧录、封面、Webhook、云同步等生态功能。
- 母带是容器重封装，不是 bit-exact 原始流；分片仍是 MPEG-TS。

## 5. 影响面与风险

### 5.1 行为与兼容

- **默认行为变化**：从“默认自动 MP4”变成“默认保留源封装”。这是有意的产品决策，不是回归。
- **旧设置不迁移**：`post.auto_remux` 被忽略；新默认 `source`。项目仍在迭代、无外部用户，这是用户明确选择。
- **旧历史不回填**：迁移只加列，不把老 `file_path` 回填到 `source_path`；老会话在媒体库没有“源封装”行。
- **旧清单按 source 恢复**：`version: 1` 的 `remux` 字段被忽略，老清单不会自动转 MP4。
- **降级不兼容**：旧二进制不认识新列；实测旧 bundle 启动报 `no such column: source_path`。升级/降级必须换对应二进制，不能指望热迁移。
- **手动转封装**：只对非 mp4 主文件可用；成功后主文件切 mp4，源保留；播放器当前流不会热切。

### 5.2 存储与性能

- **空间峰值**：转换期间约“源 + 临时文件”两份；转换成功后源进回收站，回收站未清空前仍占磁盘。
- **没有空间预检**：磁盘不足时靠 ffmpeg 失败 + 临时文件清理兜底，用户看到的是 `failed`，不是“还差多少空间”。
- **没有并发上限**：多房间同时收尾会同时跑 ffprobe/ffmpeg；长录像转换可能持续数分钟。
- **自动后处理无进度**：手动转封装有进度事件；自动转换只有最终状态，长录像时用户可能以为卡住。
- **source 模式也校验**：好处是母带不完整会显式失败；代价是极少数容器/时间戳异常的源会被判 `failed`，但文件仍在、仍可播放。

### 5.3 安全边界

- 自定义命令不经过 shell，管道/重定向/变量会被拒绝；但这不等于“任意命令沙箱”——它仍然是本机 ffmpeg 进程，能读写用户有权访问的文件。
- 源删除只发生在 `convert && delete_source && 转换成功 && DB 提交成功` 之后；`custom` 永不自动删。
- 目标文件已存在时不会覆盖源；同名派生文件按 mtime 判断是否本次产物，可能误复用用户手工放入的更新文件（会先 ffprobe 校验）。
- Linux 回收站只移动文件、不写 `.trashinfo`，桌面环境可能无法“还原”。

## 6. 建议的下一步

> 2026-11-08 更新：P0、P1、P2 已全部实现并完成真机验收，见 [81-录制后处理P0-P2修复与验收](81-录制后处理P0-P2修复与验收.md)。以下保留原始建议作为决策记录；P3 仍未做。

### P0：把“失败可恢复”补成闭环

1. 增加 `post_retry` / `post_cancel` / `post_status`，媒体库失败徽标提供“重试”。
2. 把手动“转 MP4”收编到 `post.rs` 的 convert 链路，统一 ffprobe、临时文件、回收站、错误语义；删除旧 `postprocess::remux` 分支。
3. 播放抽屉允许选择“播放主文件 / 播放源封装”，并增加“仅删源”（仅当派生文件校验通过）。

### P1：把“批量收尾”做成可控任务

1. 后处理任务队列，默认并发 1、最多 2；录制优先级高于后处理。
2. 转换前检查 `free >= source_size * 1.15 + 256 MiB`，不足直接失败并给出数字。
3. 自动后处理发进度事件，媒体库显示百分比；退出时能取消并清理临时文件。

### P2：把 custom 从“代码可用”变成“产品可用”

1. 真实平台整场跑一次转码型 custom（不是 `-c copy`），验证超时、无输出、路径含空格/中文/emoji。
2. 失败原因做用户可读映射：未生成输出、容器不识别、编码器缺失、磁盘满、超时。
3. 保留“只执行 ffmpeg、不走 shell、源永不自动删”的边界，不为了表达力放开 shell。

### P3：生态功能按需做，不要复制双链路

- 上传/压制/字幕/封面/Webhook 是另一个产品层，建议在“后处理任务”稳定后单独设计。
- 如果要做，沿用“母带 + 派生 + 多消费者删除标记”的模型；不要学 biliLive-tools 的“录制器转换 + Webhook 转换”两条链路。
- 删除标记要允许“任一消费者要求保留”覆盖“删除”，不能像 biliLive-tools 那样任一消费者要求删就毒化整个文件。

## 8. 一句话总结

HIVECAST 的录制后处理 v1 已经在“产物模型、失败安全、数据一致性”上超过三个参考项目的对应实现，但还停留在“单机、单入口、核心闭环”的阶段；它现在是一个可靠的后处理内核，还不是一个完整的媒体工作流产品。下一步最值得做的是重试/取消、统一手动链路、任务队列与磁盘预检，而不是继续堆模式或照抄上传/Webhook 生态。
