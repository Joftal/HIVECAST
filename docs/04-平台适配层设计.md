# 04 · 平台适配层设计

> 参考实现：`bililive-go/src/live/`（适配器 + 注册表 + WrappedLive 装饰器）、`streamlink/src/streamlink/plugins/`（matcher + 权重）、`biliLive-tools/packages/StreamGet/`（`PlatformParser` 契约 + 错误码，见 `17`）。
> 本文定义 HIVECAST 的平台层契约。所有平台适配器都只实现这一层，**不碰录制、不碰 UI、不碰数据库**。
> 2026-11 复核：实际实现已在 `src-tauri/src/platform/`，错误模型为 7 类；四平台取流参数、画质表与可录性门禁见 `130`。

## 1. 分层与依赖方向

```text
        ┌──────────────────────────────────────────┐
        │ UI / IPC                                  │
        ├──────────────────────────────────────────┤
        │ 应用服务：房间管理、录制编排、任务、配置    │
        ├──────────────────────────────────────────┤
        │ 领域：LiveRoom / Session / Recording / Job │
        ├──────────────────────────────────────────┤
        │ 平台适配层（本文）                          │
        │   registry → matcher → adapter → candidate │
        ├──────────────────────────────────────────┤
        │ 基础设施：HTTP(带 cookie/代理/限流)、WS、   │
        │           文件、日志、时钟                   │
        └──────────────────────────────────────────┘
```

**硬约束**：适配层返回"描述"，不返回"已打开的连接"。打开连接是录制引擎的事。这样才能做到"只监听不录制"、"只列清晰度不下载"。

## 2. 核心类型

以下为语言无关的接口草案（Rust 语法示意，Go/TS 同理）。

```rust
/// 平台标识，稳定且用于配置键，如 "bilibili" / "douyu" / "huya"
type PlatformId = &'static str;

/// 房间引用：匹配阶段的产物
struct RoomRef {
    platform: PlatformId,
    /// 平台内稳定标识：B站真实 room_id、斗鱼 room_id、虎牙 room_id
    room_key: String,
    /// 规范化 URL（去掉追踪参数）
    canonical_url: String,
    /// 用户原始输入（用于展示与调试）
    input_url: String,
}

/// 房间静态信息（可缓存，随开播状态变化）
struct RoomInfo {
    host_name: String,        // 主播名
    room_name: String,        // 房间标题
    avatar_url: Option<String>,
    cover_url: Option<String>,
    area_name: Option<String>,// 分区
    is_live: bool,
    started_at: Option<Timestamp>,
    /// 平台侧额外字段（原样透传给 UI）
    extra: JsonMap,
}

/// 流候选
struct StreamCandidate {
    /// 稳定 id，用于"记住用户上次选的档位"
    id: String,               // 例如 "qn10000-hls-avc"
    /// 展示名，平台原名优先："原画"、"蓝光4M"、"1080p60"
    name: String,
    /// 归一化权重，越大越好（见 §4）
    weight: f64,
    format: StreamFormat,     // Flv | Hls | Dash | HttpTs | AudioOnly
    codec: Option<Codec>,     // H264 | H265 | AV1 | AAC | Unknown
    width: Option<u32>,
    height: Option<u32>,
    fps: Option<f32>,
    bitrate_kbps: Option<u32>,
    /// 直接可用的地址；懒解析平台为 None
    url: Option<String>,
    /// 下载时需要的请求头（Referer/UA/Cookie）
    headers: HeaderMap,
    /// 平台附加属性，供 UI 分组与高级选择（协议/编码/索引）
    attrs: BTreeMap<String, String>,
}

/// 适配器
#[async_trait]
trait PlatformAdapter: Send + Sync {
    fn id(&self) -> PlatformId;
    fn display_name(&self) -> &'static str;

    /// 解析用户输入 → RoomRef；不匹配返回 None
    async fn resolve(&self, input: &Url) -> Result<Option<RoomRef>, PlatformError>;

    /// 房间信息。允许被装饰器缓存/限流。
    async fn room_info(&self, room: &RoomRef, ctx: &AuthCtx) -> Result<RoomInfo, PlatformError>;

    /// 流候选。允许懒解析（url 为 None）。
    async fn stream_candidates(&self, room: &RoomRef, ctx: &AuthCtx)
        -> Result<Vec<StreamCandidate>, PlatformError>;

    /// 懒解析：把某个候选补全为可下载地址
    async fn resolve_candidate(&self, room: &RoomRef, cand: &StreamCandidate, ctx: &AuthCtx)
        -> Result<StreamCandidate, PlatformError> {
        Ok(cand.clone()) // 默认已解析
    }

    /// 平台对下载器的额外要求（如必须带 cookie、必须走某 CDN）
    fn download_requirements(&self, cand: &StreamCandidate) -> DownloadRequirements {
        DownloadRequirements::from_headers(&cand.headers)
    }
}
```

### 2.1 为什么 `resolve` 与 `room_info` 分开

- `resolve` 必须**纯本地**（正则/域名），这样"添加房间"操作零网络请求即可入库并立即显示占位卡片（对应 bililive-go 的 `InitializingLive`）。
- `room_info` 才发请求，可被缓存、可失败、可重试。

### 2.2 为什么候选要允许"懒解析"

- B 站：一次 `getRoomPlayInfo` 能拿到全部档位，但**非当前 qn 的直链需要再请求**（bililive-go 用 `IsPlaceHolder` 标记）。
- SOOP：每档清晰度要单独申请凭证，全量解析 = N 倍请求量 + 触发风控。
- 结论：接口必须支持"先给元信息，选中后再解析"。

### 2.3 与 StreamGet 契约的字段对照

biliLive-tools 的 `packages/StreamGet/src/types.ts` 是三个参考项目里**唯一一份已经跑在多平台生产环境上的取流契约**，字段取舍值得逐条对照（细节见 `17-参考项目-biliLive-tools-架构解析` §5.1）。映射关系：

| StreamGet | HIVECAST | 差异与取舍 |
| --- | --- | --- |
| `LiveInfo.roomId` | `RoomRef.room_key` | 同义。我们用 `room_key` 强调"平台内稳定标识" |
| `LiveInfo.platform` | `PlatformId` | 同义 |
| `LiveInfo.living` | `RoomInfo.is_live` | 同义 |
| `LiveInfo.title` / `owner` | `RoomInfo.room_name` / `host_name` | 命名不同 |
| `LiveInfo.avatar` / `cover` | `avatar_url` / `cover_url` | 同义 |
| `LiveInfo.liveStartTime` | `started_at` | 他们是毫秒时间戳，我们用 `Timestamp` |
| `LiveInfo.raw` | `RoomInfo.extra` | **两者都要**：`raw` 存原始响应（排障 dump），`extra` 存给 UI 用的结构化附加字段 |
| `StreamInfo.url` | `StreamCandidate.url` | 我们是 `Option`（支持懒解析），他们是必填 |
| `StreamInfo.quality`（平台原值） | `StreamCandidate.attrs["platform_quality"]` | 平台原值放 `attrs`，不占一级字段 |
| `StreamInfo.qualityDesc` | `StreamCandidate.name` | 同义（UI 展示名） |
| `StreamInfo.format` | `StreamCandidate.format` | 他们是字符串 `'flv' / 'ts' / 'fmp4'`，我们用枚举 |
| `StreamInfo[key: string]: any` | `StreamCandidate.attrs` | 他们都塞在对象上；我们收敛进 `attrs`，避免类型逃逸 |
| `SourceInfo{name, streams}` | **`StreamGroup`（新增一层）** | ⚠️ 关键差异，见下 |

**必须采纳的一点：流候选按"线路（CDN）"分组。** StreamGet 的 `getStreams()` 返回 `SourceInfo[]`，每个 source 是一组线路（B 站是"主线/备线1/备线2"），组内再按清晰度排列。HIVECAST 的 `stream_candidates()` 若只返回扁平列表，就丢掉了两件事：

1. **备线切换**——主线 403/超时后能立刻在同一档清晰度上换线路，这是 biliLive-tools 抗断流的核心手段之一；
2. **UI 表达**——用户能选"优先备线 2"（某些 CDN 对自己的网络更快）。

建议在 §2 的类型里补：

```rust
struct StreamGroup {
    /// 线路名："主线" / "备线1" / "线路3"
    name: String,
    /// 线路优先级，越小越优先
    priority: u8,
    candidates: Vec<StreamCandidate>,
}
```

并把 `stream_candidates()` 的返回改为 `Vec<StreamGroup>`。§4 的权重只用于**组内**排序，组间选择由"线路优先级 + 上次成功线路"决定。

## 3. 注册与匹配

```rust
struct Matcher {
    pattern: Regex,          // 必须带命名捕获或由适配器自行解析
    priority: i32,           // 越大越先尝试
    platform: PlatformId,
}
```

规则：

1. 全局按 `priority` 降序排列，逐个尝试；第一个返回 `Some(RoomRef)` 的胜出。
2. 同一平台可以有多个 matcher（主站、短链、移动端、白名单路径）。
3. 匹配前先做**短链展开**（HEAD 跟随重定向，参考 streamlink `resolve_url`），但要有超时与缓存。
4. 匹配失败要给出可操作错误："暂不支持该平台" vs "URL 格式不对（缺少房间号）"。

内置 matcher 示例：

| 平台 | 正则 | 备注 |
| --- | --- | --- |
| bilibili | `^https?://live\.bilibili\.com/(?P<room>\d+)` | 也有 `/blanc/123`、`/h5/123` 形态 |
| bilibili 短链 | `^https?://b23\.tv/\w+` | 需展开 |
| douyu | `^https?://(www\.)?douyu\.com/(topic/)?(?P<room>\d+)` | 也支持 `?rid=` |
| huya | `^https?://(www\.)?huya\.com/(?P<room>[\w-]+)` | 房间号可能是别名 |
| douyin | `^https?://(live\.douyin\.com/(?P<room>\d+)\|v\.douyin\.com/\w+)` | 短链需展开 |
| kuaishou | `^https?://live\.kuaishou\.com/u/(?P<room>[\w-]+)` | — |

## 4. 清晰度权重模型

参考 streamlink 的 `stream_weight`，但增加"平台显式权重"通道。

```text
weight = base(分辨率) + fps_bonus + bitrate_bonus + platform_bonus
```

| 项 | 规则 |
| --- | --- |
| base | 有分辨率：`width * height` 归一（如 1080p = 1920*1080）；无分辨率：用名称解析出的 `p` 值 × 1000 |
| fps_bonus | ≥50fps 加 5%，≥60fps 加 8% |
| bitrate_bonus | 同分辨率下按码率微调（±3% 以内），避免码率主导排序 |
| platform_bonus | 平台自定义（B 站"原画" > "蓝光"；斗鱼"原画" > "超清"） |

**保留原名**：UI 显示 `name`，排序用 `weight`。二者不可互相替代。

补充约定：

- `AudioOnly` 候选权重固定为 `0.1`，单独分组，不与视频混排。
- `best`/`worst` 由权重最大/最小动态生成（参考 streamlink 的同义词机制）。
- 用户偏好可以是"候选列表"（如 `["原画", "蓝光", "best"]`），逐个回退，而不是单一档位。

## 5. 错误模型

```rust
enum PlatformError {
    RoomNotFound,        // 房间不存在/已注销
    RoomClosed,          // 房间被封禁/关闭（可展示提示，不重试）
    Offline,             // 未开播（正常状态，不是错误）
    NeedAuth { hint },   // 需要登录/扫码/过期
    RateLimited { retry_after },
    ToolMissing { tool },// 依赖的外部工具未就绪
    Unsupported,         // 平台改版/接口不可用
    Network(io::Error),
    Parse(String),       // 结构变更，需上报
}
```

调度语义（**必须写进代码**）：

| 错误 | 监听器行为 |
| --- | --- |
| `Offline` | 正常，按 interval 继续轮询 |
| `RoomNotFound/RoomClosed` | 标记房间为"不可用"，降低轮询频率（如 10× interval），UI 显示原因 |
| `NeedAuth` | 暂停该平台所有房间轮询，提示登录；登录后恢复 |
| `RateLimited` | 全局按 `retry_after` 退避该平台 |
| `ToolMissing` | 每 2s 轮询工具状态，不发平台请求 |
| `Network` | 指数退避（1s→2s→4s…上限 5min），成功清零 |
| `Parse` | 记录一次"疑似改版"，连续 N 次后告警 |

**与 StreamGet 的对应**（便于直接对照它的处理逻辑）：`RoomNotFound` ↔ `RoomNotFoundError(ROOM_NOT_FOUND)`、`Offline` ↔ `NotLivingError(NOT_LIVING)`、`Unsupported` ↔ `UnsupportedPlatformError(UNSUPPORTED_PLATFORM)`、`Network` ↔ `NetworkError(NETWORK_ERROR)`、`Parse` ↔ `ParseError(PARSE_ERROR)`。它没有 `RoomClosed`/`NeedAuth`/`RateLimited`/`ToolMissing` 四个状态，而这四个恰恰是桌面端最需要给用户解释的——保留我们的全集。

## 6. 请求治理（装饰器）

对每个 `(platform, room_key)` 组合包一层：

```text
RateLimiter(platform)          // 令牌桶：最小访问间隔 + 最大并发
  └─ RoomMutex(room_key)       // 同房间串行
      └─ Cache(TTL=interval)   // 同轮次共享结果
          └─ Backoff           // 失败退避 + 抖动
              └─ Adapter
```

参数建议（来自 bililive-go 实测值）：

- 默认轮询 `interval = 30s`，抖动 `+0..3s`（避免同秒风暴）。
- 失败退避 2 的幂，上限 `5min`，成功即清零。
- 平台最小访问间隔默认 `1s`，B 站/斗鱼建议 `2s`，抖音建议 `3s`。
- 同平台并发上限：B 站 4、斗鱼 2、抖音 1（可按实测调整）。
- "工具未就绪"轮询间隔 `2s`，**不消耗平台配额**。

> bililive-go 里这套逻辑在 `WrappedLive`，注释明确写了"同房间 requestMu 串行化"和"waiter 队列共享同一次请求结果"。桌面端同时挂 50 个房间时，这两条决定了会不会被封。

## 7. 认证与 Cookie

### 7.1 数据模型

```text
Account {
  platform, account_id, display_name,
  cookies: Map<domain, Map<name, value>>,
  tokens: Map<name, {value, expires_at}>,
  device_id: Option<String>,     // 斗鱼 dy_did 等，必须固定
  updated_at, status(valid|expired|unknown)
}
```

- **按域隔离**：B 站 `SESSDATA` 只对 `*.bilibili.com` 生效；斗鱼 `LTP0` 属于 `passport.douyu.com`，不能塞进主站 cookie。
- **敏感字段不出进程**：`LTP0`、`dy_did` 等长期凭证只存本地库，绝不下发给前端（bililive-go 用 `json:"-"` 做到了这点）。
- **设备号固定**：斗鱼签名用的 `did` 一旦确定就不要轮换，否则每次续期都像"新设备"。

### 7.2 登录方式优先级

1. **扫码登录**（B 站、斗鱼）：后端代理生成二维码 → 前端展示 → 轮询状态 → 成功后写库。
2. **内嵌 WebView 登录**（通用兜底）：用户在内嵌浏览器完成登录，应用从 cookie store 提取。
3. **手动粘贴 Cookie**（高级）：必须校验有效性并给出明确错误。

B 站扫码接口（`bililive-go/src/servers/handler.go:4054`）：

- 生成：`GET https://passport.bilibili.com/x/passport-login/web/qrcode/generate` → `data.url`（二维码内容）、`data.qrcode_key`
- 轮询：`GET https://passport.bilibili.com/x/passport-login/web/qrcode/poll?qrcode_key=...`
- **坑**：登录成功时凭证在响应头 `Set-Cookie` 里，`data.url` 只是跳转地址，光解析 URL 拼不出 `SESSDATA`。需要把 `Set-Cookie` 与 URL query 合并。
- 需要保存的字段：`SESSDATA`、`bili_jct`、`DedeUserID`、`DedeUserID__ckMd5`、`sid`（`buvid`/`_uuid` 等埋点字段不要存）。

### 7.3 续期

- 斗鱼：`LTP0` 长期凭证 → `safeAuth` 换票（bililive-go 有后台 keeper，约每 3 天一轮），续期失败要**主动停用登录态**回到匿名路径，而不是带着坏 cookie 硬试。
- B 站：`SESSDATA` 有效期较长，过期表现为 `code=-101`，需要提示重新登录。

## 8. 平台能力矩阵（用于 UI 与调度）

| 能力 | 说明 | 例子 |
| --- | --- | --- |
| `multi_quality` | 是否提供多档清晰度 | B 站、斗鱼有；抖音基本只有一档 |
| `deferred_resolve` | 是否需要懒解析 | B 站（非当前 qn）、SOOP |
| `audio_only` | 是否支持纯音频 | B 站（app 接口 `only_audio=1`） |
| `danmaku` | 是否支持弹幕录制 | B 站/斗鱼/抖音 |
| `login_required` | 是否必须登录才能取流 | 部分平台的高清晰度 |
| `needs_tool` | 是否依赖外部工具 | 抖音（bililive-tools） |

## 9. 新增平台 checklist

1. **matcher**：覆盖主站/短链/移动端三种 URL；写单测（含反例）。
2. **resolve**：把 URL 变成稳定 `room_key`（数字房间号优先，别名要转换）。
3. **room_info**：主播名、标题、开播状态三件套；额外信息放 `extra`。
4. **stream_candidates**：至少返回 1 个候选；多清晰度时填 `weight` 与 `attrs`。
5. **headers**：`Referer` 必须是房间页；UA 与取流时一致（否则 403）。
6. **错误映射**：把平台业务码映射到 §5 的枚举，禁止直接抛原始字符串。
7. **限流参数**：在平台注册表里声明 `min_interval` / `max_concurrency`。
8. **录制验证**：连续录制 ≥10 分钟，检查文件可播放、时间戳连续、无花屏。
9. **异常验证**：断网 30s、房间下播、cookie 失效三种场景下的行为。
10. **文档**：在本目录新增 `docs/xx-平台接入-XXX.md`，记录接口、坑、验证结论。
