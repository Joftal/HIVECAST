# 152 · 监控请求并发移除：实施与验证

> 范围：`src-tauri/src/monitor.rs` 的监控调度、B 站批量状态、失败兜底，以及 `platform/bilibili.rs`、`platform/http.rs`、`settings.rs` 和观看页的周边联动。
> 结论：**已删除「全局 12 + 每平台 4」的固定并发信号量。** 监控现在只有三个约束：每个房间同一时刻最多一个在途检查、同一房间 1.5 秒请求闸门、平台明确限流后的短时冷却；不再用固定请求数把房间排成队列。
> 时间：2026-11-13；基线：`b497c9c` + 本次改动。

---

## 1. 旧实现的问题

旧 `monitor.rs` 里每个单房间检查要先拿平台名额，再拿全局名额：

```rust
let Ok(_platform) = permits.acquire_owned().await else { ... };
let Ok(_global) = global.acquire_owned().await else { ... };
check_room(app, db, broker, recorder, room).await
```

B 站批量路径直接调用 `check_room_info`，**不拿信号量**。于是同一套「保护平台」的数字只惩罚没有批量接口的平台和批量兜底路径：

- 3 个平台各 238 个房间，平台池各 4、全局池 12，刚好占满；新增第 4 个平台不会更快，只会从 12 里再切一块。
- 一个慢请求可以占住名额接近 10 秒（HTTP 超时），其他房间只能等。
- 房间越多，`last_checked_at` 越不代表真实状态；用户设的 30 秒会变成「排队后的某个时间」。

旧报告和量化推导见 `docs/151-监控请求并发限制分析.md`。

## 2. 新实现

### 2.1 删除固定并发池

`monitor.rs` 中已没有：

- `GLOBAL_CONCURRENCY` / `PLATFORM_CONCURRENCY`；
- `platforms: HashMap<String, Arc<Semaphore>>`；
- `run_check` 的两次 `acquire_owned()`。

`run_check` 现在直接进入 `check_room`：

```rust
async fn run_check(...) -> Outcome {
    check_room(app, db, broker, recorder, room).await
}
```

调度仍然每秒扫一次排期，到期的房间各自 `tokio::spawn`，互不等待。

### 2.2 B 站批量改成「按拍检查全部可批量房间」

旧实现只把「刚好在批量拍点到期」的房间放进批次，拍点前 1–3 秒到期的房间要白等一个完整间隔，30 秒实际会拖成 30–60 秒。

新实现：

- `batch_at` 只决定「这一拍什么时候发」，不再参与挑人；
- 每个拍点收集全部 `platform == "bilibili" && platform_uid` 非空的房间；
- `batch_inflight` 保证同一时刻只有一批在路上；上一批没回完时整批跳过，不把拍点往后推；
- 收到 429/412/-352/-412 后写 `batch_not_before`，冷却期内不发下一批，也不降级成几百个单房间请求。

时序：

```text
每 1 秒 tick
  └─ batch_at 到期且没有在途批次
      ├─ 收集全部有 UID 的 B 站房间
      ├─ batch_at = now + interval
      ├─ spawn run_batch_check
      │   ├─ fetch_live_statuses（200 UID/片，片间并发）
      │   ├─ 每个房间：写库/推事件 → 开录/停录 spawn 到独立任务
      │   ├─ 缺失 UID：join_all 单房间并发兜底
      │   └─ 明确限流：整平台冷却；其他错误：全量并发单查
      └─ 全部结果回传后 batch_inflight = false
```

### 2.3 批量处理与开录/停录解耦

`check_room_info_deferred` 只做「写状态、推事件、决定动作」，动作本身 `tokio::spawn` 出去：

```rust
if let Some(action) = action {
    tokio::spawn(async move { run_room_action(...).await; });
}
```

这样第 50 个房间不会等前 49 个 ffmpeg 拉起。单房间检查仍同步执行动作，保持原有语义。

### 2.4 限流分类收紧

新增 `PlatformError::is_rate_limited()`，只认：

- `Throttled { retry_after }`；
- `Upstream { code: -352 | -412 | -429 | 412 | 429 }`。

普通超时、DNS、5xx 仍是 `is_throttle()`（单房间照常退避），但**不会触发整平台 30 秒冷却**，而是走「全量单查」兜底。HTTP 429/412 在 `platform/http.rs` 里读 `Retry-After`，映射成带秒数的 `Throttled`。

### 2.5 周边改动

| 位置 | 改动 | 目的 |
| --- | --- | --- |
| `settings.rs` | 新增 `MIN_MONITOR_INTERVAL = 5`，`sanitize_monitor_interval()`：0 仍关闭，其余 clamp 5..86400 | 不再用隐藏的并发上限拉长间隔，改为明确的最小间隔 |
| `platform/bilibili.rs` | `fetch_live_statuses` 的 200 UID/片从串行改 `join_all` 并发 | 5000 个关注不会把 25 片串成 20 秒 |
| `platform/http.rs` | 429/412 映射 `Throttled`，读取 `Retry-After` | 批量冷却拿到明确秒数 |
| `WatchPage.tsx` | `rooms://changed` 的 `roomsList()` 增加 200ms 合并 | 60+ 房间同拍更新时不在前端打出几百次请求 |
| `SettingsView.tsx` / i18n | 监控间隔提示补「最小 5 秒」 | 用户知道 1–4 会被抬到 5 |

保留不动：

- `broker.rs` 的 `MIN_INTERVAL = 1.5s` 同房间闸门；
- 房间级失败退避与连续失败冷却；
- 每房间 `Schedule.inflight`；
- B 站 200 UID/片的接口上限；
- 后处理 2 槽与录制侧其它保护（见 `docs/149`）。

## 3. 量化例子

### 3.1 旧实现的有效周期

对没有批量接口的平台（斗鱼/虎牙/抖音），单平台 N 个房间：

```text
有效周期 ≈ N × 单次耗时 / 4
```

全平台 M 个房间：

```text
有效周期 ≈ M × 单次耗时 / 12
```

按 0.8 秒/请求估算：

| 场景 | 旧实现有效周期 | 新实现 |
| --- | --- | --- |
| 1 平台 238 房 | 约 47.6 秒 | 由 238 个房间各自 5–30 秒排期决定，无全局排队 |
| 3 平台各 238 房 | 约 47.6 秒（3×4=12 占满全局池） | 三个平台各自独立推进 |
| 5 平台各 238 房 | 约 79.3 秒 | 同上，不再随平台数变慢 |
| 1 平台 1000 房 | 约 200 秒 | 同上 |

这张表是「固定并发」的数学后果，不是本次真机测出的延迟；本次真机用 60 个斗鱼房间验证的是「每个房间都按自己的间隔被检查，没有排队」。

### 3.2 B 站批量的请求数

B 站 238 个有 UID 的房间：

```text
每拍请求数 = ceil(238 / 200) = 2
```

不是 238 个单查。批量拍点由监控间隔驱动；旧实现的「拍点前到期要等下一拍」已去掉。

## 4. 真机验证（macOS）

环境：release bundle，真实数据库，窗口 1166×749；测试数据在验收后全部删除并恢复备份。

### 4.1 60 个斗鱼房间：没有排队

- 从斗鱼目录接口取 60 个真实房间，直接写入 `room`，`auto_record=0`；
- `monitor.interval_sec=5`；
- 运行约 35 秒，解析日志中每个房间的 `房间信息请求完成` 时间。

结果：

```text
rooms 60, samples 324
间隔 min 3.73s, p50 5.02s, p90 5.32s, p99 6.03s, max 6.05s
>7s 的间隔 0 个，>10s 的间隔 0 个
```

这组数字说明：60 个房间都在按 5 秒的目标间隔更新，没有任何房间被固定并发池拖到 7 秒以上。

### 4.2 B 站批量：状态先落库，开录不等整批

测试房间：`bilibili 7734200`（LPL），`platform_uid=50329118`，`auto_record=1`，间隔 5 秒。

```text
17:58:24.980 INFO B 站批量状态检查开始 rooms=1 interval_sec=5
17:58:25.115 INFO B 站批量状态检查完成 rooms=1 uids=1 returned=1 live=1 missing=0 elapsed_ms=135
17:58:25.309 INFO 开始录制 room_id=test-bili-7734200 ... actual_qn=10000
17:58:30.002 INFO B 站批量状态检查开始 rooms=1
17:58:30.059 INFO B 站批量状态检查完成 rooms=1 elapsed_ms=56
```

批量本身 135ms 完成；开录在 194ms 后才开始；下一拍批量只花 56ms，没有等 36 秒的录制结束。

### 4.3 批量缺失 UID / 非风控失败：降级单查

第一次用错误的 `platform_uid=5032917` 启动：

```text
INFO B 站批量状态检查开始 rooms=1 interval_sec=5
WARN B 站批量状态失败，全量降级单房间检查 error=响应解析失败 ... elapsed_ms=612
INFO B 站批量状态检查完成 rooms=1 uids=1 returned=1 live=1 missing=0 elapsed_ms=96
```

单房间兜底拿到了正确 UID（50329118）并写回房间，下一拍批量恢复正常。这条路径证明：非风控的批量失败不会被吞掉，也不会把房间误判成离线。

### 4.4 间隔下限与关闭

- 数据库写 `monitor.interval_sec=3` 后启动，日志显示 `interval_sec=5`；`settings::sanitize_monitor_interval` 把 1–4 抬到 5。
- 数据库写 `monitor.interval_sec=0` 后启动，10 秒内没有 B 站批量、没有斗鱼房间请求；只有启动时的 2 个账号 Cookie 复验请求。

## 6. 剩余限制与风险

1. **B 站批量依赖 `platform_uid`。** 没有 UID 的 B 站房间仍走单查；导入关注后 UID 丢失会退回单查，不会漏检，但请求数会变多。**已在 [153](153-UID落库强化.md) 修复：成功检查会把平台返回的 UID 纳入结构性写库判断，存量房间下一次检查即补写。**
2. **明确限流是整平台冷却。** 一批 238 个房间遇到 429 时，所有 B 站房间一起等 `Retry-After`（最少 5 秒）。这是有意的：继续发 238 个单查只会把风控拖得更久。
3. **批量 `check_room_info_deferred` 仍按房间串行写库。** 开录/停录已经异步，但 238 次 SQLite 更新 + 事件推送仍在批量任务里顺序执行；实测 1 个房间 56–135ms，238 个房间的写库成本需要更大规模数据再测。
4. **间隔下限 5 秒是产品选择。** 允许 0 关闭；1–4 会被抬到 5。
5. **前端只做了观看页 200ms 合并。** 监控页已有 200ms 合并；任务页/媒体库不订阅 `rooms://changed`。

## 7. 验收结论

- 固定并发池已从代码中删除，单房间检查不再 acquire 任何信号量；
- 60 个斗鱼房间在 5 秒目标下 p50 5.02 秒、最大 6.05 秒，没有 >7 秒的排队；
- B 站批量按拍检查全部可批量房间，状态落库与开录解耦；
- 明确限流走整平台短冷却，普通网络错误走单查兜底；
- 间隔 0 仍可关闭监控，1–4 明确抬到 5 秒；
- 301 tests、0 警告、前后端构建通过。
