# 56 监控录制联动修复二（R1–R7）

> 状态：v1.0（2026-11-06）｜前置：[54-监控与录制关系审查](54-监控与录制关系审查.md)（v2.0 提出 R1–R7）、[55-监控录制联动修复](55-监控录制联动修复.md)（S1–S5 与 C3）｜范围：R1–R7 七个残余场景｜结论：七条全部修掉，监控彻底只做「刷新状态 + 决定开录 / 停录」，录制链不再被监控的时钟或判定逻辑截断。

## 0. 一句话结论

55 修掉的是「监控间接影响录制」的旧坑，但那轮修复本身又带出两个新的空窗（R1 干净 EOF、R2 假离线），另外五个场景（R3 移除竞态、R4 墙钟、R5 换目录、R6/R7 失败循环）仍在。这一轮的共同思路是：**任何「结束录制」的决定都必须有第二份证据**——EOF 要复查平台是否仍在播，离线要复查文件是否还在长，开录要复查房间是否还存在且未暂停。

| 编号 | 改前 | 改后 | 验证级别 |
| --- | --- | --- | --- |
| R1 | ffmpeg 干净 EOF（退出码 0 且存活 > 12 秒）就 finalize 并 mark_ended，平台仍报在播时会空窗 10 分钟，还先发一条「录制结束」 | 收尾前用 broker 复查一次平台；仍 live 就按断流续录，最多 2 次（MAX_EOF_RETRIES） | 单测 |
| R2 | 连续两次假离线被 confirm_offline 确认后 stop(stream_ended)，同样 mark_ended → 截断 + 10 分钟空窗 | 停录前交叉验证最近 60 秒分片是否还在增长（recorder.flowing）；还在长就只打 WARN，不停录 | 单测 |
| R6 | 源不可用（在播但推流没起来）时每分钟一条 failed 会话 + 一条通知 | 连续 3 次非正常收尾进入 5 分钟长冷却（in_failure_cooldown），通知只发第 1 次与进入冷却那次 | 真机 |
| R7 | 假死重启 2 次用尽后 failed/stalled 不写 ended，约每 3 分钟新开一条会话 | 与 R6 同一处修：长冷却挡住自动开录，不再堆会话 | 真机 |
| R3 | room_remove / 暂停监控与在途检查竞态，已移除房间被幽灵开录 | 监控专用入口 start_checked 拿锁后复查 removed_at 与 monitor_paused | 单测 |
| R5 | 换媒体目录后活跃录制仍写旧路径，磁盘红线看新目录 → 旧盘写满记 failed 而非 disk_full | 红线改成逐路读取录制自己的父目录（active_targets + target_dir） | 单测 |
| R4 | 排期与静默窗口用墙钟 now_ts()，改系统时间会让监控停摆或提前解除静默 | Schedule.next_at 与 ended/offline/hard_failures 全部改 Instant（单调时钟） | 真机 |

## 1. 改动一览

| 文件 | 改动 | 关键符号 |
| --- | --- | --- |
| `src-tauri/src/recorder.rs` | 常量、Active 字段、三个 Mutex 表、六个新方法、start 拆分、EOF 复核、失败连击与通知去重 | MAX_EOF_RETRIES、FAILED_STREAK_LIMIT、FAILED_STREAK_COOLDOWN、ENDED_BLOCK、OFFLINE_CONFIRM_GAP、eof_retries、active_targets、flowing、in_failure_cooldown、note_hard_failure、platform_still_live、start_checked、should_check_eof、monitor_start_allowed |
| `src-tauri/src/monitor.rs` | 排期改 Instant、逐路磁盘红线、离线交叉验证、开录条件加冷却、监控专用开录入口 | Schedule.next_at、grid_next、backoff_wait、add_jitter、target_dir、should_stop_for_offline |
| 前端 i18n | 无新增键（本轮全是后端行为） | — |

常量取值：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| MAX_EOF_RETRIES | 2 | 一次会话里最多因「EOF 但平台仍在播」续录 2 次 |
| STALL_TIMEOUT | 60 秒 | 分片 60 秒不增长即判假死（55 引入） |
| MAX_STALL_RESTARTS | 2 | 同一会话内假死最多重启 2 次 ffmpeg |
| FAILED_STREAK_LIMIT | 3 | 连续 3 次非正常收尾进入长冷却 |
| FAILED_STREAK_COOLDOWN | 300 秒 | 长冷却时长；到期后计数归零重新开始 |
| ENDED_BLOCK | 600 秒 | 自然结束后的自动开录静默（55 引入） |
| OFFLINE_CONFIRM_GAP | 180 秒 | 两次离线确认的最大间隔，超过重新计数（55 引入） |

## 2. R1 干净 EOF 复核

改前 `spawn_watcher` 的判定很干脆：没有 stop_reason、退出码 0、存活超过 12 秒，就当「直播结束」，finalize 里 mark_ended（静默 600 秒）并通知。问题在于 CDN 边缘节点会优雅结束连接——ffmpeg 认为「流正常结束」，平台侧却还在直播。此时录像被截断、10 分钟内不会重开。

改后在这条路径前面加一次平台复查：

`if should_check_eof(stop_reason.as_deref(), status.success(), early, rec.eof_retries(&room_id))`

命中时调 `platform_still_live`（走 broker 的 room_info_fresh，复用缓存与冷却，不额外加压），仍 live 就打 `平台仍显示在播，按断流续录` 并复用断流续录分支：清缓存、等 3 秒、重解析签名、分片编号接续，同一个会话继续写。续录计数用 Active.eof_retries，最多 2 次；第 3 次 EOF 才真正收尾。复查失败（网络错误、房间已删）一律当作「不在播」，走正常收尾，避免因为复查本身失败而无限续录。

举例：21:30 斗鱼房间正常录制 → CDN 在 21:41 优雅断开 → ffmpeg 退出码 0、存活 11 分钟 → should_check_eof 为真 → 复查发现仍在播 → 续录 part000K，会话不变；若 21:44 又一次 EOF，再续一次；21:47 第三次 EOF 才 finalize 并静默。

## 3. R2 假离线交叉验证

55 把「一次成功响应报离线就停录」改成连续两次确认，方向对，但两次都来自同一个接口——平台接口抖动或字段缺失可以连续两次报离线，confirm_offline 仍然放行，停录后 mark_ended 又带来 10 分钟空窗。

改后停录条件多一份本地证据：`should_stop_for_offline(confirmed, flowing)` = confirmed && !flowing。flowing 由 `recorder.flowing(room_id)` 提供：分片总大小在场就刷新基线并返回 true；基线超过 60 秒没涨才返回 false。

两个分支的日志不同，便于排查：

- 真下播：confirmed && !flowing → stop(stream_ended)，正常收尾。
- 假离线：confirmed && flowing → 打 `平台报离线，但录像仍在增长，暂不停录`，会话继续；下一次检查会重新 confirm（表项在返回 true 时已清除，所以是新的连续两次）。

举例：B 站接口在 22:10:00 与 22:10:30 两次返回离线，但 ffmpeg 分片在 22:10:20 还在增长 → 不停录 → 22:11 接口恢复在线 → 录音连续，媒体库里只有一条记录。

## 4. R6 / R7 连续失败长冷却与通知去重

改前有两个独立的坏循环：

- R6：房间在播但推流没起来（源不可用），每轮监控都开录，每次都秒退或假死收尾，每分钟一条 failed 会话 + 一条系统通知。
- R7：假死重启 2 次用尽后 finalize 记 failed/stalled，但 stalled 不写 ended，所以下一轮监控（10–30 秒后）立刻再开，约每 3 分钟新增一条会话。

改后统一在「非正常收尾」上计连击：finalize 里 `note_hard_failure` 返回当前连击数（超过 300 秒的旧记录先归零再 +1），达到 3 时打 WARN `连续录制失败，暂停自动重试 5 分钟`；正常收尾（finished）调用 clear_hard_failure 清零。

冷却的两处生效点：

1. `in_failure_cooldown` 被 `start` 检查，返回错误「该房间连续录制失败，已暂停自动重试」，人工点录制也会被拦（同一句提示）。
2. `monitor.rs` 的开录条件里直接加 `&& !recorder.in_failure_cooldown(&room.id)`，监控连 start 都不调，日志里不会刷「自动开录失败」。

通知去重：finalize 的通知 match 里 `("failed", _)` 只在 failed_streak == 1 或 == 3 时发。也就是「第一次失败」发一条，「进入冷却」再发一条，中间的第 2 次静默。

举例（本轮真机三轮）：13:30:22 failed → 13:30:47 failed → 13:31:03 failed 并进入冷却 → 之后 45 秒内没有新 ffmpeg、没有新会话、没有新通知。

## 5. R3 监控开录复查

竞态场景：监控拿到房间快照（在播、auto_record 开）→ 用户在这一瞬间移除房间或暂停监控 → 监控继续调 start → ffmpeg 起来写文件，但房间里已经没有这一行，界面看不到，会话挂在软删除的房间上。

改法是把开录入口分成两个：

- `start`：给用户手动点录制用，行为不变。
- `start_checked`：监控用，拿开录锁之后再读一次库——`db.room_removed` 与 `db.get_room().monitor_paused`，任一为真返回 `AppError::User("房间已移除或监控已暂停")`；房间被物理删掉返回「房间不存在」。

因为复查放在锁之后，即使 remove 与 check 并发，也一定有一方看到对方的写入。监控对这类错误只写 room.error，不重试、不通知。

## 6. R5 逐路磁盘红线

改前磁盘红线用全局的设置值（当前媒体目录），但 55 之后每路录制可能写在不同目录（换目录前的会话仍在旧盘）。结果：旧盘写满时红线看着新盘（有空间）不动手，旧盘上的 ffmpeg 写失败 → 会话记 failed，而不是 disk_full。

改后 `recorder.active_targets()` 暴露每一路的 (room_id, host_name, 文件路径)，红线逐个取 `target_dir(&file, &recorder.media_root())`：文件有父目录就用父目录，否则退回当前媒体目录。命中 `disk::is_low(dir)` 才 stop(disk_full)，并且只停那一路。

举例：设置里从 `/Volumes/A` 换到 `/Volumes/B`，A 上仍有 2 路在录；A 剩余 200MB 时红线只停 A 的两路，B 上新开的会话不受影响。

## 7. R4 单调时钟

改前用 `now_ts()`（Unix 秒）算排期与静默窗口：用户把系统时间往前调 1 小时，所有 `next_at` 变成「一小时后」，监控停摆；往后调则静默窗口立刻失效，被抑制的房间马上重开。

改后：

- `Schedule.next_at` 改成 `Instant`，手写 `Default`（原来靠 derive）。排期只做加减与比较，不再和墙钟发生关系。
- `ended` / `offline` / `hard_failures` 三张表的第二列全部换成 `Instant`（前两张表在 55 里已经引入墙钟值，这轮一并改）。
- `grid_next(previous, now, base)`、`backoff_wait(base, streak, cap, enabled)`、`add_jitter(at, id, span)` 全部用 `Duration` / `Instant`；抖动允许负值（用 `at - Duration`），但结果被 `max(now + 1s)` 或 `max(now)` 夹住。
- `tick` 里「间隔调小后旧排期不拖」的判定改成 `entry.next_at > now + interval`。

墙钟现在只用于显示（DB 里的 started_at / last_checked_at）与通知文案，不影响调度。

## 8. 单测

新增 6 个（cargo test --lib 共 144 passed / 14 ignored）：

| 测试 | 断言 |
| --- | --- |
| `clean_eof_only_rechecks_when_nobody_stopped_it` | 有 stop_reason、非零退出、存活不足 12 秒、续录次数用尽，四种情况都不复查 |
| `monitor_start_rechecks_removed_or_paused_rooms` | monitor_start_allowed 对 removed / paused 的四种组合 |
| `repeated_failures_enter_long_cooldown` | 第 1、2 次不冷却；第 3 次冷却；clear 后回到 1 |
| `offline_stops_only_when_the_file_stopped_growing` | confirmed 且不增长才停；增长时不停 |
| `target_dir_prefers_the_recording_location` | 有父目录用父目录，否则用兜底 |
| `jitter_never_moves_far_or_backwards_in_time` | 抖动不超过 ±span，且不早于基准 |

上一轮已有的 `grid_next` / `backoff_wait` / `broker_cooldown` 三个测试同步改成 Duration / Instant 断言。

## 9. 实测

环境：macOS arm64、`pnpm tauri dev`、DB 播种 3 个房间（斗鱼 9999 / B 站 6 / 虎牙 660000，斗鱼 auto_record=1）、monitor.interval_sec=10。

| 场景 | 做法 | 结果 |
| --- | --- | --- |
| R4 节奏 | 每秒采样 last_checked_at，连续 20 秒 | 三房间各自 10–11 秒一轮、相位错开；全局每秒最多 1–2 个刷新，无尖峰 |
| 正常录制回归 | 等自动开录 60 秒 | 26MB 分片 + 同名 .jsonl；ffmpeg 命令含 `-rw_timeout 30000000` |
| app_exit 收尾 | pkill 应用 | 会话 aborted / app_exit，29,628,187 字节，文件完整 |
| R6 + R7 | 临时把 STALL_TIMEOUT 改 6 秒、MAX_STALL_RESTARTS 改 0，三轮 SIGSTOP ffmpeg | 三条 failed / stalled（3,149,463 / 2,866,612 / 1,163,608 字节）；13:31:03 日志「连续录制失败，暂停自动重试 5 分钟」；随后 45 秒无新 ffmpeg、无新会话、无「自动开录失败」刷屏 |
| 验证后还原 | 两个常量改回 60 秒 / 2 | cargo test 144 passed，grep TEMP-VERIFY 为空 |

R1 / R2 / R5 的触发条件在真机上无法安全构造（要 CDN 优雅 EOF、平台连续误报离线、把旧盘写满），只由单测覆盖，本轮不作真机结论。

## 10. 缺口

| 缺口 | 说明 | 建议 |
| --- | --- | --- |
| R1 / R2 / R5 只有单测 | 三条都依赖外部异常，真机不可控 | 后续可在调试构建里加「模拟 EOF / 模拟离线 / 模拟低磁盘」的隐藏开关 |
| 长冷却不可配置 | 5 分钟写死在 FAILED_STREAK_COOLDOWN | 若用户反馈太短，再进设置页（届时给「失败重试策略」一段） |
| 通知只在前端 | 失败通知走 app://notice，没有落库 | 若要「通知中心」，需要新增表与列表页 |
| EOF 复查依赖 broker | 复查命中缓存时可能拿到 15 秒内的旧状态 | 可接受：15 秒内的状态差不会造成误判 |
| 逐路红线只到目录 | 目录级 is_low，不是按文件剩余可写量 | 目录级足够，除非同一盘多路同时写满 |
