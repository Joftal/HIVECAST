## 1. 结论

| 项目 | 188 当轮 | 本轮之后 |
| --- | --- | --- |
| 单场事件 | 一次最多 2000 条，超出只保留最新 | 默认 200 条一页，按 `(at, id)` 游标向前翻；可一直翻到第一条 |
| 历史渲染 | 只验证 100→131 行 | 1001 个分组、1000 行全量加载实测；内存 +15.2 MB，无崩溃 |
| 详情轮询 | 所有 Run 固定 5 秒 | 只有 recording/running/finalizing/queued 每 5 秒；已结束 Run 只取一次 |
| 事件合并 | 每次刷新整段替换 | 刷新只合并最新页，保留用户已经翻出来的更早页，按 id 去重 |

## 2. 后端

### 2.1 分页契约

`src-tauri/ipc-types/src/lib.rs:832` 新增：

```rust
pub struct TaskEventPage {
    pub events: Vec<TaskEvent>,
    pub has_more: bool,
}
```

`src-tauri/src/db.rs:1781 task_event_page(run_ids, before, limit)`：

- `before: Option<(i64, i64)>` 是上一页最旧一条的 `(at, id)`，只取更早的事件；
- 每个 `run_id` 分块 400 个，避免 SQLite 999 个绑定变量上限；
- SQL 条件为 `run_id IN (...) AND (at < ? OR (at = ? AND id < ?))`，同秒事件用 id 继续稳定排序；
- 每块多取 1 条，合并后按 `(at, id)` 倒序裁到 `limit`，再反转成时间正序返回；
- `has_more = 合并后条数 > limit`，前端据此显示「加载更早的事件」；
- `limit` 夹在 1..=1000，命令默认 200。

`src-tauri/src/commands.rs:3113 task_run_events(run_id, before_at, before_id, limit)` 保持原有 `session:<group>` 展开逻辑：先 `session_group_ids` 找到同组片段，再把这些 `session:<id>` 一起分页。返回类型由 `Vec<TaskEvent>` 改为 `TaskEventPage`。

## 3. 前端

`src/features/tasks/TasksPage.tsx`：

- `EVENT_PAGE=200`；`ACTIVE_RUN_STATES = {recording, running, finalizing, queued}`；
- 新开详情时清空并取最近 200 条，记录 `hasMore`；
- 只有 `detailActive` 为真才启动 5 秒 interval；Run 从运行中变成完成时 effect 重跑一次，拉取最终页后停表；
- 轮询使用 `mergeEvents(previous, page.events)`，按 id 去重、按 `(at,id)` 正序，绝不丢掉已加载的更早页；
- 刷新不修改 `hasMore`，避免用户已经翻到底后又被重新标成「还有更多」；
- 「加载更早的事件」用当前第一条的 `(at,id)` 作游标，结果 `mergeEvents(page.events, previous)` 前插；
- 切换 Run 时用 `selectedIdRef` 丢弃迟到的旧请求结果，防止把上一个 Run 的事件插到新抽屉。

`src/lib/ipc.ts:647`：

i18n 新增 `tasks.timelineLoadEarlier`、`tasks.timelineLoadingEarlier`；`tasks.timelineError` 从「稍后自动重试」改为「可关闭后重试」，因为已结束 Run 不再自动轮询。

## 4. 真机验收

环境：release bundle 33.14 MiB，窗口 1166×749（`70,30`），窗口截图 2332×1498。测试前 DB 备份 `/tmp/hivecast-before-task-events.db`。

### 4.1 2100 条事件翻页

夹具：`session:event-head` 写入 2100 条 `task_event`，`at` 每秒递增，消息为 `事件 #0`…`事件 #2099`。

- 打开详情：首屏显示 `事件 #1900` 到 `#2099`，顶部有「加载更早的事件」；
- 点一次：顶部变成 `事件 #1700`，按钮仍在；
- 再点 9 次：顶部到 `事件 #0`，按钮消失；
- 连续两次翻页之间没有重复 id，时间正序；证明 2000 条上限已被游标分页取代。

### 4.2 1000 场历史

夹具：1001 个分组（1 个 1 小时事件 Run + 1000 个 10 秒 Run）。

- 初始「全部 101 / 最近完成 100」；点 9 次「加载更多历史」后「最近完成 1000」，底部显示「最多显示最近 1000 场」，按钮消失；
- 进程 RSS 从 30.9 MB 到 46.1 MB（+15.2 MB），CPU 0.4%；
- 每次点击含 AX 等待约 1–4 秒，1000 行全部在 DOM 中，没有虚拟列表；
- 顶部「全部 1001」= 1000 条历史 + 1 条登录失效 orphan incident，不是漏行；「最近完成」只显示历史上限 1000。

### 4.3 终态与运行中轮询

- 已结束的 `poll-fin`（0:03）打开详情后，把 DB 第一条消息从 `poll-original` 改成 `poll-CHANGED`，等待 8 秒，界面仍是 `poll-original`：证明已结束 Run 不再轮询。
- 真实录制 `e4e5f5c4-6edc-4395-9014-646af0db9096` 运行中，打开详情后向 `task_event` 插入 `active-inserted`，8 秒内出现在时间线：证明运行中 Run 的 5 秒轮询仍在工作。
- 运行中详情同时显示「录制中」、四段链路和后处理任务；没有因为分页丢掉已有事件。

## 5. 边界与剩余

1. **2100 条全部展开后 AX 树很重**：`agent-desktop find` 会超时，但界面滚动与截图正常；没有做虚拟列表。默认 200 条一页，正常使用不会一次展开 2100 条。
2. **历史 1000 行没有虚拟列表**：内存 +15.2 MB 可接受，但低配机器上首次加载 1000 行仍可能有明显布局开销。
3. **并发收尾重试仍只有单测**：本轮没有在真机同时点两个片段；`FINALIZE_RETRYING` 按 manifest 加锁的逻辑未改。
4. **事件不可全局检索/导出**：时间线只在详情里可见，这是产品功能，不在本轮收尾范围。
5. **每页上限 1000**：即使调用方传更大值也会被夹到 1000；前端固定 200。
