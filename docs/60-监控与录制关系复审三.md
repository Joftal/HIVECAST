>
> 这一轮按你的要求重做，不引用前几轮的结论，只看当前代码 + 真机行为。除真实斗鱼录制外，还用 3 GiB 稀疏卷、`kill -9`、`SIGTERM`、伪造保留记录做了注入测试。文中时间均为本地时间（UTC+8），日志里是 UTC。

一句话结论：**已开录的会话依然不受检测间隔、抖动、退避、暂停监控影响（本轮再次用量化数据证实）；但「退出应用」「并发上限」「磁盘红线」三处会直接改变录制结果，前两处已实测出真实缺陷：退出窗口里会多开一场 0 字节会话，`max_concurrent=1` 实测能同时开出两路。另有 4 条代码级隐患（转封装窗口、开录/停录竞态、抖动用全局盐、并发已满刷日志）尚未在真机复现。**

## 0. 结论速览

| 你的关注点 | 本轮结论 | 依据 |
| --- | --- | --- |
| 检测间隔会不会影响已开录的会话 | **不会**。间隔从 30 秒改到 3600 秒后，60 秒内分片仍从 3.3 MB 长到 9.5 MB，`last_checked_at` 完全冻结 | T1 |
| 失败退避会不会影响已开录的会话 | **不会**。退避只改 `Schedule.next_at`，不碰 recorder；本轮没能造出真实 429，只能确认代码路径与单测 | §2.7、[monitor.rs:180](../src-tauri/src/monitor.rs#L180) |
| 暂停监控 / 间隔设 0 | **不会**。分片继续增长，只是不再检测平台 | T2、T3 |
| 磁盘红线 | **会停录**（设计如此），但同一块盘上多路录制是「一拍停一路」，3 路花了 3 秒才全停 | T5、C3 |
| 退出应用 | **会多开一场**：SIGTERM 收尾期间监控仍会自动开录，第二次收尾把它记成 0 字节 `app_exit` | T6、C1 |
| 并发上限 | **会失效**：`max_concurrent=1` 重启后同时开出两路 | T7、C2 |
| 崩溃（kill -9）后重启 | **恢复正确**：孤儿 ffmpeg 被杀、分片合成 mp4、会话收尾 | T8 |

## 2. 实测记录

### 2.1 间隔、暂停、软删除（T1–T4）

| 测试 | 操作 | 观测 | 结论 |
| --- | --- | --- | --- |
| T1 间隔 | 36252 开录后把 `monitor.interval_sec` 从 30 改成 3600 | 60 秒内 `last_checked_at` 冻结在 1793981744，分片 3336 KB → 9492 KB | 间隔不碰已开录会话 |
| T2 关闭检测 | 间隔改 0，等 25 秒 | `last_checked_at` 不动，分片 12588 KB → 14652 KB | 关闭检测只停轮询，不停录制 |
| T3 暂停监控 | 间隔 10，房间 `monitor_paused=1`，等 25 秒 | `last_checked_at` 不动，分片 14652 KB → 17728 KB | 暂停只停该房间检测 |
| T4 软删除 | 房间 `removed_at=now`，等 25 秒 | 分片 18756 KB → 21832 KB；恢复标记后重新参与轮询 | 软删除不打断录制 |

这一组与 58 的结论一致：**监控只负责「发现」，录制由 recorder 自己的 1 秒 watcher 守护**，两套时钟互不等待。

### 2.2 磁盘红线（T5）

3 路同时录制在同一块 3 GiB 卷上，用 `dd` 写入 2450 MB，剩余 386 MB：

| 时间 | 日志 | 结果 |
| --- | --- | --- |
| 00:22:43 | 1 条「磁盘剩余空间低于红线，停止录制」+ 1 条「请求停止录制」 | 第 1 路 `aborted / disk_full`，5,023,645 字节 |
| 00:22:44 | 同上 | 第 2 路 `aborted / disk_full`，6,532,955 字节 |
| 00:22:45 | 同上 | 第 3 路 `aborted / disk_full`，4,251,962 字节 |

没有重复刷屏（B6 的幂等生效），但三路是**一拍停一路**：因为按卷去重时只对「当前遍历到的第一路」发 stop，下一拍才轮到第二路（C3）。删掉填充文件后 8 秒内三路全部自动重开。

### 2.3 退出应用（T6）

00:24:14 发 `SIGTERM`：

1. 三路依次收尾为 `app_exit`（11,183,660 / 22,693,127 / 15,415,135 字节），收尾里包含转封装；
2. 00:24:19.217 **rm-r2 又开始录制**——此时监控仍在跑，看到「不在录制 + 平台在播」就自动开录；
3. 00:24:19.402 该会话以 `app_exit` 收尾，`file_size=0`，并打出一条「分片合成 mp4 失败，改用字节拼接 err=没有分片」；
4. DB 多出一条 0 字节会话，历史里出现两条相邻记录。

`SIGTERM` 处理里先 `shutdown_all` 再 `quit_now`（[lib.rs:119](../src-tauri/src/lib.rs#L119)），全程没有「正在退出」标记；`RunEvent::Exit` 又会再执行一次 `shutdown_all`（[lib.rs:210](../src-tauri/src/lib.rs#L210)），第二次才把这场新会话收掉。

### 2.4 并发上限（T7）

把 `record.max_concurrent` 设为 1，重启后同一拍内 rm-r1 与 rm-r3 都通过了「当前 0 路 < 1」的检查，各自在 `broker.groups()` 返回后插入 active，结果同时开出两路；第三路才被拦，并每 10 秒打一条「自动开录失败 … 同时录制已达上限（1 路）」。

检查点在网络请求之前（[recorder.rs:602](../src-tauri/src/recorder.rs#L602)），插入点在请求之后（[recorder.rs:713](../src-tauri/src/recorder.rs#L713)），中间没有预留名额。

### 2.5 崩溃恢复（T8）

录制中 `kill -9` 应用：两个 ffmpeg（pid 65045 / 65046）存活并继续写分片，6 秒内分别从 38,010,880 → 39,583,744、49,545,216 → 50,855,936 字节。

重启后日志依次出现：

- 「清理上次崩溃遗留的 ffmpeg pid=65045/65046」（reap_orphans 按 pid 文件 + 命令行核对）
- 「恢复上次崩溃遗留的录像 recovered=2 recovered_bytes=89227044」
- 「收尾上次异常退出的录制记录 count=2」（两场记 `aborted / app_exit`，大小 50,134,344 / 39,092,700）
- 「媒体库保留策略：已清理旧录像 deleted=8 freed=91882221」

顺序是 `reap_orphans → recover_parts → close_orphan_sessions → retention`（[state.rs:59](../src-tauri/src/state.rs#L59)），与注释一致，没有出现「合成到一半又被追加」。

### 2.6 保留策略（T9）

造 3 条 600 MB、开始时间分别为 30/20/10 天前的会话，加 1 条 900 MB、状态仍为 `recording` 的会话，`media.max_total_gb=1`，重启：

| 结果 | 值 |
| --- | --- |
| 删除条数 | 3 |
| 释放字节 | 1,887,436,809 |
| 保留 | 900 MB 那条 |

900 MB 那条在启动时先被 `close_orphan_sessions` 改成 `aborted`，所以参与了容量计算，把三条 600 MB 全挤掉。这是正确行为（崩溃遗留也要占配额），但说明**「状态是 recording 就不参与清理」只在应用运行期间成立**；启动收尾之后它就是普通旧录像。

### 2.7 限流（T10，未复现）

- 9 个斗鱼房间、间隔 1 秒跑 50 秒：没有出现 429，`ok=false` 计数为 0；期间录制分片 23880 KB → 33160 KB。
- B 站房间间隔 3 秒：`last_checked_at` 每 4–5 秒更新一次，未进退避（适配器走 `room/v1/Room/get_info`，不会触发匿名 -352 风控）。

所以**真实限流退避这一轮没有可复现路径**，只能依赖 broker 单测与代码阅读：[monitor.rs:180](../src-tauri/src/monitor.rs#L180) 的 `Throttled` 分支按「基础间隔 × 2^streak」封顶 120 秒。

### C1 退出窗口里的自动开录

机制：

1. `SIGTERM` → `shutdown_all` 先取当前 active 列表，再逐个 `finalize`；
2. 每个 `finalize` 一开始就把自己从 active 里摘掉（[recorder.rs:1179](../src-tauri/src/recorder.rs#L1179)），随后等待转封装；
3. 监控 tick 仍是 1 秒一拍，看到「平台在播 + 不在录制 + 没有停录抑制」就开新会话；
4. 第二个 id 收尾期间新会话启动，等 `RunEvent::Exit` 的第二次 `shutdown_all` 才被收掉，于是 `file_size=0`。

为什么没有抑制：`stop()` 只在 `reason == "stopped"` 时写 suppressed（[recorder.rs:759](../src-tauri/src/recorder.rs#L759)），`app_exit` 不写。

建议：在 `Recorder` 里加 `quitting: AtomicBool`，`shutdown_all` 第一行置位；tick 开头与 `start_checked` 都检查它并直接返回。顺带可以让 `shutdown_all` 幂等提前返回，省掉第二次收尾。

### C2 并发上限的检查—占用竞态

`start_checked` 的顺序是：房间锁 → 暂停/冷却检查 → **并发检查（:602）** → 磁盘检查 → `broker.groups()`（网络，可能几百毫秒）→ spawn ffmpeg → 插 active（:713）。

同一拍里两个房间各自持不同房间锁，都能看到 `active_count()=0`，都能通过。修复有两种：

- **预留名额**：进入网络请求前在全局 mutex 下 `reserve`，失败/取消时释放，`finalize` 释放；
- **插入时复查**：在 :713 的锁内再数一次，超限就杀掉刚 spawn 的 ffmpeg、删会话行、返回错误。

第二种改动小，但要处理「已经写了几百毫秒分片」的清理；第一种更干净。

### C3 同卷多路的磁盘红线

当前循环用 `checked_volumes` 跳过后面的同卷目标（[monitor.rs:309](../src-tauri/src/monitor.rs#L309)），所以一块盘低只停第一路；下一拍照样低，再停第二路。三路共停了 3 秒，期间后两路继续写盘。

建议改成两遍：先按卷收集「哪块卷低」，再对低卷上的**所有** id 各 spawn 一次 `stop(dir, "disk_full")`；`stopping()` 仍然用于跳过已请求停止的。

### C4 收尾与重新开录的窗口

`finalize` 摘掉 active 后要等 `finish_file`（分片合成 mp4，再缩略图），大文件可能几秒到几十秒；`mark_ended` 在转封装之后（:1229）。这段窗口里监控看到的是「没在录 + 平台在播」，于是：

- 若平台确实在播（例如 ffmpeg 崩了）：开新会话是期望行为，但旧会话的 `mark_ended` 可能在新会话开始后才执行，历史里两场时间重叠；
- 若平台已下播：`confirmed_end=true` 的静默要等 `mark_ended` 才写，窗口内也可能被开一场，随后再停。

建议：把 active 的移除挪到 `mark_ended` 之后；或者先写 ended 标记再转封装。保留 active 期间 `is_recording` 为真，监控自然不会开新场。

### C5 开录在途时停录 / 建会话失败

`stop()` 在 active 里找不到目标时，只写 suppressed 就 `return Ok`（[recorder.rs:775](../src-tauri/src/recorder.rs#L775)）。如果此时 `start` 正在等 `broker.groups()` 或正在 spawn，它会继续插 active，然后无条件 `resume_auto`（[recorder.rs:737](../src-tauri/src/recorder.rs#L737)），把刚写下的抑制清掉——用户的停录被吞，而且下一拍监控也不会再停（看起来像「停了又自己开」）。

同一段里，`create_session` 失败时（:685-702）已经 spawn 的 ffmpeg 没有 kill，也没有删 pid 文件，会留下一个写文件但无会话的孤儿。

建议：

- `start` 记录进入时的抑制代数，插入 active 后若代数变了就立即 `stop("stopped")`；
- `create_session` 失败分支 `child.kill()` + 删 pid 文件，再返回错误。

### C6 抖动的「确定性」

注释写「同一房间同一时刻可复现」，但 `jitter` 每次调用都 `JITTER_SALT.fetch_add(1)`（[monitor.rs:252](../src-tauri/src/monitor.rs#L252)），盐一直在变，结果不可复现；另外 `add_jitter(entry.next_at, …)` 叠加在上次已经抖过的点上，理论上会随机游走。

实测 3 秒间隔的房间实际 4–5 秒一次，主要来自 1 秒 tick 与 broker 每房间 1.5 秒闸门，抖动不是主因；但注释与实现不符，建议要么改成真确定性（用 `id + 拍号` 作盐），要么把注释改成「每次随机」。

### C7 并发已满时的重复告警

`start_checked` 返回「同时录制已达上限」→ monitor 每拍 `warn!` + `set_error` + 发事件（[monitor.rs:464](../src-tauri/src/monitor.rs#L464)）。间隔 10 秒时每 10 秒一条，长期挂机日志会一直涨。可以像磁盘不足那样用 `last_error` 去重，只在文案变化时告警。

## 4. 修复顺序建议

1. **C2 并发上限**（一行复查就能挡住多开，直接影响磁盘与带宽）；
2. **C1 退出闸门**（避免每次退出都多一条脏历史）；
3. **C3 同卷全停**（磁盘真的快满时，多停两秒就可能写坏或写满）；
4. **C5 停录竞态 + 孤儿**（用户操作被吞比多录更难解释）；
5. **C4 收尾窗口**（大文件用户才会遇到，但会话重叠会污染统计）；
6. C6 / C7 一起收尾（注释与日志噪音）。

## 5. 已确认没问题的点

- 间隔、抖动、退避、暂停、间隔 0、软删除都不改变已开录会话的 ffmpeg 与文件；
- 磁盘红线只发一次 stop、不重复刷屏，删掉占位文件后能自动重开；
- 停录幂等：同理由重复 stop 直接返回，用户停录可覆盖磁盘红线；
- 崩溃恢复顺序正确：先杀孤儿、再合成、再收尾、最后清理；本轮 recovered=2、0 残留进程；
- 保留策略不会删「运行中」的会话（`retention_rows` 过滤 `status='recording'`）；
- 退出时转封装登记为 job，不会在写文件时被强杀。
