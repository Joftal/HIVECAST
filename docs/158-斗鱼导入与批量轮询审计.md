# 斗鱼导入与批量轮询审计

> 2026-11-14。范围：斗鱼关注导入去重、监控与录制取数、Cookie 各状态、30 秒批量流程、兜底、非关注房间、先加后导入、移除房间、日志，以及与 B 站批量链路的差异和相互影响。
> 基线：`4d234ac`（docs/157 的斗鱼关注导入与批量状态轮询）+ 本文修复。结论基于代码审计、328 个 Rust 单测与既有真机日志；本轮新增修复未重新跑真机。

## 1. 结论

斗鱼导入与批量状态发现的主链路是正确的，但审计发现并修复了 3 个会直接影响正确性的缺陷：

| # | 问题 | 影响 | 处理 |
| --- | --- | --- | --- |
| 1 | 斗鱼别名房间没有归一成数字房间号 | 先加 `/yyf`、再导入数字 `45977`，会生成两行；别名行也进不了按数字房间号的批量映射 | `douyu.rs:241` 的 `stable_id` 改为真实数字 `room_id`；`commands.rs:96` 同步把斗鱼 canonical URL 归一成 `https://www.douyu.com/{数字}` |
| 2 | 斗鱼批量状态把 `status.uid`（其实就是房间号）写进 `extra["uid"]` | `platform_uid_of` 会误当成账号 UID 落进 `platform_uid`，污染「斗鱼没有独立 UID」的模型，还会触发不必要的整行写库 | `monitor.rs:874 batch_room_info` 增加 `platform` 参数，只有 B 站写 `uid`；斗鱼只写 `roomId/shortId/liveStatus/videoLoop` |
| 3 | 批量路径忽略单房间退避 | 某房在单查里连续失败后，下一拍仍被塞进批量，退避形同虚设，持续请求平台 | `monitor.rs:97 batch_room_ready`：批量 due、批次不在途、房间不在途之外，还要求「不在退避中，或退避已到期」；成功排期的 ±10% 抖动不受影响 |

另外补了两道保护：

- `monitor.rs:1081 apply_room_info` 在写状态前检查房间是否已软删。批量结果从发出到落库之间用户移除了房间，也不会再写已删行、不会再触发开录。
- 批量完成日志新增 `authed` 字段，排障时能直接区分「登录态批量」和「匿名单查」。

审计结论按 10 个问题逐条见下。

## 2. 导入去重是否正确

### 2.1 当前规则

`commands.rs:353 rooms_import` 的平台差异：

| 项目 | 哔哩哔哩 | 斗鱼 |
| --- | --- | --- |
| 导入 identity | 账号 UID | 房间号 `room_id` |
| 第一查 | `find_room(platform, room_id)` | `find_room(platform, room_id)` |
| 第二查 | `find_room_by_uid(platform, uid)`，处理短号/UID 与真实房间号并存 | 没有独立 UID，不做第二查 |
| 命中未删 | 刷新标题/主播/封面/分区/在线/直播状态 | 同左 |
| 命中软删 | `insert_room` 恢复，`ON CONFLICT` 清 `removed_at` | 同左 |
| 未命中 | 新增 | 新增 |
| 导入日志 | rekey / merge / restore + 统计 | restore + 统计（没有 rekey/merge） |

关键点：

- 去重键是数据库唯一键 `(platform, room_key)`，跨平台不会互相覆盖。
- 斗鱼关注项来自关注列表，`room_id` 是数字房间号，所以「关注列表内部重复」「重复点导入」都能命中同一行。
- 软删行不会被 `list_rooms` 看到，但 `find_room` 不过滤软删，因此导入可以恢复它，而不是新建一条。
- 恢复会重置为本次导入的 `auto_record` / `monitor_paused` / 监控规则默认值，不保留删除前的旧设置。这是有意的产品行为，但用户如果期待「恢复后仍保持上次规则」，需要知道这一点。

### 2.2 别名缺口与修复

修复分两层。

第一层是 `platform/douyu.rs:239` 的 `stable_id`。修复前它是 `None`，`room_info` 即使从页面拿到真实数字房间号，`canonical_reference` 也不会归一 `room_key`：

```text
先添加 https://www.douyu.com/yyf
  -> room_info 拿到 room_id=45977，但 stable_id=None
  -> DB room_key 仍是 "yyf"

后导入关注里的房间 45977
  -> find_room("douyu", "45977") 查不到
  -> 新增第二行
```

现在 `stable_id = Some(room_id)`，添加时 `room_key` 和 `canonical_url` 都变成数字；导入 `45977` 会命中同一行。单测 `commands::tests::canonical_reference_promotes_douyu_alias_to_numeric_room` 覆盖归一。

第二层是真机复验时发现的页面解析缺口：斗鱼房间页把配置塞进 JS 字符串，实际是 `\"room_id\":45977`，而 `extract_room_id` 只匹配未转义的 `"room_id":`。结果是别名添加先在 `real_room_key` 报「房间不存在」，`stable_id` 根本没有机会生效。已在 `platform/douyu.rs:653` 增加 `room_id\":` 模式，并扩展现有 `extracts_room_id_from_page` 测试覆盖转义 JSON。

**存量数据注意**：本次修复只影响新添加/新解析。修复前已经用别名添加、且 `room_key` 仍是字母的斗鱼行不会自动迁移；如果同时已经导入过数字行，库里会有两条。处理办法是删除旧别名行后重新添加一次别名，或后续做一次「别名房间归一」迁移。报告不把存量别名行说成已修复。

### 2.3 去重结论

- 数字房间号：正确。
- 重复导入、关注列表重复项：正确，第二次走 existing。
- 软删后重新导入：正确恢复。
- 斗鱼别名：新数据正确；修复前存量别名行需要一次人工/迁移处理。
- B 站：短号、UID 双键、rekey、merge 都保留，未被斗鱼逻辑改写。

## 3. 监控数据和录制数据是否正确区分

区分是清楚的，两条链路只在「房间状态」和「是否该开录」上交汇，不复用播放地址：

```text
监控状态
  B 站：get_status_info_by_uids（批量） / room_info（单房）
  斗鱼：follow/list（批量） / betard（单房）
  产物：is_live、title、host、cover、avatar、area、online、started_at、videoLoop
        -> apply_room_info -> DB + 事件 -> 监控表

录制取流
  开录时由 stream_plan / 平台适配器单独请求
  斗鱼：betard -> getEncryption -> getH5Play -> 真实流地址
  B 站：getRoomPlayInfo -> 真实流地址
  产物：画质、编码、线路、ffmpeg 参数、Cookie
```

具体说：

- `batch_room_info` 只把 `LiveStatus` 映射成 `RoomInfo`，没有 `stream_url`、画质、线路字段。
- 批量结果里的 `liveStatus/videoLoop` 只用于展示与轮播判定，不参与取流。
- 录制画质来自房间设置/全局设置，取流时再按 Cookie 和平台能力解析；批量不会把「关注列表返回的画质」带进录制。
- 录制启动仍走 `recorder.start_checked`，会重新读 DB 检查 removed / monitor_paused；批量只负责把「该开录」这个动作排进 `run_room_action`。
- 停录判断也在 `apply_room_info` 统一做：离线需要连续两次确认，且录像文件不再增长才停，避免平台状态抖动误停。

结论：**监控批量只做状态发现，录制始终独立取流**。斗鱼批量不会把 B 站的取流参数或画质串过去，也不会复用关注列表里的任何播放地址。

## 4. Cookie 各种情况下的处理

### 4.1 状态定义

`credential.rs:66 is_ok(platform)` 要求两件事同时成立：

1. 内存里有 Cookie；
2. 数据库加载的状态是 `ok`。

`credential.rs:85 cookie_for_url` 只对平台接口域名注入 Cookie；状态不是 `ok` 时按匿名请求，不把过期 Cookie 发给平台。

### 4.2 行为矩阵

| 场景 | 斗鱼批量 | 斗鱼单房 | B 站批量 | 说明 |
| --- | --- | --- | --- | --- |
| 从未登录 | 关闭（`douyu_ready=false`） | 匿名 `betard` | 仍批量 | B 站状态接口可匿名；斗鱼关注列表必须登录 |
| 有效 Cookie | 开启（且 ≥3 房） | 正常登录态 | 正常 | 每拍一次 follow/list |
| 手动粘贴无效 Cookie | 不写入 | 不写入 | 不影响 | 保存前探针校验，失败 toast「斗鱼 Cookie 已失效或未登录」 |
| Cookie 刚过期、状态仍是 ok | 仍会尝试 1 次批量 | 批量失败后本拍全量单查 | 不影响 | 最坏持续到下一次 30 分钟维护循环才标记 expired |
| 已标记 expired | 关闭 | 匿名 | 仍批量 | 过期 Cookie 不注入 |
| 重新扫码/粘贴有效 Cookie | 下一拍恢复 | 登录态 | 不影响 | `set()` 立即把状态写回 ok |
| 自动续期成功 | 下一拍恢复/保持 | 登录态 | 不影响 | 写回 Cookie 与 ok |
| 自动续期失败 | 可能仍短暂批量 | 匿名或旧 Cookie | 不影响 | 退避 6h/24h；失效时标记 expired |
| 录制中 Cookie 轮换 | 不打断录制 | 下一段取流生效 | 不影响 | 已有会话继续，画质重检另走 156 的状态机 |

### 4.3 一个需要知道的窗口

斗鱼维护循环是「启动后 30 秒先跑一次，之后每 30 分钟一次」：

```text
douyu_auth.rs:1027 maintenance_loop
  sleep(30s)
  loop {
    revalidate(db, app).await;   // 内部有 5 分钟闸门
    refresh_once(db, app, false).await;
    sleep(30min)
  }
```

因此如果 Cookie 在两次维护之间失效：

- 监控批量每 30 秒仍会带着 `is_ok=true` 去请求一次关注列表；
- 关注列表返回 `error=-1`，`run_batch_check` 走「批量状态失败，全量降级单房间检查」；
- 本拍会对每个斗鱼房发一次匿名 `betard`；
- 直到下一次 `revalidate` 探活成功标记 `expired`，批量才停止。

这不是数据错误（不会把房间误判离线，单房匿名 `betard` 仍能返回真实状态），但会产生一段「每 30 秒 1 次失败批量 + N 次单查」的请求放大。当前没有在批量收到 `-1` 时立即标记过期，是本文明确保留的边界。后续如果优化，不能仅凭 `-1` 直接写 `expired`（它也可能是瞬时风控/网络问题），应在 `run_batch_check` 的 `Err` 分支对斗鱼 `-1` 触发一次强制探活：`Probe::Invalid` 才写 `expired` 并跳过本拍全量单查，`Probe::Transient` 只记录日志，避免误把可恢复账号踢下线。

### 4.4 B 站 Cookie 与斗鱼的关系

- B 站批量状态接口不依赖登录，Cookie 失效不会让 B 站批量整体失败。
- B 站 Cookie 影响的是高画质取流、风控和录制档位，属于录制链路，不在本文批量状态范围内。
- 两平台 Cookie 分开存在 `credential` / `credential_secret`，斗鱼续期不会覆盖 B 站，B 站续期也不会覆盖斗鱼。

## 5. 30 秒批量轮询的完整流程

### 5.1 调度

`monitor.rs` 的主循环每秒一拍（`TICK=1s`），但真正的检查由两层节奏控制：

- 单房间：每个房间有自己的 `next_at`，首次按 `spread(room_id, base)` 散在 `0..base`，之后每 `base` 秒一次。
- 批量：每个平台一个 `BatchState`，首次按 `spread("batch:{platform}", base)` 散在 `0..base`，之后每 `base` 秒一次。

当监控间隔设为 30 秒时，`base=30`。批量不是「每个房间各查一次」，而是「这一拍把所有可批量房收进同一批」。

### 5.2 判定顺序

```text
tick 每 1 秒
  -> 读房间列表（2 秒缓存）
  -> 若 base<=0：清空批量节奏，直接返回（关闭自动检测）
  -> schedule.retain 只保留仍在列表里的房间
  -> 对 bilibili / douyu 分别判断 batch_due
  -> 遍历房间：
       暂停监控 -> 移除排期，跳过
       batch_room_ready? -> 加入 batch_rooms，continue
       否则 -> 按单房 next_at 判断是否 run_check
  -> 每个平台最多 spawn 一个 run_batch_check
  -> 批次结束后推进 state.at，清 inflight
```

`batch_room_ready` 的完整条件：

```rust
batch_due && !batch_inflight && !entry.inflight
  && (!entry.backoff || entry.next_at <= now)
```

即：批次到点、批次不在途、房间不在途，且房间不在退避中（或退避已到期）。成功排期带 ±10% 抖动，所以不能用 `next_at <= now` 一刀切，否则正常房间会被误排除；退避状态才要求等到 `next_at`。

### 5.3 30 秒示例

假设：

- 斗鱼已登录；
- 监控里有 5 个斗鱼房间：A/B/C 在关注列表，D/E 不在；
- 关注列表 177 位、2 页；
- 监控间隔 30 秒。

时间线（首次批量拍点假设落在 t=13s，实际由哈希散点决定，不固定为 13）：

```text
t=0s    应用启动，BatchState 首次 at = now + 13s
t=1s..12s  单房排期可能各查各的；批量未到点
t=13s   批量到点：
          - 发 1 次 follow/list?page=1
          - 177 位关注 -> pageCount=2，继续 page=2（同一批内顺序拉，最多 20 页）
          - A/B/C 命中 -> 写状态、推事件、异步开录/停录
          - D/E 未命中 -> 本拍并发 run_check（各 1 次 betard）
          - 日志：批量状态检查完成 platform=douyu rooms=5 keys=5
                  returned=3 live=? missing=2 authed=true elapsed_ms=...
t=43s   下一批，重复上面的过程
t=73s   下一批
```

如果这 5 个房间全部在关注列表：

```text
每 30 秒：1 次 follow/list（通常 2 页） + 0 次单查
```

如果只有 2 个斗鱼房，或斗鱼未登录：

```text
不启用批量
每个房间按自己的 0..30s 散点，每 30 秒 1 次 betard
两个房间的请求不会合并
```

如果批量被平台限流（429/412/-352 等）：

```text
t=43s  批量请求返回限流
       err.is_rate_limited() -> wait = retry_after().unwrap_or(30).max(5)
       not_before = now + wait
       本拍不发单查，所有房间 Outcome::Retry(wait)
       state.at 不推进（冷却结束后立刻补一拍，而不是再等 30 秒）
t=73s  冷却结束，重新批量
```

如果批量失败但不是限流（网络错误、斗鱼 `error=-1` 等）：

```text
本拍：批量失败 -> 对全部房间并发 run_check（单房 betard）
下一拍：如果登录态/网络恢复，重新批量
```

### 5.4 间隔变化

`BatchState.interval != base` 时，`at` 会按新 `base` 重新散点，不沿用旧拍点。这样 30 秒改成 5 分钟不会继续按 30 秒打，5 分钟改回 30 秒也不用等满 5 分钟。

## 6. 兜底能力是否完整

| 情况 | 行为 | 是否正确 |
| --- | --- | --- |
| 关注列表缺少某个房间 | 记为 missing，本拍并发单查 | 正确，缺失不当离线 |
| 整批非限流失败 | 全部房间并发单查 | 正确，但请求量变成 N |
| 整批被限流 | 整平台冷却 `retry_after`，本拍不单查 | 正确，避免放大风控 |
| 批量任务 panic | 未回传房间补 `Outcome::Failed` | 正确，不留下永久 inflight |
| 上一批仍在途 | 本拍跳过该平台批量 | 正确，避免并发批次 |
| 单房退避中 | 本次修复后不进批量 | 正确，退避生效 |
| 单房正在检查 | 不进批量 | 正确，避免同房双查 |
| 监控暂停 | 不进批量、不计入斗鱼 3 房门槛 | 正确 |
| 房间已移除 | 排期清理；落库前再查 removed | 正确，不会幽灵开录 |
| 关注超过 20 页 | 超出部分每拍都 missing -> 单查 | 功能正确，成本高；建议后续分页游标或按需导入 |
| 斗鱼未登录 | 不批量，逐房匿名 betard | 正确 |
| 斗鱼 Cookie 过期但状态未更新 | 批量失败 -> 全量单查，直到维护循环标记 | 数据正确，请求放大，见 §4.3 |
| 应用重启 | 批量/单房拍点重新散点 | 正确，不会所有房间同一秒打平台 |

结论：**语义兜底是完整的**（缺失不判离线、失败不全灭、限流不放大、panic 清理、移除不复活）；**成本兜底不完整**（非关注房、超 20 页关注、过期 Cookie 窗口会放大请求）。这两类要分开看，不能因为「状态对」就说「实现完美」。

## 7. 非关注房间

用户手动添加的斗鱼房间可以不在关注列表里。当前行为：

- 房间仍在 `rooms` 表里，仍参与监控。
- 斗鱼房间数 ≥3 且登录时，批量照常启用；批量每拍拉关注列表，找不到该房间 -> 本拍单查 `betard`。
- 因此该房间的状态是正确的，但每拍成本是「1~2 页关注列表 + 1 次 betard」。
- 如果所有斗鱼房都不在关注列表，批量仍然会跑，因为门槛只看「斗鱼房数量 ≥3 且登录」，不看「是否有关注房」。这是当前实现的浪费点，不是正确性缺陷。

可选的后续优化：批量只对有 `platform_uid`/关注来源的房间启用，或记录房间来源（导入/手动），手动房直接走单查。但这会改变调度模型，本文不做。

## 8. 先添加直播间、后导入关注

分两种情况：

1. **手动添加的是数字房间号**（`https://www.douyu.com/9999`）：
   `room_key=9999`；导入关注拿到 `room_id=9999`，`find_room` 命中，走 existing，不新增。正确。
2. **手动添加的是别名**（`https://www.douyu.com/yyf`）：
   - 修复后：添加时 `stable_id=45977`，`room_key` 归一成 `45977`，导入命中。正确。
   - 修复前的存量别名行：`room_key` 仍是 `yyf`，导入 `45977` 查不到，会新增重复行。需要清理或迁移。

导入命中 existing 时只刷新展示字段，不会因为「导入时开着自动录制」就把已存在房间的 `auto_record` 改掉；是否开录仍看该行原有设置，下一拍监控会按设置执行。

## 9. 移除房间后的单轮询与批量轮询

`commands.rs:616 room_remove` 的顺序：

```text
1. 若正在录制 -> recorder.stop(..., "stopped")
2. view.close_room
3. recorder.resume_auto（清掉手动停录标记，避免影响下次重新添加）
4. db.delete_room（软删 + monitor_paused=1）
5. emit rooms_changed
```

监控侧：

- `tick` 的房间列表来自 `list_rooms`，只返回 `removed_at IS NULL`；下一拍（房间缓存最多 2 秒）就不再包含它。
- `schedule.retain` 清掉它的单房排期。
- 批量批次如果在删除前已经发出，结果回来时 `apply_room_info` 会先查 `room_removed`，直接返回，不写状态、不排开录动作。
- 即使动作已经排进后台，`recorder.start_checked` 还会重读 DB，removed / monitor_paused 会拒绝「房间已移除或监控已暂停」。

结论：单轮询和批量都不会让已移除房间复活或幽灵开录。唯一的时间窗是「删除后到下一拍前」最多约 2 秒的房间缓存，但落库前还有 removed 闸门，所以不会产生错误状态。

## 11. 与哔哩哔哩的差异和相互影响

### 11.1 差异

| 维度 | 哔哩哔哩 | 斗鱼 |
| --- | --- | --- |
| 批量来源 | `room/v1/Room/get_status_info_by_uids` | `wgapi/livenc/liveweb/follow/list` |
| 批量键 | `platform_uid`（账号 UID） | `room_key`（房间号） |
| 是否需要登录 | 状态接口可匿名 | 必须登录 |
| 分页 | 每 200 UID 一片，并发，单片失败重试一次 | 每页 120，最多 20 页，顺序拉 |
| 启用门槛 | 房间有 UID 即可 | 已登录 + 未暂停斗鱼房 ≥3 |
| 缺失处理 | 缺失 UID 单查 | 缺失房间单查 |
| 限流 | 整平台冷却 | 整平台冷却 |
| 批量数据 | uid / room_id / short_id / 标题 / 封面 / 开播时间 / 在线 | room_id / 标题 / 主播 / 封面 / 分区 / 在线 / videoLoop / show_time |
| 状态写入 | 共用 `apply_room_info` | 共用 `apply_room_info` |
| 录制取流 | `getRoomPlayInfo` | `betard -> getEncryption -> getH5Play` |

### 11.2 是否冲突

不会。隔离点：

- `BatchState` 按平台存在 `HashMap<&'static str, BatchState>`，`at/inflight/not_before` 各自独立；B 站限流不影响斗鱼，斗鱼失败也不拖 B 站。
- 批量键独立：B 站读 `platform_uid`，斗鱼读 `room_key`；不会把斗鱼房间号塞进 B 站 UID 列表。
- `batch_room_info` 修复后按 `platform` 决定是否写 `uid`，B 站字段保持不变。
- 数据库唯一键是 `(platform, room_key)`，跨平台同号不会撞行。
- Cookie 按平台存，斗鱼续期/过期不会改 B 站凭据。
- 开录/停录共用 `apply_room_info` 与 `run_room_action`，但平台判断在批量入口已经隔离；斗鱼改动不改 B 站取流。

### 11.3 对 B 站的影响

三处修复中：

- 别名归一：只对 `platform == "douyu"` 生效，B 站 `stable_id` 逻辑不变。
- `batch_room_info` 的 `uid`：B 站仍写，斗鱼不写；单测同时断言两边。
- `batch_room_ready`：对 B 站是增强——B 站缺 UID 的房间单查失败后，退避期间不会再被硬塞进批量。

唯一需要 B 站回归的点是 `batch_room_info` 签名新增 `platform` 参数，所有调用点已补 `"bilibili"`；单测 `douyu_batch_status_does_not_pollute_platform_uid` 同时覆盖 B 站 `platform_uid_of == Some("9999")`。

## 12. 日志是否完整可追溯

现有日志：

| 事件 | 级别 | 字段 |
| --- | --- | --- |
| 批量开始 | info | `platform rooms interval_sec` |
| 批量完成 | info | `platform authed rooms keys returned live missing elapsed_ms` |
| 批量限流 | warn | `error platform rooms retry_after elapsed_ms` |
| 批量失败全量降级 | warn | `error platform rooms elapsed_ms` |
| 缺失房间回退 | debug | `room room_id platform key` |
| 单房失败 | warn | `host hint`，同错误只告警一次 |
| 导入 | info | `total added existing restored merged rekeyed failed`，以及 rekey/merge/restore 的单条 info |
| 房间移除 | info | `room_id` |
| 手动刷新 | info/debug | `room_id live` |

缺口：

- 没有「每个房间在本批成功/失败」的 info 明细，只有汇总；排障要看 debug 的缺失回退或单房日志。
- 批量跳过退避房间没有日志；排查「为什么这房没更新」时只能从下一拍单查日志推断。
- 斗鱼 Cookie 过期导致的批量 `-1` 目前只记「批量状态失败，全量降级」，没有单独标出「登录失效」，也没有立即写 `expired`。

建议后续补一条 debug：「批量跳过退避中的房间 room=... remaining=...」，以及在斗鱼 `-1` 时增加明确日志。当前日志足以定位「批量有没有跑、返回多少、缺多少、耗时多少」，但不能逐房复盘。

### 13.2 真机复验（2026-11-14）

使用 release bundle（31.83 MiB）和真实斗鱼账号（177 位关注、15 位在播），从空库开始复验三个修复。

**别名归一与去重**

- 添加 `https://www.douyu.com/yyf`：日志 `room=yyf live=false`，DB 落成 `room_key=45977`、`canonical_url=https://www.douyu.com/45977`，标题为「机智灵敏的少年~」。
- 再添加 `https://www.douyu.com/45977`：斗鱼房间数仍为 4，没有新增行。
- 先添加数字 `9999`，再打开斗鱼导入：177 位关注、已添加 1，首行 `yyfyyf` 标记「已添加」且复选框禁用；导入 `9263298`、`252140` 后日志 `total=1 added=1 existing=0`，DB 为 3 行。
- 复验前 `https://www.douyu.com/yyfyyf` 返回 404；换成真实的 `/yyf` 后先暴露了转义引号解析问题，修复后才走通，说明第二层修复不是纸面推演。

**批量不污染 platform_uid**

- 3 个斗鱼房时日志稳定为 `批量状态检查完成 platform="douyu" authed=true rooms=3 keys=3 returned=3 live=3 missing=0 elapsed_ms=203/252/305`。

- 45977 不在关注列表，批量每拍 `missing=1`，本拍回退单查 `betard/45977`，成功后下一次仍不进批量；这正是 §7 描述的成本，但状态与 UID 都正确。

**批量尊重单房退避**

- 手工插入 `room_key=bad-room-xyz2` 的斗鱼房，关注列表找不到，批量回退单查 `https://www.douyu.com/bad-room-xyz2`，返回 404 后 `刷新房间失败` 并进入 60 秒退避。
- 19:15:18 批次 `rooms=5 keys=5 returned=3 live=3 missing=2`；19:15:48 下一批变成 `rooms=4`，退避中的房间没有再次被塞进批量。
- 在上一版 666c7a7 构建上用 `bad-room-xyz` 复现同样结果：19:09:30 `rooms=4` -> 19:10:01 `rooms=3`。
