### 1.1 退出窗口有两道门（C1）

只拦 tick 不够：一次 tick 可能已经进到房间循环里，正在解析某一路。所以第二道门放在 `start_inner`——即使监控拿到的是退出前的快照，走到这里也会被「应用正在退出」拒绝。`shutting_down` 是 `AtomicBool` 且只置位不清零，`begin_shutdown` 重入也安全。

### 1.2 并发名额：预检查省请求，插入复查保正确（C2）

完全同时的开录调用里，预检查的计数仍有竞态（三路同一毫秒开播时，实测网络请求还是发了 3 次）。真正的权威闸门是 `inner` 锁里的第二次判断：`inner.len() >= limit` 与 `insert` 在同一临界区，后到的那一路一定看得见前一路。失败路径不只返回错误，还把已经拉起的 ffmpeg `start_kill`、删掉 pid 文件、摘掉弹幕订阅、删掉 `create_session` 写进去的行和空分片——否则会留下「DB 里没有、磁盘上有」的垃圾。

### 1.3 磁盘红线一拍停全卷（C3）

旧实现是房间循环里边查边停：第一个房间的 `stop` 触发 ffmpeg 退出要几百毫秒，等循环走到第二、第三个房间时可能已经过了好几拍，看起来就是「一拍停一路」。现在先算清楚「这块卷低了」，再一次性把所有落在这块卷上的会话都停掉；同一卷只查一次 `statvfs`（5 秒缓存仍然有效）。

### 1.4 收尾窗口不再是「没在录」（C4）

`finalize` 第一件事是把会话从 `inner` 摘掉（为了不让新的 stop 再找到它），但转封装、缩略图、写库可能持续几十秒。这期间监控看到的 `active` 是空的，旧代码会立刻重开。`finalizing` 标记把「这一场还没真正结束」补上，`FinalizeGuard` 保证任何 return 路径都会摘标记，不会永久卡住这一路。

### 1.5 抖动只影响「什么时候查」，不影响节奏（C6）

`grid_at` 是理论上的等间隔网格点，每次成功检查都只从网格往前推一个 `base`；`next_at = grid_at ± 抖动`，并钳到「不早于现在 + 1 秒」。失败/限流分支让网格跟着实际重试时间走，避免补考式连发。抖动值由 `hash64(room_id, 0)` 决定：同一房间每轮都是同一个偏移，单测连算 50 次一致；20 次重排后网格严格前进 20 个间隔，实际触发与网格的差不超过 3 秒。

### 1.6 D1：文件名占位要原子

`unique_path` 是「查一下在不在，不在就用」——两个开录调用在同一毫秒都查到「不在」，于是拿到同一个路径。这与 C2 的并发窗口叠加时尤其容易发生：两路同时开播、同时命名。`create_new` 让内核做仲裁，输的一方自动试 `(2)`、`(3)`…；旁挂 `.jsonl` 先存在也会跳过该名字，避免视频换名而弹幕被覆盖。

## 3. 真机验收

环境：macOS 27.0.1 arm64、ffmpeg 9.0.2（Homebrew）、DB `~/Library/Application Support/com.hivecast.desktop/hivecast.db`、二进制按当前源码重建。时间均为本地时间（UTC+8），日志里是 UTC。

### 3.1 并发上限 + 告警去重（C2 / C7）

3 路真实在播（哔哩哔哩 6、545068、7734200），`max_concurrent=2`，`interval=1`：

- 三路在同一毫秒开录，网络请求发了 3 次（预检查的竞态，符合预期）；
- 第 3 路在插入复查时被拦：`WARN 并发已满，放弃本次开录（已清理会话与进程） room=老实憨厚的笑笑 limit=2`，DB 里没有它的会话，`pgrep` 只剩 2 个 ffmpeg；
- 之后每个检测周期只记 `DEBUG 自动开录仍失败`，`WARN 自动开录失败` 全程 1 条（C7）；
- 40 秒后 DB 仍是 2 条 `recording`。

### 3.2 退出窗口不再多开（C1）

保持上面「2 路在录 + 1 路被上限挡住」的局面，直接 `pkill -TERM`：

- `16:57:03.855 收到 SIGTERM，开始收尾`；`16:57:04.047` 两路先后 `录制结束 aborted/app_exit`（11,240,581 / 0 字节——后者与前者同名同秒，正是 D1 的现场，见 3.4）；
- 从 SIGTERM 到进程退出约 1.2 秒，跨过了至少一个 `interval=1` 的检测拍，但日志里 SIGTERM 之后没有任何 `开始录制`，DB 也没有第 3 条会话。

### 3.3 同卷磁盘红线一拍全停（C3）

3 GiB APFS 稀疏卷挂到 `/Volumes/HIVECASTC3`，经 `HIVECAST_MEDIA_DIR` 指到 `Recording`；3 路在播、`max_concurrent=4`、`interval=3`。三路全部 `recording` 后，一次 `dd` 写入 2,097,152,000 字节（2.8 秒），剩余空间降到 834 MiB：

```text

16:59:57.429246 WARN 磁盘剩余空间低于红线，停止录制 room=主播乙
16:59:57.429294 WARN 磁盘剩余空间低于红线，停止录制 room=主播丙
16:59:57.430748 INFO 请求停止录制 room_id="rm-c3-a" reason="disk_full"
16:59:57.430791 INFO 请求停止录制 room_id="rm-c3-c" reason="disk_full"
16:59:57.430811 INFO 请求停止录制 room_id="rm-c3-b" reason="disk_full"
```

3 条 WARN 与 3 条停止请求都在同一毫秒级窗口内，1 秒内全部收尾。删掉填充文件后约 8 秒，三路各开新会话恢复录制；随后 SIGTERM，三路 `aborted/app_exit`，无残留进程。

### 3.4 同名同秒不再抢文件（D1）

两个房间改成同主播名、同标题（哔哩哔哩 6 与 7734200），`max_concurrent=2`、`interval=1`，同一毫秒开录：

- 日志两条 `开始录制` 分别落到 `...2026-11-07_01-03-24.mp4` 与 `...2026-11-07_01-03-24 (2).mp4`；
- DB 两条会话的 `file_path` 不同；两个 `part0000.ts` 分别为 1,048,576 与 1,572,864 字节，各自增长；
- 修复前同样场景下两路写同一个文件，其中一路收尾时 `file_size=0`（3.2 的 0 字节记录）。

### 3.5 抖动（C6）

`interval=1` 时抖动跨度取 0，真机观察不到偏移，因此 C6 以单测为准（见 §2）；`interval=3` 的 3 路压盘测试里，各房间仍按 3 秒节奏检查，未出现连发或漂移。

## 4. 行为变化与边界

| 项 | 变化 |
| --- | --- |
| 退出时段 | 置位 `shutting_down` 后不再开新会话；已在录的照常收尾成 `aborted/app_exit` |
| 并发已满 | 预检查可能仍放行同时调用，但插入复查一定只留 `limit` 路；被拒的那一路会清掉会话、ffmpeg、空文件 |
| 磁盘红线 | 同一块卷上的所有会话在同一拍一起停，不再一拍一路 |
| 收尾窗口 | `active` 为空但 `finalizing` 为真时，监控不会重开；`finalize` 结束自动解除 |
| 开录在途 | 这时点「停止」不会被吞：请求挂起，会话一挂上就立刻停 |
| 文件名 | 冲突时由内核原子仲裁，保证两个 ffmpeg 不会写同一路径 |
| 日志 | 并发已满只第一次 WARN，后续 debug；磁盘不足仍按房间各 WARN 一次 |
