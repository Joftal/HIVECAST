# 10 · 后处理流水线

> 参考实现：`bililive-go/src/pipeline/`（manager.go 757 行、executor.go 609 行、types.go、config.go、stages/ 六个内置阶段）、`src/configs/config.go` 的 `OnRecordFinished`。
> 后处理 = 录制结束之后、对文件做的所有事情：修复、转封装、截图、烧字幕、上传、执行自定义命令。

## 1. 为什么需要"流水线"而不是"一串 if"

朴素做法：

```text
录制结束 → if 需要修复 { 修复 } → if 需要转 mp4 { 转 } → if 需要截图 { 截图 } → ...
```

问题：

1. 失败后无法从中间重试（只能从头再来，重复转码几小时）。
2. 无法并行（截图和转码其实可以同时做）。
3. 无法持久化（应用重启后不知道哪些文件还没处理）。
4. 无法观测（用户不知道卡在哪一步）。

流水线模型解决全部四点。

## 2. 核心抽象

```rust
struct StageConfig {
    name: String,              // "convert_mp4"
    enabled: Option<bool>,     // None = 默认启用
    parallel: Vec<StageConfig>,// 非空 = 并行子阶段
    options: JsonMap,          // 阶段私有配置
}

#[async_trait]
trait Stage {
    fn name(&self) -> &'static str;
    async fn execute(&self, ctx: &mut PipelineContext, files: Vec<FileInfo>)
        -> Result<Vec<FileInfo>, StageError>;
}

struct PipelineContext {
    record: RecordInfo,        // live_id, platform, host, room, display_name, start_time
    work_dir: PathBuf,
    temp_dir: PathBuf,
    ffmpeg: Option<PathBuf>,
    last_stage_files: Vec<FileInfo>,
    uploaded_paths: Vec<String>,
    progress: ProgressSink,
}

struct FileInfo {
    path: PathBuf,
    size: u64,
    kind: FileKind,            // Video | Cover | Other
    source_path: Option<PathBuf>,  // 转换后的"原始文件"
    metadata: JsonMap,
    deletable: bool,           // 全流程成功后可删
}
```

### 2.1 `Deletable` 的语义（易错点）

- 只有**所有阶段都成功**，才删除 `deletable=true` 的文件。
- 任一阶段失败或取消，**保留全部文件**，包括中间产物。

原因：失败后用户要能手动检查/重试，删了就没了。bililive-go 有专门的测试 `TestExecute_StageFailed_AllFilesPreserved` 守住这条。

### 2.2 阶段顺序

```text
fix_flv → convert_mp4 → extract_cover → burn_subtitles → cloud_upload → custom_command
```

顺序原则：

1. **修复在最前**：时间戳坏的 FLV 转 mp4 会失败。
2. **转换在截图前**：截图要读可 seek 的文件。
3. **烧字幕在转换后**：烧录本身要重编码，先转成 mp4 再烧可以一次编码搞定（也可以直接烧 FLV，但兼容性差）。
4. **上传在最后**：只有最终产物才值得上传。
5. **自定义命令最后**：用户可以基于最终文件做任何事。

## 3. 内置阶段详解

### 3.1 fix_flv

**问题**：录制中断（崩溃/强杀）的 FLV，时间戳会跳变或元数据缺失，导致：

- 播放器无法 seek；
- 转 mp4 失败（`Non-monotonous DTS`）；
- 时长显示为 0。

**做法**：

```bash
ffmpeg -err_detect ignore_err -i broken.flv -c copy -f flv fixed.flv
```

- `-c copy` 不重编码，秒级完成。
- 部分场景需要 `-fflags +genpts` 重建时间戳。
- 修复后校验：`ffprobe` 能读出 duration 才算成功。

**配置**：`on_record_finished.fix_flv_at_first`（默认 **true**）。

### 3.2 convert_mp4

```bash
# 直接封装（快，但要求编码兼容）
ffmpeg -i in.flv -c copy -movflags +faststart out.mp4

# 不兼容时转码
ffmpeg -i in.flv -c:v libx264 -crf 18 -preset medium -c:a aac out.mp4
```

- 先试 `-c copy`，失败再转码（判断依据：ffmpeg 退出码 + stderr 关键词）。
- `-movflags +faststart` 把 moov 移到文件头，网页播放必需。
- 进度解析：ffmpeg 的 `-progress pipe:1` 输出 `out_time_ms=`，配合已知总时长算百分比。

**配置**：`convert_to_mp4`、`delete_flv_after_convert`。

### 3.3 extract_cover

```bash
ffmpeg -ss 00:00:03 -i in.mp4 -frames:v 1 -q:v 2 cover.jpg
```

- 取第 3 秒（避开开头的黑帧/加载画面）。
- 视频短于 3 秒则取第一帧。
- 产物 `FileKind::Cover`，`deletable=false`（要保留）。

**配置**：`save_cover`。

### 3.4 burn_subtitles

```bash
ffmpeg -i in.mp4 -vf "ass=/path/danmaku.ass" -c:v libx264 -crf 18 -preset medium -c:a copy out.mp4
```

- ASS 路径转义是最大的坑（Windows 盘符冒号、空格、单引号）。
- 必须做**时长校验**：ASS 与视频差太多就跳过并警告（见 09 文档 §6.4）。
- 进度同 convert_mp4。

**配置**：`burn_subtitles`、`burn_subtitles_codec`（默认 `libx264`）、`burn_subtitles_crf`（默认 `"18"`）、`burn_subtitles_preset`（默认 `medium`）、`burn_delete_ass`、`burn_delete_source`。

### 3.5 cloud_upload（OpenList）

```text
上传目标路径模板：
/录播归档/{{ .Platform }}/{{ .HostName }}/{{ .FileName }}
```

流程：

1. 登录 OpenList（`POST /api/auth/login`，用户名密码）拿 token。
2. `PUT /api/fs/put` 流式上传（带 `File-Path` 头）。
3. 可选：上传后删除本地（`delete_after_upload` / `delete_all_after_upload`）。

**配置**：`cloud_upload{enable, storage_name, upload_path_tmpl, delete_after_upload, delete_all_after_upload}`、`upload_timing`（`immediate` 立即上传 / `after_process` 处理完再传）。

> 建议默认 `after_process`：避免上传中间产物。

### 3.6 custom_command

```text
模板：ffmpeg -i "{{ .FilePath }}" ... 
```

- 模板变量：`FilePath`、`FileName`、`Dir`、`Platform`、`HostName`、`RoomName`、`StartTime`。
- **必须做 shell 转义**，否则标题里的引号能注入命令。
- 超时要可配（默认 30 分钟），超时杀进程组。

**配置**：`custom_commandline`。注意：**设置了自定义命令时，内置阶段不再执行**（bililive-go 的行为），避免重复处理。

## 4. 并行子阶段

`StageConfig.parallel` 非空时，该阶段变成"容器"，其子阶段并行执行：

```yaml
- name: post
  parallel:
    - name: extract_cover
    - name: burn_subtitles
```

实现要点：

- 用 `tokio::JoinSet` / `rayon` 并发跑；
- 任一失败 → 整体失败，但**取消其他任务要优雅**（发取消信号，等 5s）；
- 共享 `ctx` 需要 `Arc<Mutex>` 或改为每个子任务拿只读快照 + 独立输出收集。

> bililive-go 的 `executeParallel` 就是这个模型。注意它的 `onProgress(stageIndex, stageName, status)` 回调是按"扁平化后的阶段索引"上报的。

## 5. 任务队列与持久化

### 5.1 数据模型

```text
PipelineTask {
  id, record_id, live_id,
  status: pending | running | completed | failed | canceled,
  current_stage, stage_index,
  files: [FileInfo],
  error, attempts,
  created_at, started_at, finished_at
}
```

SQLite 表 `pipeline_tasks`。**必须持久化**，否则重启丢任务。

### 5.2 调度

```text
poll_loop（每 1s）:
  1. 取出 status=pending 的任务
  2. 按 max_concurrent（默认 3）填充执行槽
  3. 启动任务 → 更新 status=running
  4. 完成 → completed/failed
```

### 5.3 重启恢复

```text
启动时：
  UPDATE pipeline_tasks SET status='pending' WHERE status='running'
```

把"运行中"重置为"待处理"。**不要标记为失败**——它可能只是没跑完。

### 5.4 重试

| 操作 | 语义 |
| --- | --- |
| `retry(task)` | 从第一个阶段重跑 |
| `retry_from_stage(task, stage)` | 从指定阶段开始，之前的产物复用 |

后者是关键：转码跑了 2 小时失败在上传，不该重转。实现方式：任务记录每个阶段完成后的 `files` 快照，重试时从该快照恢复。

## 6. 进度上报

```text
on_progress(task_id, stage_index, stage_name, status, percent?)
```

- `percent` 只对有明确总时长的阶段有意义（转码/烧录/上传）。
- UI 展示：`[2/5] 转封装 mp4 ... 45%`。
- 没有百分比的阶段（修复 FLV）显示"处理中"即可。

## 7. 失败处理矩阵

| 失败阶段 | 后续阶段 | 文件处理 |
| --- | --- | --- |
| fix_flv | 全部跳过 | 保留原始文件 |
| convert_mp4 | 跳过截图/烧录/上传 | 保留 flv + 半成品 mp4 |
| extract_cover | 继续后续 | 无封面，继续 |
| burn_subtitles | 继续上传（无字幕版） | 保留 ASS |
| cloud_upload | 标记失败，可重试 | 保留本地文件 |
| custom_command | 标记失败 | 保留全部 |

**原则**：非关键阶段（截图、封面）失败不应阻断主流程；关键阶段（转换、上传）失败要显式标记。

## 8. 临时文件管理

```text
work_dir/<record_id>/
  ├─ source.flv          // 原始
  ├─ fixed.flv           // 修复后
  ├─ output.mp4          // 最终
  ├─ cover.jpg
  └─ danmaku.ass
```

- 每个任务独立目录，避免并发冲突。
- 任务完成/失败后按 `deletable` 清理。
- 启动时清理"孤儿目录"（DB 里没有对应任务的）。
- 清理孤立 ASS：录制中断可能留下没有对应视频的 ASS（bililive-go 有 `cleanupOrphanedAssFiles`）。

## 10. 反模式

1. ❌ 在录制线程里做转码 → 阻塞下一段录制。
2. ❌ 任务不持久化 → 重启丢失，文件永远不处理。
3. ❌ 失败就删文件 → 无法排查。
4. ❌ 重试从头开始 → 重复几小时转码。
5. ❌ 自定义命令不做转义 → 命令注入。
6. ❌ 上传与转码串行且都在主流程 → 用户看到"录制完成"但文件还没好。
7. ❌ 并行子阶段共享可变 ctx 无锁 → 数据竞争。
8. ❌ 不清理临时目录 → 磁盘慢慢被吃满。
