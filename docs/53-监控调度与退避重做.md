# 53 · 监控调度与退避重做

> 状态：v1.0（2026-11-06）已实施
> 前置：docs/52（监控设置的界面与配置项）。本文只改「怎么调度、怎么退避」，配置项不变。
> 影响文件：`src-tauri/src/monitor.rs`（重写）、`src-tauri/src/broker.rs`、`src-tauri/src/platform/mod.rs`、`src-tauri/src/settings.rs`

## 0. 结论

| 维度 | 改前 | 改后 |
| --- | --- | --- |
| 调度方式 | tick 内 JoinSet 等所有房间跑完（阻塞） | tick 只派发，结果走 channel 回填，永不阻塞 |
| 单请求超时对全局的影响 | 一个 10 秒超时会拖慢整轮（最多 ceil(N/4)×10s） | 只影响它自己那个房间 |
| 排期 | 完成时刻 + 间隔（会累积漂移） | 固定网格（上一拍 + 间隔），落后太多从现在重算 |
| 相位 | 所有房间同一相位，每间隔一次尖峰 | 首次按房间 id 哈希散开 + 每次 ±10% 抖动 |
| 并发 | 全局 4 | 全局 12 + 每平台 4（平台之间不再互相排队） |
| 限流退避计数 | 一个 failures 什么都加 | throttle_streak 只加真限流；普通错误只记 error_count |
| broker 冷却期返回 | 合成一个 Network 错误（被当成真限流再翻倍） | 新增 PlatformError::Throttled{retry_after}，不计失败、按秒重排 |
| 退避判定 | broker 与 monitor 两套（-412/412 不一致） | 统一走 PlatformError::is_throttle |
| 退避抖动 | 无 | ±20% |
| 退避上限默认 | 300 秒 | 120 秒（可配范围仍 60–3600） |
| 平台级熔断 | 无 | 本版不做（用户裁决：等量起来再看） |

实测一句话：6 个房间、间隔 10 秒时，请求从「每 10 秒 6 个同时打」变成「每秒 0–2 个、均匀铺开」；一个房间人为卡满 10 秒，其余 5 个仍然稳定 10 秒一轮。

## 1. 改前的问题

### 1.1 调度

1. **tick 是阻塞的**：`while let Some(joined) = set.join_next().await` 要等本轮所有房间结束。HTTP 超时 10 秒（`platform/http.rs:18`），20 个房间里有 5 个卡住时，整轮约 22 秒，其余 15 个房间即使早该检测也只能等。
2. **间隔从完成时刻算**：`next_at = now_ts() + wait` 的 now 是全部跑完的时间，真实节奏 = 间隔 + 本轮耗时，房间越多越慢。
3. **相位完全对齐**：启动时所有 next_at = 0，之后又同批加同样的间隔，于是长期「每 30 秒一起打 20 个请求，中间 29 秒静默」——最容易被判定异常流量的形态。
4. **全局并发 4 把不同平台串起来**：限流是按平台的，斗鱼在跑时 B 站却在排队。

### 1.2 退避

1. **假错误被当真限流**：broker 冷却期内直接返回 `PlatformError::Network("平台请求过快…")`，而 `is_throttle()` 把所有 Network 都算限流 → 监控 failures 再 +1 再翻倍。一次真实 429 可能被放大成 5–6 次失败，直接把房间冻到上限。
2. **普通错误也累加**：RoomNotFound、Parse 失败都会让 failures 增长，只是「等多久」看那个 bool；等第一次真限流到来时，shift 已经很大。
3. **两套判定不一致**：broker 只对 -352/-429/429 退避，monitor 还包含 -412/412。
4. **没有抖动**：同时被限流的房间同时等 60 秒，再同时重试，二次撞墙。
5. **没有平台级熔断**：平台整体 429 时，20 个房间各自退避、各自重试，对平台的压力并没有下降。
6. **上限 300 秒太钝**：限流通常几十秒恢复，300 秒意味着最坏错过 5 分钟开播。

## 2. 新调度模型

```
每 1 秒一拍：
  1. settings::load → base / cap / backoff_on（base = 0 时清空排期并丢弃结果）
  2. drain(rx)：把已经回来的结果按 Outcome 落进排期表（纯内存）
  3. tick()：读房间 → 磁盘红线（停录扔后台）→ 清理已删房间 →
     对每个到期且不在途的房间：标记 inflight、spawn 任务、立即返回
  4. sleep 1s
```

任务里先抢「平台名额」再抢「全局名额」（平台才是瓶颈），跑完把 (room_id, Outcome) 发回 channel。

### 2.1 四种结果

| Outcome | 触发 | 排期 | 计数 |
| --- | --- | --- | --- |
| Ok | 正常返回（含未开播） | 上一拍 + 间隔 + ±10% | streak/error 清零 |
| Throttled | 平台限流 / 网络错误 | min(base×2^streak, cap) + ±20% | streak+1、error+1 |
| Retry(n) | broker 冷却期（没出门） | now + n | 不变 |
| Failed | 房间不存在 / 解析失败等 | now + 间隔 + ±10% | 只 error+1 |

### 2.2 固定网格

`grid_next(previous, now, base)`：`previous + base`；如果已经落后（≤ now，例如机器休眠），就从 now 重算，不补课、不连发。

### 2.3 抖动

`jitter(id, span)` 用 DefaultHasher(id, salt) 取模，确定性、可复现。排期抖动 ±10%，退避抖动 ±20%。

### 2.4 首次散开

新房间 `next_at = now + hash(id) % base`，把启动瞬间的 N 个请求摊到一个间隔里。

## 3. 新退避模型

- `PlatformError::Throttled { retry_after }`：broker 冷却期专用，`code() = "platform_throttled"`，`retry_after()` 返回秒数。
- `broker::should_backoff` 直接复用 `PlatformError::is_throttle()`，两处判定统一（-352/-412/-429/412/429/Network/Throttled）。
- 监控先看 `retry_after()`：有值就 Retry，不 set_error、不发事件、不计失败。
- 普通错误仍然 `recorder.set_error` + 发 `EVENT_ROOMS_CHANGED`，但不改节奏。

## 5. 实测

环境：macOS arm64，`pnpm tauri dev`，6 个房间（B 站 2、斗鱼 2、虎牙 1、抖音 1），`auto_record=0`，间隔 10 秒，每秒采样一次 `room.last_checked_at`。

### 5.1 相位分散

40 秒采样里，每一秒只有 0–2 个房间刷新，单房间间隔稳定 10–11 秒。改前同配置会在同一秒出现 6 个相同时间戳。

### 5.2 慢房间不阻塞

用临时探针让 `room_key=21452505` 在请求前 sleep 10 秒：

- 慢房间：7406 → 7426 → 7446…（20 秒一轮 = 10 秒超时 + 10 秒间隔）
- 其余 5 个：7396/7406/7417/7427/7437…（稳定 10 秒）

说明 tick 不再等待任何一个请求。

### 5.3 间隔收缩与关闭

- 间隔从 300 改成 5：6 个房间里 5 个在 6 秒内刷新（第 6 个正在 10 秒请求中，16 秒后刷新）。改前旧排期会继续拖最多 300 秒。
- 间隔改 0 后连续 20 秒所有 `last_checked_at` 完全不变（改前已支持，回归验证）。

### 5.4 Retry 不计失败

用临时探针让 `room_key=6` 直接返回 `Retry(5)`：刷新时刻 7511 → 7517 → 7523 → 7529（6 秒 = 5 秒 + 1 秒节拍），`room.error` 保持 NULL——没有把「冷却中」写成错误，也没有翻倍。

探针验证后已删除（grep `TEMP-VERIFY` / `HIVECAST_SLOW_ROOM` / `HIVECAST_FORCE_THROTTLE` 无输出）。

## 7. 缺口与后续

- 没有平台级熔断（用户裁决：等房间量起来再做）。现在平台整体 429 时仍是各房间独立退避，只是有了 ±20% 抖动不会完全同步。
- 开播检测的物理上限仍是「间隔」；要秒级捕捉只能接平台长连接（B 站弹幕 WS 自带开播事件），另立项。
- 调度节拍 1 秒，间隔最小有效值约 1 秒。
- 每拍读一次 `settings::load`（几条 SQLite 查询）；房间上千时可改成事件驱动刷新配置。
- 退避上限从 300 降到 120 只改默认值，已保存过 300 的配置不会被自动改写。
