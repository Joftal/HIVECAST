# 82 录制后处理复盘：改动、影响面与四方对比

> 状态：复盘稿（2026-11-08）。覆盖 v1（`e288844`）与 P0–P2 工作区改动；实测与边界以 [81-录制后处理P0-P2修复与验收](81-录制后处理P0-P2修复与验收.md) 为准。
> 对比对象：`bililive-go`、`streamlink`、`biliLive-tools`。本文回答四件事：改了什么、影响多大、现在的工作流是什么、与三个参考项目相比处在什么位置。

## 0. 结论先行

1. **这不是“多了一个转 MP4 开关”，而是把录制成品拆成了两层。** 录制器只负责封出与直播源对应的“源封装母带”；转封装、自定义命令产出的都是“派生文件”。派生失败不影响母带，源路径永远不被派生路径覆盖。
2. **安全顺序是四方里最严格的。** HIVECAST 的顺序是：临时文件 → ffprobe 校验 → fsync → rename → DB 提交 → 才允许把源移入回收站。三个参考项目里，只有 bililive-go 的内置 Pipeline 接近这个顺序；biliLive-tools 转换成功就删源且 DB 可能仍指旧文件；streamlink 根本不做后处理。
3. **当前已经不是“后处理内核缺能力”，而是“缺任务中心与生态”。** 重试、取消、并发槽、磁盘预检、进度、失败文案、双文件播放、仅删源都已闭环；剩下的是全局任务列表、跨平台回收站细节、派生文件登记，以及上传/压制/字幕/封面/Webhook 等 P3。
4. **按本项目“录制 + 后处理”目标，完成度约 90%–95%；按四个项目功能并集，约 50%–55%。** 差距主要不在正确性，而在生态广度和任务产品化。
5. **最值得学的不是功能清单，而是边界。** 学 bililive-go 的阶段化和“全部成功再删源”，学 biliLive-tools 的回收站/输出占用检查/引用计数思路，学 streamlink 的抓流与后处理解耦；不要学 shell 自定义命令、成功即删、单路径覆盖、双转换链路。

## 1. 这次到底改了什么

### 1.1 产物模型：母带 + 派生

| 产物 | 定义 | 谁生成 | 是否可删 |
| --- | --- | --- | --- |
| 源封装母带（source） | 与直播源容器对应的完整文件：FLV→FLV、HLS/TS→TS、DASH→MP4、FLV+HEVC/AV1→MKV、AudioOnly→M4A/MKA | 录制收尾时合并/重封装 | 默认保留；只能显式“仅删源”进回收站 |
| 派生文件（derived） | 转封装或自定义 FFmpeg 的输出：MP4/MKV/TS/自定义扩展名 | 后处理 | 可重做；失败不影响母带 |

数据库用两个路径表达这件事：`source_path` 是母带，`file_path` 是当前主播放文件。`source` 模式下两者相同；`convert/custom` 成功后 `file_path` 指向派生文件，`source_path` 仍指向母带。媒体库因此能同时展示“主文件”和“源封装”，而不是只知道一个路径。

### 1.2 三种互斥模式

| 模式 | 默认 | 产物 | 删源 | 自定义命令 | 适用 |
| --- | --- | --- | --- | --- | --- |
| `source` | 新安装默认 | 母带本身 | 不动 | 不执行 | 想保留直播源封装，后续手动处理 |
| `convert` | 否 | 母带 + MP4/MKV/TS | 仅显式开启，且转换成功、DB 提交后 | 不执行 | 想直接得到剪辑软件可用的容器 |
| `custom` | 否 | 母带 + 自定义输出 | **永不自动删** | 执行 ffmpeg argv | 转码、压制、裁切等高级处理 |

互斥是后端强制的，不只是 UI 隐藏：`custom` 的 `delete_source` 计算结果恒为无；`source` 不进入转换分支；切到非 `convert` 时设置页会把删源开关复位。

### 1.3 后处理内核

核心在 `src-tauri/src/post.rs`（约 1596 行），入口是 `post::run`（`post.rs:210`）：

- **模式分派**：`execute` 按 `post_mode` 走 `run_convert` / `run_custom` / 源校验。
- **容器映射**：`source_extension`（`post.rs:398`）决定母带扩展名，FLV+HEVC/AV1 走 MKV，DASH 走 MP4，HLS/HTTP-TS 走 TS。
- **转换**：`run_convert`（`post.rs:415`）用 `-map 0 -c copy`，MP4/MOV 加 `+faststart`；同扩展名直接校验复用，不生成第二份。
- **自定义**：`run_custom`（`post.rs:467`）把模板分词，替换 `{input}`/`{output}`，只启动 ffmpeg，不经过 shell；必须同时含两个占位符，拒绝管道、重定向、shell 变量。
- **临时文件**：`.{原文件名}.post-{uuid8}.{ext}`（`post.rs:933`），与目标同目录，避免跨卷 rename。
- **校验**：ffprobe 检查至少一个流且能读出时长/流信息；缺 ffprobe 时用 ffmpeg 只读前 1 秒（`post.rs:1046`）。
- **提交**：临时文件非空、校验通过、fsync 成功，才删旧目标并 rename（`post.rs:519` 起）。
- **删源**：`trash`（`post.rs:1117`）移入系统回收站；只有 `convert + delete_source + target != source` 才返回待删源，调用方在 DB 提交后才执行。
- **并发**：自动 1 + 手动 1 + 全局 2 三组信号量（`post.rs:91`）。自动任务先拿自动槽再拿全局槽，手动最多占一个全局槽，始终给录制收尾留余量。
- **磁盘预检**：`ensure_disk_headroom`（`post.rs:832`）要求 `free >= 源大小 + 15% + 256 MiB`，不足直接失败并给出“需要约 X，当前可用 Y”。
- **进度**：解析 `out_time_us/out_time_ms/time=`，映射 5%–90%，校验 93%，完成 100%；失败/取消回 0。
- **取消**：会话级 `AtomicBool` + 任务级 `TaskSlot`；排队每 120ms、运行每 150ms 检查；杀进程后最多等 5 秒，删临时文件；应用退出 `shutdown` 最多等 6 秒。
- **失败文案**：`explain_failure` 把 stderr 归为磁盘满、编码器不可用、容器无法识别、输入打不开、无权限、无输出、无有效流、通用失败，附退出码与最后 3 行。

### 1.4 UI 与数据

- 设置页从单个“自动转 MP4”开关改为三张互斥卡片（`SettingsView.tsx:803` 起），只有选中 `convert` 才显示目标封装/删源，只有 `custom` 才显示命令/扩展名/超时。
- 媒体库卡片显示统一后处理徽标：`排队中`、`N% · 取消`、`后处理失败 · 重试`、`后处理已取消 · 重试`、`已转封装`、`自定义后处理`、`保留源封装`；源已删追加 `· 源已删`。
- 详情抽屉只有在 `source_path != path` 时显示“文件”区：播放主文件、播放源封装、仅删源（二次确认）。源删后隐藏源播放与删源。
- 手动“转 MP4”已收编到 `post::run`（`commands.rs:525`），不再走旧的 `postprocess::remux`；成功后若没有 `source_path`，把旧主文件登记为母带，新 MP4 成为主文件；失败保持原主文件可播。
- 新增命令：`post_retry`（`commands.rs:607`）、`post_cancel`（`commands.rs:688`）、`media_delete_source`（`commands.rs:694`）；事件 `post://progress`。

## 2. 当前工作流程

### 2.1 开录

1. 解析实际线路，拿到 `StreamFormat` + `Codec`，用当前设置快照一份 `PostConfig`（中途改设置只影响下一场）。
2. `post::source_extension` 决定母带扩展名，不再固定 `.mp4`。
3. 原子占位创建母带路径，DB 写 `source_path`、`post_mode`、`post_state=recording`。
4. 录制期间 ffmpeg 实际写同 stem 的 `.partNNNN.ts` 分片；母带是收尾时合并出来的，不是录制期间直接写源容器。

### 2.2 录制中

- 仍是一条连续 ffmpeg，不在停止/重启之间丢画面。
- 分片、清单、看门狗、崩溃恢复沿用原有链路。
- 后处理不参与录制中；只有收尾才开始。

### 2.3 收尾

```text
停止 ffmpeg
  → 按分片规划 clip
  → 每段合并成源封装母带（失败退化为字节拼接）
  → post::run
       source  : 只 ffprobe 校验
       convert : 临时文件 → -c copy → ffprobe → fsync → rename
       custom  : 分词 → 替换占位符 → ffmpeg → 校验 → rename
  → DB 事务提交 file_path / source_path / post_mode / post_state
  → convert + delete_source：DB 提交成功后才把源移入回收站
  → 全部片段与 DB 成功后清单标 completed 并删除
```

关键顺序：

- **先有母带，才跑后处理。** 母带合并失败不会进入转换。
- **先校验，再 rename。** ffmpeg 退出码 0 不等于产物完整。
- **先 DB，再删源。** 删源失败只 WARN，源保留，状态仍 `done`；不会把“删源失败”误报成“转换失败”。
- **失败不丢源。** 转换失败、超时、校验失败、rename 失败都会删临时文件，返回源路径 + `failed` + `post_error`。
- **已失败的段不会在下次启动自动重跑。** 恢复只补缺失的源/最终文件，保留失败状态，避免无限重试。

### 2.4 三种模式的实际差别

- `source`：收尾后只校验母带；媒体库主文件就是母带。
- `convert`：生成派生文件；主文件切派生；源默认保留，除非用户显式开删源。
- `custom`：生成自定义派生文件；源永不自动删；命令失败时主文件仍是母带。

### 2.5 重试、取消、删除

- **重试**：只接受 `failed` / `cancelled`；源优先 `source_path`，否则 `file_path`；沿用原 `post_mode`，其余参数取当前设置。成功切主文件；失败/取消保持原主文件，只更新状态与错误。
- **取消**：覆盖整场，不只当前片段；排队中也能取消；取消后清理临时文件并写 `cancelled`。
- **仅删源**：拒绝录制中、无独立源、源==主文件；源已不存在直接标记；源还在时先校验主文件，通过后停回放、进回收站、写 `source_deleted=1`。
- **删除整场**：主文件、源封装、弹幕、sidecar 一起删；单段失败保留该段记录，方便重试。

### 2.6 状态机

```text
recording
  → 收尾
      ├─ source  → done（母带）
      ├─ convert → done（派生主文件，源可保留/已删）
      ├─ custom  → done（派生主文件，源保留）
      ├─ 失败    → failed（源保留，可重试）
      └─ 取消    → cancelled（源保留，可重试）
```

DB 只持久化 `recording/done/failed/cancelled` 四个状态；`queued/preparing/converting/validating` 是运行期事件阶段，不落库。重启后不会自动续跑排队任务。

## 3. 影响面

### 3.1 行为变化

- **默认行为变化**：从“默认自动 MP4”变成“默认保留源封装”。这是有意的产品决策，不是回归。
- **旧设置不迁移**：`post.auto_remux` 被忽略；新默认 `source`。项目仍在迭代、无外部用户，这是用户明确选择。
- **旧历史不回填**：迁移只加列，不把老 `file_path` 回填到 `source_path`；老会话在媒体库没有“源封装”行。
- **旧清单按 source 恢复**：`version: 1` 的 `remux` 字段被忽略，老清单不会自动转 MP4。
- **降级不兼容**：旧二进制不认识新列；升级/降级必须换对应二进制，不能指望热迁移。
- **手动转封装**：只对非 mp4 主文件可用；成功后主文件切 mp4，源保留；播放器当前流不会热切。

### 3.2 数据与 API

- `record_session` 新增 `source_path/post_mode/post_state/source_deleted/post_error` 五列；SQLite 启动迁移只加列。
- `finish_session_with_post`（`db.rs:599`）一次事务写入主文件与后处理状态。
- `MediaItem.has_source` 让前端区分“源仍在”和“源已删”；`post://progress` 让卡片显示百分比。
- 新增 12 个 i18n 键；`check:i18n` 从 536 增到 548。

### 3.3 存储与性能

- **转换峰值**约“源 + 临时文件”两份；删源进回收站也不会立即释放空间，清空回收站才释放。
- **磁盘预检**在启动 ffmpeg 前完成，避免跑到一半才因磁盘满留下半成品。
- **并发上限**为自动 1 + 手动 1 + 全局 2；多房间同时收尾会排队，不会同时起无限 ffmpeg。
- **自动后处理有进度**，长录像不再只有“卡住”感；但进度按 ffprobe 时长估算，时间戳异常的源可能不准。
- 后处理仍与录制共享磁盘 I/O；极端情况下长录像转换会拖慢同盘录制，这是桌面单机应用的固有取舍。

### 3.4 安全边界

- 自定义命令不经过 shell，管道/重定向/变量会被拒绝；但这不等于“任意命令沙箱”——它仍是本机 ffmpeg 进程，能读写用户有权访问的文件。
- 源删除只发生在 `convert && delete_source && 转换成功 && DB 提交成功` 之后；`custom` 永不自动删。
- 目标文件已存在时不会覆盖源；同名派生文件按 mtime 判断是否本次产物，可能误复用用户手工放入的更新文件（复用前仍 ffprobe 校验）。
- Linux 回收站只移动文件、不写 `.trashinfo`，桌面环境可能无法“还原”；Windows 文件被占用时删源失败可重试。

## 4. 四方对比

### 4.1 真实模型

| 维度 | bililive-go | streamlink | biliLive-tools | HIVECAST 当前 |
| --- | --- | --- | --- | --- |
| 定位 | 直播录制 + 阶段化后处理 | 抓流 CLI/库 | 录制 + 转封装 + 上传/弹幕/Webhook 工作流 | 桌面录制 + 后处理内核 |
| 抓流层职责 | 拉流并按源写 FLV/TS/AAC | 只把流字节写入文件 | 拉流并固定 `-c copy` 到 ts/m4s/flv | 拉流 + TS 分片 |
| 成品模型 | 源对应封装，录完进 Pipeline | 用户指定，无后处理概念 | 录制层直接出 ts/m4s/flv，可选立即转 MP4 | **源封装母带 + 派生文件** |
| 后处理入口 | `OnRecordFinished` + Pipeline | 无 | 录制器 `convert2Mp4` + Webhook 转封装（两条） | 收尾时 `post::run` 单入口 |
| 内置转换 | 临时文件 + rename，`-c copy` | 无，交给外部 ffmpeg | 同目录直接输出，`-c copy` | 临时文件 + ffprobe + fsync + rename |
| 删源 | 所有阶段成功统一删；自定义成功即删 | 无 | 录制器 `unlink`；Webhook 可 `trash` | DB 提交后移入回收站，失败保留 |
| 自定义命令 | 有，shell 模板，无超时 | 无 | 无任意命令，只有 ffmpeg `extraOptions` | ffmpeg argv，不走 shell，有超时 |
| 数据模型 | 文件/通知为主 | 无 | 单 `video_file`，转换后常不更新 | 5 个后处理字段，主/源双路径 |
| 崩溃恢复 | 依赖文件系统 | 无 | 弱，无统一后处理状态机 | 清单 v2 + DB 状态 + 文件系统 |
| 扩展生态 | 烧字幕、封面、上传、通知 | 无 | 上传、弹幕压制、Webhook、预设 | 仅录制 + 后处理 |

### 4.3 各项目优缺点

#### bililive-go

**优点**

- 阶段化 Pipeline 是参考里最成熟的：修复 FLV、转换、封面、上传等阶段可组合。
- 内置转换用临时文件 + rename，且所有阶段都成功后才统一删源，失败保留现场。
- 平台覆盖广，录制产物与源格式对应。

**缺点**

- 自定义命令走 shell（Linux `sh -c`、Windows `cmd /C`），无超时；失败只打 Debug 日志。
- 自定义命令退出 0 且勾了“转换后删除 FLV”就 `os.Remove`，不检查输出文件是否存在、是否非空、是否真的是转换产物。
- 自定义命令一开，内置 Pipeline 全部绕过；一个“上传/发通知”的命令也可能把源删掉。
- 没有“母带 + 派生文件”的双路径模型，媒体库无法同时展示两个产物。

**可学 / 不可学**：学阶段化、全成功再删、临时文件 + rename；不学 shell 模板、成功即删、失败只 Debug。

#### streamlink

**优点**

- 边界最干净：抓流层只负责拿到字节并写文件，容器、后处理、上传都是外部工具的事。
- 不偷偷改扩展名、不偷偷删文件；用户完全掌控输出路径。
- 作为 CLI/库组合性强，适合被别的工具调用。

**缺点**

- 没有后处理、没有媒体库、没有状态机、没有删除安全语义；普通桌面用户要自己写 ffmpeg 命令。
- 不适合直接作为“桌面应用默认体验”的参考；它证明的是解耦，而不是产品完整度。

**可学 / 不可学**：学抓流与后处理解耦；不学把容器选择完全丢给用户。

#### biliLive-tools

**优点**

- 生态最完整：录制、转封装、上传、弹幕压制、Webhook、预设串成一条工作流。
- 有输出占用检查：目标已存在时按“已完成”复用，避免重复转换，但也可能把用户手工放入的文件当成自己的产物。
- Webhook 链路用系统回收站；fileRef 式多消费者删除标记的收敛思路值得借鉴。
- 有任务/进度/错误事件，用户可见性比 bililive-go 的自定义命令好。

**缺点**

- 不是“源封装 + 派生文件”模型，而是“录制层固定 `-c copy`，可选录完立即转 MP4 并删源”。
- 录制器链路转换成功后 `fs.unlink` 源，但 DB/历史仍指原文件；重启也不会自愈。
- Webhook 是第二条转换链路，默认删源，覆盖 `rawFilePath`，原路径直接丢失；官方 UI 自己提示两条链路不要同时开。
- 没有任意自定义命令；`extraOptions.split(" ")` 这种“伪自定义”遇到带空格路径会拆坏。
- 转换直接写目标，失败可能留下半截 MP4。

**可学 / 不可学**：学回收站、输出占用检查、fileRef 式删除标记、任务可见性；不学双链路、单路径覆盖、立即 `unlink`、按空格拆参数。

#### HIVECAST 当前

**优点**

- **产物模型正确**：母带永远保留，派生文件可重做、可删除，不影响母带。
- **顺序正确**：临时文件 → 校验 → fsync → rename → DB 提交 → 回收站；任何一步失败都不丢源。
- **自定义命令安全**：只执行 ffmpeg argv，不走 shell，必须含输入/输出占位符，有超时，源永不自动删。
- **数据一致**：`file_path` 是当前主播放文件，`source_path` 是母带，媒体库能同时展示；手动转封装也更新 DB。
- **恢复能力**：清单 v2 记录每段源、最终文件、后处理状态；崩溃后优先复用，不重复转换，不把失败误标成功。
- **用户可见**：失败有红色徽标和 `post_error`；源可定位，源删有明确标识；重试/取消可直接操作。

**缺点**

- 没有全局任务中心：并发槽和进度已有，但没有“历史任务/排队列表”页面；任务只活在本次进程内，重启不续跑。
- 自定义命令仍是本机 ffmpeg 进程，不是安全沙箱。
- 回收站跨平台语义不同；Linux 无法保证桌面“还原”。
- 同名派生文件按 mtime 复用，可能误复用用户手工放入的新文件。
- 手动转封装改变主文件扩展名时，旧派生文件可能留下；当前不自动删，避免误删。
- 仍没有上传、压制、字幕烧录、封面、Webhook、云同步、预设管理。
- 母带是容器重封装，不是 bit-exact 原始流；分片仍是 MPEG-TS。

### 4.4 几个关键反例

1. **“成功即删源”反例（bililive-go）**：用户把自定义命令写成“上传到网盘/发 webhook”，同时勾了“转换后删除 FLV”。上传命令退出 0，源 FLV 被删，但网盘可能只传了一半，或者根本没有转换文件。HIVECAST 的 `custom` 永远不会自动删源，而且命令必须是 ffmpeg 参数。
2. **“DB 仍指旧文件”反例（biliLive-tools）**：录 1 小时 `.ts`，转成 `.mp4` 后删 `.ts`；媒体库的 `video_file` 还是 `.ts`，点播放会“文件不存在”，重启也不会自愈。HIVECAST 在同一个事务里更新主文件与母带路径。
3. **“半成品”反例（biliLive-tools）**：转封装到 60% 磁盘满，目标路径留下半截 MP4；如果 UI 或别的进程误把它当成品，就会播放失败。HIVECAST 先写临时文件，失败只删临时文件。
4. **“抓流层不该管后处理”反例（streamlink）**：它没有后处理，反而证明了边界清晰；HIVECAST 也把录制器限定为“封母带”，转换由独立编排器做。

### 5.2 两个口径

- **按“录制 + 后处理”核心目标**：约 **90%–95%**。三条主路径、失败恢复、并发/磁盘/进度、双文件、手动收编、真机验收都完成；缺的是任务中心和少量边界。
- **按四个项目功能并集**：约 **50%–55%**。HIVECAST 的录制与后处理正确性不落后，但上传、压制、字幕、封面、Webhook、预设、云同步等生态明显缺失。
- **按“桌面产品完整体验”**：还处在“可靠内核 + 基础 UI”阶段，不是完整媒体工作流产品。

## 6. 建议的下一步

1. **先做任务中心，不要继续加模式。** 统一展示排队/运行/失败/完成，支持重启后续跑或明确标记“已中断”；这是当前最大产品缺口。
2. **补派生文件登记。** 一场录像可能有多个派生文件（手动转封装、重试、不同格式）；用一张派生表或引用计数管理，删除时只删无人引用的文件。
3. **把回收站差异产品化。** macOS/Windows 走系统回收站；Linux 明确提示“仅移动到回收站目录，桌面可能无法还原”，或提供“永久删除”单独选项。
4. **custom 保持边界。** 不为了表达力放开 shell；如果要做“上传/通知”，应作为独立后处理阶段，而不是让任意命令承担删源。
5. **P3 生态另立产品层。** 上传、压制、字幕烧录、封面、Webhook 都应复用“母带 + 派生 + 多消费者删除标记”的模型，不要复制 biliLive-tools 的双转换链路。

## 7. 一句话总结

HIVECAST 的录制后处理已经在“产物模型、失败安全、数据一致性、可恢复性”上超过三个参考项目的对应实现，当前是一个可靠的后处理内核；它还不是完整的媒体工作流产品，下一步最值得做的是任务中心、派生文件登记和 P3 生态，而不是继续堆模式。
