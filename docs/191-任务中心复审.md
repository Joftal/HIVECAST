# 任务中心复审：陈旧收尾、重试入口与历史分页

- 日期：2026-11-23
- 范围：任务中心聚合、任务页、Run 详情/时间线、历史分页、跨 Run 检索导出，以及与监控、录制文件、账号异常的周边联动
- 基线：`be2c1d2`（任务中心历史虚拟化与跨 Run 检索）之后的复审改动
- 结论：核心链路可用，本轮修掉 4 处会误导用户的边界问题；仍有明确未覆盖的排队态与失败路径需要后续补测

## 1. 当前实现总览

### 1.1 后端聚合

- `src-tauri/src/task_center.rs` 是唯一聚合入口：按 `record_session.group_id` 把同一场直播的片段收进同一个 Run，再挂上 `task_history`、内存任务、房间与平台凭据状态。
- 一条 Run 固定四段链路：录制 → 收尾 → 后处理 → 入库。
  - 录制：`recording` / `finished` / `failed` / `aborted`；`aborted + app_exit` 归为「已中断」。
  - 收尾：分割清单合并、生成成品；`finalize` 任务只推进这一段，不再作为独立后处理任务展示。
  - 后处理：`source`（保留源封装）/ `convert`（转封装）/ `custom`（自定义命令）。
  - 入库：历史行是否已经有可播放产物；异常中断有产物时是 `partial`，没有产物时是 `failed`。
- Run 状态优先级（本轮 192 已修正）：`recording > running > queued > finalizing > failed/partial > interrupted > cancelled > done`；详情、统计、筛选都读同一份 `RunView`。
- 任务页首屏不再携带事件：详情抽屉打开时调用 `task_run_events`，只读当前 Run（分组会展开到所有片段），每页 200 条、按 `(at,id)` 游标向前翻。
- 历史默认 100 场、每次「加载更多」加 100、上限 1000；前端表格按 420px 视口 + 8 行 overscan 只渲染可见行。
- 跨 Run 检索由 `db::task_event_search` 完成，消息/阶段/状态/任务/主播/标题都参与 LIKE，导出 CSV 按同一筛选重查，上限 5 万条。

### 1.2 任务页

- 顶部：全部 / 运行中 / 排队 / 需要处理 四个筛选 + 房间/直播中/录制中/排队/24 小时失败五张统计卡。
- 其下：四平台态势卡（凭据状态、房间数、直播数、录制数、批量耗时）、系统行（ffmpeg、磁盘、录制目录）。
- 需要处理：登录失效、录制失败、任务失败；动作分别是打开账号、打开直播间、查看任务/重试后处理/重试收尾。
- 进行中：Run 卡展示平台、房号、画质、主播、标题、时长、体积、四段轨、当前阶段与详情入口。
- 最近完成：虚拟化表格；状态列只保留一个状态 Chip（此前阶段文字与 Chip 重复，已在前一轮去掉）。
- 详情抽屉：四段链路、阶段时间线、任务列表、上下文、复制诊断；底部按状态给「录制文件 / 重试收尾 / 重试后处理 / 关闭」。
- 周边导航：`open_room` / `open_account` / `open_task` / 录制文件入口都复用应用现有路由；任务页不复制监控或设置页的逻辑。

## 2. 本轮修复

### 2.1 陈旧收尾失败不再污染已完成的 Run

- 问题：收尾任务失败后，崩溃恢复或手动重试可能已经把场次写成 `finished`，但 `task_history` 里仍留着旧的 `finalize failed`。旧逻辑会让 Run 永远显示失败，并且继续给「重试收尾」。
- 修复：`task_center.rs` 的 `finish_run` 在构造最终状态前，只保留最新一条 finalize 任务；若最新一条是 `failed` / `interrupted`，而分组内所有片段都已 `finished`，则清掉这条陈旧失败。旧记录仍留在 `task_history`，不会丢审计。
- 分组边界：必须所有片段都 finished 才清；只要还有片段未完成，失败和重试入口都保留。
- 单测：`stale_finalize_failure_on_finished_session_is_not_retryable`、`stale_finalize_failure_is_cleared_only_when_every_group_member_finished`。

### 2.2 重试收尾必须有可用的分割清单

- 问题：场次失败、收尾阶段失败，但 `split_manifest` 已被清理时，页面仍给「重试收尾」；点击后只能得到「没有待恢复的收尾清单」。
- 修复：`RunDraft` 增加 `finalize_manifest_ready`；聚合时用 `db.split_manifest_for(representative_id)` 取清单路径并检查文件仍存在。`RunView.finalize_retry_ready = 清单存在 && 收尾阶段失败 && 仍有未完成片段`。
- 行为：没有清单的失败 Run 只保留「查看任务」；有清单的 Run 才出现「重试收尾」。即使清单记录存在但文件被手工清理，也不会给出死按钮。
- 单测：`finalize_retry_requires_a_live_manifest`。

### 2.3 旧版收尾任务统一归一到 finalize

- 问题：早期版本把收尾写成 `kind=post`、`id=job:*`。如果只看 `kind == "finalize"`，这些任务会被当成后处理，导致链路、异常动作和重试分流全部错位。
- 修复：`task_view` 对 `job:` 前缀 + `kind=post` 归一为 finalize；新的 `kind=finalize` 与旧记录走同一条路径。`auto:<session>:0` 仍是 post，不受影响。
- 单测：`finalize_tasks_are_recognized_and_never_listed_as_post_work`。

### 2.4 历史「加载更多」失败时正确回滚

- 问题：`loadMore` 先推进本地上限再请求；如果请求真的失败，上限不回滚，下一次轮询会带着更大的 limit，界面却没有任何数据，按钮也消失了。
- 修复：只有 `!result.ok && !result.stale` 时回滚 `historyLimitRef` 与 state；`stale` 表示并发轮询已经用新上限拿到了数据，不能回滚。`refresh` 也只在 `load().ok` 时提示成功。
- 说明：失败路径本轮只做代码审查，未在真机注入网络失败；正常加载与并发轮询已验收。

## 4. 没有做或仍有边界

1. **排队态未自然构造**：本轮只有一个真实录制，后处理槽位没有出现真正的排队 Run；「排队」筛选和 QueuedRow 只做了代码审查，没有新的真机证据。历史轮次曾用夹具验证，但不能等同于本轮。
2. **加载更多失败未注入**：只审查了回滚分支；真实网络失败、超时、并发轮询覆盖仍未在界面复现。
3. **有效清单重试未重复真机**：`finalize_retry_ready` 的单测与上一轮真实重试验证了链路；本轮只验证「无清单不再给入口」，没有再次造有效清单跑一次合并。
4. **历史上限固定 1000**：超过 1000 场只能看到最近 1000 场；「全部」数字包含筛选后的历史与无法归属的 orphan incident，不是数据库总组数。
5. **事件仍需手动翻页**：单场超过 200 条时按「加载更早」逐页取；没有时间跳转、按阶段过滤或一次性导出单场全部事件。
6. **检索窗口 200、导出 5 万**：检索结果默认最近 200 条；导出超过 5 万会被截断并写日志。
7. ~~**收尾锁只在进程内**~~：已在 [192](192-任务中心五项边界确认.md) 扩为清单文件锁，并在创建任务前抢占；锁冲突不再留下假失败任务。
8. **失败 Run 的入库阶段**：后处理失败且没有可重试产物时，入库可能仍显示「等待中」；这是状态模型对「以后可能重试」的保守表达，本轮未改。
