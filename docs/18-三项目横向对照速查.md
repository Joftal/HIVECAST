# 18-三项目横向对照速查

> 对象：`bililive-go`（Go 服务端录制器）、`streamlink`（Python 取流库）、`biliLive-tools`（Electron 桌面录制工具）。
> 用途：做技术决策时先看这一页；需要细节再跳 `01`/`02`/`17`。
> 口径：行数按各仓库 `src` 下的实现代码统计（不含测试/文档），仅用于量级比较。
> 2026-11 复核：取流、录制状态机、登录、弹幕的逐项实现已拆到 `129`–`133`；本文保留全维度对照，具体参数与新差距看那五篇。

## 1. 三者角色

| | bililive-go | streamlink | biliLive-tools |
| --- | --- | --- | --- |
| 一句话 | 常驻服务，盯着直播间，开播就录，录完做后处理 | 把任意直播页/URL 变成可播放的流，交给播放器 | 桌面应用，多平台录制 + 弹幕 + 上传 + 切片，一站式 |
| 你最该从它拿什么 | 领域模型、监听/录制状态机、阶段化后处理、配置分层 | 流抽象（HLS/DASH/HTTP）、分片下载与缓冲、清晰度权重、插件匹配 | 取流/录制/下载三段切分、弹幕落盘与压制、任务队列、桌面端工程化 |
| 它不该被抄的地方 | Web UI 与 API 的耦合、Go 的隐式接口装配 | 一次性 CLI 的生命周期假设（无持久状态） | monorepo 15 包、awilix DI、Koa+passKey 本地服务 |
| 语言/构建 | Go 1.2x，单二进制，Makefile | Python 3.9+，pyproject + hatch | TS/Electron，pnpm workspace + Vite + electron-builder |
| 许可 | MIT | BSD-2-Clause（注意部分插件例外） | **GPL-3.0-only**（代码不能直接抄进闭源项目） |
| 规模 | ~38k 行 Go + React UI | ~257 个 py 文件（含插件） | ~110k 行 TS/TSX/Vue |

**许可提醒**：biliLive-tools 是 GPL-3.0。**读它的设计、照着它的思路自己写没问题；把它的源码文件拷进 HIVECAST 会传染 GPL**。本文所有"照搬"均指"按同样的参数/流程自己实现"。

## 2. 全维度对照

| 维度 | bililive-go | streamlink | biliLive-tools | HIVECAST 取舍 |
| --- | --- | --- | --- | --- |
| 进程模型 | 单进程，goroutine | 单进程，CLI 退出即结束 | Electron 主进程 + 本地 Koa + 渲染进程 | 单进程（主进程）+ 渲染进程，无本地 HTTP 服务 |
| 平台扩展 | `live.Register(domain, builder)` + `Live.Start()` | `Plugin` 子类 + `@pluginmatcher` 正则（带优先级） | 每个平台一个 npm 包，实现 `PlatformParser` 与 `RecorderProvider` | 一个 `PlatformAdapter` 接口，`src/platforms/<id>/` 目录 |
| 匹配 | 域名精确匹配（map） | 正则列表 + 优先级排序 | 正则 `matchURL`（StreamGet）+ 正则（RecorderProvider） | 正则 + 优先级 + 规范化 URL |
| 房间信息 | `GetInfo()` 返回 `Info` 结构 | 不关心（只在取流时顺带拿） | `getRoomInfo()` 返回 `LiveInfo`（含 `raw`） | 与 biliLive-tools 同构，但字段更收敛 |
| 流候选 | `GetStreamInfos()` 返回 name/url/quality | `_get_streams()` 返回 `{name: Stream}` | `getStreams()` 返回 `SourceInfo{name, streams}`（按线路分组） | **按线路分组**（主线/备线），这是 biliLive-tools 比另两者都好的地方 |
| 清晰度模型 | 平台字符串 + 选择打分 | 统一 `stream_weight` 数值 | 平台原始 `quality` + `qualityDesc`，上层映射 | 原始值 + 统一权重双写 |
| 取流实现 | 平台返回直链，交给 ffmpeg | 自己实现 HLS/DASH 解析、分片拉取、解密 | 平台返回直链（StreamGet），交给下载器 | 直链优先；需要解密/过滤时自研 segmented |
| 下载引擎 | ffmpeg 子进程（native-flv 例外） | 自研分片 + RingBuffer + ffmpeg 合流 | ffmpeg / mesio / bililive 三选一，接口统一 | ffmpeg + 自研 HTTP 下载器两条，接口统一 |
| 抗断流 | 监听循环 + 录制重试 | `check_sequence_gap` + 无新分片超时 + HLS 重载 playlist | 短录制阈值 + 备用流切换 + 立即重查（≤10 次） | 三者合并：gap 检测 + 短录制重试 + 备线切换 |
| 分段 | 时长/大小/改名 | 时长/分片边界 | 时长/大小，文件名 `-PART%03d` | 时长/大小/标题变化/序列号断裂 |
| 文件收尾 | ffmpeg 正常退出 | 自己写容器 | 先临时名，段结束 rename；fmp4 抗损坏参数 | **沿用 rename 语义** + fmp4 参数 |
| 弹幕 | 内置多平台 WS 客户端 + ASS 渲染 | 无 | 平台 DanmaClient + XML 10s 批量落盘 + DanmakuFactory | 自己写 XML 落盘（照流程），ASS 自己渲染 |
| 后处理 | 阶段流水线 + 任务队列 + 从阶段重试 | 无 | TaskQueue 按类型限流 + webhook 接入外部录制器 | bililive-go 的阶段模型 + biliLive-tools 的限流 |
| 持久化 | SQLite/文件 + 会话心跳/名称变更 | 无 | better-sqlite3 主库 + 弹幕库分离，STRICT 表 | SQLite 单库 + WAL，表按域拆但同库 |
| UI 通信 | REST + SSE | 无（stdout） | REST + SSE + 录像 WS | Electron IPC（invoke + event） |
| 调度 | 每房间 listener + 全局并发控制 | 单次 | **每 provider 一个 setTimeout 循环** + 线程池 | 单调度器 + 每房间下次检查时间（heap） |
| 配置 | 三层（默认/文件/命令行）+ 热重载 | CLI 参数 + 插件选项 | JSON 文件 + defaultsDeep + `update` 事件 | 单文件 JSON + schema 校验 + 事务式保存 |
| 崩溃恢复 | 有（录制中断标记） | 无 | 部分（record_history + 临时文件清理） | 必须做：启动扫描孤儿文件/孤儿任务 |

## 3. 同一个问题，三种解法

### 3.1 "怎么判断该不该录"

- bililive-go：`Live.Verify` 系列规则 + 房间状态字段，规则较薄。
- streamlink：不管。
- biliLive-tools：**多层门禁**，顺序固定：标题关键词 → 付费/加密/大航海/密码房 → 清晰度是否可满足 → 时间段（`handleTime`）→ 手动禁录场次（`banLiveId`）。
- **HIVECAST**：照 biliLive-tools 的顺序，但把"门禁"抽成独立模块（`RecordGate`），每个门禁返回 `Allow / Skip(reason) / Force`，UI 能解释"为什么没录"。这是三者都没做好的地方（现在的产品只显示状态，不解释原因）。

### 3.2 "流坏了怎么办"

- bililive-go：ffmpeg 退出 → 等 `RetryInterval` 重开，简单但慢。
- streamlink：检测分片序号跳变/长时间无新分片 → 重新请求 playlist。
- biliLive-tools：ffmpeg stderr 里连续 35 行（HLS）/18 行（FLV）无效即判死；录制 <12s 连续 2 次 → 下次换备线；≥60s 非手动停止 → 1s 后立即重查（最多 10 次）。
- **HIVECAST**：三层递进 —— ① 分片级检测（不等 ffmpeg 退出）② 秒退计数 + 备线切换 ③ 指数退避重连，并记录"本次失败原因"给 UI。

### 3.3 "怎么保证文件不损坏"

- bililive-go：依赖 ffmpeg 正常退出；强杀会丢 moov。
- streamlink：自己写容器，控制力最强但复杂度最高。
- biliLive-tools：`-movflags +frag_keyframe+empty_moov+separate_moof -min_frag_duration 10000000` + 先临时名再 rename + KILL 时最多丢一个 fragment。
- **HIVECAST**：默认 fmp4 参数；对必须用 ts 的平台，保留 `.ts.tmp` 直到收尾完成；启动时扫描 `.tmp` 并尝试修复/隔离。

### 3.4 "弹幕怎么落盘"

- bililive-go：内存聚合，录制结束写一次（长时间直播有内存风险）。
- streamlink：无。
- biliLive-tools：**每 10s 追加写**，首次写头部 + metadata，停止时补 `</i>`；XML 带内联 XSL，浏览器可直接看。
- **HIVECAST**：10s 批量 + 强制 flush；但改用 `.jsonl` 旁挂 + 结束时生成 XML/ASS（避免"XML 只写了一半"的不可恢复态），或者双写。

### 3.5 "怎么通知 UI"

- bililive-go：SSE（`/api/events`）+ 轮询兜底。
- streamlink：无。
- biliLive-tools：SSE 四个端点 + WS 只给录像流。
- **HIVECAST**：`webContents.send` 推事件 + `invoke` 拉快照；事件按"房间 id + 版本号"增量，避免整表刷新。

### 3.6 "怎么组织后处理"

- bililive-go：`pipeline` 阶段数组，每阶段有输入/输出后缀，任务持久化在 DB，可从未完成的阶段续跑。
- streamlink：无。
- biliLive-tools：`TaskQueue` 按类型限流（各 3 并发）+ 队列上限 300 + 结束事件补位 + 夜间时段限制。
- **HIVECAST**：阶段图（DAG，允许"转封装"和"上传"并行）+ 每阶段可取消/可重试 + 单类型并发上限。

## 5. 三个项目共同的坑（提前避）

1. **"检查"和"下载"耦合**：三者早期都有这个问题，导致下载卡住时检测不到下播。HIVECAST 从第一版就分两个循环。
2. **文件名/路径含中文与空格**：三者的日志里都有相关 issue。所有外部进程调用必须用参数数组，不拼 shell 字符串。
3. **平台风控**：请求频率、UA、Cookie 域、Referer 缺一不可。桌面端可以做"低频模式"（间隔 ≥90s）作为默认。
4. **长时间运行的内存**：弹幕/日志/事件历史都必须有上限（biliLive-tools 的 `timeline = 40` 就是这类保护）。
5. **时钟**：弹幕时间戳用"服务端时间 - 开播时间"还是"本地时间 - 开始录制时间"，三者实现不同。跨时区/系统休眠后必然错位，HIVECAST 要选定一种并在文件里记录基准。

## 6. 决策速查（只记 10 条）

1. 平台层：**一个接口 + 按线路分组的流候选 + 错误码**（biliLive-tools 的形状，bililive-go 的注册方式）。
2. 录制层：**检查循环与下载循环分离**（bililive-go），下载器可插拔（biliLive-tools）。
3. 抗断流：**分片级检测 → 秒退重试 → 备线切换 → 指数退避**（四层，缺一不可）。
4. 文件安全：**fmp4 参数 + 临时名 rename + 启动扫描孤儿**（biliLive-tools + 自研）。
5. 门禁：**独立 RecordGate 模块**，每条规则给出可展示的 skip reason。
6. 调度：**单调度器 + 每房间下次检查时间**，不要每房间一个 timer。
7. 弹幕：**批量落盘 + 强 flush**，格式优先 JSONL 旁挂，XML/ASS 作为导出产物。
8. 后处理：**阶段 DAG + 类型限流 + 可取消**。
9. 通信：**IPC invoke 拉快照 + event 推增量**，不做本地 HTTP。
10. 许可：**只读 GPL 项目的设计，不拷它的代码**。
