> 状态：复查、修复、单测与真机验收完成（2026-11-21）。承接 [186-任务中心复查与边界收口](186-任务中心复查与边界收口.md)。
> 本轮范围：重新通读任务中心后端聚合与前端页面，重点检查分组多片段后处理、阶段事件、历史分页、异常入口和周边链路；只改本轮确认有问题的路径，不新增任务类型或数据库语义。
> 后续：第 6 节的全局事件上限、表格行语义与长录制回归已在 [188-任务中心时间线懒加载与表格可访问性](188-任务中心时间线懒加载与表格可访问性.md) 处理，本节保留其余风险。

## 1. 结论

任务中心的主链路仍然正确：录制中的 Run 会实时更新时长与体积，停止后按「录制 → 收尾 → 后处理 → 入库」推进，失败/中断进入「需要处理」，历史按 Run 分组，平台筛选会同时重算统计卡与列表。

本轮确认并修掉 4 个问题：

| 问题 | 修复前 | 修复后 |
| --- | --- | --- |
| 分组内两个片段都后处理失败 | 重试好第一段后，异常卡仍指向第一段；再点只报「只有失败或已取消的后处理才能重试」 | 逐片段清理已恢复的任务，异常卡立刻转到第二段 |
| 中断的后处理重试成功 | 旧 `interrupted` 任务仍留在 Run 里，继续提供重复重试入口 | 与 `failed` 一样，在场次 `post_state=done` 后隐藏 |
| 一次读取上千条 Run 的阶段事件 | SQL 按时间升序截断，最近完成的 Run 可能整条没有时间线 | 先取最新事件，再裁掉最旧，保留最近 20000 条 |
| 同一秒内多条历史场次分页 | 只按 `started_at` 排序，OFFSET 可能重复或漏行 | `started_at DESC, id DESC` + 联合索引 |

另外补了历史行的键盘入口（Enter/Space 打开详情），让这批可点击的表格行不再只能靠鼠标。

## 2. 当前实现与逻辑

### 2.1 Run 从哪里来

任务中心不新增录制表，而是把已有数据聚合为 Run：

- 房间：`room`，给 Run 提供平台、主播、标题、头像；
- 场次：`record_session`，一条录制会话或一个分割片段；
- 任务：`task_history`，录制、收尾、后处理、合并等任务；
- 内存任务：`jobs`，正在排队/运行的任务板；
- 阶段事件：`task_event`，详情时间线。

有 `group_id` 的场次按 `group_id` 合成一条 Run；首片段没有 `group_id` 时启动阶段会回填为自身 id。无分组的普通场次 Run id 为 `session:<session_id>`，分组 Run id 为 `session:<group_id>`。

### 2.2 状态机

Run 状态按以下优先级计算（`src-tauri/src/task_center.rs` 的 `finish_run`）：

| 状态 | 条件 |
| --- | --- |
| `finalizing` | 收尾任务正在合并/切片/写库 |
| `recording` | 有活动录制任务、场次 status=recording，或正在起流 |
| `running` | 后处理/合并任务正在运行 |
| `queued` | 有排队任务，且没有活动任务 |
| `failed` | 有失败任务、失败场次、收尾失败 |
| `partial` | 同组既有成功片段又有失败片段，且不是整场失败/收尾失败 |
| `interrupted` | 场次或后处理被上次退出打断 |
| `cancelled` | 用户取消 |
| `done` | 其余已结束情况 |

阶段不是独立状态机，而是从任务与场次推导：录制阶段看 `record` 任务和 session.status；收尾看 `finalize` 任务；后处理看 `post/remux`；入库看文件是否存在、是否部分产物。详情里的四段链路和顶部的状态 Chip 使用同一份推导结果，避免两处口径不一致。

### 2.3 需要处理与动作

`build_incidents` 只收集最近 24 小时的失败、部分失败和中断；同一 Run 最多先给一条任务异常，避免一个分组刷出多条重复卡片。动作分四类：

- `retry_post`：失败/中断的 post/remux，有 session_id 才能重试；
- `retry_finalize`：收尾失败且仍有未 finished 的片段、存在可恢复清单；
- `open_task`：收尾清单已消费或没有可重试工作，只打开详情；
- `open_room` / `open_account`：录制失败、监控退避、登录失效。

登录失效、ffmpeg 缺失、磁盘不足属于平台/系统级异常，不受 Run 筛选影响。

### 2.4 历史与筛选

- 首屏 `HISTORY_PAGE=100`，每次「加载更多」+100，最多 1000；
- 后端 `history_has_more` 由「已结束分组数 > 当前 history」决定；
- 顶部「全部 / 运行中 / 排队 / 需要处理」与四平台筛选共用同一份 Run 集合；
- 选中平台后，房间/直播/录制/排队/24 小时失败五张统计卡与进行中/历史列表一起重算，不再显示全局数字；
- 历史按已结束 Run 分组，分割片段只出现一行，体积/时长/结束时间求和。

## 3. 本轮修复

### 3.1 逐片段清理已恢复的失败/中断任务

位置：`src-tauri/src/task_center.rs:460-476`。

原逻辑只在「分组内所有片段 post_state 都 done」时清失败任务。两个片段都失败时，重试第一段后旧失败任务仍在，异常卡继续指向第一段；用户再点只会得到「只有失败或已取消的后处理才能重试」，真正失败的第二段没有入口。

现在先收集 `post_done` 场次，再逐条保留任务：

```rust
let post_done: HashSet<&str> = group_members
    .iter()
    .filter(|session| session.post_state == "done")
    .map(|session| session.id.as_str())
    .collect();
```

- 有 `session_id` 的任务：该场次 done 就隐藏；
- 没有 `session_id` 的旧任务：仍按「全部片段 done」保守处理；
- 只处理 `post/remux`，不碰录制任务。

复查时又发现同类边界：中断的 post 任务重试成功后，session 已是 done，但旧任务状态是 `interrupted`，原条件只清 `failed`，仍会留下重复入口。现在失败与中断一起清理：

```rust
if !matches!(task.kind.as_str(), "post" | "remux")
    || !matches!(task.state.as_str(), "failed" | "interrupted")
{
    return true;
}
```

新增单测：

- `retrying_one_failed_clip_keeps_the_other_clip_actionable`；
- `retrying_an_interrupted_post_hides_the_old_task_when_session_is_done`。

### 3.2 阶段事件保留最新

位置：`src-tauri/src/db.rs:1749-1801`，调用上限在 `src-tauri/src/task_center.rs:294`。

任务中心一次可能读上千条 Run 的事件。原 SQL 用 `ORDER BY at ASC LIMIT`，超限时先保留最旧事件，最近完成的 Run 反而没有时间线。现在：

- 每个 `IN (...)` 分块按 `at DESC, id DESC` 取最新；
- 汇总后按 `(at, id)` 升序排序；
- 总长度超过上限时 `drain(..len-limit)`，只裁最旧；
- `task_events` 上限从 4000 提到 20000。

新增单测 `task_events_keeps_the_newest_events_when_capped`：写 5 条、limit=3，断言保留 at=3/4/5。

### 3.3 历史分页稳定排序

位置：`src-tauri/src/db.rs:1163`、`:1176`，索引在 `:50-53`。

同一秒内结束的多条场次如果只按 `started_at` 排序，SQLite 不保证次序稳定，分页时可能重复或漏行。两条 `list_sessions` 查询都改为：

```sql
ORDER BY started_at DESC, id DESC
```

并新增：

```sql
CREATE INDEX IF NOT EXISTS idx_record_session_started_id
    ON record_session (started_at DESC, id DESC);
```

### 3.4 历史行键盘入口

位置：`src/features/tasks/TasksPage.tsx:1348-1362`。

历史 `<tr>` 增加 `role="button"`、`tabIndex={0}`、可读的 `aria-label`，并处理 Enter/Space 打开详情，点击路径保持原样。

## 6. 未做与剩余风险

1. **实时录制回归仍不算长场次**：188 已补 9 分钟真实 B 站录制（10 分片 → 51.4 MB），但未跑小时级场次；任务中心消费的录制/收尾链路未改。
2. **20000 条全局事件上限已在 188 改为按 Run 读取（单场上限 2000）**：首屏不再读事件，极端长任务不再挤掉别的 Run；仍未做 2000+ 事件真机压力测试。
3. **历史最多 1000 场**：只验证了 100 → 131 的加载，没有验证 1000 行全量渲染性能；后端有上限和「还有更多」语义。
4. **历史行可访问性已在 188 修正**：外层恢复 `<tr>` 语义，入口改为状态单元格内的真实「详情」按钮。
5. **并发收尾重试**：只有单测覆盖「同清单互斥/不同清单并行」，没有真机同时点两个片段。
6. **测试环境提醒**：SQLite WAL 模式下，退出后立即删除 `-wal/-shm` 会丢掉尚未 checkpoint 的提交；清理测试库前应先正常退出并执行 `PRAGMA wal_checkpoint(TRUNCATE)`。
