# 虎牙关注导入与批量状态

> 日期：2026-11-18  
> 范围：虎牙关注列表导入、关注房批量状态、重播复核、登录态降级。  
> 结论：已接入监控「导入关注」的虎牙来源；11 位关注一次分页加载，导入用 lUid 去重、房号建房；登录后按 30 秒一拍走 WUP 关注列表，只对在播项逐房复核，重播不再显示成直播。

## 1. 背景

哔哩哔哩、斗鱼、抖音先后接入「导入关注」后，虎牙仍只能手工粘贴房间链接。虎牙没有给关注列表提供普通 JSON 接口，网页端走的是 TAV/TUP 的 WUP 二进制协议；直接复用网页请求比逆网页 JS 的签名更稳定。

目标：

- 全量分页拉取关注，展示主播、标题、头像、分区、人气、在播状态。
- 在播关注直接建房，离线关注保留在导入结果里（虎牙没有抖音式关注池）。
- 已添加房间按 UID/房号/别名去重；先手工添加、后导入同一房间时不许出现两行。
- 登录后关注房走批量状态，缺失项回退单房，登录失效降级单房。
- 重播（`is_replay=1`）不能被关注列表的 `liveStatus=1` 带成直播。

## 2. WUP 协议

| 项 | 值 |
| --- | --- |
| 地址 | `https://cdnws.api.huya.com/?baseinfo=default&timestamp=<ms>` |
| Servant | `huyauserui` |
| Func | `getUserSubscribeToInfoList` |
| 请求 | JCE 结构 `GetUserSubscribeToInfoListReq`：UserId{uid, guid} + iPageIndex |
| 响应 | `GetUserSubscribeToInfoListRsp`：items、total、pageSize、pageCount、bcode |
| 分页 | 服务端固定 120 条/页，请求里没有 pageSize；页码从 0 开始 |
| 鉴权 | 必须登录；Cookie 里要有 `udb_uid` 与 `guid`，否则直接报「虎牙关注列表需要登录」 |

关注项字段（JCE tag）：

| tag | 字段 | 用途 |
| --- | --- | --- |
| 0 | lUid | 账号 UID，导入写 `platform_uid`，批量按它匹配 |
| 1 | lProfileRoom | 直播间号，导入写 `room_key` / `room_id` |
| 2 | sNick | 主播昵称 |
| 3 | sShortId | 别名，如 `lpl` |
| 4 | sAvatar | 头像 |
| 5 | iLiveStatus / room id 兼容字段 | 在播标记（见 §5 的重播陷阱） |
| 9 | iLiveStatus | 1 = 在播 |
| 11 | sGameName | 分区 |
| 12 | sLiveDesc | 直播间标题 |
| 14 | iTotalCount | 人气 |
| 15 | iStartTime | 开播时间（Unix 秒） |

## 3. JCE 字符串长度陷阱

第一版把字符串长度写成 `head(0, T_INT32) + i32`，服务端直接返回 **HTTP 502**。JCE 的字符串长度是**裸长度**，不带 tag/type：

- 长度 ≤ 255：`T_STRING1(0x36)` + 1 字节长度 + 内容；
- 长度 > 255：`T_STRING4(0x37)` + 4 字节大端长度 + 内容。

`Writer::string` 与 `Reader::string_value/skip` 已按这个规则重写，单测 `jce_string_uses_raw_length_prefix` 覆盖 `abc` 与 300 字节两种情况。

## 4. 导入与去重

前端 `ImportFollowsDialog.tsx` 的虎牙分支：

- 行键用 `status.uid`（lUid），不是房号。斗鱼没有 UID 才用房号；虎牙如果误用房号，批量会拿 `660000` 去匹配 `1346609715`，每轮都「缺失」并回退单房。
- 提交 `ImportRoomInput`：`platform=huya`、`uid=lUid`、`roomId=房号`、`shortId=别名`，不写 `internalRoomId`。
- 后端 `rooms_import` 先按 `platform_uid`、再按 `room_key`、再按别名找已有房：

| 场景 | 结果 |
| --- | --- |
| 全新关注 | 新增一行，`batch_follow=1`、`platform_uid=lUid` |
| 已按房号添加 | 复用旧行，`rekeyed=1`，房号更新为真实直播间号 |
| 已添加但未进批量 | `upgraded=1`，补 `platform_uid` / `batch_follow` |
| 已添加且在批量 | `existing=1`，界面显示「已添加」，复选框禁用 |
| 软删除后再次导入 | `restored=1`，恢复旧行，保留录像历史 |

真机：

```text
导入关注：已有虎牙房间加入批量状态 room_id=... room_key="660000" uid="1346609715"
批量导入关注 total=1 added=0 existing=1 restored=0 merged=0 rekeyed=1 upgraded=1 failed=0
```

手工先加 `https://www.huya.com/lpl`（room_key=lpl），再导入 660000，最终库中只剩一行：`room_key=660000, platform_uid=1346609715, batch_follow=1`。

## 5. 批量状态与重播复核

登录后 `huya_batch_ready` 为真，即使只有 1 个关注房也走批量：

```text
批量状态检查开始 platform="huya" rooms=2 interval_sec=30
批量状态检查完成 platform="huya" authed=true rooms=2 keys=2 returned=2 live=1 missing=0 unresolved=0 elapsed_ms=116
```

关键设计：

- **只请求一次关注列表**：`fetch_live_statuses` 按 lUid 翻页，缺项回退单房，绝不把「没返回」当离线。
- **只复核在播项**：关注列表把重播标成 `liveStatus=1`（660000 的 `is_replay=1` 在 WUP 里没有对应字段）。批量拿到在播项后逐房打开页面，用 `is_live = isOn && !banned && !replay` 复核；复核失败保留批量结果，避免网络抖动把正在直播的房间误停。
- **请求量**：2 个关注房（1 直播 + 1 重播）= 1 次 WUP + 1 次页面复核；离线项不额外请求。相比逐房检查 2 次页面请求，关注越多节省越明显。
- **登录态降级**：WUP 返回登录失效（`-1`、`-101` 等）时，本拍降级为并发单房检查；明确风控才整平台冷却 120 秒。
- **无 Cookie**：`huya_batch_ready=false`，不进批量，全部走单房匿名检查；导入弹窗明确提示「虎牙关注列表需要登录」，并提供「重试」。

重播复核真机（660000）：

```text
批量状态检查完成 platform="huya" authed=true rooms=1 keys=1 returned=1 live=0 missing=0 unresolved=0 elapsed_ms=527
room_key=660000  is_live=0
```

同一批里真实在播的 222523：

```text
批量状态检查完成 platform="huya" authed=true rooms=2 keys=2 returned=2 live=1 missing=0
room_key=222523  is_live=1  online=1988511
```

导入弹窗同样走 `fetch_follow_page` 的复核，因此 660000 显示为未开播，不会在导入时短暂把回放当直播。

## 6. 真机证据

| 场景 | 结果 |
| --- | --- |
| 登录态导入 | 11 位关注/1 页；导入 660000 后 DB `platform_uid=1346609715`，批量 `returned=1 live=0` |
| 别名 rekey | 先加 `/lpl` 再导入 660000，`rekeyed=1 upgraded=1`，无重复行 |
| 已添加去重 | 再开导入，660000 显示「已添加」，复选框禁用 |
| 重播 | 单房检查与批量都 `live=false`，不自动开录 |
| 真实直播 | 222523 批量 `live=1`，人气写回 1,988,511 |
| 无 Cookie | 导入弹窗「关注列表读取失败。请检查网络或虎牙登录状态后重试。」；监控按 2 个单房请求轮询，660000 仍判重播 |
| B 站/斗鱼/抖音 | 只改虎牙关注模块与虎牙批量分支，三平台代码路径未动 |

## 7. 限制与后续

1. WUP 是网页内部协议，没有公开文档；字段 tag 变化时解析会报「虎牙关注列表协议解析失败」，需要重新对照网页请求。
2. 在播项复核会让「关注数 × 在播数」各多一次页面请求；关注量很大且大量在播时，请求量接近逐房检查。当前按 30 秒一拍、并发复核，实测 2 房 116–254ms。
3. 关注列表的标题是平台给的 `sLiveDesc`；复核只修正开播状态、人气与开播时间，不用页面标题覆盖，避免直播标题在两次请求间抖动。
4. 手工粘贴的 Cookie 若没有 `udb_uid`，只能单房监控，不能导入/批量；需要扫码登录。
5. 导入仍只支持「在播直接建房」，没有虎牙关注池；离线关注不会后台转正。
