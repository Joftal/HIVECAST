# 任务中心全链路追踪 P1 实现

> 状态：P1 已完成并真机验收（2026-11-20）。设计稿见 [179-任务中心全链路追踪设计](179-任务中心全链路追踪设计.md)。
> 范围：不改数据库 schema，不新增 `task_event` 表；先把已有的 `record_session`、`task_history`、`jobs` 聚合为 Run。

## 1. 目标与边界

任务页原来只是把「进行中的后处理任务」和「最近完成记录」平铺，用户看不出一次录制从开录到入库的完整链路，也分不清「在录制」「在收尾」「在转封装」「排队」分别卡在哪一步。

P1 把 **Run（一次录制链路）** 作为第一对象：

```
监控/开录 → 录制 → 收尾（分片合并） → 后处理（转封装/自定义/合并） → 入库（record_session）
```

页面同时提供四平台态势、需要处理异常、进行中 Run、排队 Run 和最近完成历史。

P1 不做：事件级时间线（P2 的 `task_event`）、跨进程持久化运行态、按片段重跑任意阶段、历史详情里的逐秒进度回放。

### 2.1 数据源

| 来源 | 用途 |
| --- | --- |
| `recorder.active_all()` | 正在录制的房间；构造 `record:<session>` 合成任务 |
| `recorder.starting_rooms()` | 正在开录、还没有 session 的房间；用 `starting:<room>` 临时 Run |
| `record_session.status = recording` | 录制进程刚退出、正在收尾的场次；避免 Run 从页面消失 |
| `record_session` 历史 | 最近完成 Run、失败/中断、入库路径 |
| `jobs.board()` / `task_history` | 后处理、转封装、合并、收尾任务 |
| `account::list()` | 四平台登录态 |
| `MonitorStatusMap` | 下次检查、退避、最近结果 |
| `disk::free_bytes()` + ffmpeg 探测 | 系统行与磁盘/ffmpeg 异常 |

`history` 由前端传 100，后端 `clamp(1, 500)`。session 取 `(history*4).clamp(200,1200)`，任务历史取 `(history*4).clamp(200,1600)`，避免一个 Run 的多片段任务被截断。

### 2.2 Run 的 key 与合并规则

- 有 session：`session:<session_id>`。
- 只有开录中：`starting:<room_id>`。
- 录制中的房间先按 session 建 Run；未开始的按 room 建。
- 所有 `status=recording` 的 session 即使 recorder 已摘除也补进 Run。
- 历史 session 倒序补 Run；若已有同 key（录制中）不重复。
- `task_history` 的 `session_id` 命中 Run 就并入；没有对应 session 的独立任务（例如合并）单独建 Run。

### 2.3 Run 状态优先级

`finish_run`（`task_center.rs:351`）按以下顺序判定：

1. `finalizing`（收尾中，优先级最高）
2. `recording`（recorder 活动或 session 仍 recording）
3. `running`（后处理任务活动）
4. `queued`（有 queued 任务且没有活动任务）
5. `failed` / `partial`（有失败；有成功片段时为 partial）
6. `interrupted`（任务中断或 session.reason = app_exit）
7. `cancelled`
8. `done`

其中「排队」不算「运行中」，避免任务页把排队画成有进度的活动 Run。`summary.queued` 与筛选、QueuedRow 都按 Run 计数；`TaskCenter.queued` 仍保留逐条 queued 任务，供详情和后续 P2 使用。

同一 session 可能留下多条收尾记录（崩溃恢复、手动重试）。`draft.finalizing` / `draft.finalize_finished` 用「或」合并，后读到的旧 `done` 不会把正在进行的收尾状态抹掉；`finalize` 任务本身始终不进入任务列表，只驱动「收尾」阶段。

### 2.4 阶段推导

`build_stages`（`task_center.rs:568`）输出四段：

| 阶段 | 数据 |
| --- | --- |
| 录制 | recorder 活动 / session.status / 录制任务 |
| 收尾 | `finalize` 任务或 recorder 的 finalizing 标记 |
| 后处理 | `post/remux` 任务；按 task 状态与百分比归并 |
| 入库 | session 是否有 `file_path`、后处理状态 |

每段有 `state`、`started_at/finished_at`、`percent`、`detail`。

### 2.5 平台态势

`build_platforms`（`task_center.rs:679`）固定四平台（bilibili/douyu/douyin/huya），每张卡包含：

- 登录态（ok/expired/none）
- 房间数、直播数、录制数、暂停数
- 批量关注房间数、是否正在检查、是否退避、下次检查秒数
- `level`：登录失效 error；退避 warn；无房间 idle；否则 ok

### 2.6 需要处理（Incident）

`build_incidents`（`task_center.rs:749`）取最近 24 小时，按严重级别与时间排序，最多 8 条：

| code | 触发 | 动作 |
| --- | --- | --- |
| `task_failed` | failed/partial Run 中的失败任务 | retry_post（有 session）或 open_task |
| `record_failed` | session.status=failed 且没有任务失败（避免重复） | open_room |
| `monitor_backoff` | 监控退避 | open_room |
| `login_expired` | credential.status=expired | open_account |
| `ffmpeg_missing` | 找不到 ffmpeg | open_storage |
| `disk_low` | 媒体目录剩余 < 1 GiB | open_storage |

同 id 去重，避免 tasks 与 history 把同一次失败报两遍。

### 2.7 后处理重试后的旧失败

真机验证发现：转封装失败 → 重试成功 → `record_session.post_state` 回到 `done`，但 `task_history` 里旧的 failed `post` 任务还在，导致 Run 继续显示失败、「需要处理」永远清不掉。

`finish_run` 开头新增：

```rust
if draft.session.as_ref().is_some_and(|session| session.post_state == "done") {
    draft.tasks.retain(|task| {
        !(matches!(task.kind.as_str(), "post" | "remux") && task.state == "failed")
    });
}
```

只有 session 当前后处理确实为 `done` 时才过滤；录制本身失败（session.status=failed）仍保留失败 Run 和 `record_failed` 异常。

## 3. 前端任务页

文件：`src/features/tasks/TasksPage.tsx`

- 页头：眉题「全链路追踪」、标题「任务中心」、说明、右侧刷新。
- 筛选：全部 / 运行中 / 排队 / 需要处理，数字实时。
- 五张统计卡：房间、直播中、录制中、排队、24 小时失败。
- 平台态势四卡；点击按平台过滤，再点取消。
- 需要处理列表：标题、说明、动作按钮（重试后处理 / 打开账号 / 打开监控/房间）。
- 进行中：RunCard 显示头像、平台·房号·画质、主播、标题、时长、体积、状态 Chip、四段轨、开始时间、详情。
- 排队：QueuedRow 独立分组，不混进进行中；行内显示任务类型、片段序号（多片段时）、同 Run 其余排队任务数量、等待时长和平台。
- 最近完成：表格显示直播间、时长、体积、结束时间、状态 Chip；行可打开详情抽屉。
- 详情抽屉：RUN 编号与状态、主播、平台·房号、四段链路、任务列表（类型、名称、状态、百分比）、上下文（场次/开始/房间）、录制文件、复制诊断、关闭；失败时显示重试后处理。
- 轮询：每 2 秒 `taskCenter(100)`；刷新按钮立即拉取并提示。
- 取消：对活动后处理调 `postCancel(sessionId)`；重试调 `postRetry(sessionId)`。

状态标签只显示一次：历史行只留 Chip；抽屉副标题只显示平台·房号；只有 `run.stage !== run.state` 时才额外显示阶段文本；复制诊断同样去重。

已验证：

- 空态：统计、平台卡、系统行、空态文案与「打开监控」。
- 添加 `https://live.bilibili.com/6` 自动开录：Run 卡出现 1:52 → 15:57，体积 19 MB → 417 MB，状态「录制中」；完成后历史行 19:01 / 482 MB / 11/20 10:24 /「完成」。
- 详情抽屉：四段链路全完成、任务 100%、上下文 session、录制文件跳转、复制诊断内容完整。
- 录制中 Run → 停止 → 3 秒内收尾完成，DB `file_size=505,021,233`、`danmaku_count=13`、`post_state=done`。
- 失败注入：`record_session.status=failed + post_state=failed + task_history.state=failed` → 需要处理 1、24 小时失败 1、历史失败行、失败抽屉、重试按钮。
- 将源文件指回真实 FLV 后重试：`post_state=done`、`file_path` 变 mp4、`source_path` 保留 flv；修复旧 failed task 后「需要处理」只剩录制失败，不再出现任务失败。

- 筛选：需要处理只剩异常；运行中只剩活动 Run 卡；平台卡点击过滤。
- 重复标签修复：历史行只显示一个「完成/失败」Chip；抽屉只显示一个状态 Chip。
- 排队态：DB 注入一条 finished session + `task_history.state=queued`，筛选「排队」为 1、统计卡「排队」为 1，QueuedRow 显示「测试主播 / 后处理 · 等待后处理槽位 · 已等 18:19 / 哔哩哔哩」；未混入「进行中」。验收库随后恢复为空库。

## 6. 已知边界

- P1 没有事件表，阶段时间线来自 tasks/session 的起止时间；同一阶段多次重试只保留当前任务，历史尝试要等 P2 `task_event`。
- 需要处理只看最近 24 小时、最多 8 条；更早的失败在历史表里仍可查。
- 排队数按 Run 计，依赖 `task_history` 里的 queued 记录；任务刚创建、尚未写历史时有最多一个轮询周期的延迟。
- 一个 Run 同时有多个片段排队时，QueuedRow 只展示第一条任务并标注 `+N`；逐片段状态在详情抽屉的任务列表里查看。
- 平台卡的「登录态」只看 credential.status，不判断当前请求是否被风控；风控体现在监控退避与房间状态。
- 每次轮询聚合最近 100 个 Run 与最多 1600 条任务历史，数据量大时以后需要分页或增量接口。
