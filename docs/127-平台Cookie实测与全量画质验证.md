> 状态：v1.1（2026-11-11 补充 B 站高档探测与 25000 实测）；使用用户提供的 Cookie，通过真实适配器枚举画质、回选并 ffprobe 验证。

## 0. 结论速览

- 四个平台的 Cookie 均被正确解析：B 站 26 项、斗鱼 31 项、虎牙 36 项、抖音 68 项。
- B 站 Cookie 登录有效且为年度大会员；2K（15000）成功解锁并实测为 H.264 2560×1440。
- 斗鱼 4 个档位全部可选，实测 H.264 1920×1080 / 1280×720 / 960×540。
- 虎牙 H.264 四档与 HEVC 2K/2K HDR 全部可选；2K HEVC 实测 2560×1440。

- 虎牙 4K/4K HDR 匿名和带 Cookie 均返回 403；属于账号/房间权限或 4K 取流限制，不是画质 qn 丢失。

## 6. 测试方法

- 临时 Rust 探针直接引入仓库的 `platform` 模块，使用真实适配器与 Cookie 注入逻辑。
- 对能力清单中的每个 available 档位重新调用 `stream_plan(qn)`，确认返回候选的 `attrs.qn` 与请求一致。
- 对候选 URL 调用 ffprobe（带候选请求头；必要时再试一次带平台 Cookie），解析 `codec_name/width/height`。
- Cookie 值只存在临时进程内存与请求头中，不写入仓库、不打印。

## 7. 仍存在的权限边界

- 虎牙 4K/4K HDR 403：需要账号/房间的 4K 权限；应用已把档位和参数正确发出。
- B 站 4K/杜比：抽样的直播房间 `accept_qn` 最高到 15000，无法凭空解锁未返回的档位。
- 平台返回档位不等于账号一定有权限；应用会显示实际画质/降级或在取流失败时给出错误。
- 浏览器/硬件不支持 HEVC 时，观看侧仍会禁用对应档位；录制侧不受此限制。

## 9. 2026-11-11 补充：B 站高档探测与 25000

### 9.1 为什么旧表会漏 25000

旧实现把 40000 哨兵映射成 10000，并用「请求档位」的响应构造能力清单。登录账号请求 10000 时 `current_qn` 被封在 10000，2K/4K/杜比自然全部标灰；同时 qn 表未收 25000。修复见 [142](142-B站画质档位与高档探测修复.md)：

- 40000 → 30000（B 站接口最高档）；
- 另发一次 qn=30000 能力探测，`granted_qn` 取高档响应 `current_qn` 最大值；
- qn 表补 25000「原画真彩」；
- `quality_available` 要求 `accept_qn` 命中且 `qn <= granted_qn`。

| 20000 | 4K | 灰 | 超过 granted=25000 |
| 15000 | 2K | 灰 | 该房间 `accept_qn` 不含 15000 |
| 10000 | 原画 | 可选 | |

- 选中 25000 后播放器标签为「原画真彩」，分辨率 1920×1080。
- 录制 5 分 22 秒，`record_session.quality=原画真彩 · FLV · H.264`，`quality_history` 的 qn=25000；ffprobe 为 H.264 1920×1080 60fps + AAC，文件 499,451,170 B。

### 9.3 与旧结论的关系

- 旧表「B 站 4K/杜比抽样最高 15000」是当时的房间/账号权限结论，仍然成立；本轮房间上限是 25000。
- 旧表「2K 15000 可用」来自房间 `6` 的 `accept_qn`；本轮房间不含 15000，所以 2K 标灰，不矛盾。
- 高清/流畅在本轮房间同样不在 `accept_qn`，标灰是平台能力，不是 UI 漏项。

### 9.4 录制 AV1 门禁

B 站请求已加 `codec=2`。观看侧可使用 AV1；录制侧不能把 AV1 直接 copy 进 MPEG-TS/Matroska，否则 ffmpeg 报 `Output file does not contain any stream`、产物 0 字节。录制选流会跳过 AV1，只给 AV1 时返回「当前直播只提供 AV1 编码，录制链路暂不支持 AV1」。本轮未找到真实 AV1-only 房间，门禁由单测覆盖。
