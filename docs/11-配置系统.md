# 11 · 配置系统

> 参考实现：`bililive-go/src/configs/config.go`（2054 行，全项目最长的文件）、`src/configs/` 其余文件、`config.yml`（156 行示例）。
> 配置系统的复杂度被严重低估：它同时要满足"新手一键能用"、"高级用户精细控制"、"多房间差异化"、"热更新不重启"、"密钥不外泄"。

## 1. 三级覆盖模型

```text
默认值（代码内置）
   └─▶ 全局配置（config.yml 顶层）
          └─▶ 平台配置（platform_configs.<platform>）
                 └─▶ 房间配置（live_rooms[i] 内的同名字段）
```

合并规则：**逐字段覆盖**，不是整块替换。`ResolveConfigForRoom(room, platformKey)` 的语义：

```text
resolved.field = room.field ?? platform.field ?? global.field ?? default.field
```

### 1.1 "未设置" 必须可表达

如果字段用值类型（`i32`、`String`），就无法区分"用户设成 0"和"用户没设"。必须用 `Option<T>`：

```rust
struct OverridableConfig {
    interval: Option<u64>,
    output_path: Option<PathBuf>,
    ffmpeg_path: Option<PathBuf>,
    output_tmpl: Option<String>,
    video_split: Option<VideoSplitStrategies>,
    on_record_finished: Option<OnRecordFinished>,
    stream_preference: Option<StreamPreference>,
    danmaku_enable: Option<bool>,
    danmaku: Option<DanmakuConfig>,
    timeout_us: Option<u64>,
    log: Option<LogConfig>,
    feature: Option<FeatureConfig>,
}
```

> bililive-go 用指针（`*int`、`*string`）实现这一点。YAML 反序列化时"字段缺失"= nil，"字段为 0"= 指向 0。这是整个配置系统能工作的前提。

### 1.2 房间配置的两种写法

```yaml
# 简写：字符串
live_rooms:
  - https://live.bilibili.com/123

# 完整：对象
live_rooms:
  - url: https://live.bilibili.com/123
    is_listening: true
    quality: 0
    audio_only: false
    nick_name: "我的备注"
    notify_only: false
    interval: 60
    out_put_path: /data/bilibili
```

解析时要先尝试字符串，失败再试对象（或自定义 `Deserialize`）。

## 2. 完整配置结构

### 2.1 顶层

### 2.2 video_split_strategies

```yaml
video_split_strategies:
  on_room_name_changed: false
  max_duration: 0        # 0 = 不分段；单位纳秒或时长字符串
  max_file_size: 0       # 0 = 不限；支持 "500MB" / "1GB"
```

- `max_file_size` 要支持可读格式（`500MB`、`1GB`），**负数非法**（启动时报错）。
- `max_duration` 建议用 `"2h"` 这类字符串，比纳秒友好。

### 2.3 on_record_finished

见 10 文档 §9，字段完全一致。

### 2.4 notify

```yaml
notify:
  send_recording_summary: false
  telegram: { enable, withNotification, botToken, chatID }
  email: { smtpHost, smtpPort: 465, ... }
  ntfy: { URL, token, tag }
  bark: { serverURL, deviceKey, sound, group, icon, level }
  wxpusher: { appToken, uids }
```

**注意**：`botToken`、`appToken`、`deviceKey` 属于密钥，API 返回时要脱敏（`****`），只在"保存"时接受明文。

## 3. 热更新与并发控制

### 3.1 版本号 + 乐观锁

```rust
struct ConfigStore {
    current: ArcSwap<Config>,   // 读多写少，无锁读
    version: AtomicU64,
    write_mu: Mutex<()>,        // 串行化写
    after_update: Vec<Box<dyn Fn(&Config)>>,
}

fn update(new: Config, expected_version: u64) -> Result<(), Conflict> {
    let _g = self.write_mu.lock();
    if self.version.load() != expected_version { return Err(Conflict); }
    self.current.store(Arc::new(new));
    self.version.fetch_add(1);
    for cb in &self.after_update { cb(&self.current); }
    Ok(())
}
```

- 前端每次保存带上它读到的 `version`，不匹配返回 `409 Conflict`，UI 提示"配置已被其他窗口修改"。
- 写成功后触发回调：重启监听器、重载日志级别、重建 pipeline 配置等。

### 3.2 哪些变更需要重启什么

| 变更 | 动作 |
| --- | --- |
| `interval` | 通知监听器下一轮生效（不重启） |
| `live_rooms` 增删 | 启动/停止对应监听器 |
| 房间的 `quality`/`audio_only` | 当前录制继续，下一段生效 |
| `out_put_path` | 下一段生效 |
| `on_record_finished` | 立即生效（新任务用新配置） |
| `danmaku` | 当前录制继续，下一段生效 |
| `proxy` | 重建 HTTP 客户端 |
| `log` | 重载日志器 |

**原则**：能不重启就不重启。录制中的任务不要因为配置变更被打断。

## 4. 文件名模板

默认：

```text
{{ .Live.GetPlatformCNName }}/{{ .HostName | filenameFilter }}/[{{ now | date "2006-01-02 15-04-05" }}][{{ .HostName }}][{{ .RoomName }}].flv
```

### 4.1 模板引擎选择

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| Go `text/template`（参考实现） | 功能全、有管道 | Rust 无直接对应 |
| `handlebars` / `tera` | Rust 生态成熟 | 语法与 Go 不同，用户迁移成本 |
| 自研极简 | 可控、可预览 | 功能少 |

**建议**：用 `minijinja`（Jinja2 语法），并提供**兼容层**：把 `{{ .HostName | filenameFilter }}` 这类 Go 语法在解析前转换成 Jinja 语法，这样老用户的模板能直接迁移。

### 4.2 必须提供的函数

| 函数 | 用途 |
| --- | --- |
| `filename_filter` | 过滤 `/ \ : * ? " < > \|` 与控制字符 |
| `date(fmt)` / `now` | 时间格式化 |
| `replace(a, b)` | 字符串替换 |
| `trim` / `lower` / `upper` | 常规处理 |
| `default(v)` | 空值兜底 |

### 4.3 预览与校验

- API：`POST /api/config/preview-template`，body `{template, sample}` → 渲染结果。
- 校验：渲染失败要返回**具体错误位置**，而不是"模板无效"。
- 安全：禁止模板访问文件系统/环境变量。

## 5. 密钥与脱敏

三类敏感数据：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| Cookie | `SESSDATA`、`LTP0`、`dy_did` | 存本地库（加密），API 只返回"已配置"布尔 |
| Token | Telegram botToken、OpenList 密码 | 同上 |
| 路径 | 用户目录 | 可返回，但 UI 要支持"复制"而非明文展示 |

**规则**：

1. `GET /api/config` 返回的敏感字段一律 `"******"` 或 `null` + `has_value: true`。
2. `PUT` 时收到 `"******"` 表示"不修改"，收到新值才覆盖。
3. 日志里禁止打印 cookie/token（用 `Debug` 实现时手动打码）。

> bililive-go 用 `json:"-"` 让 `DouyuAuth.LTP0`、`DyDid` 完全不出现在 JSON 里，这是最彻底的做法。

## 6. 校验

启动时和保存时都要校验：

| 字段 | 规则 |
| --- | --- |
| `interval` | ≥ 5（太小会触发风控） |
| `out_put_path` | 可创建、可写 |
| `ffmpeg_path` | 存在且可执行（或留空自动查找） |
| `max_file_size` | ≥ 0，格式合法 |
| `max_duration` | ≥ 0 |
| `rpc.bind` | 端口合法、未被占用 |
| `platform_configs.*.min_access_interval_sec` | ≥ 1 |
| `live_rooms[].url` | 能被某个 matcher 匹配 |
| 模板 | 能渲染 |

校验失败要**逐条列出**，不能只报第一个。

## 7. 导入导出与迁移

- `GET /api/raw-config` → 整份 YAML 字符串（**脱敏后**）。
- `PUT /api/raw-config` → 整体替换（用于"高级编辑"）。
- 导出时附带 `config_version`，导入时做迁移。

迁移策略：

```text
v1 → v2: out_put_path 从相对路径改为绝对路径
v2 → v3: danmaku 从顶层移到 danmaku 对象内
...
```

每一步都是纯函数 `fn migrate_v1_to_v2(yaml) -> yaml`，可单测。

## 8. 配置的 UI 呈现

三类用户，三种入口：

| 用户 | 入口 | 呈现 |
| --- | --- | --- |
| 新手 | 设置向导 | 只问 3 件事：输出目录、是否要弹幕、是否要转 mp4 |
| 普通 | 表单 | 分组 + 默认值 + 帮助文案 |
| 高级 | YAML 编辑器 | 全文编辑 + 语法高亮 + 校验 |

**每个字段都要有默认值和一句人话解释**。配置项数量 > 50 时，没有搜索功能的表单是不可用的。

## 9. 反模式

1. ❌ 用值类型存可覆盖字段 → 无法表达"未设置"。
2. ❌ 整块替换而非逐字段合并 → 房间配置会意外清空平台配置。
3. ❌ 配置变更重启整个应用 → 录制中断。
4. ❌ 敏感字段原样返回给前端 → 泄露（前端日志、崩溃报告都会带出去）。
5. ❌ 无版本号 → 多窗口同时编辑互相覆盖。
6. ❌ 校验只报第一个错误 → 用户改 5 次才能保存成功。
7. ❌ 模板渲染失败继续录制 → 生成 `<no value>` 文件名。
8. ❌ 热更新时重建正在使用的对象 → 竞态崩溃。
