# 149 · 移除录制并发上限

> 范围：录制启动链路、全局设置、IPC 类型、设置页「录制与观看」与中英文文案。
> 结论：**录制侧不再有全局并发上限。** 用户添加多少房间、其中多少路在播，就允许开多少路；只保留磁盘空间、停录冷却、平台与后处理等与「录制数量」无关的保护。
> 时间：2026-11-13；基线：`ce53237` + 本次改动。

---

## 1. 为什么移除

旧实现把「同时录制」当成一个需要产品兜底的资源：默认 4 路，设置页可在 1–8 之间调。达到上限后：

- `start_checked` 在网络解析前直接返回 `同时录制已达上限（N 路）`；
- 解析、起 ffmpeg 之后还会在插入 active 时再复查一次，超限就杀掉刚起好的进程、删会话与空分片；
- 监控每个检测周期都会再试一次，形成周期性的失败与行内错误；
- 设置页有独立 Section、搜索项与 i18n 文案，等于明确告诉用户「这里有个入口限制」。

这与「录制数量应该由用户控制」冲突：用户已经通过房间列表、自动录制开关和手动录制决定了要录什么，应用不该再额外拒绝第 5 路。并发对磁盘与带宽的压力仍然存在，但应由用户判断，并由已有的磁盘守卫兜底。

### 2.1 明确保留的限流

移除的只是「录制路数」这一层。以下限制与录制数量无关，全部保留：

- 监控检测的全局 12 / 每平台 4 请求并发；
- 后处理自动 1 + 手动 1 + 全局 2 的任务槽；
- 本地回放的窗口/并发上限；
- 磁盘可开录门槛与录制红线；磁盘不足仍会拒绝新开录并写行内原因；
- 每房间开录锁、停录竞态处理、`starting` / `finalizing` 标记；
- 连续开录失败冷却、断流续录与假死看门狗。

### 2.2 旧数据

数据库里可能仍残留 `app_setting['record.max_concurrent']`。新版本不再读取也不再写入该键，残留值不会生效，也不会阻止启动；不做迁移。

## 3. 行为变化

| 场景 | 旧行为 | 新行为 |
| --- | --- | --- |
| 第 5 个房间开播（默认上限 4） | 拒绝开录，行内错误「同时录制已达上限（4 路）」 | 正常开录 |
| 设置页「录制与观看」 | 有「录制并发」Section，可填 1–8 | 不再出现 |
| 搜索「并发」 | 命中「同时录制上限」 | 无结果（监控/后处理等设置不受影响） |
| 超限失败计入连续失败 | 明确排除 | 错误不存在，无需排除 |
| 退出时判断是否还有任务 | active + starting | 不变，仍两者都算 |

## 5. 边界与后续

- 录制路数现在完全由用户与平台可用性决定。若同时开启大量房间，ffmpeg 进程数、磁盘写入与网络带宽会同步上升；磁盘守卫只能阻止「空间不足」，不能阻止「写满带宽」。
- 没有新增「建议上限」提示或确认框，符合「不做明显入口限制」的要求。
- Windows 未做真机多路验证；本次改动不涉及平台分支。
