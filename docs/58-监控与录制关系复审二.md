# 58 监控与录制关系复审二（真机验证）

> 状态：v1.1（2026-11-06，第四轮；对 57 之后代码的独立复验，真机录制 + 故障注入；B1–B9 已在 [59](59-监控录制联动修复四.md) 全部修掉并真机验收）｜审查对象：monitor.rs、recorder.rs、broker.rs、commands.rs、disk.rs、lifecycle.rs、lib.rs 与 57 的 A1–A12 修复结果｜审查视角：不看历史结论，只用「进程、文件、数据库、日志」四类可观测证据回答「监控到底能不能碰正在跑的录制」

一句话结论：**57 修完之后，「检测间隔 / 抖动 / 退避 / 暂停监控不影响已开录会话」这句话在真机上成立，且这次是用 54.7 MB 的真实斗鱼录像验证的，不是读代码。** 但源健康时仍有一条**会真的丢 10 分钟录像**的新路径：**连续秒退把续录预算耗尽后，即使平台明明在播，也会被记成「直播已结束」并静默 600 秒**（B1，本轮用伪造 ffmpeg 实测复现）。另有 8 条边界问题（B2–B9），其中 B2 会让一次假离线推翻用户的手动停录。

## 0. 先回答四个问题

| 说法 | 结论 | 本轮证据 |
| --- | --- | --- |
| 已开录的房间不受检测间隔影响 | **成立** | T2：间隔从 30 秒改成 3600 秒后，`last_checked_at` 冻结 70 秒以上，同一会话的 `.part0000.ts` 从 24,379,392 长到 34,603,008 字节 |
| 不受失败退避影响 | **成立，但有共享闸门的间接影响** | 退避只改 `Schedule.next_at` 与 broker 的等待时长；录制进程由 recorder 自己的 1 秒 watcher 轮询。间接影响见 §4：续录时 `broker.invalidate` 会清掉共享冷却（B3） |
| 监控只是更新状态 | **不对** | 监控 tick 会：自动开录、两次确认离线后停录、每秒磁盘红线、写行内错误。另有 UI/生命周期 6 个入口能停录（沿用 54 §3 的结论，本轮抽验了磁盘、SIGTERM、刷新三条） |
| 只有直播源真没数据才影响录制 | **仍不成立** | 本轮新增反例：源「有数据但连续秒退」时，录制会在平台仍显示在播的情况下被记成自然结束并静默 10 分钟（B1/T9）；另有磁盘红线（T6）与手动停录被假离线推翻（B2） |

### 1.2 三种故障注入

1. **杀进程**：`kill -9` 模拟断流 / CDN 掐连接；`kill -STOP` 模拟进程假死（不退出、不写盘）。
2. **占满磁盘**：3 GiB 稀疏 APFS 卷（`hdiutil create -size 3g`），录到一半用 `dd` 写 2.1 GiB，把剩余空间压到 0.7 GiB（红线 1 GiB、开录线 2 GiB）。
3. **伪造 ffmpeg**：把 `/tmp/fakebin` 放到 `PATH` 最前，脚本收到 `-version` 正常应答，收到真实参数时写 200 KB 假分片、0.3 秒后 **exit 0**——用它在真实在播的平台上制造「干净 EOF / 秒退」，这是真实 ffmpeg 很难稳定复现的路径（B1 就靠它抓到）。

### T9 伪造秒退循环 → 误报「直播已结束」（B1 实测）

| 时刻 | 事件 |
| --- | --- |
| 23:05:29 | 开始录制 |
| 23:05:34 | restarts=1 |
| 23:05:38 | restarts=2 |
| 23:05:42 | restarts=3 |

### T10 误报之后真的 10 分钟不录

T9 结束后继续观察：23:06:56 `last_checked_at` 仍在更新（监控在查、平台报在播），但 23:05:44–23:06:56 之间 **没有第二次「开始录制」**，会话数保持 4 条。这与 `ENDED_BLOCK=600` 完全吻合：一次误报要让这个房间空等 10 分钟。

| 失败类型 | 是否退避 | 退避加在哪 | 谁能清 | 对正在录的会话 |
| --- | --- | --- | --- | --- |
| 平台返回限流（is_throttle） | 是，5s→10→20→40→60s 封顶 | broker `failures` + `wait_turn` 睡眠 | 成功请求、`invalidate`、刷新、续录 respawn | 续录会等闸门；B3 说明 respawn 直接清掉冷却 |

| 录制秒退（<12s，非 0 退出） | 是，3 次进 5 分钟冷却 | recorder `hard_failures` | 成功开录 / 正常收尾 | 只影响下次自动开录 |

## 5. 本轮新发现

### B1（P1）连续秒退 / 续录失败会被记成「直播已结束」，并静默 10 分钟

**现象**：平台在播、源也能连上，但连续 4 次「0.3 秒退出」后，会话落库 `finished/stream_ended`，发结束通知，并 600 秒不再自动开录（T9/T10 实测）。

**机制**：两条路径都把一个「没有平台凭据」的收尾当成确认下播：

1. 秒退路径：`early=true` 时 `should_probe_platform` 直接返回 false（recorder.rs:871-889），于是跳过平台查询；3 次续录用尽后落到 recorder.rs:943 `finalize(..., true)`。
2. 干净 EOF 路径：探测到 `PlatformState::Live` 后调 `respawn`，若 `respawn` 因预算用尽 / 解析线路失败返回 false，代码继续往下走到同一个 `finalize(..., true)`（recorder.rs:906-943）。

`finalize` 里 `status.success()` → `finished/stream_ended`（recorder.rs:1150-1160）；`confirmed_end=true` 再触发 `mark_ended`（recorder.rs:1184）与 `emit_notice("ended")`（recorder.rs:1247），`auto_blocked` 用 `ENDED_BLOCK=600` 挡住重开。

**影响**：CDN 抖动、地址瞬时失效、平台侧 0 字节响应都可能触发；一旦触发，最长 10 分钟不录，且用户收到「直播已结束」的错误通知。

**建议**：`confirmed_end` 只允许来自 `PlatformState::Offline` 或用户停录；秒退路径在预算用尽前至少查一次平台，查到 Live 就以 `confirmed_end=false` 收尾（不通知、不静默，让监控按失败冷却去重试）。补两个单测：`finalize(confirmed_end=false)` 不写 `ended` 通知；early 路径耗尽预算时传 false。

### B2（P2）一次假离线就会清掉「手动停录」抑制

**机制**：monitor.rs:427 在**每一拍离线**（还没凑够两次）就调 `resume_auto`，而它同时清 `suppressed`（手动停录标记）与 `ended`（刚结束静默）。停录本身要两次确认（S1），抑制复位却只要一次。

**影响**：用户点了「停止录制」→ 平台状态抖动报一次离线（不录像时也照清）→ 下一拍恢复在播 → `auto_suppressed` 已为空 → **同一场直播又被自动开录**，用户的操作被无声推翻。

**建议**：离线分支也先 `confirm_offline`，只有确认两次后才 `resume_auto`；未录像的房间同样走两次确认（或单独一个「离线确认」计数器），与停录保持同一口径。

### B3（P3，权衡项）续录会清掉共享失败退避

**机制**：`respawn` 为了拿新签名地址调 `broker.invalidate`（recorder.rs:1057），而 `invalidate` 会连 `failures` 一起清（broker.rs:224-233）；A5 只把观看端改成了 `invalidate_address`。

**影响**：限流风暴中一次续录会把该房间的冷却清零，下一次平台请求立刻发出。**但不能简单改成 `invalidate_address`**：`respawn` 若保留冷却，可能要在 `wait_turn` 里睡满 60 秒，续录窗口从 3 秒变成 1 分钟。建议给 broker 加「失效地址但保留冷却 + 本次请求免等」的显式参数，而不是二选一。

### B4（P3）探测到在播但续录失败后，会再走一次续录

**机制**：`PlatformState::Live` 分支里 `respawn` 返回 false 后没有 `return`，继续落到 recorder.rs:937 的兜底分支，再调一次 `respawn`（再睡 3 秒、再解析一次线路），然后才收尾。

**影响**：平台抖动时多一次 3 秒空窗与一次 API 请求；日志里会出现两次「续录次数用尽」以外的重复告警。

**建议**：Live 分支无论成败都 `return`（失败就按 B1 的 `confirmed_end=false` 收尾），删掉兜底分支的重复调用。

### B5（P3）检测间隔 >180 秒时，离线二次确认永远不成立

**机制**：`confirm_offline` 用 `OFFLINE_CONFIRM_GAP=180s` 做窗口（recorder.rs:354-362）；间隔 181–86400 秒时，每次调用都先把计数清零，永远停在 1 次。

**影响**：平台下播后不能通过「两次离线」停录，只能等 ffmpeg EOF；若 CDN 保持连接，最长要等看门狗的 60 秒 + 续录探测。实际影响小，但与文档里「两次确认」的承诺不一致。

**建议**：窗口改成 `max(180s, 2×interval+60s)`，或干脆不用时间窗，改成「连续两次成功检查都离线」——后者与调度语义天然一致。

### B6（P3）磁盘红线每拍都会重复 `stop()`

**机制**：monitor.rs:286-291 每拍对每个低空间卷 spawn 一次 `stop`；`stop()` 不是幂等的（recorder.rs:757-766 每次都重设 `stop_reason`、重发 SIGINT、打一条 INFO）。

**影响**：ffmpeg 正常时 1 秒内退出，实测只有 1 次（T6）；但 ffmpeg 卡在写满的盘上不退时，会每秒一次 SIGINT + 一条 WARN/INFO，直到收尾。

**建议**：`stop` 里判断 `stop_reason.is_some()` 就直接返回（用户改主意除外），日志也只打第一次。

### B7（P3）监控 tick 每秒读一次房间表与设置

**机制**：tick 每 1 秒 `db.list_rooms()`（monitor.rs:263）与 `settings::load`（monitor.rs:94），与「有没有房间到期」无关。

**影响**：4 个房间时可忽略（约 8.6 万次/天，SQLite 读，WAL 下无写入）；房间多、或与设置写入并发时会有无谓的锁竞争与 CPU 唤醒。桌面端更在意耗电。

**建议**：`list_rooms` 只在有房间到期时读，或缓存 5–10 秒；磁盘红线只依赖 `recorder.active_targets()`，不需要房间表；设置改成保存时推一个版本号/事件。

### B8（P3）检测任务 panic 会让房间永久不再被检测

**机制**：`inflight` 在派发任务时置位，只在收到结果消息时清除（monitor.rs 的结果循环）；任务 panic 不会发结果。

**影响**：概率低，但一旦发生，该房间从此不再检查，也没有任何提示，只能重启应用。

**建议**：用 `Drop` guard 清 `inflight`，或 `catch_unwind` 包住 `check_room`，panic 时按失败上报。

### B9（P3）「刷新」绕过暂停 / 手动停录 / 结束静默 / 失败冷却

**机制**：`room_refresh` 在房间在播时只看 `auto_record && !is_recording`（commands.rs:167-172），直接 `start()`，不走 `start_checked`，也不看 `auto_suppressed` / `auto_blocked` / `in_failure_cooldown`。

**影响**：监控已暂停的房间点刷新仍会开录；手动停录后点刷新会重新开录（同一场）；刚误报结束后点刷新会绕过 600 秒静默。可以解释为「用户主动操作即覆盖」，但与监控口径不一致，且「暂停监控」的语义被削弱。

**建议**：明确产品语义。若刷新只应更新状态，则开录条件与监控完全一致；若允许覆盖，至少在暂停状态下不自动开录，并在 UI 上说明。
