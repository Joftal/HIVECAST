本阶段解决的是 M6 遗留的三个体验断点：**找不到旧录像**（没有搜索/排序）、**只能一条一条删**、**一次只能回放一条**。顺带把 M5 写完但没接 UI 的后处理命令接了出来。

## 2 搜索、筛选、排序

三者都在前端算，不新增 IPC：媒体库规模是「本机录像条数」，几千条的过滤在 16ms 量级，没必要为它加一层后端查询。

- **搜索**：`query` 同时匹配 `title` 与 `hostName`，统一 `toLowerCase()`。用户既可能记得标题（「陪伴每一天」），也可能记得主播名（「yyfyyf」），所以两个字段都进。
- **平台筛选**：胶囊列表来自 `items` 去重后的 platform 集合，不写死四个平台——这样以后少一个平台，胶囊自然消失。
- **排序**：`recent` = `startedAt` 倒序；`duration` / `size` 降序。实现用 `[...list].sort(...)`，不动原数组，否则切换排序会让 `items` 的语义漂移。
- **摘要**：`media.summary` 渲染「N 条 · 合计 X」，体积换算在前端 `formatSize`。

空态分两套，这点容易漏：库里本来就没录像 → `media.emptyTitle`（去监控页录一条）；有录像但被筛没了 → `media.noMatchTitle` + `media.noMatchBody`（清空筛选）。混用一套文案会让用户以为录像丢了。

## 3 批量删除

交互用「卡片左上角复选框」而不是长按或多选模式：复选框始终可见，选中后顶部浮出琥珀色操作条（「已选 N 条」+ 取消选择 + 删除所选），比模式切换少一次点击。

删除顺序是有讲究的：

1. 若该条正在回放，先 `mediaStop(id)`，否则 ffmpeg 还握着文件，删了之后回放端会读到半截；
2. 调 `mediaDelete(id, hasFile)`；`hasFile` 为 false 时后端只删 DB 行（录像已被手工挪走）；
3. 全部成功后 `notice = media.deletedBatch`，清空 `selected` 并 `reload()`；任何一条失败立刻中断并显示 `media.deleteFailed`——批量删除里「部分成功」比「全部失败」更难解释，宁可停下让用户看到是哪条。

## 4 多实例回放

M6 的 `local.rs` 是 `Mutex<Option<Active>>`，`open()` 开头先把上一条停掉。现在改成 `Mutex<HashMap<String, Active>>`，key 是 `session_id`。

```rust
pub const MAX_ACTIVE: usize = 3;
```

三条规则：

- **同一条重复 open 直接复用**：返回已有 `Active` 的播放地址，不重新转封装。否则用户点两下「播放」，磁盘上就多一份等大的分片。
- **超上限拒绝**：`len() >= MAX_ACTIVE` 时返回 `AppError::User("最多同时回放 3 条，先停掉一条再开")`。上限取 3 而不是 4：观看页已经能占 4 路解码，回放再叠 4 路会把 CPU 打满。
- **按 session 停**：`stop(&self, session_id)` 删掉对应实例并 `teardown`（发 `q` 给 ffmpeg、等 `STOP_TIMEOUT = 4s`、注销回环路由、删缓存目录）；`stop_all()` 给退出流程用。

`teardown` 被抽成自由函数，是因为它同时被 `stop`、`open` 的失败回滚、`stop_all` 调用，挂在 `&self` 上会反复借 `Mutex`。

前端对应两张表：`playbacks: Record<string, Playback>` 与 `volumes: Record<string, number>`（默认 0，即静音）。播放器从「页面顶部一块大面板」移进卡片内（`aspect-video`），这样「哪条在放」是位置自明的。卸载时遍历 `playbacksRef.current` 逐个 `mediaStop`，避免切 Tab 后 ffmpeg 还在转。

## 5 后处理入口

`session_remux` / `session_screenshot` / `session_export_danmaku@@ 三个命令 M5 就写完了，但一直没接 UI，等于白写。现在卡片第二行放三枚小按钮：

| 按钮 | 调用 | 产物 |
| --- | --- | --- |
| 转 mp4 | `sessionRemux(id)` | 同目录 `.mp4`（去掉 `.flv`/`.ts` 换容器） |
| 截图 | `sessionScreenshot(id, null)` | `.jpg`，`atSecs` 为空时后端取第 10 秒 |
| ASS | `sessionExportDanmaku(id)` | 同名 `.ass`，来自同名 `.jsonl` |

`posting: string | null` 保证**同一时刻只跑一个**：三个命令都是 ffmpeg 子进程，与正在进行的回放/录制抢 IO，串行比并行稳。完成后 `media.postDone` 提示「{{what}}已生成 · {{size}}」。

**没接合并**（`room_merge_sessions`）：它会把该房间**所有**已完成录像拼成一个文件，属于一次性的大范围写操作，需要范围选择（时间区间/条数）与二次确认，留作后续。

## 6 实测

构造两条样本：

```bash
ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30 -f lavfi -i sine=frequency=440 \
  -t 20 -c:v libx264 -preset veryfast -c:a aac "$HOME/Movies/HIVECAST/测试/[test-a].mp4"
```

| 样本 | 时长 | 体积 |
| --- | --- | --- |
| `[test-a].mp4` | 20s | 6,899,360 B |
| `[test-b].mp4` | 35s | 12,072,756 B |

DB 里直插两条 `finished` 会话（`sess-test-a` / `sess-test-b`），启动应用后两条**同时**进入回放：

- 缓存目录出现两个：`sess-test-a-1793874511528` / `sess-test-b-1793874511702`；
- 各自 `index.m3u8` + `seg_00000..00002.ts`；
- 两个清单都带 `#EXT-X-PLAYLIST-TYPE:VOD`、`#EXT-X-INDEPENDENT-SEGMENTS`、`#EXT-X-ENDLIST`。

→ 多实例并发转封装成立（单例版本下第二个会顶掉第一个，只会存在一个目录）。

> **证据形态说明**：本轮验收时 macOS 屏幕处于锁定状态（`screencapture` 只能拿到黑屏或登录窗，`caffeinate -u` 唤醒后停在登录界面），因此 **没有 UI 截图**，证据是进程与磁盘产物。样式回归待下次开发环境验收补。

后处理链路的自动化验证：`cargo test --lib postprocess -- --ignored` 通过（`ffmpeg_pipeline_on_synthetic_clips`，0.34s），覆盖 remux / 截图 / ASS 三个产物存在且可被 ffprobe 读到。

## 7 已知缺口

| 缺口 | 影响 | 建议 |
| --- | --- | --- |
| 合并未接 UI | `room_merge_sessions` 只能靠 IPC 手调 | 加范围选择 + 二次确认 |
| 回放缓存等于录像体积 | 3 条 4 小时录像同时回放 ≈ 3 倍磁盘 | 改成滑窗（只保留当前播放点前后 N 分钟） |
| 无进度百分比 | 大文件 remux 时只有转圈 | `ffmpeg -progress` + 事件推送 |
| 音量按卡片独立且默认静音 | 想听某条要点两次 | 顶部加「统一音量」 |
| 无 UI 截图 | 样式回归未验 | 下次开发环境验收补 |
