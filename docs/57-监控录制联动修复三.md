# 57 监控录制联动修复三（A1–A12）

> 状态：v1.0（2026-11-06）｜前置：[54-监控与录制关系审查](54-监控与录制关系审查.md)（v3.0 提出 A1–A12，编号跳过 A10，共 11 条）｜范围：审查报告列出的 11 条残余问题 + 磁盘红线检查频率｜结论：11 条全部修掉；磁盘剩余空间改为「按卷缓存 5 秒 + 每拍按卷去重」，同一块盘上 4 路录制从每秒 4 次查询降到每秒 0.2 次。

## 0. 一句话结论

这一轮修的都是「判定逻辑在极端时序下出错」的场景：平台说离线就停、续录预算是终身制、抖动后空窗 10 分钟、续录窗口吞掉手动停录。共同改法是把**单点判断换成带凭据的判断**——结束要有「平台确认离线」或「复核预算用完」的凭据，停止要在换进程前再看一眼用户意图，磁盘检查则从「每路每秒」改成「每卷 5 秒」。

## 1. 磁盘红线检查：每秒一次是否过频？

先回答你的三个问题。

| 问题 | 结论 |
| --- | --- |
| 每秒查一次是否过频？ | **原来确实过频**，而且不是「一秒一次」，是「每路一秒一次」：4 路录制 = 每秒 4 次 statvfs |
| 会不会影响磁盘写入速度？ | **基本不会**。statvfs 只读文件系统超级块（内存里的计数），不写盘、不碰分片文件；代价是系统调用与文件系统锁，量级是微秒 |
| 磁盘空间是否共享？ | **应该共享，之前没共享**：每个房间各自查自己目录，同一块盘重复查同一份数据 |

改法（[disk.rs](../src-tauri/src/disk.rs)）：

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 查询粒度 | 每个房间每秒一次 | 每卷 5 秒一次（CACHE_TTL，disk.rs:20） |
| 卷标识 | 无 | volume_key：Unix 取 st_dev（`dev:N`），Windows 取盘符；目录还没建时向上找第一个存在的祖先（disk.rs:33） |
| 同一拍内 | 4 路各查一次 | monitor 用 checked_volumes 去重，同一卷只判一次（monitor.rs:275-282） |
| 缓存读取 | 无 | cached_free_bytes：命中直接返回，未命中才 statvfs 并写缓存（disk.rs:59-76） |

效果：同一块盘上 4 路录制，查询频率从 4 次/秒降到 0.2 次/秒（20 倍）；10 路也是 0.2 次/秒。多块盘时最坏是「盘数 ÷ 5」次/秒。

为什么是 5 秒而不是 60 秒：红线是 1 GiB，4 路 1080p 合计约 20–30 MB/s，5 秒最多吃掉约 150 MB，仍留足反应时间；再长就会让「刚越过红线」多录十几秒。查询本身不写盘，5 秒的代价可以忽略。

一个已知取舍：can_start 也读缓存，最坏会拿「5 秒前还很空」的结果放行一次开录。开录后 watcher 每秒复查红线，真写满会立刻按 disk_full 收尾，所以只影响一次开录尝试，不会把盘写爆。

## 2. 逐条改法

| 编号 | 改前 | 改后 | 位置 |
| --- | --- | --- | --- |
| A1 | 「刷新」按钮拿到一次离线就 stop(stream_ended)，接口抖一下就把健康录像切断 | 与监控同口径：confirm_offline 连续两次 + flowing 文件仍在增长，才停录；停前记「平台确认离线」 | commands.rs:171-180 |
| A2 | 续录预算按会话终身累计，长播第 4 次断流直接收尾 | 稳定录制满 30 分钟（HEALTHY_RESET）且预算被消耗过，就把 restarts / eof_retries 归零 | recorder.rs:962-966、1320 |
| A3 | 续录用 db 里最新的画质/线路，用户中途改设置会渗进正在录的这一场 | Active 记住 qn / line，respawn 用快照而不是重新读库 | recorder.rs:85-86、1025-1043 |
| A4 | 平台查询失败（限流）时把干净 EOF 当成本场结束：弹结束通知 + 静默 10 分钟 | 查询失败先等 20 秒复查一次；仍未确认就按「未确认结束」收尾：不通知、不写静默，监控下一拍可重新开录 | recorder.rs:894-905、1129、1246-1252 |
| A5 | 观看端重连调用 broker.invalidate，把录制侧共享的失败退避一起清了 | 新增 invalidate_address：只丢播放地址与房间信息，保留 failures | broker.rs:215-222、view.rs:554、591 |
| A6 | 应用崩溃后遗留的 ffmpeg 继续写分片，下次启动合并时文件损坏 | 开录/续录写同名 .ffmpeg.pid，收尾删除；启动时 reap_orphans 校验命令行含 ffmpeg 与该文件名后先 SIGTERM 再 SIGKILL | recorder.rs:1325-1344、1346；state.rs:61 |
| A7 | 可以同时开两个实例，抢分片、抢缩略图缓存 | app_data_dir/instance.lock 上加排他锁，拿不到就通知 + 退出；锁随进程释放，崩溃不会挡下次启动 | instance.rs:18；lib.rs:62 |
| A8 | 抖动恢复后平台仍报同一开播时间，auto_blocked 挡满 600 秒 | 停录前记「平台确认离线」，mark_ended 存 confirmed；下一拍平台又报在播且开播时间没变就解除静默 | recorder.rs:293-317、320-325、770-776 |
| A9 | 磁盘 1–2 GiB 灰区里自动开录被静默拒绝，界面没有任何提示 | 自动开录前判断 can_start，不足时把原因写进房间行内错误（同一原因不重复刷） | monitor.rs:411-419 |
| A11 | 半关连接让 ffmpeg 非 0 退出，平台明明已下播却记成 failed | 非 0 退出但活过 12 秒也先问平台：离线按正常下播收尾 | recorder.rs:1307-1315、918-924 |
| A12 | 续录的 3 秒等待窗口里点「停止录制」，新 child 换进 active 后继续录 | 换 child 前检查 stop_reason，有值就 kill 新进程并放弃续录 | recorder.rs:1100-1105 |

A4 与 A11 共用一条新的判定链：

```text
退出 → 有人叫停？ → 直接收尾
     → 秒退（<12s）？ → 续录分支
     → 该问平台？（干净 EOF 且预算未用完 / 非 0 退出但活过 12s）
         → platform_state: Live / Offline / Unknown
             Live     → 续录（干净 EOF 才消耗复核预算）
             Offline  → 确认下播收尾（mark_ended + 通知）
             Unknown  → 等 20 秒再问一次；仍 Unknown → 未确认收尾（不通知、不静默）
```

## 3. 常量与状态

| 常量/字段 | 值 | 含义 |
| --- | --- | --- |
| CACHE_TTL | 5 秒 | 同一卷剩余空间缓存时长 |
| HEALTHY_RESET | 30 分钟 | 稳定录制多久后补满续录预算 |
| PLATFORM_RECHECK_DELAY | 20 秒 | 平台状态未知时的复查间隔 |
| offline_stops | HashSet | 已被「平台确认离线」标记、尚未收尾的房间 |
| ended 的值 | (Instant, Option<i64>, bool) | 增加「确认下播」标志，供 A8 解除静默 |
| confirmed_end | finalize 参数 | 没有凭据时不发结束通知、不写 10 分钟静默 |

## 6. 仍存在的缺口

1. A6 的孤儿清理依赖 pid 文件与命令行匹配，极端情况下（pid 复用且命令行恰好含同名文件）可能误杀；概率极低，但没做二次校验（如启动时间）。
2. can_start 读 5 秒缓存，最坏会多放行一次开录（见 §1）。
3. A8 的解除依赖「平台再次报在播」；如果平台抖动后直接进入长时间离线，仍要等 600 秒兜底窗口。
4. 结束通知以「平台确认离线」为前提；接口长期限流时，一场真下播不会有结束通知，只在日志里留 WARN。
