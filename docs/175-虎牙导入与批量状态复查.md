# 虎牙关注导入与批量状态复查

> 复查对象：fca210a feat(monitor): 新增虎牙关注导入与批量状态。
> 口径：代码路径复核 + 既有真机日志 + 本轮修复后的 release 真机复验；cargo test --lib 396 passed / 19 ignored。

## 0. 结论摘要

主链路成立：导入用 lUid 做账号身份、数字房号做房间身份；重复导入、别名先加后导、登录后 30 秒批量、缺失单房兜底、重播复核、移除房间都有处理。监控批量只取状态，取流/画质/线路仍由单房 stream_plan 独立完成。Cookie 失效后批量门槛关闭，单房匿名检查继续；恢复登录后下一拍自动回批量。四平台 BatchState 独立，虎牙不会阻塞 B 站/斗鱼/抖音。

复查时发现 3 个边界，均已在第 15 节修复并复验：

1. 导入去重的软删边界：数字房号行已软删、别名行仍活跃时，再导入会留下两行活跃房间。B 站有合并分支，虎牙没有。建议优先修。
2. 已取关但本地 batch_follow 仍为 1：每 30 秒批量缺项后回退单房，持续双请求，不会自动降级。
3. 批量登录失效/未知 bcode 的降级放大：整批改逐房页面检查；若 Cookie 已失效但尚未标记，可能每 30 秒对全部房间打一轮页面请求。方向安全，但请求量需要收敛。

低风险：confirm_live 对在播项无并发上限；关注超过 6000 位静默截断；逐房日志偏少。

## 1. 导入去重

正常路径：前端 ImportFollowsDialog.tsx 用 roomKey、platformUid、user.uid、status.roomId、status.shortId 判断已存在；已存在且 batch_follow=0 的行显示“已添加 / 可加入批量”，允许再次勾选，这是升级入口，不是重复建房。

后端 rooms_import（src-tauri/src/commands.rs:508）按顺序查找：数字房号 find_room → 虎牙别名 find_room(short_id) → lUid find_room_by_uid。命中后 room_key 不同则 rekey；软删行 insert_room 恢复；活跃行 update_room_info；虎牙补 batch_follow/platform_uid 时 upgraded+1。

已真机验证：先手动加 https://www.huya.com/lpl，再导入 660000，最终只有一行 room_key=660000、platform_uid=1346609715、batch_follow=1，日志 rekeyed=1 upgraded=1，随后批量 rooms=1 keys=1 returned=1 live=1 missing=0。

软删边界会留双行：之前导入过 660000（batch_follow=1）→ 移除（软删）→ 手动加别名 lpl（活跃、batch_follow=0）→ 再导入 660000。find_room(660000) 先命中软删行，known 已有值，虎牙分支不再查 short_id/UID；软删行恢复并继承 batch_follow=1，别名行仍活跃。结果两条活跃行都指向 660000。

更根本的一层：huya.rs:118 的 room_info 返回 stable_id: None，而 B 站/斗鱼都会把别名归一成数字稳定 ID。因此手动加 https://www.huya.com/lpl 会真的建一条 room_key=lpl 的行；之后再手动加 https://www.huya.com/660000 又会建一条数字行，不经过导入也会出现两条活跃记录。导入时才会通过 short_id 查到 lpl 并 rekey，但不能保证用户一定导入。

建议同时做两件事：① huya::room_info 从页面解析数字房号并作为 stable_id，canonical_reference 的 huya 分支把 canonical_url 改成数字地址；② 仍保留导入时的合并兜底，处理历史已经产生的双行（软删数字行+活跃别名行）。只做②不做①，用户不导入时仍会重复。

B 站有对应合并逻辑（commands.rs:526-572）：同时查 find_room_by_uid，按“哪条活跃保留哪条”选 keep/drop，merge_room 迁移设置和历史后删除 drop。虎牙只有 rekey。建议抽成平台无关 helper，虎牙在 known 命中后额外查 short_id 与 UID，对 id 不同的行做 active-keep 合并，再 rekey。

batch_follow 粘性：insert_room 的 ON CONFLICT 使用 batch_follow=MAX(batch_follow,excluded)、platform_uid=COALESCE(excluded,旧)。移除关注房后再手动加同一房号，会继承旧的 batch_follow=1 和 UID；若已取关，下一拍批量缺项并回退单房。是否把“手动添加”视为退出批量需要产品决定。

## 2. 监控和录制是否区分

正确。批量只调用虎牙 WUP 关注列表，产出 LiveStatus（是否在播、标题、主播、封面、分区、人气、开播时间、lUid、房号）。batch_room_info 只用于写库、推前端、决定 Start/Stop。真正开录走 recorder.start_checked → broker.plan → HuyaAdapter::stream_plan，重新请求房间页、解析 gameStreamInfoList、画质和线路，不把关注列表字段当流地址。

停止录制不是只看批量状态：apply_room_info 离线分支要连续两次确认，并检查文件是否还在增长；批量误报不会立刻杀掉正在写的录像。录制失败冷却与 monitor 的 entry.backoff 也是两套状态。

展示层小问题：虎牙批量写回的 internal_room_id 是数字房号（import_room_info 的 stable_id 导致），对虎牙没有业务语义，批量只读 platform_uid；不影响正确性，但排查时容易误解。

## 3. Cookie 四态

无 Cookie：导入返回 Upstream code=-1“虎牙关注列表需要登录”，前端显示“关注列表读取失败。请检查网络或虎牙登录状态后重试。”；huya_batch_ready=false，关注房不进批量，已有房继续单房匿名页面检查；匿名可取流录制，画质上限 15100，4K 灰显“登录后可用”。

失效：credential::is_ok 为 false，cookie_for_url 不再注入，批量门槛关闭；单房匿名检查继续，录制中的 ffmpeg 不受影响。若状态还没标 expired 但 WUP 返回鉴权错误，is_auth_expired 只认 code 8/-101/-1 或“未登录/登录态失效/not login”；虎牙若返回其他 bcode，会落入“其他错误→全量降级单房”，不误判离线但放大请求。失效不删房间/关注标记，恢复后下一拍回批量。

补 Cookie：account::save_cookie → huya_auth::prepare_cookie 校验 udb_uid/登录态 → 写库 → 重置复验时钟。下一拍 huya_batch_ready 看到 is_ok=true，已有 batch_follow=1 的房自动回批量。注意：登录本身不会把普通手动房加入批量，批量资格要求 batch_follow=1；手动房必须通过导入升级。账号页文案没有直接说明这个区别。

自动续期：maintenance_loop 每 20 分钟尝试 cookieExchange，无凭据/不可续期时 30 分钟醒一次；独立 revalidate 每 30 分钟醒一次，但 checkLogin 受 6 小时窗口限制，扫码/手动保存重置时钟。只有服务端下发不同 Cookie 才写“已轮换”，相同值写 fresh；续期不重启已运行 ffmpeg；鉴权错误才标 expired，网络错误只写 failed。

请求泄露：WUP Cookie 在 JCE 请求体，HTTP 头只有 Content-Type/Referer；页面请求只对 huya.com 注入账号 Cookie；CDN 候选和 ffmpeg 命令行不带账号 Cookie；日志 URL 脱敏。流签名 wsSecret 仍可能出现在进程命令行，这是既有边界。

## 4. 30 秒批量流程

排期：monitor_interval_sec=30 时，每个平台 BatchState.at 首次取 now + hash("batch:huya") % 30，启动后 0–29 秒之间某一拍开始，不是整点同时开始；之后每 30 秒一拍，不再加抖动。单房检查仍有 ±10%（约 ±3 秒）抖动。修改检测间隔会按新间隔重新散开。批量拍只包含：登录态 ok、batch_follow=1、platform_uid 非空、没有单房在途、没有未到期退避的房间。

举例：A=660000 重播，WUP liveStatus=1 但页面 is_replay=1；B=222523 真实直播；C=9999 手动添加、不在关注、batch_follow=0；A/B 开自动录制，C 不开。首拍落在第 12 秒：

1. 日志“批量状态检查开始 platform=huya rooms=2 interval_sec=30”，rooms 只含 A/B。
2. 一次 WUP 请求拉第 1 页，命中 A/B 两个 lUid，returned=2。
3. confirm_live 只对两个在播项各打一次房间页：A 页面 is_replay=1 → is_live=false，清空 started_at/online；B 保留直播并刷新人气/开播时间。
4. 匹配回房间：A 写回离线，若正在录则两次离线确认+文件不增长才停；B 写回在播，若未录且满足自动录制，start_checked 异步取流开录。
5. 日志“批量状态检查完成 platform=huya authed=true rooms=2 keys=2 returned=2 live=1 missing=0 unresolved=0 elapsed_ms=116”。
6. C 不参与这一拍，按自己的单房排期每 30±3 秒请求一次 https://www.huya.com/9999。
7. 第 42 秒下一拍；B 仍直播则重复 WUP+一次页面复核；A 仍被 WUP 标在播则重复纠正。

被取关/不在关注列表：WUP 没有它，missing=1；DEBUG“批量状态缺少该房间，回退单房间检查”，带 room、room_id、platform、key；同一拍并发单房检查，不判离线。

新导入“已存在但之前是手动房”：导入当拍只写 batch_follow/platform_uid；等下一次批量拍点，最多约 30 秒；若已在直播且 auto_record=1，导入不会重复开录，start_checked 会检查当前是否已在录。

## 5. 兜底能力

| 情况 | 当前行为 | 评价 |
|---|---|---|
| WUP 缺某个 UID | 该房单房页面检查 | 正确，不误判离线 |
| WUP 整页失败/网络错误 | 整批降级单房 | 结果正确，但 N 房 N 请求 |
| WUP 已知鉴权错误 | 整批降级单房，继续匿名 | 正确，监控不停 |
| WUP 未知 bcode | 归入其他错误，整批降级 | 安全，但可能每 30 秒放大 |
| 429/412/限流 | 整平台 not_before 冷却，默认 30 秒，最低 5 秒 | 正确 |
| 风控 10011/10012/10013 | 整平台冷却 120 秒 | 正确 |
| 批次 panic | 未回传房间补 Failed，清 inflight | 正确 |
| 单房已软删 | apply_room_info 第一道闸忽略 | 正确，不复活 |
| confirm_live 失败 | 保留 WUP 结果，只记 DEBUG | 安全但可能短暂把重播当直播 |
| 关注超过 6000 位 | 翻页到 MAX_PAGES=50 静默停止 | 缺口：超出部分永远缺项，每拍单房兜底 |
| 多个在播关注 | join_all 无并发上限 | 风险：关注多时瞬时页面请求过大 |

结论：兜底“不误判、不停摆”正确；不足在请求放大和超长关注列表截断，不是状态正确性。

## 6. 新增房不在关注列表

手动添加默认 batch_follow=0，即使已登录也不进批量；走单房页面检查，30 秒 ±10% 抖动，匿名也能拿 host/title/area/cover/is_live/online；自动录制、画质、线路与批量房同一套 stream_plan。后来导入关注会升级 batch_follow=1，下一拍转批量；一直不在关注就保持单房，不会因为批量没有而误判离线。

例外是粘性：曾导入、后取关、再手动加同一房号，可能继承 batch_follow=1，于是每拍批量缺项+单房兜底。表现仍正确，只是多一次请求。

## 7. 先加房后导入

正常，已真机验证。前端 isExisting 命中，同时 isBatchUpgradable=true，允许勾选；后端按数字房号/别名/UID 找到已有行；别名行 rekey 到数字房号；补 platform_uid 和 batch_follow；日志“导入关注：已有虎牙房间加入批量状态”，汇总 existing=1 upgraded=1 rekeyed=1；下一拍进批量。

两点：导入弹窗的“监控/自动录制”只对新建或恢复房生效，已存在房不会被导入覆盖 auto_record/monitor_paused，这是保护用户设置；已有房升级分支不会立即 start_checked，要等下一拍，已录时不会重复开录。

## 8. 移除房间

room_remove（commands.rs:795）：正在录→stop 合并；view.close_room；recorder.resume_auto 清“手动停录”；删除抖音关注池项（虎牙无本地关注表）；delete_room 软删 removed_at+monitor_paused=1；emit rooms_changed。

在途：批量拿到移除前快照，apply_room_info 首先查 db.room_removed，命中直接返回，不写状态不开录；start_checked 再查一次；下一 tick schedule.retain 移出排期；不会因批量晚到而复活或重录。

重新添加同一房号：软删行恢复；batch_follow/platform_uid 可能因粘性保留；若已取关，下一拍批量缺项→单房兜底，表现正确但多请求。

## 15. 本轮修复（m74797）

### 15.1 别名归一与导入折叠

- `src-tauri/src/platform/huya.rs` 的 `room_info` 从页面 `profileRoom` 解析数字房号作为 `stable_id`；`stable_room_id` 兼容裸数字和引号数字，0/缺失返回 None。
- `src-tauri/src/commands.rs` 的 `canonical_reference` 增加 huya 分支：别名添加后 `room_key` 与 `canonical_url` 都落数字房号。
- 新增 `fold_import_alias`：导入命中短 ID 行/lUid 行时，与当前 `known` 行按“活跃者优先”合并（`merge_room`），再 rekey 到数字房号；同 id 跳过。这样历史遗留的“软删数字行 + 活跃别名行”也会被折成一行。
- 真机：添加 `https://www.huya.com/lpl` 后 DB 直接是 `room_key=660000`、`canonical_url=https://www.huya.com/660000`；再添加 `https://www.huya.com/660000`，`room` 表仍只有 1 行。
- 真机导入：已有 660000 行显示“已添加 / 可加入批量”，勾选后日志 `existing=1 upgraded=1`，DB `platform_uid=1346609715`、`batch_follow=1`。

### 15.2 连续缺项降级

- `monitor.rs` 为每个平台 BatchState 增加按 `room.id` 的连续缺项计数；命中即清零。
- 虎牙连续 3 拍在关注列表缺失且 `batch_follow=1` 时，`clear_batch_follow` 把标记清零，下一拍走单房；不删房间、不删 UID，重新导入会再补上。
- 真机模拟：把导入房改成关注列表不存在的 `999999999`，日志连续 `misses=1/2/3`；第 3 拍 WARN“虎牙关注房连续缺项，改为单房间检查”，DB `batch_follow` 从 1 变 0，下一拍 `批量状态检查开始 ... rooms=1`，该房不再进入批量。

### 15.3 905 鉴权分类

- 用无效 `udb_uid`/`udb_cred` 和 uid=0 请求 WUP，均返回 `bcode=905`，确认是登录态/票据无效。
