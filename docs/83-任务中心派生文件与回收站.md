# 任务中心、派生文件登记与回收站（v1）

> 状态：已实现并通过 macOS 真机验收（2026-11-08）。
> 本文补上三块产品化缺口：后台任务可见/可取消、一条录像的多个文件可见/可定位、删除行为可解释并可找回。
> 前序设计见 `79-录制后处理`、`80-后处理任务中心`、`82-媒体库与播放器体验`。

## 1. 任务中心

### 1.1 为什么需要

后处理（转封装/转换/自定义命令）、合并、弹幕导出原本只在日志和局部按钮的 loading 里可见。用户切走页面就不知道任务还在不在，也无法取消。录制本身也需要和这些任务放在同一个地方看。

### 1.2 数据与合并规则

新增表 `task_history`（`db.rs:43`）：

| 列 | 含义 |
| --- | --- |
| id | 任务 id，如 `post:<session>`、`merge:<group>` |
| kind | record / post / merge / danmaku |
| title / detail | 给用户看的标题与副标题 |
| state | running / done / failed / cancelled / interrupted |
| percent / stage / message | 进度、阶段、失败原因 |
| session_id / room_id | 可跳回录像或主播 |
| started_at / finished_at | 秒级时间戳 |

运行时任务在 `jobs.rs` 内存表里，`TaskBoard` 每次轮询时合并：

1. 正在开录的房间（`record:starting:<room>`，0%）；
2. 正在录制的房间（`record:<session>`，带已录时长）；
3. jobs 内存表中的后处理/合并/弹幕导出；
4. `task_history` 最近 100 条已结束任务。

启动时 `mark_tasks_interrupted()` 把上次残留的 running 改成 interrupted，避免永远转圈。历史查询明确排除 running，防止内存任务和数据库行重复。

### 1.3 取消语义

- 只对真正可取消的 post/merge/danmaku 显示取消；录制不提供任务页取消（录制有独立的停止按钮）。
- `post_cancel` 触发已有的 CancellationToken，ffmpeg 子进程被杀；任务以 cancelled 落库，不是 failed。
- 取消后现场清理沿用后处理模块的规则：临时输出删除，母带保留。

### 1.4 界面

`src/features/tasks/TasksPage.tsx` 每 2 秒轮询 `task_board`。运行中卡片显示标题、阶段、进度条和取消按钮；历史区按时间倒序，失败显示原因，取消显示「已取消」。页面在没有任务时给出空状态，不占位。

## 2. 一条录像的多个文件

### 2.1 三角色

新增表 `media_file`（`db.rs:63`），唯一键 `(session_id, path)`：

| role | 含义 |
| --- | --- |
| main | 当前主文件（播放、导出、详情默认指向它） |
| source | 源封装母带（convert/custom 模式保留的原始文件） |
| derived | 历史派生文件（转封装产物、重新转换的旧主文件） |

`state` 为 present / missing / deleted。`record_session.file_path` 仍是主索引，`media_file` 只负责完整清单，避免大改播放链路。

### 2.2 写入时机

- 录制开始：登记 main。
- 源封装模式成功：登记 source，主文件不变。
- 转换模式成功：旧主文件降级为 derived，新文件登记 main；源文件按设置删除或登记 source。
- 手动「转 MP4」成功：同一条链路，旧主文件降级 derived。
- 删除文件：不删行，标 deleted，保留历史。

`sync_media_files_on(session)` 是唯一同步入口，`update_session_post_file` 和删除命令都走它，避免 UI 与 DB 各写一套。

### 2.3 迁移

旧库在启动迁移时按现有 `file_path`/`source_path` 补登记，不移动文件、不改文件名。没有 `media_file` 行的历史录像首次打开详情时也能看到主文件。

### 2.4 展示与定位

- `media_files(session_id)` 返回整条录像的文件清单。
- 媒体库详情抽屉在文件数大于 1 时显示「文件」区，逐行给出角色、文件名、大小、状态。
- `media_reveal_file(session_id, path)` 只允许定位登记在册且位于录像目录内的文件，防止前端传任意路径变成文件系统浏览器。
- 文件丢失时显示 missing 而不是假装能播放；删除后显示 deleted。

## 3. 回收站

### 3.1 能力探测

`trash_info()` 返回平台、模式、是否可还原、位置和说明：

| 平台 | mode | 位置 | 还原 |
| --- | --- | --- | --- |
| macOS | system | ~/.Trash | 访达 → 废纸篓 |
| Windows | system | 回收站 | 资源管理器 |
| Linux | freedesktop | ~/.local/share/Trash | 文件管理器 |

删除源文件不是 `remove_file`，而是移到系统回收站（Linux 按 FreeDesktop 规范）。设置页存储卡片读取 `trash_info`，把「删除后去哪、能不能找回」直接写在按钮上方。

### 3.2 打开回收站

`trash_open()`：

- Windows：`explorer shell:RecycleBinFolder`；
- macOS：`open ~/.Trash`（不能 `open -R`，否则只会定位到主目录里的隐藏项）；
- Linux：确保目录存在后 `xdg-open`。

macOS 首次实现用了 `open -R`，真机点开只弹出主目录；改为直接打开目录后，Finder 前台窗口标题为「废纸篓」，路径为 `/Users/joftal/.Trash`，能看到真实废纸篓内容。

### 已知限制

- 手动「转 MP4」的成功登记只做了代码路径审查，没有在 UI 上完成一次点击复验（验收时按钮命中坐标反复偏移）。接口与自动后处理共用 `update_session_post_file`，风险集中在 UI 触发，不在登记逻辑。
- 任务历史目前保留全部记录，只按 100 条展示；没有自动清理策略。
- 回收站只负责“移进去”和“打开”，应用内不做还原或清空，避免和系统行为打架。
