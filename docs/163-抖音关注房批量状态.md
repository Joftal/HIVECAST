# 抖音关注房批量状态

> 2026-11-16。范围：抖音关注房的 follow/feed 批量状态发现、内部 room_id 持久化、缺失房间保护，以及它与录制/画质/弹幕链路的边界。

## 1. 要解决的问题

抖音单个房间的一次监控检查要发两个 HTTP 请求：先 GET 房间页拿 ttwid，再请求 `webcast/room/web/enter`。50 个房间、30 秒轮询，平均约 3.3 req/s，容易触发抖音风控。

关注列表里的房间有更轻的状态接口：`GET https://www.douyin.com/aweme/v1/web/follow/feed/`。一次最多带 20 个**内部 19 位 room_id**，只返回当前在播的房间，并带标题、在线人数、封面、主播和开播时间。50 个关注房因此从每轮 100 个请求降到 3 个请求。

## 2. 接口实测

请求：

```text
GET https://www.douyin.com/aweme/v1/web/follow/feed/
  ?device_platform=webapp&aid=6383&channel=channel_pc_web
  &cursor=0&level=3&count=20&pull_type=0&refresh_type=0
  &room_ids=<内部 room_id,内部 room_id,...>
  &a_bogus=<签名>
```

约束与实测结果：

| 项 | 结果 |
| --- | --- |
| 匿名请求 | 带正确签名也只返回 7 字节 `blocked`，必须登录 Cookie |
| 不签名 | 200 + 空 body |
| room_ids 语义 | 必须是内部 19 位 room_id，不是 URL 里的 web_rid |
| 传 web_rid `938611933111` | `data=0`，不认 |
| 传内部 `7708406515142462227` | `data=1`，rawdata 完整 |
| 20 个内部 id | 200，只返回其中在播的项 |
| 两个内部 id | `data=2` |
| JSON 数组形态 `["id"]` | 200 + 空 body，不可用 |
| 返回项形态 | `cell_room.rawdata` 是 JSON 字符串；个别是 `{"additional_stream_url":...}`，没有 id/status/title |

关注列表 `/aweme/v1/web/user/following/list/` 的实测：当前账号 1531 个关注、77 页、每页 20、全量约 22 秒；分页靠 `max_time=上一页 min_time`，不是 offset。关注项自带内部 `room_id`，但在播项的 `room_data` 经常是空对象，**不保证带 web_rid**。

## 3. 数据模型

房间新增两个持久字段：

- `room.batch_follow INTEGER NOT NULL DEFAULT 0`：是否来自关注导入。只有它为 1 的抖音房才走 follow/feed 批量；手动添加的抖音房不在关注列表里，继续单房检查。
- `room.internal_room_id TEXT`：抖音内部 19 位 room_id，批量请求的键。它与 `room_key`（web_rid，用于打开房间页/取流）分开保存，避免污染 `platform_uid`。

相关代码：

- `src-tauri/ipc-types/src/lib.rs:56` 的 `RoomRecord` 新增 `batch_follow`、`internal_room_id`。
- `src-tauri/src/db.rs` 的 schema、迁移、`ROOM_SELECT`、`map_room`、`insert_room`、`update_room_info` 全部带上两列；`internal_room_id_of(info)` 从 `extra["roomId"]` 读取，兼容字符串和数字。
- `insert_room` 的冲突分支用 `COALESCE(excluded.internal_room_id, internal_room_id)` 保留已有内部 id；`update_room_info` 同样不会因为平台这次没返回而清空。
- `rooms_import` 对 `platform == "douyin"` 写 `batch_follow = true`，并写入 `internal_room_id`。

## 4. 监控链路

接入点都在 `src-tauri/src/monitor.rs`：

- `spawn` 注册 `BatchState::new()`，tick 的平台列表加入 `"douyin"`。
- `batchable_platform(room, douyu_ready, douyin_ready)` 对抖音要求：`platform == "douyin"`、`batch_follow`、`internal_room_id` 非空、抖音已登录。只有 web_rid 的旧房先单房检查一次，拿到内部 id 后下一轮自动进批量。
- `run_batch_check` 的抖音 keys 用 `internal_room_id`，不用 `room_key`；返回项按内部 id 映射回房间。
- `batch_room_info` 对抖音只写 `roomId / liveStatus` 等字段，不写 `uid`，避免污染 `platform_uid`。
- 批量返回在播：正常更新标题、在线、封面、开播时间；若自动录制开启且未在录，走原来的开录路径。
- 批量返回缺失，分三种：
  1. 上一轮已离线、整批没有不可解析项：合成离线状态，不请求单房。离线关注本来就不会出现在 follow/feed。
  2. 上一轮在播：单房确认一次，避免批量漏项导致误停；确认离线仍要走连续两次的 `confirm_offline`。
  3. 整批有不可解析 rawdata：这一批的缺失项全部单房回退，不拿缺失推断离线。
- 批量整体失败：维持现有规则，普通错误全量降级单房，429/412 整平台短冷却。
- 录制进程、画质升档、线路、弹幕都不走批量；批量只做状态发现，开录后仍由各房间独立取流和订阅弹幕。因此批量不会改变已启动 ffmpeg 的生命周期。

测试前备份真实库到 `/tmp/hivecast-before-douyin-batch.db`。新 bundle 启动后 `pragma table_info(room)` 末尾出现：


写回结果：`title=健康分你回来吧`、`online=34`、`is_live=1`、`last_checked_at` 更新。

再插入一个永远不在关注列表的离线房：`room_key=111111111111`、`internal_room_id=7700000000000000000`、`batch_follow=1`、`is_live=0`。两房日志连续三轮都是：

## 7. 边界与后续

- **当前没有抖音关注导入界面**。前端 `ImportFollowsDialog.tsx` 的来源仍只有哔哩哔哩和斗鱼；后端也没有 `douyin_followings` 命令。本轮把批量所需的数据模型、批量客户端、监控分支和缺失保护做完了，但普通用户目前无法在 UI 上产生 `batch_follow=1` 的抖音房。手动添加的抖音房仍然逐个检查。
- 抖音关注列表的在播项经常没有 web_rid，导入需要同时保留内部 room_id 和可打开的 web_rid，或者补一个「关注池 → 开播后转房间」的模型；这是独立的导入功能，不能只加一个 tab。
- 批量接口需要登录 Cookie；Cookie 过期时抖音批量直接跳过，所有抖音房回退单房。这会增加请求量，但不会把房间误判离线。
- rawdata 只有 `additional_stream_url`（连麦/舞台）时计 unresolved，不解析成普通房间，也不依据这一批的缺失判离线。
- 手动房、非关注房、关注后取关都可能在批量里缺失；对上一轮在播的房间仍会单房确认一次，代价是每轮多一个请求，换取不误停录制。
