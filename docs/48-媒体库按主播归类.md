# 48 - 媒体库按主播归类

> 状态：v1.1（2026-11-06）· 关联：[47-媒体库按主播归类-设计方案](47-媒体库按主播归类-设计方案.md)、[46-媒体库重构](46-媒体库重构.md)、[41-监控页重做](41-监控页重做.md)
> 一句话：媒体库的外层从「一条录像一张卡」改成「一个主播一张大卡」，点卡片下钻到该主播的录像页；录像页复用 46 的九宫格封面墙。v1.1 起只保留封面墙、工具栏与监控/观看统一、录制结束即生成缩略图、主播默认按名字排序。

## 0. 结论

用户裁决（m16392）后落地的形态：**主播墙是默认页**（封面大卡，卡上是平台 / 主播名 / 录像数 / 总体积 / 最新一条时间），点卡片整页切到**主播页**（头像 + 统计 + 该主播的录像网格）；**不提供「删除全部录像」**，批量删除放在主播页里多选；**所有平台彩色圆点全部去掉**，平台名只以文字出现。

v1.1（m16611 六条反馈）在此基础上收敛：列表视图整段删除，只留封面墙；工具行改成监控页那套 h-9 控件；主播默认按名字排序；主播页不再有搜索框；缩略图在录制完成时由录制器排队生成；时间戳一律到秒。

## 2. 聚合口径：一个主播 = 一个 room.id

三条可选口径（docs/47 §2）里选了**按 `room.id` 聚合**：

- `host_name` 会改名、也会在不同平台重名，按它聚合会把两个人并成一张卡；
- `room.id` 是加房间时就固定的主键，主播页筛录像也正好按它走 `record_session.room_id`，一条 SQL 就够；
- 代价是「同一个主播在两个平台各有一个房间」会显示成两张卡（见 §8）。

只统计**有效录像**：`s.status = 'finished' AND s.file_path IS NOT NULL AND s.file_path <> ''`。录制中的会话、文件已被外部删掉的记录都不进主播卡，否则「录像数」和磁盘上的文件对不上。

聚合主体：

```sql
SELECT r.id, r.platform, r.host_name, r.title, r.avatar_url, r.cover_url,
       COUNT(s.id), COALESCE(SUM(s.file_size), 0), MAX(s.started_at)
FROM room r JOIN record_session s ON s.room_id = r.id
WHERE <host_where>
GROUP BY r.id
ORDER BY <order_by>
LIMIT ? OFFSET ?
```

- 排序四选一：`name`（v1.1 起的默认，`r.host_name COLLATE NOCASE ASC, MAX(s.started_at) DESC`）、`latest`（`MAX(s.started_at) DESC`）、`size`（`SUM(s.file_size) DESC`）、`count`（`COUNT(s.id) DESC`），后三者都再按最新时间兜底。按名字排序用 `NOCASE`，英文主播名不受大小写影响；中文按码点序，不做拼音排序。
- 总数用子查询 `SELECT COUNT(*) FROM (SELECT r.id ... GROUP BY r.id)`，不要用 `COUNT(s.id)`，那是会话数。
- 平台计数走 `host_counts_locked(conn, filter)`：`COUNT(DISTINCT r.id)`，**忽略平台筛选**、其余条件（搜索 / 时间范围）生效。前端「全部」取各平台计数之和，而不是 `total`（`total` 会随平台筛选变小）。
- 分页每页 60，底部「加载更多」。

## 3. 主播墙

工具行没有标题，从左到右：搜索框（h-9 / w-[228px] / 13px 字号 / 14px 放大镜，placeholder「搜索主播或房间」）→ 平台下拉（h-9，只列有录像的平台，带计数）→ 右对齐一组：排序下拉（w-[140px]，按主播名 / 按最新录制 / 按体积 / 按条数）+ 刷新按钮（`size="lg"`）。控件尺寸与监控页工具行一致（搜索 h-9、下拉 h-9、按钮 32px 高），页面左右留白 `px-5`、上 `pt-4`、下 `pb-5`。

卡片（网格 `repeat(auto-fill, minmax(250px, 1fr))`）：

- 封面 16:10，`object-cover`，没有封面时用平台色底 + 平台名；
- 底部 `bg-gradient-to-t from-black/75` 渐变，压住头像与文字；
- 左上角平台徽标（半透明黑底 + 平台名，无圆点）；
- 底部一行：36px 圆形头像（有 `avatar_url` 用图，否则平台底色 + 首字）+ 白色主播名 + 其下 `text-white/60` 房间标题；
- 卡脚两行：第一行「N 个录像 · 16.6 MB」，第二行整行「最新 2026-11-06 11:33:07」（`font-mono tabular-nums text-faint`，到秒）。

列表视图（文件列表与主播列表两套）在 v1.1 已整段删除，`ViewMode` / `VIEW_KEY` / 切换按钮 / 相关图标与列宽常量一并移除。理由：两种视图的信息量完全一样，封面墙能直接看图，列表只是把同一批数据再排一次；保留切换反而让工具行多一个控件。

空态三种：还没有任何录像（`hosts.emptyTitle/emptyBody`）、搜索无匹配（`hosts.noMatchTitle/noMatchBody`）、主播的录像被删光后回到墙（`hosts.goneTitle/goneBody`）。

## 4. 主播页

顶部一行：`← 全部主播`（ghost 按钮）→ 64px 头像（`onCover=false`，带 border）→ 18px 主播名 + 平台 chip → 统计行「N 个录像 · 体积 · 最新 MM-DD HH:mm · 房间标题」；右侧是全选与刷新。

下面一行是筛选行：时间范围分段控件（全部时间 / 今天 / 近 7 天 / 近 30 天，h-9）、仅看弹幕（h-9 描边按钮）、右对齐排序下拉（按时间 / 时长 / 体积，w-[140px]）。**v1.1 删掉了搜索框**：主播页只列一个主播的录像，条数通常几十条，搜索的收益不如扫一眼九宫格。

录像卡片、列表、批量条、播放抽屉全部沿用 46 的实现，只有两处差异：

1. 卡片与列表里的平台色点删掉了，平台名纯文字；
2. 卡脚第一行改成「开始时间 + 体积」（46 是「标题 + 体积」），因为主播页里标题重复度高。

Esc 是分层退出：抽屉开着先关抽屉，再按一次才回主播墙（用 `playingRef` 判断，避免闭包里拿到旧的 `playing`）。

## 4.1 缩略图在录制结束时就生成（v1.1）

v1.0 的九宫格是**懒生成**：只有进到主播页、`media_list` 返回这一条时，前端才去请求缩略图，服务端发现缓存没有就现场抽帧。结果是从录制结束到第一次进媒体库之间，磁盘上没有任何封面；主播墙上的卡图也要等用户点进去一次才有。

v1.1 改成**录制器在 finalize 时排队生成**：

1. `Recorder` 新增 `thumbs: RwLock<Option<Arc<thumbs::Thumbs>>>`，`state.rs` 构造完 `Thumbs` 后 `attach_thumbs(thumbs.clone())` 注入；
2. `finalize` 里只有 `final_status == "finished"` 才 `queue_thumb(app, session_id)`（失败、取消、异常结束不生成，避免抽到半截文件）；
3. `queue_thumb` 重新读一次 `db.get_session`，拿**最终** `file_path` 与 `duration_ms`（录制中 `file_path` 还是 .part 分段，不能用），再 `thumbs.ensure(...)`；
4. `ensure` 自带「已存在就跳过」，与 `media_list` 的懒生成兜底并存：老会话（v1.0 录的）第一次被列出来时仍会补生成。

实测：B 站房间 14:59:36 开录、60 秒后停止，`d51706de-….jpg`（134 KB）在 15:00 录制结束的同一分钟出现，而当时媒体库停留在另一个主播的主播页（列表里根本没有这条会话），证明是 finalize 触发而不是列表触发。

## 5. 后端接口

`MediaHost`（camelCase 导出到前端）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `roomId` | string | 聚合键，也是主播页筛录像的条件 |
| `platform` | string | bilibili / douyu / huya / douyin |
| `hostName` | string | 卡片标题 |
| `roomTitle` | string | 卡片副标题 |
| `avatarUrl` | string \| null | 空时前端画首字母头像 |
| `coverUrl` | string \| null | 卡片大图 |
| `count` | number | 有效录像条数 |
| `bytes` | number | 总体积 |
| `latestAt` | number | 最新一条的开始时间（unix 秒） |

`MediaHostPage` = `{ items, total, platformCounts }`。

`media_hosts(query?, platform?, days?, sort?, limit?, offset?)` 返回 `MediaHostPage`；`media_list` 新增可选 `room_id`，与原有 query / platform / days / only_danmaku / sort 可叠加。

两条单测（`src-tauri/src/db.rs`）：

- `media_hosts_aggregates_finished_sessions_per_room`：两个房间四条会话（其中一条 recording），断言 total=2、`rm-a` 的 count=2 / bytes=400 / latest=3000、录制中不计入、平台计数 2 个、按体积排序、平台筛选后计数仍是 2 个平台；
- `media_list_can_be_scoped_to_one_room`：`room_id=rm-a` → total=3 且全部属于该房间。

| 默认排序 | 按最新录制倒序（11-06 11:33 → 11-04 15:06） |

## 8. 缺口

| 缺口 | 影响 | 后续 |
| --- | --- | --- |
| 主播身份只有 `room.id` | 同一主播多平台 / 多房间会拆成多张卡，没有手动合并入口 | 需要「合并主播」时再加 `host_group` 表 |
| 主播卡不给「删除全部」 | 想清空一个主播要先下钻再全选 | 有明确诉求再加，避免误删 |
| 缩略图 968x548 放在 250px 卡上偏小 | 九宫格在卡片上只能看个大概 | 与 46 同一个缺口，需要按卡片宽度生成第二档 |
| 分页 60 无虚拟滚动 | 上千条时「加载更多」会越来越长 | 后续换虚拟列表 |
| 没有封面的房间卡是灰底 | 离线且从未抓到封面的房间（如测试里的抖音房间）只能显示平台名 | 可用该主播最新录像的九宫格兜底，需要 `MediaHost` 带一个 latest session id |
| 即时生成是逐条串行 | 同时结束多路录制时抽帧排队，几百 MB 的片子约 1 秒/条 | 并发上限 2 已由 `thumbs` 内部限制，够用 |
