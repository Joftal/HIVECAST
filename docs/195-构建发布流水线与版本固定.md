# 195 - 构建发布流水线与版本固定

> 2026-11-23，2026-11-24 复核工具链与计数。目标：为真机验收准备一套可重复的 Windows / macOS 构建与发布链路，并把构建期会变化的外部输入固定下来。
>
> 本文记录当前仓库实际使用的工具链、直接依赖、GitHub Actions 动作与运行时外部依赖。直接依赖全部写成精确版本；传递依赖由已入库的 `pnpm-lock.yaml` 与 `src-tauri/Cargo.lock` 锁定。

| --- | --- | --- |
| 依赖精确固定 | `package.json` | 所有 dependencies / devDependencies 去掉 `^`，写成精确版本 |
| Rust 依赖精确固定 | `src-tauri/Cargo.toml`、`src-tauri/ipc-types/Cargo.toml` | 所有直接依赖写成 `=x.y.z` |

| Rust 固定 | `rust-toolchain.toml` | 1.100.0，minimal profile，含 rustfmt / clippy |
| 版本注入 | `scripts/ci/set-version.mjs` | 把 workflow 输入的版本写入四处版本源并回读校验 |

## 2. 版本号如何流转

GitHub Actions 的 `workflow_dispatch` 接收一个 `version` 字符串，先校验 SemVer，再调用：

```bash
node scripts/ci/set-version.mjs "$VERSION"
```

脚本会同步写入四个位置：

| 位置 | 字段 | 用途 |
| --- | --- | --- |
| `package.json` | `version` | 前端工程版本、构建元数据 |
| `src-tauri/tauri.conf.json` | `version` | Tauri 安装包版本、DMG 文件名 |
| `src-tauri/Cargo.toml` | `[package].version` | `env!("CARGO_PKG_VERSION")` 编译期版本 |
| `src-tauri/Cargo.lock` | 根包 `hivecast` 的 `version` | 保证 `--locked` 不会因根包版本不一致失败 |

写入后脚本会回读四个位置，任何一个不等于输入版本就失败。版本号不允许带 `v` 前缀；允许预发布后缀，例如 `0.2.0-rc.1`。

运行期显示的版本来自 Rust 的 `CARGO_PKG_VERSION` 与 Tauri `package_info()`，因此安装包、设置页和 Cargo 包版本一致。`src/features/design/SettingsDesign.tsx` 里仍有硬编码的 `v0.1.0`，但它是没有 IPC 引用的设计稿 mock，不在真实设置页使用。

CI 的版本注入只发生在 runner 工作区，不回写仓库。仓库默认版本仍是 `0.1.0`；正式发布以 GitHub tag `v<version>` 和 Release 资产为准。这样不需要为每次发布提交版本号，也不会让构建任务反向改 main。

| Rust | 1.100.0 | `rust-toolchain.toml`、workflow `toolchain: 1.100.0` | rustup 与 CI 都按此版本 |
| Rust 组件 | rustfmt、clippy | `rust-toolchain.toml` | CI 也显式安装 |

| macOS 构建机 | `macos-15`（arm64） | workflow matrix | macOS 14 已于 2026-11-02 从 GitHub Actions 退役 |
| Windows 构建机 | `windows-2022`（x64） | workflow matrix | 使用 MSVC 工具链 |

`src-tauri/Cargo.toml` 声明 `rust-version = "1.89"`，这是 crate 的最低支持版本；实际构建统一用 1.100.0。这样保留 MSRV 信息，同时避免不同机器用不同 stable 版本编译。rusqlite 0.43 与 std 文件锁要求至少 1.89。

workflow 把 `actions-rust-lang/setup-rust-toolchain` 的 `build-warnings` 显式设为 `warn`，避免平台相关但无害的警告阻断发布；真正的编译错误仍会让 job 失败。

## 6. 构建与发布流程

workflow 文件：`.github/workflows/build-release.yml`。触发方式为 GitHub Actions 页面的 **Run workflow**，三个输入：

| 输入 | 类型 | 默认 | 规则 |
| --- | --- | --- | --- |
| `version` | string | 无（必填） | SemVer，不带 `v`；正式版 `0.2.0`，预发布 `0.2.0-rc.1` |
| `prerelease` | boolean | `false` | 必须与版本号是否带 `-` 后缀一致，否则 validate job 直接失败 |
| `publish` | boolean | `false` | `false` 只构建并保留 artifact；`true` 才创建 GitHub Release |

Job 结构：

1. `validate`（ubuntu-24.04）：校验 SemVer、预发布标记一致性，输出规范化版本。
2. `build`（matrix）：
   - `macos-15` / arm64：`pnpm tauri build --bundles app`，再由 `scripts/build-dmg.sh --no-build` 生成 DMG。
   - `windows-2022` / x64：`pnpm tauri build --bundles nsis`，取 NSIS `.exe`。
   - 两个平台都先做 `pnpm install --frozen-lockfile`、版本注入、`check:docs`、`check:i18n`。
3. `release`（ubuntu-24.04，仅 `publish=true`）：下载两个 artifact，检查 `v<version>` tag 是否已存在，然后 `gh release create`。

产物命名：

| 平台 | workflow artifact | 发布资产 |
| --- | --- | --- |
| macOS arm64 | `hivecast-macos-arm64` | `HIVECAST-v<version>-macOS-arm64.dmg` |
| Windows x64 | `hivecast-windows-x64` | `HIVECAST-v<version>-Windows-x64-setup.exe` |

发布行为：

- tag：`v<version>`，指向触发 workflow 的 commit。
- 标题：`HIVECAST v<version>`；release notes 用 GitHub 自动生成。
- `prerelease=true` 加 `--prerelease`；正式版加 `--latest`。
- 如果 tag 已存在，release job 失败，不覆盖旧资产。
- artifact 默认保留 14 天；`publish=false` 时从 Actions run 页面下载。

macOS 打包仍走 `scripts/build-dmg.sh`：Tauri 只产出 `.app`，脚本用 `hdiutil` 生成简单 DMG，避开 Tauri 自带 DMG 脚本在无 Finder 自动化权限环境下的 AppleScript `-1712` 超时。DMG 没有背景图和图标布局，只有应用与 `/Applications` 链接。

## 7. 运行时外部依赖

这些不参与编译，但会影响安装包在用户机器上的可用性。

| 依赖 | 是否随包 | 版本策略 | 说明 |
| --- | --- | --- | --- |
| FFmpeg / ffprobe | 否 | 用户机器决定；本机验收用 9.0.2 | 录制、转封装、缩略图、探测都依赖；设置页可手动指定，检测顺序为手动路径 > PATH > 常见目录；保存时执行 `-version` 校验 |
| WebView2 Runtime | Windows 系统组件 | Evergreen | Windows 10/11 通常已带；Tauri NSIS 安装器可按默认 WebView2 安装模式引导 |
| NSIS | 否 | 由 tauri-bundler 2.10.4 管理 | 首次 Windows 打包时 bundler 下载并校验哈希；版本随 CLI 升级，不在仓库单独固定 |
| macOS 系统 | — | 最低 11.0 | 当前只构建 arm64；Intel Mac 需要另加 x64 构建机 |
| 图标 / 字体 / 图片 | 是 | 仓库内文件 | `src-tauri/icons`、`public`、`assets` 均为本地资源，不拉 CDN；CSP 也不允许远程脚本 |

FFmpeg 没有强制最低版本检查。当前代码使用的能力（HLS/TS 读取、`-c copy`、AAC `aac_adtstoasc`、ASS 封装、缩略图）在 FFmpeg 6/7/8/9 上都可用；真机验收记录的是 9.0.2。若要把 FFmpeg 也做成完全可复现，需要把二进制放进安装包或单独的 runtime 目录，这会显著增大包体，本轮没有做。

## 8. 固定状态与升级判断

| 资源 | 是否固定 | 固定方式 | 当前建议 |
| --- | --- | --- | --- |
| npm 直接依赖 | 是 | package.json 精确版本 + lock | 按模块升级；每组跑构建、翻译与文档检查 |
| npm 传递依赖 | 是 | pnpm-lock.yaml + frozen lockfile | 随直接依赖升级后重新生成，不手工改 |
| Rust 直接依赖 | 是 | Cargo.toml `=x.y.z` + Cargo.lock | 按模块升级；升级后跑 `cargo test --locked` 与 release 构建 |
| Rust 传递依赖 | 是 | Cargo.lock | 由 `cargo update` 显式更新，CI 不自动变 |
| Node | 是 | .node-version + setup-node | 24.22.3；跟随 Node 24 LTS 安全更新，升级前改 .node-version |
| pnpm | 是 | packageManager + action 参数 | 12.23.0；升级时同步更新 action 参数与 `pnpm-workspace.yaml` |
| Rust | 是 | rust-toolchain.toml + action 参数 | 1.100.0；升级后跑全量测试与 release 构建 |
| Tauri CLI / crate | 是 | 精确版本 | CLI 2.12.6 与 crate 2.12.7 同 minor；升级时成对检查 |
| GitHub Actions | 是 | commit SHA | 每月看一次 release，按 SHA 升级并记录 |
| NSIS | 间接 | tauri-bundler 内置策略 | 不单独升级；升级 CLI 后重新验证 Windows 安装器 |
| FFmpeg | 否 | 运行时检测 | 文档记录验收版本；不随包固定 |
| WebView2 | 否 | 系统 Evergreen | 不固定；安装器负责引导 |
| 构建机 OS | 是 | macos-15 / windows-2022 | 关注 GitHub runner 退役公告；macOS 14 已退役 |
| Xcode / MSVC / SDK | 否 | 随 runner 镜像 | 镜像每周更新，无法在仓库固定；需要完全固定时改用 self-hosted |

runner 镜像本身是滚动的：`macos-15` 的 Xcode 小版本、Windows 镜像的 MSVC 与 Windows SDK 会随 GitHub 更新。Node、pnpm、Rust 由 action 拉取并固定，系统编译工具链不在仓库控制范围内。这是当前方案与「完全可复现构建」之间最大的缺口；如果验收后要求逐字节复现，应改用带固定镜像的 self-hosted runner。

构建期仍会访问 npm registry、crates.io 与 GitHub Releases，但版本由 `pnpm-lock.yaml`、`Cargo.lock` 与 action SHA 锁定，不会解析到「最新版」。

## 10. 已知限制与未做事项

1. **没有代码签名与公证**。macOS 产物是 ad-hoc 签名，首次打开会被 Gatekeeper 拦截，需要右键「打开」或在系统设置中放行；Windows 未签名，SmartScreen 会提示「更多信息 → 仍要运行」。要消除提示需要 Apple Developer ID / 公证账号与 Windows 代码签名证书，本轮未配置。
2. **macOS 只出 arm64**。`macos-15` 标准 runner 是 arm64；Intel 用户需要增加 `macos-15-intel` 或 universal 构建，当前没有做。
3. **Windows 安装器未在本机实际构建**。本机是 macOS，workflow 已按 `windows-2022` + NSIS 配置，但首次真实 Windows 构建要在 GitHub 上跑一次确认；NSIS 由 Tauri bundler 下载，需要 runner 能访问 GitHub。
4. **没有自动更新器**。Release 只是下载页，应用内不检查新版本。
5. **版本注入不回写仓库**。发布 tag 与资产版本一致，但 main 上的 package.json 仍是开发版本；如果要求“仓库版本=发布版本”，需要另加提交步骤。
6. **设计稿 mock 仍硬编码 v0.1.0**。`SettingsDesign.tsx` 不接 IPC、无引用，不影响真实设置页；后续可删或改成占位。
7. **没有在 GitHub 上实跑过该 workflow**。本轮只做了 YAML 语法与脚本级验证；第一次手动触发时重点看 macOS runner 架构、Windows NSIS 下载和 Release 权限。
8. **pnpm 12 的锁文件结构变了**。`pnpm-lock.yaml` 顶部新增一个 `---` 分隔的 YAML 文档，记录 pnpm 自身的版本与各平台 `@pnpm/exe` 产物；这是 pnpm 12 的 `packageManagerDependencies` 行为，不是重复内容。不要手工删除该文档，否则 `pnpm install --frozen-lockfile` 会失败。
9. **pnpm 12 默认启用发布年龄保护**。发布不足 24 小时的包会被拒绝安装；`pnpm-workspace.yaml` 的 `minimumReleaseAgeExclude` 仅为 `i18next`、`lucide-react` 放行（当天已验证的版本）。后续升级这两个包时，要么等满 24 小时，要么同步更新例外列表。
10. **6 条上游 advisory 已显式豁免**。项目已把直接依赖从 `chrono` 迁到 `jiff 1.0.2`；`Cargo.lock` 仍保留 `chrono 0.4.45`，因为 `serde_with` 的 optional `chrono_0_4` 会写入 lock，但无 feature 启用、实际不编译。其余 `proc-macro-error`、`zbus_names`、`zvariant`、`zvariant_derive`、`glib` 只经 Linux GTK/zbus 链路，不进入 macOS/Windows 产物。`src-tauri/.cargo/audit.toml` 逐条记录原因，`cargo audit --no-fetch --target-os macos` 输出 0 条、exit 0；详见 199 第 3.2 节。不要把这当成上游已修复，Tauri Linux 栈升级后应删除豁免并复跑。

## 11. 维护清单

升级 pnpm / 工具链时：

1. 同时修改 `package.json` 的 `packageManager`、`.github/workflows/build-release.yml` 的 `pnpm/action-setup` 参数、`.node-version` 与 `rust-toolchain.toml`。
2. pnpm 12 起构建脚本白名单在 `pnpm-workspace.yaml` 的 `allowBuilds`，不再读 `package.json` 的 `pnpm.onlyBuiltDependencies`。
3. 新版本若在发布年龄保护期内，优先等待；确需立即使用时在 `minimumReleaseAgeExclude` 精确加包名，不要关闭整个保护。
4. 升级后跑一次 `pnpm install --frozen-lockfile`，确认锁文件中的 `packageManagerDependencies` 与 `packageManager` 一致。

升级任何直接依赖时：

1. 修改 `package.json` / `src-tauri/Cargo.toml` 的精确版本。
2. 重新生成锁文件：`pnpm install --lockfile-only`、`cargo update -p <crate> --precise <version>`（或改 Cargo.toml 后 `cargo check`）。
3. 确认 `pnpm-lock.yaml` 只出现预期变化，`Cargo.lock` 没有意外升级其他 crate。
4. 跑 `pnpm check:deps`（等价于 frozen install、i18n/docs、build、fmt/clippy/test），或手动跑 `pnpm check:docs`、`pnpm check:i18n`、`pnpm build`、`cargo test --locked --manifest-path src-tauri/Cargo.toml`。
5. 更新本文对应表格与「升级判断」。
6. 提交时把依赖、锁文件、文档放在同一个 commit，方便回滚。

升级 GitHub Action 时：

1. 查 release 的 tag 与 commit SHA，不要用分支。
2. 同时改 `uses:` 的 SHA 和本文表格。
3. 触发一次 `publish=false` 的构建验证，再发正式版。
