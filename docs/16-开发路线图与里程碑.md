# 16 · 开发路线图与里程碑

> 前置阅读：`03-架构对比与设计取舍`、`14-桌面端技术选型与工程结构`。
> 本文给出"从空目录到可用产品"的推进顺序，每一阶段都有明确的验收标准。原则：**先打通一条竖线，再横向扩平台**。

## 1. 总体策略

```text
M0 骨架 → M1 单平台竖线（B站） → M2 录制可靠性 → M3 后处理 → M4 多平台
   → M5 弹幕 → M6 产品化 → M7 分发与更新
```

三条原则：

1. **竖线优先**：先用 B 站打通"添加房间 → 监听 → 录制 → 出文件"，再考虑第二个平台。
2. **可靠性优先于功能**：能连续录 8 小时不出错，比支持 10 个平台更有价值。
3. **每个里程碑都可交付**：M1 结束就应该能自己用起来。

## 2. M0 · 工程骨架（约 3–5 天）

**目标**：能跑起来一个空壳，CI 通过。

| 任务 | 产出 |
| --- | --- |
| 初始化 Tauri 2 + React + TS + Vite | `pnpm tauri dev` 能开窗 |
| 目录分层（commands/domain/platform/recorder/storage） | 空模块 + trait 定义 |
| 日志（tracing）+ 全局错误处理 | 控制台能看到结构化日志 |
| SQLite 接入 + 迁移框架 | `hivecast.db` 自动创建 |
| 配置加载（YAML + 默认值） | 能读 `config.yml` |
| CI：fmt / clippy / test / tsc / lint | 三平台矩阵（可先只 macOS） |

**验收**：应用能启动、能读写配置、能建库、CI 绿。

## 3. M1 · 单平台竖线（B 站，约 1–2 周）

**目标**：手动添加一个 B 站房间，开播时自动录制出可播放的 flv。

| 任务 | 说明 |
| --- | --- |
| matcher + resolve | `live.bilibili.com/<id>` → RoomRef |
| room_info | 标题、主播名、是否在播 |
| stream_candidates | 调 `getRoomPlayInfo`，解析三层结构 |
| 监听循环 | 30s 轮询 + 事件 |
| 录制：ffmpeg sidecar | 起进程、解析 stderr、优雅停止 |
| 文件命名 | 默认模板 + 过滤 |
| 房间列表 UI | 添加/删除/开始/停止 + 状态 |
| 录制状态推送 | 2s 一次进度事件 |

**验收**：

- 添加房间后 1 分钟内能识别开播并开始录制；
- 录 30 分钟，文件可播放、可 seek、音画同步；
- 手动停止后文件完整（ffprobe 能读出时长）；
- 主播下播后自动停止并更新状态。

> 此时**不要**做：多清晰度选择、弹幕、后处理、云上传。先把主链路跑通。

## 4. M2 · 录制可靠性（约 1–2 周）

**目标**：连续 8 小时录制不中断、不产生坏文件。

| 任务 | 说明 |
| --- | --- |
| 秒退检测 + 指数退避 | 见 08 文档 §4 |
| 看门狗（无数据超时） | 见 08 文档 §9 |
| 断线重连 | 网络抖动后自动恢复 |
| 分段（时长/大小/改名） | 状态交接（RecordingSession/Segment） |
| 崩溃恢复 | 启动时修复未结束场次 |
| 磁盘空间检查 | 低于阈值告警/停止 |
| 日志按房间分文件 | 便于排查 |

**验收**：

- 拔网线 30s 后恢复，录制能自动接上（可能产生新分段）；
- 强杀应用后重启，未完成场次被标记为 `crash` 并可修复；
- 连续 8 小时无坏文件；
- 磁盘写满时优雅停止并告警，而不是写坏文件。

## 5. M3 · 后处理流水线（约 1 周）

| 任务 | 说明 |
| --- | --- |
| 任务队列 + SQLite 持久化 | 见 10 文档 |
| fix_flv / convert_mp4 | 两个最常用的阶段 |
| extract_cover | 封面 |
| 进度上报 + 任务列表 UI | 能看到卡在哪一步 |
| 重试 / 从指定阶段重试 | |
| 重启恢复（running → pending） | |

**验收**：录制结束后自动转 mp4、生成封面；失败可重试；重启不丢任务。

## 6. M4 · 多平台（每平台约 3–7 天）

顺序建议（按难度递增）：

1. **虎牙**：有防盗链签名，但可纯算法实现，页面结构相对稳定。
2. **斗鱼**：签名 + 设备号，坑多但有 streamlink 参考。
3. **抖音**：先接外部工具服务（btools），不自研签名。
4. **其他**（快手、SOOP、Twitch、YouTube）：按需，模式已成熟。

每个平台必须交付：

- matcher + resolve + room_info + candidates；
- fixture 测试（正常/下播/改版三类快照）；
- 连续录制 10 分钟验证；
- 一份 `docs/xx-平台接入-XXX.md`。

**验收**：新增平台不需要改动录制引擎与 UI（只加适配器 + 注册）。

> 这个里程碑是**架构是否成功**的试金石：如果接第二个平台要改核心代码，说明 04 文档的抽象没做好。

## 7. M5 · 弹幕（约 1 周）

| 任务 | 说明 |
| --- | --- |
| B 站弹幕客户端（WS + proto） | 见 09 文档 |
| ASS 生成 + 时间轴对齐 | 与视频同名 |
| 弹幕配置 UI | 字号/颜色/区域/开关 |
| 实时弹幕面板（可选） | 订阅制，节流 |
| 烧录阶段 | 接进 pipeline |

**验收**：录制的视频旁边有同名 .ass；用播放器打开字幕与画面同步；可选烧录成硬字幕。

## 8. M6 · 产品化（约 2 周）

| 任务 | 说明 |
| --- | --- |
| 配置 UI（三级覆盖） | 全局/平台/房间 |
| 账号与扫码登录 | B 站、斗鱼 |
| 场次历史 + 文件管理 | 列表、筛选、打开目录、删除 |
| 统计面板 | 录制时长、文件大小、成功率 |
| 通知（系统通知/Telegram） | |

| 首次启动向导 | 输出目录、ffmpeg 检测 |

**验收**：非技术用户能在 5 分钟内完成"安装 → 添加房间 → 开始录制"。

**验收**：老版本能一键更新到新版本，且不损坏正在录制的文件。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 平台改版 | 取流失败 | fixture 测试 + 快速降级路线（如 B 站三条路线） |
| 风控封 IP | 全部房间失效 | 严格限流 + 退避 + 可配置代理 |
| ffmpeg 兼容性 | 录制失败 | 固定版本 + 启动自检 |
| 长时间运行内存泄漏 | 应用被杀 | 环形缓冲 + 定期压测（24h） |
| 用户磁盘写满 | 坏文件 | 预留空间检查 + 提前停止 |
| 签名算法变更 | 单平台失效 | 把签名参数做成配置，支持热修 |
| macOS 公证失败 | 无法分发 | 提前配置证书，CI 里验证 |

## 12. 第一个可用的最小版本（MVP）定义

```text
✅ 添加 B 站房间
✅ 自动检测开播并录制
✅ 录制文件可播放
✅ 手动停止
✅ 房间列表显示状态
❌ 不需要：多平台、弹幕、后处理、云上传、登录
```

**建议把 MVP 控制在 3 周内**。能自己用起来之后，后续每个功能都是增量，而不是"还没法用"。

## 13. 每个阶段的"停止信号"

出现以下情况，说明该停下来重构而不是继续加功能：

- 接第二个平台需要改录制引擎 → 抽象错了。
- 加一个配置项要改 5 个文件 → 配置系统没设计好。
- 每次改 UI 都要动 Rust → 前后端边界不清。
- 录制失败要靠看日志才能定位 → 可观测性不足。
- 一个 bug 修了三次还在 → 缺少回归测试。
