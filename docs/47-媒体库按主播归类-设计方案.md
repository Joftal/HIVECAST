# 47 - 媒体库按主播归类（设计方案）

> 状态：v0.1（2026-11-06）· 关联：[46-媒体库重构](46-媒体库重构.md)、[45-媒体库重构方案](45-媒体库重构方案.md)、[41-监控页重做](41-监控页重做.md)
> 一句话：媒体库从「按录像平铺」改成「按主播汇总」——外层是主播大卡（平台 / 主播名 / 录像数 / 总体积 / 最新一条时间），点进去看这个主播的全部录像。

## 0. 结论

| 方案 | 形态 | 评价 |
| --- | --- | --- |
| **A 下钻（推荐）** | 主播墙 → 整页切到「主播页」（头像 + 统计 + 该主播录像网格） | 最贴合「点进去看这个主播的文件」，层级清楚，一屏能放 9–12 个主播 |
| B 抽屉 | 主播墙不动，点卡片右侧 420px 抽屉列出该主播的录像 | 切换快、上下文不丢，但抽屉里只能放列表，九宫格缩略图用不上 |
| C 主从 | 左 264px 主播列表 + 右侧该主播的录像区 | 主播多时好扫，但主播卡的大图展示不了，与「大卡图」的诉求冲突 |

推荐 **A 作为主形态**，把 B 的抽屉留给「回放」这一件事（点录像 → 右侧抽屉播放，沿用现在媒体库的播放抽屉），C 不做。

## 1. 为什么按主播归类

现在的媒体库是「录像平铺」：一个主播录了 128 场，就要在墙上占 128 张卡，同一个主播反复出现，找「某个主播的某一场」只能靠搜索。按主播汇总后：

- 首屏信息量从「N 条录像」降到「M 个主播」（M 通常是个位数到几十），扫一眼就知道谁录得多。
- 体积/条数/最新时间是主播维度的健康度指标：谁快把盘吃满了、谁最近还在录，一眼可见。
- 进入某个主播后再做「按时间/大小排序、按天筛选」，检索路径从两步搜索变成一次点击。

## 2. 四条要求的落点

| 你的要求 | 落点 |
| --- | --- |

| 主播卡片信息重做：平台、主播名、录像数、大小、最新时间 | 卡片下半条：`128 个录像 · 86.4 GB` 左对齐，`最新 11-06 14:12` 右对齐；平台徽标在封面左上角，主播名 + 房间名叠在封面左下角 |

## 3. 聚合口径（这一节是实现的真正难点）

### 3.1 主播怎么算一个人

`record_session` 只连到 `room`，而 `room` 是「平台 + 房间号」。同一个人在 B 站可能有主号房间和赛事房间，同一场赛事在虎牙/斗鱼各有一个房间，甚至改过昵称。三种可选口径：

| 口径 | 分组键 | 优点 | 代价 |
| --- | --- | --- | --- |
| **按房间（推荐 v1）** | `room.id` | 实现最简单，头像/封面/房间名现成；改名后仍是同一个主播卡 | 同一个人两个房间会显示成两张卡 |
| 按主播名 | `platform + host_name`（去空格、大小写归一） | 跨房间合并 | 改名就裂开；不同主播重名会合并错 |
| 手动合并 | 用户在多选后「合并为主播」 | 最准 | 需要新表与 UI，v1 不做 |

v1 用「按房间」，卡片标题显示 `host_name`、副标题显示房间名（`room.title`），这样既满足「按主播归类」的观感，又不会因为改名/重名出错。文档里把它叫「主播卡」，但底层键是 `room_id`。后续要真按人合并时，加一张 `host` 映射表即可，不影响现有查询。

### 3.2 聚合查询

```sql
SELECT r.id AS room_id,
       r.platform, r.host_name, r.title, r.avatar_url, r.cover_url,
       COUNT(s.id)              AS count,
       COALESCE(SUM(s.size), 0) AS bytes,
       MAX(s.started_at)        AS latest
FROM room r
JOIN record_session s ON s.room_id = r.id
WHERE s.status = 'finished'
GROUP BY r.id
ORDER BY latest DESC;
```

- 只统计 `finished` 的会话（录制中的不算「媒体库」）。
- `bytes` 用 `size` 之和，不读磁盘（与列表页口径一致）。
- 主播没有录像的房间不出现在墙上（INNER JOIN 天然过滤）。
- 搜索：`host_name LIKE ?` 或 `title LIKE ?`；平台筛选同现在；时间范围筛选落在 `s.started_at` 上（筛选后 count/bytes 也跟着变，语义是「这个时间范围内有多少」）。

### 3.3 主播页的文件查询

复用现有 `media_list`，只加一个 `room_id` 过滤条件，其余（搜索、时间范围、仅看弹幕、排序、分页）全部不变。这样主播页里的一整套筛选逻辑与现在的媒体库完全一致，不需要第二套代码。

## 4. 三套设计稿的取舍

| 维度 | A 下钻 | B 抽屉 | C 主从 |
| --- | --- | --- | --- |
| 主播大卡图 | ✅ 16:10 满宽 | ✅ 满宽 | ❌ 只有 28px 小头像 |
| 一屏主播数 | 9（3 列） | 9 | 20+ |
| 进入某个主播 | 一次点击 + 整页切换 | 一次点击 + 抽屉 | 一次点击 + 右侧替换 |
| 主播的录像展示 | 九宫格大卡 | 82×46 小行 | 九宫格大卡 |
| 返回成本 | 点「← 全部主播」或 Esc | 关抽屉 | 无（一直在同一屏） |
| 播放 | 抽屉（沿用） | 抽屉里再点 | 抽屉（沿用） |
| 缺点 | 有「页面跳转」的心智负担 | 大图九宫格用不上，信息密度低 | 主播卡展示不了大图 |

A 的「跳转」其实很轻：主播墙的滚动位置与筛选状态保留在组件里，返回即原位（不做路由，纯状态切换）。

## 5. 交互细节

| 场景 | 行为 |
| --- | --- |
| 点主播卡 | 进入主播页；卡片 hover 抬升 1px + 阴影，光标 pointer |
| 主播页返回 | 「← 全部主播」按钮、`Esc`、鼠标侧键（能拿到 `button === 3` 时）都返回 |
| 主播页播放 | 点录像卡 → 右侧播放抽屉（现有 `mediaPlay` + 滑窗转封装），抽屉关闭回主播页 |
| 主播页批量 | 全选/多选 → 底部批量条（转 MP4 / 导出弹幕 / 合并 / 显示 / 删除），范围仅限当前主播 |
| 主播卡上的批量 | v1 不做（避免误删整位主播的录像）；删除走主播页里的多选 |
| 搜索 | 主播墙搜主播名/房间名；主播页内搜该主播的录像标题 |
| 排序 | 主播墙：按最新录制 / 按体积 / 按条数；主播页：沿用现有的时间/时长/大小 |
| 空态 | 一个主播都没有 → 「还没有录像」；主播页为空（筛选后）→ 「没有匹配的录像」 |
| 主播卡角标 | 封面左上平台徽标；右下角可选「N 场」角标（与卡片下半条的条数重复，v1 不加） |

## 6. 后端缺口

| 项 | 变化 |
| --- | --- |
| `MediaHost`（ipc-types） | `room_id, platform, host_name, room_title, avatar_url, cover_url, count, bytes, latest_at` |
| `MediaHostPage` | `items: Vec<MediaHost>, total: i64` |
| `media_hosts(filter)` | 新增命令：搜索 + 平台 + 时间范围 + 排序 + 分页 |
| `media_list` | 增加可选 `room_id` 参数，其余不变 |
| `media_platform_counts` | 主播墙的计数要按「主播数」而不是「录像数」统计，另加一个 `host_platform_counts`（或给现有函数加 `distinct` 开关） |
| 缩略图 | 不变，仍按 session 生成；主播卡的封面用 `room.cover_url`，不生成 |

## 8. 待裁决

1. 主播身份用「按房间」（推荐）还是「按主播名」合并？
2. 平台徽标位置：保持左上（推荐，只去圆点）还是挪到右上？
3. 主播墙要不要保留「列表视图」（一行一个主播，带小头像与统计）？推荐保留，主播多时更好扫。
4. 主播卡上要不要直接给「删除这个主播的全部录像」入口？推荐不要，走主播页多选。
5. 主播页里还要不要「合并录像」按钮？现在合并要求同一房间，主播页正好满足，可以保留。
