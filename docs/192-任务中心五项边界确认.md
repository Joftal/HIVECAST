- 日期：2026-11-23
- 范围：任务中心 Run 状态机、历史分页、事件时间线、跨 Run 检索/导出、收尾重试锁
- 基线：`dc757c8`（任务中心复审：陈旧收尾、重试入口与历史分页）
- 结论：上一轮报告列出的五项未覆盖边界，本轮逐项做了真实构造或故障注入；同时修掉三个会让用户误判的问题——排队态被收尾任务吞掉、跨实例重试收尾没有互斥、锁冲突会留下假的失败任务。

## 1. 排队态：从「不可见」到真实可见

### 1.1 问题

后处理槽位只有 1 个（`src-tauri/src/post.rs` 的 `auto_slots()`）。第一段后处理运行时，第二段会以 `queued` 进入内存队列；但在页面上它一直显示成「收尾中」或「运行中」，`排队` 统计始终为 0。

根因有两层：

1. 收尾期间 `record_session.status` 仍然是 `recording`，`session_active` 一直为真；
2. 收尾父任务在整个后处理期间保持 `running`，`processing_active` 也为真。

`finish_run` 原先把 `finalizing` 放在最前面，于是 `queued` 永远轮不到。

### 1.2 修复

`src-tauri/src/task_center.rs` 的 `finish_run`：

- `has_finalize_attempt = !draft.finalize_tasks.is_empty()`；
- `session_active` 只在「没有收尾任务」时才看 `status == "recording"`；
- `processing_active` 排除 `kind == "finalize"` 的父任务，只看真正的 post/remux 片段任务；
- 状态顺序改为 `recording > running > queued > finalizing > failed/partial > interrupted > cancelled > done`；
- `current_processing_stage` 同样把 `queued` 放到 `finalizing` 之前。

这样「收尾任务还挂着，但 post 已经在排队」时，Run 会先报 `queued`，不会继续冒充收尾/运行。

### 1.3 真机证据

- 两个直播间同时自动录制，分别是 `tf-room-c`（哔哩哔哩英雄联盟赛事）与 `tf-room-e`（斗鱼 9263298 若若跑的贼快）。
- 自定义后处理使用 `-re` 实时重封装，确保一次只跑得动一段。
- 同时停止后，DB 中两条 post 任务分别为：
  - `auto:49434...:0 | running | converting | 5%`
  - `auto:cc396...:0 | queued | queued | 0%`
- 任务页顶部显示 `运行中 1 / 排队 1 / 录制中 0`；
- 滚动到「排队中」分组，QueuedRow 显示：
  - 主播：哔哩哔哩英雄联盟赛事
  - 说明：`后处理 · 等待后处理槽位 · 已等 07:06`
  - 平台：哔哩哔哩
- 截图：`/tmp/tf-queue-final1.png`（顶部计数）、`/tmp/tf-queue-final4.png`（QueuedRow）。

这证明「排队」不再依赖夹具，也不再是代码审查推断。

## 2. 加载更多历史：真实失败会回滚

### 2.1 注入方法

在一个测试库里插入 280 条历史场次，把第 250 条（`fail-page-250`）的 `file_size` 写成文本 `bad`。`map_session` 读取该列时返回 `InvalidColumnType`，后端 `taskCenter(limit)` 直接失败。

选择第 250 条而不是第 150 条，是因为 `load_sessions` 每次固定读 200 行：`limit=100` 只解析前 200 行，能正常返回；`limit=200` 会读到第二页并撞上坏行。

### 2.2 结果

- 首屏正常：`最近完成 100`，底部有「加载更多历史」。
- 点击「加载更多历史」后：
  - toast：`操作失败 / database error: Invalid column type Text at index: 7, name: file_size`；
  - 表仍显示 `最近完成 100`，没有变成 0，也没有跳到 200；
  - 「加载更多历史」按钮仍在；
  - 2 秒轮询继续用 100 取数，页面恢复稳定。
- 截图：`/tmp/tf-loadmore-before.png`、`/tmp/tf-loadmore-fail2.png`。

对应代码在 `src/features/tasks/TasksPage.tsx` 的 `loadMore`：请求失败且不是 stale 时，把 `historyLimitRef` 和 `historyLimit` 一起退回上一页，避免下一次点击从 200 直接跳到 300、永久跳过失败的那一页。

本轮注入的是数据库列类型损坏，不是网络超时；但走的是同一条 `load() -> catch -> 回滚` 分支。

## 3. 有效清单收尾重试与跨进程锁

### 3.1 锁从进程内扩到跨进程

`src-tauri/src/recorder.rs`：

- `FinalizeRetryLease` 增加 `_lock: std::fs::File`；
- `acquire_finalize_retry` 在内存 `HashSet` 之外，再对 `{manifest}.lock` 调用 `try_lock_exclusive()`；
- 文件锁失败时撤回刚插入的内存标记，返回「这一场正在别的窗口重试收尾，请稍候」；
- 文件锁由内核在进程退出时释放，锁文件本身留在清单旁边。

### 3.2 锁冲突不再留下假任务

原先 `finalize_retry` 先 `jobs.begin_for` 创建任务，再在 `retry_finalize` 里拿锁；锁冲突时任务已经落库，于是页面上多出一条 `finalize failed`，把本来只是「别的窗口在跑」的操作变成一次失败。

现在：

- `src-tauri/src/commands.rs:1509` 先校验 `split_manifest` 存在，再 `acquire_finalize_retry(&manifest)?`；
- 拿到 lease 之后才 `jobs.begin_for`；
- 真正的重试主体是 `retry_finalize_with_lease(db, session_id, lease)`，不再在函数内部重新抢锁。

### 3.3 真机证据

测试场次 `tf-lock2`，清单 `/tmp/tf-lock2-manifest.json`，源文件 `/tmp/tf-lock2-source.flv`（31,287 B）。清单必须包含 `source` 字段，否则解析会报 `missing field source`，被判定为清单损坏。

- 用 Python 对 `/tmp/tf-lock2-manifest.json.lock` 持 `fcntl.flock(LOCK_EX)` 20 秒；
- 点「重试收尾」：toast「操作失败 / 这一场正在别的窗口重试收尾，请稍候」；
- `task_history` 仍然只有原来的 `finalize:tf-lock2 failed`，没有新增 `job:4` 假任务；详情里的失败原因仍是原来的「合并失败（注入）」，没有被锁错误覆盖；
- 释放锁后再点：DB 变为 `tf-lock2 | finished | post_state=done | split_manifest 空 | file_size=31287`，`task_history` 新增 `job:3 | done | 收尾完成`，清单文件被删除。

这同时覆盖了「有效清单重试成功」与「两个实例同时重试时只允许一个」。

## 6. 仍有的边界

1. **排队态依赖真实后处理槽位**：队列只在内存 `Jobs` 里，应用重启后排队任务会被中断，不会恢复成排队；这是现有任务模型的约束。
2. **跨进程锁只按清单文件**：两个实例指向不同媒体目录时互不影响；如果清单被手工删除，文件锁也随之失效。
3. **导出 5 万未压测**：代码有硬上限与日志，但没有构造 5 万条真实事件验证耗时和内存。
4. **历史 1000 仍是硬上限**：超过 1000 场只能看到最近 1000 场；「全部」数字包含异常，不等于数据库总场次。
5. **检索只展示 200 条**：要看更早结果只能缩小关键词或平台/失败筛选；没有分页。
