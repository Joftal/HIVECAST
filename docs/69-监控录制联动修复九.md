# 69 监控录制联动修复九（I 系列）

> 状态：v1.0（2026-11-07，第十二轮；修复 [68 复审七](68-监控与录制关系复审七.md) 的 I1–I4）｜对象：segment.rs、db.rs、retention.rs、state.rs、recorder.rs、ipc.ts、MediaPage.tsx｜上游：[68](68-监控与录制关系复审七.md)、[54 v4.2](54-监控与录制关系审查.md)

一句话结论：**I1–I4 四条全部改完，并逐条通过真机复验。** 崩溃收尾现在按分片最后写入时间结算（实测开始后 300 秒写入的分片，`duration_ms=300000`，不再是 5 小时）；恢复合并挪到后台（假 ffmpeg 拖 15 秒，初始化与监控照常跑）；合并失败不再留 `.concat.txt`；保留策略按「一条录像的全部产物」删除（`freed=1,081,367`，目录清空）。没有改检测间隔、退避与录制主链路的关系——这条结论第十二次不变。

### 1.1 I1：收尾必须发生在合并之前

顺序写死在 `AppState::init`：`reap_orphans`（杀掉遗留 ffmpeg）→ `close_orphan_sessions`（按 mtime 收尾）→ 保留策略 → 后台 `recover_parts`。收尾若放在合并之后，分片已经被删，就再也取不到最后写入时间。

`last_data_at` 的取值顺序：先看 `file_path` 本身（成品已存在时以它为准），再看同名 `.jsonl`，最后遍历 `collect_parts` 得到的分片；三者都取 mtime 的**最大值**。这里不按「最后一个分片」取，是因为崩溃时 ffmpeg 可能先建了 next 分片再写到一半，文件名更大不代表时间更晚。

`orphan_ended_at` 只做一件事：把结果夹在 `[started_at, now]` 内。时钟回拨、分片 mtime 晚于当前时刻（外接盘常见的时区/挂载误差）都不会产生负时长或未来时间。没有分片、`file_path` 为空时退回 `now`，行为与旧版一致。

代价：`file_path` 指向的 mp4 在合并前可能是 0 字节（失败会话），此时以分片 mtime 为准；恢复流程随后会把 `file_path` 改写成兜底产物的路径，而时长已经定好，不再变。

### 1.2 I2：合并挪到后台，用事件补刷新

旧路径 `recover_parts(...).await` 之后才 `app.manage(state)`、建窗口，一条 10 GB 的录像要等几分钟。现在 `init` 里只 `spawn`，把 `Db` 与 `AppHandle` 克隆进任务：

```rust
tauri::async_runtime::spawn(async move {
    let (recovered, recovered_bytes) = crate::recorder::recover_parts(&recovery_db).await;
    if recovered > 0 {
        let _ = recovery_app.emit(crate::recorder::EVENT_MEDIA_CHANGED, ());
    }
});
```

前端 `MediaPage` 在挂载时注册监听：收到事件先 `loadHosts(0)`，有选中主播再 `loadFiles(0)`。事件只在 `recovered>0` 时发——没有残留分片就不打扰界面。

取舍：窗口先出来时，媒体库里看到的还是收尾后的 `aborted` 记录，恢复中的文件可能还没进列表；合并完成后由事件补一次刷新。如果合并失败，媒体库保持 `aborted` 记录（`file_size` 可能是 0），与旧行为一致。

### 1.3 I3：清单只活到 ffmpeg 结束

`merge` 的清单（`*.concat.txt`）是给 `ffmpeg -f concat` 的输入，失败时留着没有任何用处，媒体库也看不到。现在三条 `return Err` 之前都 `remove_file(&list)`，成功路径原本就删；调用方（`recover_parts`）失败后走字节拼接兜底，兜底产物是 `.ts`，不会再碰清单。

### 1.4 I4：一条录像的产物是一个集合

`artifacts(path)` 返回：`path`、`path.with_extension("jsonl")`、`path.with_extension("ass")`、`path.with_extension("concat.txt")`，再加上 `collect_parts(path)` 的分片。删除时逐个 `remove_file` 并累加 `metadata.len()`，全部处理完才调 `delete_session`——中途有文件删不掉（权限、占用），库行保留到下次再试，不会出现「库没了、文件还在」。

容量统计仍以数据库 `file_size` 为准（`select()` 的既有口径），这里只改「删什么、算多少」。两者本期没有合并，`file_size` 为 0 的失败会话在按容量淘汰时仍按 0 计——这是已知的、独立的小口径问题，不影响按天淘汰。

## 3. 真机验收

环境：macOS 27.0.1 arm64、ffmpeg 9.0.2、`target/debug/hivecast`（含本轮全部改动，13:20 构建）、真实 DB；媒体目录用 `HIVECAST_MEDIA_DIR` 指到 `/tmp/hc-iN/Recording`，避免污染真实媒体库。

| 编号 | 场景 | 结果 |
| --- | --- | --- |
| T1 | 3 天前的 finished 会话：mp4 1,048,576 + `.jsonl` 2 + `.ass` 13 + `.concat.txt` 8 + `.part0000.ts` 32,768；`media.retention_days=1` | INFO「媒体库保留策略：已清理旧录像 deleted=1 freed=1081367」；目录里一个文件不剩、会话行删除 |

| T3 | recording 会话 `started_at=1794011371`，分片 mtime 设为 `1794011671`（开始后 300 秒），重启 | `ended_at=1794011671`、`duration_ms=300000`、`status=aborted/reason=app_exit` |
| T4 | PATH 前置假 ffmpeg：合并时 `sleep 15` 再写 11 字节；同时放一个真实在播房间（`auto_record=0`，间隔 2 秒） | 05:30:25.07 启动；4 秒时房间 `last_checked_at` 已更新（监控在合并期间照常跑）；05:30:40.13（+15.06 秒）INFO「恢复上次崩溃遗留的录像 recovered=1 recovered_bytes=11」 |

### 3.1 T3 的第一次失败是测试手法问题

第一次用 `touch -d "@1794011389"` 设 mtime，结果 `duration_ms` 仍是 18,000,000（`ended_at=now`），看起来像没生效。复查发现 macOS 的 `touch -d` 不会把 `@epoch` 当作 Unix 时间解析，文件的 mtime 实际没变；改用 `python3 os.utime` 后一次通过（`duration_ms=300000`）。

这条记下来给后续验收用：**在 macOS 上设 mtime 用 `os.utime` 或 `touch -t`，不要用 GNU 风格的 `touch -d @...`**；设完先 `stat` 复核再启动应用。

## 4. 行为变化与取舍

| 变化 | 说明 |
| --- | --- |
| 崩溃恢复的时长以分片最后写入为准 | 同一条会话的 `ended_at` 可能早于应用重启时刻；历史里不再出现「重启多久就录了多久」的虚高。用户感知是「时长终于对了」 |
| 主窗口不再等合并 | 打开应用即可操作；恢复完成由 `media://changed` 补刷新。代价是恢复中的文件短暂不在列表里 |
| 合并失败不留清单 | 媒体目录更干净；失败仍按原逻辑走 `.ts` 兜底，`recovered` 记账不变 |
| 保留策略删得更彻底 | `.ass`、残留分片、清单都计入 `freed`；删除前逐个删文件，失败则保留库行等下次 |
| 启动顺序固定 | `close_orphan_sessions` 必须在 `recover_parts` 之前；顺序写反会让 mtime 依据消失，I1 修复失效（代码注释已标注） |

## 5. 没覆盖到的

- 真实 10 GB 级录像的恢复耗时（T4 用假 ffmpeg 把合并拖到 15 秒，验证的是「不阻塞」，不是真实吞吐）；
- Windows 平台（`last_data_at` 只用标准库 mtime，但未在 Windows 实测）；
- 恢复合并到一半再崩溃（窗口很窄，未造）；
- `.ass` 由外部工具改名/移走后的保留策略行为（按同名约定，不追踪重命名）；
- 删除时文件被占用（macOS 上未造出稳定复现；代码路径是「删不掉就保留库行」）。

## 6. 结论

I1–I4 都是「收尾之后」的数据/目录整洁问题，不涉及「录制是否继续」。四条改动都局限在启动恢复、合并失败清理、保留策略删除三处，没有碰 monitor 的排期、recorder 的停录判定，也没有新增跨模块调用。**建议按本版收口**；如果后续要动容量口径（`file_size` 与目录实际大小不一致），单独开一条，不要和保留策略的删除逻辑混在一起。
