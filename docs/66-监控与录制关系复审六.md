# 66 监控与录制关系复审六（第九轮）

> 状态：v1.1（2026-11-07，H1–H8 已在 [67](67-监控录制联动修复八.md) 修复并验收）｜审查对象：65 之后的代码（monitor.rs、recorder.rs、broker.rs、cmd 层 commands.rs、state.rs、settings.rs、disk.rs、lifecycle.rs、segment.rs、前端 MonitorPage.tsx）｜审查视角：**一个普通用户会怎么用**——插入外接盘、拔掉外接盘、把间隔从 5 分钟调到 5 秒、房间失效、直接关窗退出；只关心这些操作会不会让正在录的东西出错、让界面说谎。
>
> 方法：4 组真机测试（2 路真实 bilibili 录制、3 GiB 稀疏卷上拔盘、把媒体目录指到不存在的路径后重启、无效房间 + 改间隔看退避），另有 4 条纯代码核验（spawn 失败、假死收尾、退出窗口、斗鱼开播时间）。

一句话结论：**「检测间隔 / 退避 / 暂停碰不到已经开录的会话」这一条第九次仍然成立（本轮又用量化数据复验）。** 但这一轮从「用户实际会做的事」里翻出 8 条新问题，其中两条会直接把用户的数据写到错误的位置、或让历史记录说谎：

- **H2（P2）**：外接盘没插就启动，媒体目录会**静默回落**到应用安装目录，界面和数据库仍然显示外接盘路径；这个状态下用户在设置页改任何一项都会保存失败。
- **H4（P2）**：掉盘 + ffmpeg 卡住（USB 拔盘时很常见）时，1 秒后已经正确记下 `disk_lost`，但 60 秒后的假死看门狗又把它**改写成 `failed/stalled`**，历史显示「录制失败、0 字节」，而 16.5 MB 分片其实还在盘上。

环境：macOS 27.0.1 arm64、ffmpeg 9.0.2、`target/debug/hivecast`（含 65 的全部改动）、真实库 `~/Library/Application Support/com.hivecast.desktop/hivecast.db`。测试结束已清库（room=0、record_session=0、设置 10 项）、删测试卷与录制目录、无残留进程。

## 2. 四个问题的判定（第九轮版）

| 你的说法 | 结论 | 本轮依据 |
| --- | --- | --- |
| 已在录的直播间不受检测间隔影响 | **成立** | T1：间隔改 3600 后 88 秒内 `last_checked_at` 冻结，同期分片 7.1 MB→17.8 MB、13.4 MB→21.0 MB |
| 不受失败回退机制影响 | **成立** | 退避只写 `Schedule.next_at`，与 recorder 无交集（T4 里坏房间退避时，两路录制照常写入） |
| 监控只是更新主播状态、房间状态 | **不成立** | 还会自动开录、连续两次判离线后停录、按卷发磁盘红线停录；退出/删房间/暂停也会改变录制 |
| 只有直播源真没数据才会影响录制 | **不成立** | H4：盘拔了、源好着，最后记成「源故障」；H2：盘没插，录像被静默写到安装目录 |

## 3. 真机测试

### 3.1 T1 间隔 30 → 3600：已开录不受影响，但在线人数会冻住

两路真实直播（bilibili 6「预告 T1 vs KC」、545068「德云色」），`monitor.interval_sec=30`：

| 时刻（UTC） | 事件 |
| --- | --- |
| 01:53:36.574 | 主播乙「开始录制」，`…/主播乙/…2026-11-07_09-53-36.mp4` |
| 01:53:59.720 | 主播甲「开始录制」 |
| 01:55:03 | 把间隔改成 3600（epoch 1794016503） |
| 01:55:05 / 01:55:25 | 两路最后一次检测（改动前已排上的那一拍） |
| 01:56:33 | 检查：`last_checked_at` 仍停在 1794016505 / 1794016525；分片 13,369,344→20,971,520、7,077,888→17,825,792；日志里「取流请求完成」总数为 2（没有新请求） |
| 02:06:32 | `pkill -TERM`；02:06:33 两路 `aborted/app_exit`，51,027,950 / 133,079,214 字节，时长 754 秒 / 777 秒 |

**结论**：间隔只决定「多久发现下播」，与已开录会话无关（与第三～八轮一致）。

**顺带发现的 H1**：同一时间窗里主播甲的 `online` 从 148,576,505 变成 146,790,521，而 `is_live`、标题、封面都没变 —— 按 [monitor.rs:509-525](../src-tauri/src/monitor.rs#L509) 的判定，这属于「非结构变化」，只走 `touch_room_throttled` 写库、**不发 `rooms://changed`**。前端 [MonitorPage.tsx:305-333](../src/features/monitor/MonitorPage.tsx#L305) 只在挂载和收到事件时重新拉列表（唯一的定时器是给「录制时长」用的 1 秒 tick，见 :338），所以**监控页底部的在线人数会一直显示旧值**，直到标题/封面/开播时间之类发生变化。

### 3.2 T2 掉盘 + ffmpeg 卡死：`disk_lost` 被改写成 `stalled`

3 GiB 稀疏卷 `/Volumes/HIVECASTH4`，`HIVECAST_MEDIA_DIR` 指到卷内，1 路真实直播，间隔 5 秒：

| 时刻（UTC） | 事件 |
| --- | --- |
| 02:07:53.947 | 开始录制（卷上 `part0000.ts` 长到 12.3 MB） |
| 02:08:45 | `kill -STOP` ffmpeg（模拟 USB 盘被拔时进程卡在不可中断 IO）+ `hdiutil detach -force` |
| 02:08:49.495 | WARN「录制目录不可用，停止录制」→ INFO `reason="disk_lost"`（G3 的新路径，1 秒内生效，符合预期） |
| 02:09:44.288 | WARN「录制长时间没有新数据，重启 ffmpeg」（SIGSTOP 满 60 秒） |
| 02:09:47.506 | INFO「续录等待期间已被停录，放弃续录」 |
| 02:09:47.509 | INFO 录制结束 `status="failed" reason="stalled" file_size=0` |

数据库里是 `failed | stalled | 0`；重新挂载卷后能看到 `part0000.ts` **16,515,072 字节**、`.jsonl` 2,732 字节、`.mp4` 0 字节 —— 数据都在，记录却说 0 字节失败。

影响链路：`stalled` 在 [recorder.rs:1416](../src-tauri/src/recorder.rs#L1416) 映射成 `failed` + `error="直播流长时间没有数据"`，于是 ①历史页显示「录制失败」而不是「磁盘不可用」；②[recorder.rs:1516-1519](../src-tauri/src/recorder.rs#L1516) 的 `disk_lost` 通知不会发，用户收到的是通用失败通知；③这次收尾还被计入连续失败。根因是假死分支无条件用 `Some("stalled")` 收尾（[recorder.rs:1064-1070](../src-tauri/src/recorder.rs#L1064)），不检查已经置好的 `stop_reason`；而且它在收尾前还会先 `respawn` 一次（3 秒等待 + 一次取流请求），明知要停也要多打一次平台接口。

### 3.3 T3 外接盘没插就启动：静默改到安装目录

把 `app_setting.media.root` 设成 `/Volumes/NOPE/Recording`（该卷不存在，`/Volumes` 非 root 不可写，`create_dir_all` 必然失败），重启应用：

| 观察点 | 实际结果 |
| --- | --- |
| `/Volumes/NOPE` 是否被创建 | 没有 |
| 录像落在哪 | `/Library/dshproject/HIVECAST/src-tauri/target/debug/Recording/哔哩哔哩/主播乙/…mp4`（默认目录） |
| 数据库 `media.root` | 仍是 `/Volumes/NOPE/Recording`（**没被改写**） |
| 日志 | **一行都没有**，没有 WARN、没有提示 |
| 收尾 | `pkill -TERM` 后 `aborted/app_exit` 67,494,496 字节、229 秒；`ffprobe` 读得到 `duration=234.83`，`.ass` 也导出了 |

对应 [state.rs:88-95](../src-tauri/src/state.rs#L88)：回落只改内存里的 `settings`，不写库、不告警。于是设置页显示外接盘路径、文件却在安装目录 —— 用户以为插着盘在录，实际吃掉的是系统盘。附带后果：这种状态下任何一次「保存设置」都会走 [settings.rs:190-200](../src-tauri/src/settings.rs#L190) 的校验（`create_dir_all` 失败直接报错），用户会看到「保存失败」，但提示指向的是媒体目录，而不是「你的盘没插」。

### 3.4 T4 坏房间退避：调小间隔不会让它早点重试

插入一个无效房间（bilibili `999999999`），当时间隔是 3600：

| 时刻（UTC） | 事件 |
| --- | --- |
| 01:57:41.007 | 唯一一条 WARN「刷新房间失败 hint=响应解析失败…error decoding response body」 |
| 01:58–02:01 | 无任何重试（`last_checked_at` 停在 1794016661） |
| 02:01:58 | 把间隔改回 30 |
| 02:05:13 | 坏房间 `last_checked_at` 仍是 1794016661；同期健康房间在 02:04:53 / 02:05:03 各检测了一次 |

原因有两层：①`backoff_wait` 的结果永远不短于基准间隔（[monitor.rs:247-254](../src-tauri/src/monitor.rs#L247)，`min(base*2^n, cap.max(base))`），间隔 3600 时一次失败就排到 3600 秒后；②G7 的「间隔调小重排」只对非退避条目生效（`needs_reschedule` 里 `!entry.backoff`），退避中的房间不会被提前。用户的直觉是「我把间隔调成 5 秒，坏房间应该马上重试」，实际要等满一小时。缓解手段是监控页的「刷新」按钮（`room_refresh` 会 `invalidate` 并立即取一次），但用户未必知道。

### H2 细节（启动期掉盘）

- 相关代码：[state.rs:88-95](../src-tauri/src/state.rs#L88)（回落后只改内存）、[settings.rs:190-200](../src-tauri/src/settings.rs#L190)（保存时重新校验并失败）。
- 与 G3 的区别：G3 管的是**运行中**掉盘（已修好，T2 里 1 秒内停录）；H2 是**启动时**盘就不在。
- 修复方向：回落时把新路径写回库并推一次事件，同时发一条「媒体目录不可用，已暂时改用 X」的通知；或干脆不回落，进入「等待目录」状态并在顶栏常驻提示。两种都比「悄悄换目录」好。

### H4 细节（假死覆盖停止原因）

- 相关代码：[recorder.rs:1050-1072](../src-tauri/src/recorder.rs#L1050)（假死分支）、[recorder.rs:1410-1426](../src-tauri/src/recorder.rs#L1410)（状态映射）。
- 为什么真实：USB/网络盘被拔掉的瞬间，进程常常卡在不可中断的写系统调用里，十几秒到几分钟都不返回 —— 正好落进 60 秒假死窗口；机器睡眠醒来也有类似效果。
- 修复方向：假死分支先读 `stop_reason`，有值就按它收尾（`disk_lost` / `disk_full` / `stopped`），并且不再 `respawn`。

### H7 细节（没有开播时间的平台）

- [douyu.rs:236](../src-tauri/src/platform/douyu.rs#L236) 硬编码 `started_at: None`；`douyin` 在缺 `start_time` 时回落到 `create_time`（房间创建时间，同样一场不变）。
- [recorder.rs:386-399](../src-tauri/src/recorder.rs#L386) 的提前解除条件要求 `confirmed && live_started.is_some()`，因此这两类房间只能等满 600 秒；[recorder.rs:357-371](../src-tauri/src/recorder.rs#L357) 的手动停录抑制同理（只能靠「成功看到一次离线」复位）。
- 影响：主播下播后 1 分钟又开播（换游戏、断流重开很常见），斗鱼房间会白等约 9 分钟才开始录。
- 修复方向：给斗鱼补开播时间；或在「确认下播」时记录当时的分片/在线人数指纹，用指纹变化判定新场次。

## 6. 修复建议顺序

1. **H2**：启动回落必须写库 + 通知，避免「以为在录外接盘、其实在录系统盘」。
2. **H4**：假死收尾尊重既有 `stop_reason`，并跳过无意义的 `respawn`。
3. **H8**：间隔调小时把退避条目的 `next_at` 夹到 `now + base`（保留 `error_count`）。
4. **H1**：在线人数变化也走一次节流事件（或监控页 10 秒轮询）。
5. **H7**：补斗鱼开播时间 / 用指纹判新场次。
6. **H3/H5/H6**：三处清理型修补，可合并成一次提交。
