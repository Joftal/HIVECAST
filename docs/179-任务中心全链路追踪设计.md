# 任务中心全链路追踪设计

> 状态：设计稿，未实施
> 日期：2026-11-20
> 范围：任务页 + 只读聚合接口；P1 不改录制/后处理执行逻辑，P2 才加阶段埋点
> 目标：把「任务列表」升级为「运行链路控制台」

## 1. 结论

任务页的第一对象不应该是 Task，而应该是 **Run（一次录制链路）**。

一条 Run 从监控发现开播开始，经历：

```
监控 → 开录 → 录制 → 收尾（合并分片/切片段/弹幕落盘）→ 后处理（每片段转封装）→ 入库（缩略图/ASS/文件登记）
```

一个 Run 下可以有 0..N 个 Task：

- 录制本身是一个长任务；
- 收尾是一个阶段，不是一条独立任务；
- 每个录制片段各有一个后处理任务；
- 手动转封装、合并是挂在 Run 上的操作任务；
- 缩略图、弹幕导出、入库目前是隐藏步骤，后续应显式化。

页面按「平台态势 → 运行中的 Run → 排队 → 异常 → 最近完成」组织。Task 只在 Run 内展开，不再平铺。

## 2. 现在为什么看不清

### 2.1 所有任务平铺，缺少父子关系

`src/features/tasks/TasksPage.tsx` 把 `TaskBoard.running` 和 `history` 当成两组同质记录。实际后端返回的是：

- 录制任务（`record:{session_id}`）；
- 开录中任务（`record:starting:{room_id}`）；
- 收尾父任务（`jobs.begin("post", ...)`）；
- 每个片段的后处理任务（`auto:{session_id}:{index}`）；
- 手动转封装、合并任务。

同一个直播间的一场录制会在页面上出现多条互不相干的记录，用户无法知道「这三条其实是一条链」。

### 2.2 排队任务被显示成「运行中」

`src-tauri/src/post.rs:210` 的 `run` 在拿到信号量之前就 `ctx.emit(0, "queued", "queued", None)`，所以 `TaskRecord.state` 已经是 `queued`。

但 `TasksPage.tsx` 的运行中卡片把状态写死成 `STATE_STYLE.running` / `STATE_KEYS.running`，历史行遇到未知状态又回退成「已取消」。结果是：

- 真正在排队的任务显示「运行中」；
- 进度条 0%，看起来像卡住；
- 用户不知道它在等什么。

### 2.3 录制任务画 0% 进度条

`commands.rs:3036 task_board` 给录制任务写死 `percent: 0`。录制时长没有上限时，百分比没有意义。当前页面仍然画一条 0% 的进度条，制造「没开始」的错觉。

正确信息是：已录时长、已写入字节、分片数、画质、是否在等磁盘。只有设置了「最大录制时长」时才适合显示「距离自动分割」的进度。

### 2.4 收尾父任务会以 queued/0% 挂很久

`src-tauri/src/recorder.rs:2317`：

```rust
let _post_job = jobs.begin("post", post_label, Some(active.recording.quality.clone()));
```

这个父任务从录制停止一直活到所有片段后处理结束，期间没有任何 `progress` 更新，stage 一直是 `queued`、percent 一直是 0；同时每个 `auto:session:index` 又各是一条任务。页面会同时看到「父任务 0%」和「片段任务 42%」。

这是当前「看不清」的最大结构性问题。父任务应该变成 Run 的 `finalize` 阶段，而不是一条独立 Task。

### 2.5 历史只有任务，没有链路

`task_history` 只存单个任务的最终 `stage/message/started_at/finished_at`，没有阶段时间戳、没有父 Run、没有片段序号。历史页只能看到「后处理 / 完成 / 09:44」，看不到：

- 这场录了多久；
- 合并花了多久；
- 转封装花了多久；
- 最终产物多大；
- 哪一步失败了。

### 2.6 平台健康完全不在任务页

当前任务页没有任何平台级信息。用户要判断「是不是平台挂了」，只能回监控页逐行看。`MonitorStatus` 也只有单房查询，没有平台聚合。

## 4. Run 卡片

### 4.1 卡片结构

1. **标题行**：头像、主播、平台、房间号、当前状态、总耗时。
2. **副标题**：直播间标题；右侧操作（停止录制 / 取消后处理 / 详情）。
3. **链路轨**：录制 → 合并 → 后处理 → 入库。节点状态一眼可见。
4. **当前动作**：一句人话，说明此刻在做什么。
5. **进度区**：只有可量化阶段才画进度条；录制阶段画「实时信息 + 细呼吸线」。
6. **片段条**：多片段时显示每个片段的状态，避免片段任务散落。

### 4.2 链路节点

| 节点 | 正常文案 | 跳过文案 | 失败文案 |
| --- | --- | --- | --- |
| 录制 | 录制中 01:12:33 / 已完成 | — | 录制失败 |
| 合并 | 合并 12 个分片 / 12.4s | 无需合并 | 合并失败 |
| 后处理 | 片段 2/3 · 转封装 42% | 保留源封装 | 转封装失败 |
| 入库 | 正在生成缩略图 / 已入库 | — | 入库失败 |

节点状态：

- **done**：实心小圆 + 实线，accent 色；
- **active**：实心圆 + 外圈 3px 柔光，accent 色；
- **pending**：空心圆 + 细线，muted；
- **skipped**：空心圆 + 虚线，faint，副文案「无需合并 / 保留源封装」；
- **failed**：红色实心圆，后续节点全部 muted。

不要用整条彩色进度条表达阶段，阶段是离散的，线只是连接。

### 4.3 录制阶段不要画百分比

录制中显示：

```
正在录制 · 已录 01:12:33 · 已写 1.8 GB · 42 个分片 · 原画 1080P
```

如果设置了最大录制时长或最大文件大小，才显示：

```
距离自动分割 02:47:12  ·  ▰▰▰▰▰▰▱▱▱▱  63%
```

否则进度条区域用一条 1px 的 accent 呼吸线，不显示 0%。

### 4.4 后处理阶段显示片段

```
后处理  2/3 段完成
[片段 1  ✓ 18s] [片段 2  42%] [片段 3  排队]
```

- 片段按钮可点击，打开详情抽屉并定位到该片段任务；
- 片段很多时折叠成 `片段 1 ✓ · 2 42% · 3 排队 · +4`；
- 当前片段显示 stage：`准备中 / 转封装 / 校验文件`；
- 排队片段显示 `等待后处理槽位 · 已等 00:18`。

### 4.5 排队卡片

排队任务不用大卡片，用紧凑行：

```
后处理 · 片段 3/3   Asaki大人 · 睡前推主线   等待后处理槽位   已等 00:18   [取消]
```

不显示伪造的「队列第 N 位」。如果后续后端提供真实 FIFO 序号，再加 `#2`；P1 只显示等待时长与阻塞原因。

P1 实现按 Run 聚合排队行：一个 Run 同时有多个片段排队时，行内显示第一条任务并标注 `+N`，逐片段状态在详情抽屉里查看；这样可以避免同一场录制在排队区重复出现多行。

### 4.6 完成态卡片

完成后的 Run 收进历史表格，不再占一张大卡。历史行点击后打开同一个详情抽屉。

## 5. 平台态势

### 5.1 每个平台一张卡

```
┌──────────────────────────────┐
│ ● 哔哩哔哩          已登录   │
│ 12 监控   3 直播   2 录制    │
│ 8s 前检查 · 关注批量 5 · 正常│
└──────────────────────────────┘
```

字段：

- 左侧状态点：正常/注意/异常/未监控；
- 平台名 + 登录态：已登录 / 未登录 / 登录失效；
- 三个数字：监控房间、直播中、录制中；
- 底部：最近检查时间、批量房间数、健康结论。

点击卡片 = 过滤该平台的 Run 与历史；再次点击取消。

### 5.2 健康分级

| 级别 | 条件 | 文案 |
| --- | --- | --- |
| 正常 | 无退避、无失败、登录有效 | 正常 |
| 注意 | 有房间退避 / 批量缺项回退 / 未登录但可匿名 | 注意 |
| 异常 | 登录失效且需要登录 / 批量风控 / 近 24h 有录制或后处理失败 | 异常 |
| 未监控 | 房间数为 0 | 未添加直播间 |

不要因为「未登录」直接标红：B 站、抖音、虎牙匿名也能看和录；只有依赖登录的批量或高清能力才降级。

### 5.3 系统行

平台卡下面一条细行：

```
ffmpeg 9.0.2 可用 · 后处理槽 1 运行 / 1 排队 · 流服务正常
```

磁盘不足、ffmpeg 缺失时才变成红色，并提供「打开存储设置」。

## 6. 需要处理（异常）

异常不是一类任务，而是跨对象的提醒。P1 聚合：

1. 近 24h 失败的 `task_history`；
2. 近 24h 失败的 `record_session`；
3. 单房监控退避 / 连续错误；
4. 平台登录失效；
5. ffmpeg 缺失；
6. 磁盘剩余低于阈值（如果后端能拿到全局磁盘）。

每条 Incident：

```rust
Incident {
    id: String,              // 稳定去重键：task:xxx / room:xxx / platform:xxx
    severity: String,        // error | warn
    scope: String,           // monitor | record | post | system
    platform: Option<String>,
    room_id: Option<String>,
    task_id: Option<String>,
    title: String,
    detail: Option<String>,
    at: i64,
    action: String,          // room | task | settings | retry
}
```

UI 只显示前 3 条，其余进「异常」筛选。点击「查看房间」回监控并打开对应房间抽屉；点击「重试」调现有 `post_retry(sessionId)`。

去重规则：同一 `scope + room_id + code` 只保留最新一条；失败任务恢复后自动消失。

## 7. 最近完成

### 7.1 一行一条 Run

```
时间        直播间        链路                                              产物      耗时      状态
11-20 09:44 Asaki大人 B站  录制 01:32:10 → 合并 12s → 转封装 18s → 入库 1s  2.1 GB   01:33:12  ● 完成
11-20 08:12 洞主 斗鱼      录制 00:41:09 → 合并 8s → 转封装失败             812 MB   00:41:31  ● 失败
```

- 「链路」用 10.5px 小字，阶段之间用 `→`，不换行；
- 失败阶段红色，后续阶段用 `—`；
- 产物显示主文件大小；
- 状态：完成 / 部分失败 / 失败 / 已取消 / 已中断；
- 点击行打开详情抽屉。

### 7.2 历史范围

- 默认最近 100 条 Run，按结束时间倒序；
- 过滤：平台、房间、状态、时间范围（今天/7 天/30 天）；
- 搜索：主播名、房间号、标题、文件名；
- 没有录制的旧数据时，空态显示「完成的录制会按链路归档在这里」。

## 9. 数据模型

### 9.1 两级对象

```rust
/// 一次录制链路，或一次独立的手动操作（合并）。
TaskCenter {
    generated_at: i64,
    summary: TaskSummary,
    platforms: Vec<PlatformHealth>,
    running: Vec<RunView>,
    queued: Vec<TaskView>,
    history: Vec<RunView>,
    incidents: Vec<Incident>,

RunView {
    id: String,                 // session id；独立合并用 merge:{task_id}
    room: Option<RunRoom>,
    state: String,              // recording | finalizing | queued | running | done | partial | failed | cancelled | interrupted
    stage: String,              // recording | merging | postprocessing | ingesting | done | failed
    started_at: i64,
    ended_at: Option<i64>,
    duration_ms: i64,
    bytes: i64,
    quality: Option<String>,
    tasks: Vec<TaskView>,

TaskView {
    id: String,
    kind: String,               // record | finalize | post | remux | merge | ingest
    title: String,
    detail: Option<String>,
    state: String,              // queued | running | done | failed | cancelled | interrupted
    stage: Option<String>,      // queued | preparing | converting | validating | ...
    percent: i64,
    message: Option<String>,
    started_at: i64,
    finished_at: Option<i64>,
    clip_index: Option<u32>,
    clip_count: Option<u32>,
    bytes: Option<i64>,
    queue: Option<String>,      // auto | manual
    queued_at: Option<i64>,
    eta_secs: Option<i64>,
}

StageView {
    key: String,                // recording | merging | postprocessing | ingesting
    state: String,              // done | active | pending | skipped | failed

    ended_at: Option<i64>,
    detail: Option<String>,
    percent: Option<i64>,
}
```

```rust
PlatformHealth {

    live: u32,
    recording: u32,
    paused: u32,
    batch_rooms: u32,
    checking: u32,
    backoff: u32,
    last_checked_at: Option<i64>,
    next_check_in_secs: Option<i64>,
    level: String,              // ok | warn | error | idle
    message: Option<String>,
}
```

P1 可由以下数据实时拼出，不需要新表：

- `room` 表：房间数、直播数、暂停数、`batch_follow`；
- `recorder.active_all()`：录制中；
- `MonitorStatusMap`：inflight、backoff、last_checked_at、last_outcome；
- `credential`：登录态；
- `task_history` / `record_session`：近 24h 失败。

### 9.3 Run 聚合规则

1. 取最近 N 条 `record_session`（默认 200）与全部运行中 session；
2. 取 `Jobs::board(500)`；
3. 有 `session_id` 的任务挂到对应 Run；
4. 无 `session_id` 的任务（合并）作为独立 Run；
5. 有 session 但无任务的历史，仍然生成 Run（保留源封装 / 直接录制）；
6. 同一个 session 的多个 `auto:{session}:{index}` 按 `clip_index` 排序；
7. 父 `finalize` 任务不单独展示，只作为 Run 的 `finalizing` 阶段；
8. 历史按 `ended_at` 倒序，运行中按 `started_at` 正序。

### 9.4 父子任务修正

P1 必须处理 `recorder.rs:2317` 的父任务：

- 把 `jobs.begin("post", ...)` 改成 `jobs.begin("finalize", ...)`；
- 给 `JobGuard` 增加 `progress(percent, stage, message)`；
- 收尾期间更新：`merging` → `splitting` → `postprocessing` → `ingesting`；
- 任务页不把 `finalize` 当独立 Task 展示，而是映射成 Run 的阶段。

这样既保留「收尾中」的实时状态，又不会出现一条永远 0% 的父任务。

## 10. 阶段与状态字典

### 10.1 阶段

| stage | 中文 | 英文 | 说明 |
| --- | --- | --- | --- |
| starting | 开录中 | Starting | 已决定开录，ffmpeg 尚未出流 |
| recording | 录制中 | Recording | ffmpeg 正在写分片 |
| finalizing | 收尾中 | Finalizing | 停止后合并/切片段/弹幕落盘 |
| merging | 合并分片 | Merging | 收尾内部子阶段 |
| splitting | 切分片段 | Splitting | 按标题/时长/大小切片段 |
| queued | 排队中 | Queued | 等待后处理槽位 |
| preparing | 准备中 | Preparing | 已拿到槽位，校验输入 |
| converting | 转封装 | Converting | ffmpeg 正在输出 |
| validating | 校验文件 | Validating | fsync/rename/大小校验 |
| ingesting | 入库 | Ingesting | 缩略图、ASS、文件登记 |
| done | 完成 | Done | — |
| failed | 失败 | Failed | — |
| cancelled | 已取消 | Cancelled | — |
| interrupted | 已中断 | Interrupted | 进程退出/崩溃 |

### 10.2 Run 状态判定

| Run 状态 | 条件 |
| --- | --- |
| recording | 有活动录制 |
| finalizing | 录制已结束，finalize 任务在跑 |
| queued | 所有后处理任务 queued，且无 running |
| running | 至少一个 post/merge/remux 在 running |
| done | 录制完成，所有任务 done 或 skipped |
| partial | 至少一个片段失败，至少一个成功 |
| failed | 录制失败，或所有后处理失败 |
| cancelled | 用户取消 |
| interrupted | 进程中断 |

「部分失败」很重要：三片段转封装，成功两个、失败一个，不能显示整条 Run 成功，也不能显示全失败。

## 11. 接口

新增命令：

```rust
pub fn task_center(
    state: State<'_, AppState>,
```

## 12. P1 / P2 范围

### P1：先把结构做对（不改 schema）

- 新增 `task_center` 聚合与类型；
- Run 分组、父子任务修正、`queued` 状态；
- 平台态势卡 + 系统行；
- 运行卡（链路轨、当前动作、片段条、录制实时信息）；
- 排队区、异常区、历史表；
- 详情抽屉（任务级时间线，先用开始/结束时间）；
- i18n 中英文、明暗主题、1166px 验收。

P1 完成后，用户已经能回答：

- 哪个平台不正常；
- 哪一路在录、哪一路在转封装、哪一路在排队；
- 每个片段进行到哪一步；
- 最近一次为什么失败。

### P2：补真实阶段时间线

- 新增 `task_event` 表，记录 stage/state 转换，不按秒存进度；
- `queued_at` / `started_running_at` / `finished_at` 真实落库；
- 记录合并、切片段、缩略图、ASS 导出、入库的子阶段；
- 详情抽屉显示完整时间线；
- 支持按阶段耗时排序/筛选（可选）。

`task_event` 建议：

```sql
CREATE TABLE task_event (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id TEXT NOT NULL,
  run_id TEXT,
  kind TEXT NOT NULL,
  stage TEXT NOT NULL,
  state TEXT NOT NULL,
  percent INTEGER NOT NULL DEFAULT 0,
  message TEXT,
  at INTEGER NOT NULL
);
CREATE INDEX idx_task_event_run ON task_event(run_id, at);
CREATE INDEX idx_task_event_task ON task_event(task_id, at);
```

写入时机：stage 变化、state 变化、25/50/75/100% 各一次。不要每次 4Hz 进度都写。

### P3：可选增强

- 真实队列序号（需要显式 FIFO 票据，不靠信号量猜测）；
- 阶段耗时统计（近 7 天 P50/P95）；
- 异常规则可配置；
- 导出诊断包（任务 JSON + 脱敏日志尾部）。

## 13. 交互细节

### 13.1 点击

| 区域 | 行为 |
| --- | --- |
| 平台卡 | 过滤该平台；再点取消 |
| Run 卡 | 打开详情抽屉 |
| 片段按钮 | 打开抽屉并定位到该任务 |

| 查看房间 | 回监控并打开房间抽屉 |
| 打开录制文件 | 复用房间录制文件页 |

### 13.2 轮询

- `task_center` 2s；
- 本地 1s tick 只更新「已录/已等/已运行」文案，不请求后端；
- 页面隐藏时暂停轮询，重新可见立即刷新；
- 进度条宽度用 CSS transition 500ms，避免 2s 一跳；
- 列表排序按 started_at，新任务插入顶部，不因百分比变化重排。

### 13.3 空态

| 场景 | 空态 |
| --- | --- |
| 没有监控房间 | 「还没有监控中的直播间」+ 去添加 |
| 有监控、无运行任务 | 「监控运行中，等待开播」+ 平台态势仍显示 |
| 无排队 | 不显示排队区（不要一个空框） |
| 无异常 | 不显示异常区；平台卡显示正常 |
| 无历史 | 「完成的录制会按链路归档在这里」 |

### 13.4 错误

- 轮询失败不弹 toast，只在页面顶部显示一条「状态暂不可用，正在重试」；
- 恢复后自动消失；
- 取消/重试失败才 toast。

## 14. 视觉规范

- 暖纸底、1px `border-line`、14px 面板圆角，沿用现有 token；
- 数字用 tabular-nums，时间/大小/房间号用 mono；
- 链路轨是页面唯一「图形化」元素，不要再加环形图/柱状图；

- 红只给失败/异常，绿只给完成/正常，琥珀只给当前阶段与注意；
- 阶段节点 7px，当前节点外圈 3px `accent/20`；
- 卡片内边距 14–16px，行高 22–24px；
- 1166×749 下不横向滚动；平台卡 4 列，低于 1000px 变 2×2。

## 15. 验收用例

1. **三平台混合**：B 站 2 录、斗鱼 1 录、抖音 0 录；平台卡数字与监控页一致。
2. **一场多片段**：3 片段后处理，页面只有 1 张 Run 卡、3 个片段按钮，不出现 3 条独立记录。
3. **排队**：自动后处理槽被占，第二个片段显示「排队中 · 等待后处理槽位 · 已等 00:18」，不能显示「运行中」。
4. **录制中**：显示时长/字节/分片，不显示 0% 进度条。
5. **收尾父任务**：只出现在 Run 的「合并/收尾」阶段，不作为独立 Task 出现在列表。
6. **部分失败**：3 片段成功 2、失败 1，Run 显示「部分失败」，历史链路失败节点红色。
7. **登录失效**：对应平台卡红点「登录失效」，异常区出现一条，点击进设置账号页。
8. **监控退避**：平台卡「注意」，异常区显示房间与下次检查时间。
9. **无任务**：监控正常、无录制时，空态写「监控运行中，等待开播」，平台卡仍显示。
10. **主题/语言**：明暗、中英文、i18n key 全部通过。
11. **窗口宽度**：1166×749 无横向滚动，操作按钮不换行。
12. **性能**：100 条历史 + 10 条运行，2s 轮询无明显卡顿/布局跳动。
