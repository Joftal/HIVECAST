# 27 · M7.1 实现记录：录制健壮性

> 阶段：M7.1（docs/19 §5 之后的补强，对应 M6 复盘 P0-3/4/5）
> 日期：2026-11-05
> 结论：录制从「单段 FLV 一直写到停」改成「分段落盘 + 收尾合成 mp4 + 崩溃可恢复 + 断流同会话续录 + 保留策略」。断流续录的关键不是重开进程，而是**丢掉线路缓存重新解析**——直接用旧地址只能续上 1 秒。

## 2 分段录制

### 2.1 命令

```text
ffmpeg -hide_banner -nostdin -loglevel warning -y \
  [-headers "Cookie: ...\r\nOrigin: ...\r\n"] \
  -i <stream url> \
  -c copy \
  -f segment -segment_time 300 -segment_format mpegts \
  -reset_timestamps 1 \
  [-segment_start_number N] \
  <媒体目录>/[时间][主播][标题].part%04d.ts
```

| 参数 | 为什么 |
| --- | --- |
| `-f segment` + `-segment_time 300` | 每 5 分钟落一个独立文件；断电/强杀最多丢尾片，而不是整场不可播 |
| `-segment_format mpegts` | ts 每片自带时间戳与分片边界，合并时可以直接 `-c copy`；换成 flv/mp4 分片要么时间戳断裂要么需要重封装 |
| `-reset_timestamps 1` | 每片时间戳从 0 开始；否则 concat 后音画会错位 |
| `-segment_start_number N` | 续录时接着编号，不覆盖已有分片（首次录制 N=0，不传该参数） |
| 输出后缀 `.mp4` | 分片是 ts，最终产物是 mp4；会话记录里的路径就是最终路径，收尾时不再改目录 |

分片命名规则在 `segment::parts_pattern`：把最终文件的扩展名换成 `.part%04d.ts`，即

```text
[2026-11-05 17-31-05][yyfyyf][陪伴每一天！].part0000.ts
[2026-11-05 17-31-05][yyfyyf][陪伴每一天！].part0001.ts
...
```

`collect_parts` 只认 `{stem}.part` 前缀 + `.ts` 后缀并按文件名排序，所以同目录下的其他文件（`.jsonl`、别的会话）不会被误收。

### 2.2 测试素材必须给关键帧间隔

segment muxer **只在关键帧处切分**。单测里用 4 秒素材、默认 GOP 时只会切出 1 片，`merge_makes_playable_mp4` 会报「至少要切出两片」。修法是生成素材时加 `-g 20`（25fps 下约 0.8 秒一个关键帧）。

真机同理：`-segment_time 15` 实际片长会是 15–17 秒，取决于源的 GOP。

## 3 合并与兜底

### 3.1 正常路径：concat demuxer

```text
ffmpeg -hide_banner -nostdin -loglevel error -y \
  -f concat -safe 0 -i <stem>.concat.txt \
  -c copy -movflags +faststart <最终 mp4>
```

清单文件每行 `file '<绝对路径>'`，路径里的单引号按 ffmpeg 规则转义成 `'\''`。成功后删掉全部分片与清单，返回产物字节数；stderr 只保留末尾 240 字符用于报错。

`-c copy` 不重编码，5 分钟 1080p 大约 1–2 秒完成；`+faststart` 把 moov 挪到文件头，媒体库里边下边播/拖动才不用等整文件。

### 3.2 兜底一：字节拼接成 .ts

concat demuxer 失败（分片时间戳断裂、某片被截断）时，`fallback_concat` 直接按文件名顺序把分片字节拼成一个 `.ts`，删掉分片并返回新路径。ts 本身可播，代价是没有 moov、部分播放器拖动体验差。

### 3.3 兜底二：只报分片总量

两条路都失败时保留分片原样（不删），`file_size` 记为分片总量，至少历史里数字不为 0，用户还能自己拿分片去播。

`finish_file` 返回 `(实际路径, 字节数)`；路径与记录不同时用 `db.update_session_file` 改写库里的 `file_path`，媒体库才不会指向已删除的分片名。

## 4 崩溃恢复

### 4.1 启动顺序

`state.rs` 的 `init` 里顺序是刻意排的：

```text
Db::open
  → recorder::recover_parts(&db)      // 先救文件
  → db.close_orphan_sessions()        // 再把 recording 状态改成 aborted
  → retention::enforce_from_settings  // 最后按阈值清理
```

`recover_parts` 依赖 `db.recording_sessions()` 里的 `status = 'recording'` 行。如果先跑 `close_orphan_sessions`，这些行已经变成 `aborted`，就再也找不到「哪些会话还留着分片」。

### 4.2 两种遗留形态

| 遗留 | 处理 |
| --- | --- |
| 有分片、没有成品 | `finish_file` 合成 mp4，`update_session_file` 写回路径与大小 |
| 没有分片、成品已在（上次合并完但没来得及写库） | 按 `metadata` 的大小更新 `file_size` |

恢复过程打一条 info：`恢复崩溃遗留的录像 recovered=N recovered_bytes=M`。

### 4.3 实测

录制 35 秒（3 片）后 `pkill -9 ffmpeg` + `kill -9` App，重启后：

```text
[2026-11-05 17-19-34][yyfyyf][陪伴每一天！].mp4   4,610,593 字节
DB: aborted / app_exit / file_size=4610593
```

分片目录已清空，同时监控循环按 `auto_record` 又拉起了一场新录制。

## 5 断流续录

### 5.1 判定

watcher 每秒轮询子进程。满足下面任一条件且不是用户主动停/平台下播，就尝试续录：

| 条件 | 说明 |
| --- | --- |
| 退出码非 0 | 网络中断、DNS 失败、ffmpeg 崩溃 |
| 退出码 0 但本段只活了不到 12 秒（`EARLY_EXIT`） | 地址过期时 ffmpeg 会把「服务端提前关连接」当正常 EOF 退出，不重试就整场提前结束 |

续录最多 3 次（`MAX_RESTARTS`），用尽后按正常收尾走，避免对着一个真下播的房间无限重连。

### 5.2 为什么必须重新解析线路

第一版 `respawn` 直接复用开录时存下的 URL 与 headers，结果每次都是「续录成功 → 1 秒后又结束」：

```text
INFO  断流后续录 start_number=2 restarts=1
DEBUG 录制 ffmpeg line=[https @ ...] Stream ends prematurely at 944569, should be ...
DEBUG 录制 ffmpeg line=[in#0/flv @ ...] Error during demuxing: Input/output error
```

原因有两层：

1. 平台播放地址是带时效签名的（斗鱼 anti-code、虎牙 wsSecret），旧地址在几十秒后就不再被 CDN 接受；
2. `StreamBroker` 的线路结果缓存 60 秒，续录时直接 `groups()` 拿到的还是同一个过期地址。

修法（`recorder::respawn`）：

```text
取快照（session_id / 分片路径 / start_number / restarts）→ 放锁
  → db.get_room → broker.invalidate(&room_ref)
  → sleep 3s（给 CDN 回收上一条连接）
  → broker.groups(room_ref, room.record_qn) → pick_candidate
  → build_command(start_number=已有分片数) → spawn → drain_stderr
  → 重新加锁：session_id 没变才挂上新 child，否则 kill 掉新进程
```

三个细节都不能省：

- **先放锁再 await**：`inner` 是 `std::sync::Mutex`，持锁跨 await 会卡住整个录制表；
- **invalidate**：不丢缓存等于没换地址；
- **3 秒退避**：立刻重连常被 CDN 判成重复会话而秒断（实测连试 3 次全部失败）。

### 5.3 start_number 的作用

`start_number = segment::collect_parts(&path).len()`。续录时传给 `-segment_start_number`，新分片从 part0004 开始，不会覆盖前 4 片。

### 5.4 实测

```text
17:31:05 开始录制（part0000–0003）
17:32:05 kill -9 ffmpeg
17:32:05 断流后续录 start_number=4 restarts=1 quality=蓝光4M · FLV
17:32:25 新进程存活，part0004–0007 持续增长
17:32:4x 优雅停止 → 合并为 15,660,517 字节 / 114.95s，DB 单条 aborted/app_exit
```

## 6 保留策略

### 6.1 两个阈值

| 键 | 含义 | 范围 |
| --- | --- | --- |
| `media.retention_days` | 只保留最近 N 天；0 = 不按天删 | 0–3650 |
| `media.max_total_gb` | 已结束录像总容量上限；0 = 不限 | 0–100000 |

两个都为 0 时直接返回，一次数据库查询都不做。

### 6.2 选择算法

`retention::select` 输入按 `started_at` 倒序的行：

1. 先按天删：`started_at < now - days*86400` 直接进删除集；
2. 再按容量删：累计字节超过上限后，**后面更旧的全部删**（不是跳着删），避免「删了新录像、留着更旧的大文件」。

### 6.3 删除范围与触发时机

每条命中删除：视频文件、同名 `.jsonl` 弹幕、`record_session` 行。正在录制的会话永远不参与（SQL 里 `status <> 'recording'`）。

触发点三个：

- 应用启动（长期不录制时也有机会清理）；
- 每次录制收尾（媒体库唯一增长来源）；
- 设置保存后（调小阈值立即生效）。

### 6.4 实测

把 [17-18-24] 这场改成 10 天前、`media.retention_days=1`，重启后该 mp4 与 DB 行消失，另外两条保留。

## 7 踩坑：stderr 不读会卡死 ffmpeg

分段命令把 stderr 设成 `piped`。管道缓冲区只有 64 KB，不读就会写满，ffmpeg 随后阻塞在写日志上——表现是「录到一半既没声音也不退出」。

修法：`drain_stderr` 把 stderr take 出来，起一个 task 用 `BufReader::lines` 读到 EOF，逐行 `tracing::debug!(target: "ffmpeg")`。开 `RUST_LOG=debug` 才能看到这些行，平时不占日志。

## 9 已知缺口

| 缺口 | 影响 | 后续 |
| --- | --- | --- |
| 分片边界丢 0–1 秒 | 每片在关键帧切分，首片开头可能缺一个 GOP | 可接受；如需严格对齐改用 `-segment_time 0 -break_non_keyframes 0` 之外的重封装流程 |
| 合并失败时留下 `.ts` | 产物可播但拖动体验差，界面仍显示为一条录像（后缀不同） | 收尾时把兜底产物再尝试一次重封装，并给用户可见提示 |
| 续录有 3 秒空档 | 退避期间画面缺失 | 与 CDN 回收连接的耗时相关；可改成「先解析、成功后再杀旧连接」进一步缩短 |
| 保留策略不感知「正在被回放」 | 清理可能删掉媒体库正在播的那条 | v1 回放时会持句柄，删除失败即跳过（当前会先删文件） |
| 续录只有单测+真机手工验证 | 没有自动化集成测试 | 可用本地 HTTP 假流做集成测试 |
