### 1.1 H2：回落不再「只改内存」

旧逻辑只把 `settings.media_root` 改成默认目录（内存里），数据库仍是用户填的外接盘路径。于是设置页显示外接盘、文件却全在安装目录；更糟的是用户在这个状态下随便改一项设置，`save()` 会拿「外接盘路径」做存在性校验，必然失败——表现成「设置页怎么都存不上」。

现在（[state.rs:93](../src-tauri/src/state.rs#L93) 起）：

1. 回落成功后立即 `persist_media_root(&db, 实际目录)`，库里的值就是真正在用的目录；
2. 记录 `media_fallback = Some((配置值, 实际值))`；
3. `lib.rs` 在 `app.manage(state)` 之后读它，发一条系统通知：「{配置值} 当前不可用，新录像已改存到 {实际值}；设置里已同步为后者」。

只写库不通知的话，用户会以为设置被「偷偷改了」；只通知不写库，下一次启动又回落一遍。两件事一起做，界面、库、文件三者才一致。

### 1.2 H4：假死看门狗不能覆盖已发出的停录原因

拔盘时 `stop()` 只置 `stop_reason` 并发 SIGINT；如果 ffmpeg 正卡在 IO 上（USB 拔盘很常见），信号送不进去，进程一直活着。60 秒后看门狗按「长时间没有新数据」处理，旧代码直接 `finalize(..., Some("stalled"), true)`，把 1 秒前刚记下的 `disk_lost` 顶掉，历史变成「录制失败：直播流长时间没有数据」，而分片其实还在盘上。

现在看门狗分三步：先查 `stop_reason`；有值就 kill 等待、按原原因收尾并 `return`；没有值才走原来的「重启 ffmpeg → 预算用尽 → stalled」路径。日志会留一条「已有停录请求，不再重启 ffmpeg，直接收尾 reason=...」，方便事后对时间线。

### 1.3 H8：调小间隔也要立刻作用到退避房间

`needs_reschedule` 原来的条件是「不是退避条目 + 基准间隔变小 + 下次触发还在未来」。坏房间失败一次后 `backoff=true`，用户把间隔从 1 小时改到 30 秒，这个房间仍按 1 小时的退避等待——用户看到的仍是「改了没用」。

现在把「不是退避条目」去掉；命中后如果正处退避，直接 `next_at = now + base`、`grid_at = next_at`、`backoff = false`，**不加 spread**：否则刚改小间隔又要再等一个随机偏移。退出退避状态是有意的——用户调小间隔就是在说「我想更频繁地看它」，不该继续把他锁在旧的失败节奏里；如果仍然失败，下一次 `Outcome::Failed` 会按新的基准间隔重新算退避。

### 1.4 H1：写进去了就推一条事件

G2 引入节流写库后，在线人数这类高频字段只更新数据库、不推 `EVENT_ROOMS_CHANGED`；监控页只在挂载和收到事件时全量拉取，于是人数一直停在打开那一刻（H1）。现在节流写入返回 `true`（真的执行了 UPDATE）且人数确实变了，就补一条事件。10 秒节流仍然有效：事件最多 10 秒一次，不会把前端刷爆。

### 1.5 H7：没有开播时间的平台，靠「离线 → 在播」判新一场

`auto_blocked` 的提前解除要求「平台确认下播后又报在播」且 `live_started.is_some()`。斗鱼（[douyu.rs:236](../src-tauri/src/platform/douyu.rs#L236) 恒 `None`）和缺 `start_time` 的抖音永远拿不到开播时间，只能等 600 秒静默自然过期；快速重开一场就会丢最多 10 分钟。

新增 `offline_seen`：确认离线（`confirm_offline` 通过）时打点；下一次看到在播时消费这个点，清掉 `ended` 与 `suppressed`。只有「先看到离线、再看到在播」才成立——平台单次误报在播不会解掉刚写下的 600 秒静默。消费后 `new_session_after_offline` 返回「是否真的解掉了什么」，正常每场开播都经过这里，不值得每次都刷一条 INFO。

代价：如果平台在「真的下播」后又短暂误报在播，会多一次开录尝试；ffmpeg 秒退会被连续失败计数拦住（G5），3 次后冷却 5 分钟。这与 A8 对「有开播时间的平台」的取舍一致。

### 1.6 H6 / H3 / H5：三处小口子

- **H6**：开录流程从 `begin_start` 到挂进 `active` 之间有一个窗口（选流、建目录、起进程）。这期间点退出，任务表是空的，`app.exit(0)` 直接把 ffmpeg 留在后台写文件。现在任务表把 `starting` 里的房间也列出来，退出会等它们落定。
- **H3**：`reserve_unique_path` 是原子占位（先建空文件抢名字，D1）。进程起不来时这个空文件没人清理，媒体库多一条 0 字节录像。spawn 失败分支现在先 `remove_file` 再返回错误。
- **H5**：兜底拼接（ffmpeg 合并失败时按字节拼 mpegts）用 `File::create(final.ts)`。同名 `.ts` 来自上一场的兜底产物时会被直接截断。现在目标存在就 `reserve_unique_path` 另起一个名字，旧文件保留。

## 3. 真机验收

环境：macOS 27.0.1 arm64、ffmpeg 9.0.2、`target/debug/hivecast`（含本轮全部改动）、真实 DB、真实在播房间（bilibili 6 / 545068）。

### 3.1 T1：媒体目录不可用 → 落库 + 告警（H2）

1. 库里把 `media.root` 设为 `/Volumes/NOPE/Recording`（该路径不可创建）；
2. 启动应用，8 秒后查库。

结果：`media.root` 从 `/Volumes/NOPE/Recording` 变为 `/Library/dshproject/HIVECAST/src-tauri/target/debug/Recording`；日志一条 WARN：

```
WARN 媒体目录不可用，已回落到默认目录 configured=/Volumes/NOPE/Recording actual=.../target/debug/Recording
```

落库之后再进设置页保存，校验用的是真正存在的目录，不会像 66 里那样「改什么都失败」。系统通知在无头运行里看不到，但走的是与「单实例锁提示」相同的 `notification().builder().show()` 路径。

### 3.2 T2：退避中调小间隔 → 30 秒内重新检测（H8）

1. `monitor.interval_sec=3600`，插入无效房间 `bilibili 999999999`；
2. 03:06:33 首次检测失败（WARN「刷新房间失败 … error decoding response body」），按 3600 基准进入退避，下一次本应在一小时后；
3. 03:07:34 把间隔改成 30；
4. 03:08:04 该房间 `last_checked_at` 更新（新一拍已执行），WARN 因「同一错误去重」没有重复刷。

对照修复前：退避条目被 `!entry.backoff` 排除，改间隔后仍要等完一小时的退避。

### 3.3 T3：掉盘 + ffmpeg 卡死 → 保持 `disk_lost`（H4）

1. 3 GiB 稀疏卷挂到 `/Volumes/HIVECASTH4b`，媒体目录指到卷内，`interval=5`；
2. 11:11:37 开始录制（bilibili 545068）；
3. 11:12:17 `kill -STOP` ffmpeg 并 `hdiutil detach -force`；
4. 观察 75 秒。

结果：

- 11:12:18.472 WARN「录制目录不可用，停止录制」→ 置 `disk_lost`；
- 11:13:17.224 INFO「已有停录请求，不再重启 ffmpeg，直接收尾 reason=disk_lost」；
- 11:13:17.330 INFO 录制结束 `status="aborted" reason="disk_lost" file_size=0`；
- 全程没有「录制长时间没有新数据，重启 ffmpeg」，DB 也没有 `failed/stalled`。

修复前同样的操作会在 60 秒后被改写成 `failed/stalled`，历史显示「直播流长时间没有数据」。

### 3.4 T4：在线人数变化会落库并触发刷新（H1）

`interval=5`、`auto_record=0` 的 bilibili 6 房间，4 次采样（每 8 秒）里 `last_checked_at` 每约 10 秒前进一次（节流 10 秒生效），`online` 从 5,396,042 变为 5,371,707。事件由 `EVENT_ROOMS_CHANGED` 发出，前端 `MonitorPage` 收到后重新拉取；无头环境无法截图，但「写库成功 → 发事件」这个条件已由该采样与代码分支共同确认。

## 4. 行为变化与边界

- 媒体目录回落现在会**改设置**（并通知）。这是有意的：以前那种「界面说 A、文件在 B」的状态更糟。用户想换回外接盘，插上盘后在设置页重新选即可。
- 掉盘/磁盘红线后的收尾原因以第一次 `stop()` 为准；假死看门狗只负责把进程收掉，不再改判。
- 退避房间在「间隔调小」时会立即退出退避状态；若仍失败，按新间隔重新累计退避。频繁改间隔会让退避反复清零，这是用户主动行为，不再额外限制。
- 在线人数事件最多 10 秒一条（沿用 G2 节流），不会因为人数每次检测都变而刷爆前端。
- `offline_seen` 只在内存里，进程重启后丢失；重启后的第一场仍按 600 秒静默处理，属于可接受退化。
- 开录在途出现在退出任务表后，退出会等它结束（成功则进入正常收尾，失败则任务消失）；不会永久卡住退出。

## 5. 未覆盖

- **H3**：本机 `ffmpeg::resolve` 总会命中 `/opt/homebrew/bin/ffmpeg`（`extra_dirs` 兜底），无法构造「spawn 失败」；改动只有三行，靠代码核验。
- **H5**：已用单测覆盖；真机上要触发「兜底拼接 + 同名文件」需要人为破坏合并流程，本轮未做。
- **H6**：退出窗口只有毫秒级，且需要「正在选流/起进程」时点退出；单测覆盖了任务表数据源，真实退出流程未做定时复现。
- **H7**：需要斗鱼/抖音真实开播-下播-再开播，本轮没有可用场次；逻辑由单测覆盖。
- 仍未覆盖：Windows、真实 429、系统睡眠唤醒、6 小时以上长播、多外接卷同时掉线。

## 6. 验收结论

- 八条问题全部落地，没有引入新的编译警告（`cargo check --all-targets` 0 警告）。
- 真机三条（H2/H8/H4）都与 66 的描述对得上：回落不再静默、退避跟着间隔走、掉盘原因不再被覆盖。
- 上一轮 G1–G7、C1–C7、B1–B9 的行为没有回退：本轮的改动都限定在「停录原因优先级」「退避重排」「离线记号」「任务表补漏」「文件清理」这几处。
- 前端与 IPC 结构未改（H2 的通知走 Tauri 系统通知，不新增事件类型），因此不需要重新生成绑定。
