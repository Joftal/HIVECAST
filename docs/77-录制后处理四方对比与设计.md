# 77 录制后处理四方对比与设计

> 状态：v1 设计评审稿（2026-11-08）。对比 `bililive-go`、`streamlink`、`biliLive-tools` 与 HIVECAST 现有实现。
> 实现说明：实际实现见 [78-录制后处理实现与验收](78-录制后处理实现与验收.md)；按用户 m29073 决策**不做老用户迁移**，本文 §5.3、§9 仅作历史方案保留。
> 本文只定方案，不改代码。核心结论：**录制先产出源封装母带；后处理是独立的、可重入的单入口状态机；只有转换成功、校验通过、数据库提交之后，才允许把源文件移入回收站。**

## 0. 结论先行

1. **biliLive-tools 不是“后处理三模式”的参考。** 它的模型是“录制层固定 `-c copy` 到 ts/m4s/flv，可选录完立即转 MP4 并删源”，不是“源封装成品 + 可选后处理”。它还有两条转换链路（录制器 `convert2Mp4` 与 Webhook 转封装），官方 UI 自己提示二者不要同时开。
2. **bililive-go 的“所有阶段成功后才统一删源”是对的，但自定义命令分支不能照抄。** 它只要自定义命令退出码为 0 且勾了 `DeleteFlvAfterConvert` 就 `os.Remove`，不检查命令是否真的产出了转换文件；失败还只打 Debug 日志。一个“发通知”的命令也可能把源删掉。
3. **streamlink 证明了抓流与后处理应该解耦。** `--record` 只负责把流字节写进文件，转封装/删源/上传都不在抓流层。HIVECAST 也应该让录制器只负责“封口”，后处理由独立编排器做。
4. HIVECAST 现有 `auto_remux` 是“二选一”：开则收尾合 MP4，关则字节拼 TS；没有“源封装”概念，也没有转换/删源/自定义命令。新设计保留它已经做对的部分——**分片、清单、崩溃恢复、失败降级**——但把“成品容器”和“后处理”拆开。

一句话目标：

> **默认录成直播源对应的封装（FLV 源→FLV，HLS/TS 源→TS，DASH 源→MP4）；需要 MP4 时显式转换；删除源必须显式开启、校验后执行、进回收站；自定义 FFmpeg 是第三条互斥路径，源文件永不自动删除。**

## 1. 四个项目的真实模型

### 1.1 bililive-go

**录制产物**

- `src/recorders/recorder.go:519-525`：`m3u8` 录成 `.ts`，`AudioOnly` 录成 `.aac`，其余默认 `.flv`。
- 默认 `FixFlvAtFirst=true`，录完先修 FLV 再进后处理。

**后处理入口**

- `src/configs/config.go:421-436` 的 `OnRecordFinished`：
  - `ConvertToMp4`
  - `DeleteFlvAfterConvert`
  - `CustomCommandline`
  - `FixFlvAtFirst`
  - 另有一组烧录字幕、云上传、封面字段。
- `src/recorders/recorder.go:774-841`：**自定义命令非空时走自定义分支，内置 Pipeline 完全不跑**（`else` 在 `:842`）。这是“互斥”的实现，但代价是自定义命令一开，修复、封面、上传、烧字幕全部绕过。

**内置转换**

- `src/pipeline/stages/convert_mp4.go:46-239`：写临时文件、`-c copy`、成功后 rename，产物标记 `Deletable`。
- `src/pipeline/executor.go:251-300`：**所有阶段都成功后**才统一删源；任一阶段失败，源和中间产物都保留。

这是四方里失败语义最稳的内置转换实现。

**自定义命令的坑**

- `src/recorders/recorder.go:818-840`：
  - Linux 用 `sh -c`，Windows 用 `cmd /C`，整条字符串交给 shell。
  - 命令失败只 `Debugf`，用户在 UI 上看不到。
  - 命令成功且 `DeleteFlvAfterConvert=true` 就 `os.Remove(fileName)`，**不检查输出文件是否存在、是否非空、是否真的是转换产物**。
- 例子：用户把 `CustomCommandline` 写成“上传到网盘/发 webhook”，同时勾了“转换后删除 FLV”。上传命令退出 0，源 FLV 被删，但网盘可能只传了一半，或者根本没有转换文件。这是不可接受的默认行为。

**可借鉴**

- 阶段化后处理。
- “全部成功才删源”。
- 内置转换用临时文件 + rename，不直接写目标。

**不能照抄**

- 自定义命令成功即删源。
- shell 执行、无超时、失败只 Debug。
- 自定义命令一开就绕过全部内置阶段。

### 1.2 streamlink

- `src/streamlink_cli/argparser.py:742-787`：`--output` / `--record` 只把流字节写入文件；`--ffmpeg-fout` 只在必须混流时指定输出封装。
- 没有“录后转 MP4 / 删源 / 自定义后处理”的配置。
- 它的边界很清楚：**抓流层只负责拿到字节并写文件；容器、后处理、上传都是外部工具的事。**

**可借鉴**

- 抓流与后处理解耦。
- 输出路径由用户负责，工具不偷偷改扩展名、不偷偷删文件。

**不能照抄**

- streamlink 把“录成什么容器”完全交给用户和 ffmpeg，HIVECAST 是桌面应用，需要给普通用户一个安全的默认值。

### 1.3 biliLive-tools

**录制参数**

- `packages/liveManager/src/recorder.ts:10-104`：
  - `formatName`：`auto|flv|hls|fmp4|flv_only|hls_only|fmp4_only`
  - `videoFormat`：`auto|ts|mkv|flv`
  - `convert2Mp4?: boolean`
  - `segment?: string`
  - `recorderType`：`auto|ffmpeg|mesio|bililive`
- `packages/shared/src/enum.ts:865-903` 默认：`segment:"60"`（60 分钟）、`convert2Mp4:false`、`videoFormat:"auto"`、`recorderType:"ffmpeg"`。

**录制输出**

- `packages/liveManager/src/downloader/FFmpegDownloader.ts:40-65`：`segment` 为数字才分段；`videoFormat=auto` 时不分段输出 `.m4s`，分段输出 `.ts`。
- `:160-189`：固定 `-c copy`，加 `-movflags +frag_keyframe+empty_moov+separate_moof`、`-fflags +genpts+igndts`、`-min_frag_duration 10000000`；分段时 `-f segment -segment_time 3600 -reset_timestamps 1`。
- `docs/features/live-record.md:59-66`：自动=默认 ts，不存在分段时 m4s；可选 MKV/TS/FLV；FLV 分辨率/参数变化会花屏。

**自动转 MP4（录制器链路）**

- `packages/shared/src/recorder/index.ts:199-229` `convert2Mp4(videoFile)`：
  - 输出同目录同名 `.mp4`；
  - 目标已存在直接抛 `目标文件已存在`，不覆盖；
  - `transcode(encoder:"copy", audioCodec:"copy", override:false, removeOrigin:false)`。
- `:532-543` 先把**原文件路径**写进 `recordHistory`，并更新时长、文件名、quick hash。
- `:571-579` 然后才 `await convert2Mp4(filename)`，成功后 `await fs.unlink(filename)`。
- 结果：**数据库和历史记录仍指向已经被删掉的原文件；`finally` 里的 `file_completed` 事件也带原路径。** 如果转换失败，只 `logger.error`，源文件保留，但用户没有可见错误。
- 例子：录完 1 小时 `.ts`，转成 `.mp4` 后删 `.ts`。媒体库记录的 `video_file` 还是 `.ts`；点播放会“文件不存在”。重启后也不会自愈，因为没有“最终路径”字段。

**Webhook 转封装（第二条链路）**

- `packages/http/src/services/webhook/webhook.ts:346-371` `processConversion`：
  - 在弹幕压制/上传/同步之前执行；
  - `removeVideo = config.removeSourceAferrConvert2Mp4 ?? true`（默认删源）；
  - 转换后把 `options.filePath`、`context.part.filePath`、`context.part.rawFilePath` 全部改成 mp4，**原路径直接丢失**。
- `:791-833` `transcode`：
  - 输出同目录 `basename.mp4`；
  - 若目标已存在，**直接返回已有文件，即使 `removeVideo=true` 也不删源**；
  - 否则 `transcode(removeOrigin=removeVideo)`，任务结束时删源，不走引用计数。
- `ConfigManager.ts:161/172/230`：`convert2Mp4` 与“转换后删除源”是两个独立开关；没开转换时删除开关强制 false。
- UI `app/src/renderer/src/enums/recorder.ts:466-469` 明确提示：转封装会删除原始文件；**如使用 Webhook 请用 Webhook 的转封装功能**。等于官方承认两条链路互斥，同时开容易重复处理。

**引用计数删除**

- `packages/http/src/services/webhook/fileRefManager.ts`：
  - `Map<path,{count,shouldDelete}>`；
  - `addRef` 时 `count++`，`shouldDelete = shouldDelete || shouldDeleteOnZero`；
  - `releaseRef` 到 0 且 `shouldDelete` 才 `trashItem`。
- 思路可借鉴：上传、同步、压制等多个消费者共享一个文件时，不要第一个消费者结束就删。
- 但语义有坑：**任意一个消费者要求删，就把整个文件的 `shouldDelete` 置真**；另一个消费者想保留也拦不住。而且 Webhook 转换的删源根本不走这套计数，任务一结束就删。例子：转换任务结束删源，随后上传失败，源已经没了。

**任务失败**

- `packages/shared/src/task/task.ts:137-300` `FFmpegTask`：直接写目标文件；失败只发 `task-error`、释放命令，不删除半成品；`onEnd` 才触发删源。
- `packages/shared/src/task/video.ts:989-1089` `mergeAssMp4`：`onEnd` 才 `trashItem(videoInput)`，`onError` 只清高能进度临时文件。
- 例子：转封装到 60% 磁盘满，目标路径留下半截 MP4；如果 UI 或别的进程误把它当成品，就会播放失败。HIVECAST 必须在临时文件里写，失败就删临时文件。

**自定义命令**

- biliLive-tools **没有任意 post-record shell 命令**。
- 只有 FFmpeg 预设的 `extraOptions`：`packages/shared/src/presets/ffmpegPreset.ts`，`packages/shared/src/utils/index.ts:163-166` 把字符串按空格 `split(" ")` 后逐个 push。
- 这意味着：路径带空格会拆坏；不支持引号、管道、多条命令；只能做转码/压制/裁切，不能做任意命令模板。
- 所以“自定义命令”这一项，biliLive-tools 不能作为参考；bililive-go 有，但安全语义要重做。

**可借鉴**

- 输出已存在时拒绝覆盖（`convert2Mp4` 的 `目标文件已存在`）。
- 用系统回收站 `trashItem`，不是永久 `unlink`。
- 多消费者引用计数的**思路**（不是当前实现）。
- 转换前检查输出是否存在，避免覆盖别人刚生成的文件。

**不能照抄**

- 一条记录只有一个 `video_file`，转换后不更新。
- 转换成功立即 `fs.unlink`，不等数据库、不等其他消费者。
- 录制器与 Webhook 两条转换链路。
- 把 `rawFilePath` 覆盖成转换后路径。
- `extraOptions.split(" ")` 这种伪自定义命令。

### 1.4 HIVECAST 现状

**当前实现**

- `src-tauri/src/recorder.rs:972`：开录前用固定 `"mp4"` 扩展名预占路径；`:1029-1044` 立刻把该路径写进 `record_sessions.file_path`。此时文件只是 0 字节占位，真正写入的是同目录 `.partNNNN.ts`。
- `:2541-2550`：ffmpeg 固定 `-c copy -f segment -segment_format mpegts -reset_timestamps 1`，**录制中间层永远是 MPEG-TS 分片**，不管源是 FLV、HLS 还是 DASH。
- `:1837`：收尾读 `auto_remux`。
- `:1937/:1939`：`finish_range` / `finish_file` 收尾。
- `:2902-2929` `finish_file`：`auto_remux=true` 走 `segment::merge` 合成 MP4；失败或关闭时走 `fallback_concat` 字节拼接成 `.ts`。
- `src-tauri/src/postprocess.rs:180-225`：手动转封装 FLV→MP4，`-c copy -movflags +faststart`，保留源文件。
- `src-tauri/src/settings.rs:98`：`auto_remux` 默认 `true`。
- `src/features/settings/SettingsView.tsx:784-797`：设置页只有“录制结束后自动转成 MP4”一个开关；提示“关闭后保留 .ts 拼接文件”。

**已经做对的部分**

- 录制期间始终一条连续 ffmpeg，不在停止/重启之间丢画面。
- TS 分片 + `finish_range` / `finish_file` 的降级链。
- `SplitManifest` 崩溃恢复：成品完整时复用，分片还在时重试，失败不写 0 字节历史。
- 手动转封装保留源文件。
- 合并用临时文件 + rename，避免直接覆盖成品。

**缺口**

- 没有“源封装成品”概念：FLV 源最终也变成 MP4 或 TS。
- 没有转换目标选择、删除源、自定义命令。
- 设置项是一个布尔值，无法表达“保留源 / 转换 / 自定义”三种意图。
- 数据库只有一个 `file_path`，没有 `source_path` / `post_state`，无法在崩溃后判断“转换做到哪一步”。
- 收尾直接写最终路径；转换失败时靠降级成 TS 兜底，但没有“转换失败但源完整”的显式状态。
- 开录占位扩展名固定 `.mp4`，与实际产物可能不一致；媒体库在录制中可能展示一个尚不存在的 MP4。

## 3. 目标模型

### 3.1 两个产物，不是两个入口

每场录制最终最多有两个文件：

1. **源封装母带（source）**：录制器封口后产出的、与直播源容器对应的文件。它是“证据/母带”，默认保留。
2. **派生文件（derived）**：用户选择 MP4/MKV/MOV 或自定义 FFmpeg 产出的文件。它可以被删除、重做，不影响母带。

数据库同时记录两者；媒体库一张卡展示一场，卡内列出两个文件。**永远不覆盖源路径，永远不把源路径改写成派生路径。**

### 3.2 容器映射

内部仍然用 MPEG-TS 分片做崩溃恢复的“保险丝”，收尾时按首段实际源格式重封装成母带：

| 源格式 | 编码 | 母带容器 | 说明 |
| --- | --- | --- | --- |
| FLV | H.264 + AAC | `.flv` | 最常见的 B 站/斗鱼/虎牙 FLV 源；`-c copy` |
| FLV | H.265 / AV1 | `.mkv` | FLV 对 HEVC/AV1 兼容性差；MKV 无损承载，UI 标注“源封装不适合该编码，已用 MKV 无损封装” |
| HLS | 任意 | `.ts` | HLS 本质就是 MPEG-TS 分片 |
| HTTP-TS | 任意 | `.ts` | 同上 |
| DASH / fMP4 | H.264/H.265/AV1 | `.mp4` | fMP4 源，MP4 是原生容器 |
| AudioOnly | AAC | `.m4a` | 只录音；非 AAC 用 `.mka` |
| 未知 / 重封装失败 | 任意 | `.ts` | 最稳的兜底，保证“有成品” |

**必须说清楚的区别：**

- 这是**容器重封装**，不是字节级原始流。编码数据 `-c copy` 不变，但时间戳、FLV header、TS PAT/PMT 会重写。
- 如果用户要求“和上游 CDN 拉下来的字节完全一致”，那需要另做“直录源容器”管线：分片也保持源容器，收尾只做拼接/索引，不重封装。当前架构不保证 bit-exact。
- 第一版不改成直录，因为 TS 分片是现有崩溃恢复、分割、续录的基础；先保住稳定性，再谈 bit-exact。

### 3.3 三种互斥模式

| 模式 | 默认 | 产物 | 删除源 | 自定义命令 | 适用 |
| --- | --- | --- | --- | --- | --- |
| `source` 保留源封装 | 新安装默认 | 母带本身 | 不动 | 不执行 | 想要原始容器、后续手动处理 |
| `convert` 转换容器 | 老用户 `auto_remux=true` 迁移目标 | 母带 + MP4/MKV/MOV | 可选，默认关 | 不执行 | 想要直接能拖进剪辑软件的 MP4 |
| `custom` 自定义命令 | 不默认 | 母带 + 自定义输出 | **永不自动删** | 执行 | 需要转码/压制/裁切等高级处理 |

互斥规则：

- 选了 `custom`，内置转换与“删除源”全部隐藏/禁用；开启自定义就关闭 1/2，符合用户原始要求。
- 选了 `convert`，自定义命令字段保留但不执行；UI 明确“切到自定义才会执行”。
- 选了 `source`，后处理不跑；媒体库手动“转封装”仍然可用，且**手动操作永远保留源**。

### 3.4 状态机

```
recording
  └─ sealing（停 ffmpeg、等分片写完）
       └─ sealed（母带已生成并通过 ffprobe）
            ├─ mode=source ──────────────────────────┐
            ├─ mode=convert → posting（写临时文件）   │
            │                   └─ validating（ffprobe）│
            │                        ├─ fail → failed（源保留，临时文件删除）
            │                        └─ ok → committing（rename + DB 事务）
            └─ mode=custom  → posting（写临时文件）   │
                                └─ validating（同上） │
                                                     ▼
                                                   done
                                                     │
                                      delete_source? ├─ no → done（源保留）
                                                     └─ yes → trashing（回收站）
                                                                ├─ ok → done（源已删）
                                                                └─ fail → done（源仍在，提示可重试）
```

关键顺序：

1. **先封口母带**，再谈转换。母带没生成，不启动任何后处理。
2. **临时文件写在与目标同目录**，成功后 `fsync` + rename；失败只删临时文件。
3. **校验通过才提交 DB**。ffmpeg 退出码 0 不等于文件完整；必须 `ffprobe` 检查流、时长、大小。
4. **DB 提交后才删源**。顺序是“rename → DB 事务 → 回收站”，不是“转换 → 删源 → 更新 DB”。
5. **删源失败不算转换失败**。派生文件已经可用，源还在只是多占空间；状态写 `done` + `source_deleted=0`，给“重试删除”入口。

### 3.5 失败与幂等

| 失败点 | 现场 | 恢复动作 |
| --- | --- | --- |
| 母带合并失败 | 分片还在、母带 0 字节 | 保留清单与分片，启动后重试；不写历史 |
| 转换 ffmpeg 失败 | 源完整、临时文件半截 | 删临时文件；`post_state=failed`；源保留；可重试 |
| 校验失败 | 源完整、临时文件完整但无流/时长异常 | 删临时文件；报“转换结果不完整”；源保留 |
| rename 失败 | 临时文件完整、目标不可写 | 保留临时文件；报错；源保留；下次启动可重试 rename |
| DB 提交失败 | 目标文件已 rename、DB 仍旧 | 清单记录目标路径；启动时校验并补提交；绝不删源 |
| 删源失败 | 派生完整、源仍在 | `done` + 提示“源文件仍在，可重试删除”；不报转换失败 |
| 转换中崩溃 | 临时文件 + 清单 | 启动时删临时文件，按清单从 `sealed` 重跑 |
| 删源后崩溃 | 派生完整、源已进回收站 | DB 已提交；启动时只补 `source_deleted=1` |

幂等原则：

- 目标文件已存在且通过校验：直接复用，不覆盖。
- 目标文件存在但校验失败：改名到 `.corrupt-<timestamp>` 保留现场，再重跑；不静默覆盖。
- 同一场同一模式只允许一个后处理任务；重复请求返回现有任务状态。
- 应用启动时扫描 `.hivecast-post-*` 临时文件：有清单引用的保留，无引用的超过 24 小时删除。

### 3.6 空间与并发

- 转换前检查剩余空间：`free >= source_size * 1.15 + 256 MiB`；不足直接失败，提示“需要约 X GB，当前 Y GB”，不启动 ffmpeg。
- 转换期间峰值约为“源 + 临时文件”；母带校验通过后即可删分片，避免“分片 + 源 + 临时”三份。
- 后处理默认并发 1；最多 2，避免多场同时转封装把磁盘打满。录制优先级高于后处理：磁盘紧张时暂停后处理队列。
- 删除源用系统回收站（`trash` crate），不用 `std::fs::remove_file`。Windows 文件被播放器/杀软占用时，删源失败要可重试，不能强删。

## 8. 明确不做

- **不做“录制器直接转 MP4”**：录制器只封母带，转换是后处理。
- **不做两条转换链路**：没有 Webhook 转封装，也没有“录制器转换 + 手动转换”两套代码；只有一个 orchestrator。
- **不做 shell 自定义命令**：只执行 ffmpeg，argv 直传；不支持管道、重定向、多条命令。
- **不做永久删除**：删源只进系统回收站；删整场也优先用回收站，除非用户明确清空。
- **不做静默覆盖**：目标存在必须校验/改名，不覆盖。
- **不承诺 bit-exact 原始流**：母带是容器重封装；需要字节级原流时另立直录管线。
- **不把“转换失败”当“录制失败”**：母带完整就是录制成功；后处理失败只影响派生文件。

## 9. 需要拍板的三件事

> **已拍板（m29073）**：不做老用户迁移；FLV + HEVC/AV1 用 `.mkv`；自定义命令用完整 ffmpeg argv 模板、必须含 `{input}`/`{output}`、不走 shell、源永不自动删。实际实现见 [78](78-录制后处理实现与验收.md)。以下保留决策过程。

1. **老用户 `auto_remux=true` 怎么迁？**
   - A（推荐）：保留老结果，迁成 `convert/mp4/delete_source=true`，用回收站；升级提示一次。
   - B：统一迁成 `source`，所有人默认源封装；老用户会发现不再自动出 MP4。
   A 更不 surprise，B 更符合“新默认”。我倾向 A，但需要你确认。
2. **FLV + HEVC/AV1 的母带容器？**
   - A（推荐）：`.mkv`，兼容性最好，UI 说明“源封装不适合该编码”。
   - B：`.ts`，更接近“源封装”，但部分剪辑软件对 TS 支持一般。
3. **自定义命令的边界？**
   - A（推荐）：完整 ffmpeg 参数模板，必须含 `{input}`/`{output}`，不经过 shell，源永不自动删。
   - B：只允许“额外参数”，输入输出由应用固定，最安全但表达能力弱。
   A 能满足转码/压制/裁切；B 更简单。需要你选一个。

确认这三项后，按 P0→P3 开发；P0 完成即可先让“默认源封装”上线，不阻塞后续转换/自定义。
