## 0. 结论速览

- **已按推荐口径落地，不需要新子系统。** 录制侧沿用 `DanmakuHub → WebSocket → RecordWriter → JSONL`，只增加四个设置字段、开录门禁、写入器过滤与设置页一个入口。
- **全局唯一入口。** 设置 → 录制与媒体 → 弹幕录制。观看端每个播放槽的「弹幕」开关控制画面叠加，媒体库「导出弹幕 ASS」消费已有 JSONL，均不与本设置合并。
- **最终语义：总开关管整场，三个子开关管事件。** 总开关关闭 = 本场不挂录制 writer、不产生 JSONL、不自动导出 ASS；子开关关闭 = 只过滤对应 `kind`，`chat` 与未知事件始终保留。
- **已裁决（m33206）：** Q1=A 总开关=全部弹幕；Q2=A 礼物保持全记（含免费/连击）；Q3=A 舰长只消费 `GUARD_BUY`，不处理续舰；Q4=A 新增独立「弹幕录制」页。
- **评审时识别的最危险缺陷均已处理：** 过滤放在 `RecordWriter` 内，不影响观看端；无 writer 时 DB 不再写假路径；优雅收尾时 0 条事件的 JSONL 会被删除；`attach_record` 两条失败路径都补了 `release`。

## 3. 逐条评审

### 3.1 录制弹幕总开关

**结论：可行，建议做。** 关闭时从源头上不挂录制写入器，而不是「挂上再全部丢弃」。

推荐行为：

1. 自动开录/手动开录都会读一次设置（`recorder.rs:925` 已有快照），总开关关闭时跳过 `attach_record`；
2. 即使观看端正在看同一个房间，观看端照常收弹幕，只是没有录制侧 writer；
3. 没有观看者时，因为录制侧也不 `retain`，这条房间的 WS 根本不会建立；
4. 不生成 `.jsonl`，`danmaku_count=0`，收尾不自动导出 ASS；
5. 已存在的旧录像不受影响，媒体库仍能播放/导出旧弹幕。

为什么不能「挂 writer 再全丢」：会创建空文件、占用一个 WS 引用，而且之后必须靠收尾逻辑清理；直接在门禁处不挂更简单，也不会出现「DB 有路径、磁盘没文件」。

边界：

- 总开关关闭时，三个子开关在 UI 上置灰但**保留值**。用户重新打开总开关后，之前的细项选择还在。
- 总开关只影响**新会话**。正在录的这一场不换档（与现有 A3 约束一致），UI 要写清楚。

### 3.2 礼物 / SC / 舰长三个开关

**结论：可行。** 三个开关分别对应 `kind`：

| UI | kind | 哪些平台会产出 | 关闭后的效果 |
| --- | --- | --- | --- |
| 礼物消息 | `gift` | B 站 `SEND_GIFT`、斗鱼 `dgb`、虎牙 6501、抖音 `WebcastGiftMessage` | 录制 JSONL 不写礼物；观看端仍显示 |
| 醒目留言（SC） | `super_chat` | 仅 B 站 `SUPER_CHAT_MESSAGE` | 录制 JSONL 不写 SC；观看端仍显示 |
| 上舰消息 | `guard` | 仅 B 站 `GUARD_BUY` | 录制 JSONL 不写上舰；观看端仍显示 |

**平台差异只做说明，不做分支。** 设置是全局的：用户在 B 站房间关掉 SC，之后添加斗鱼房间，SC 开关仍然是关的，但斗鱼本来就没有 SC，不报错、不置灰。这样避免「切平台设置变一套」的认知负担。

**普通聊天永远保留。** 三个子开关不控制 `chat`。这样「关礼物」不会把整场弹幕变成空文件，也符合「礼物/SC/舰长是附加事件」的直觉。

如果用户真正想要的是「只录礼物、不录聊天」，当前语义做不到，需要把总开关拆成「普通弹幕」+ 三个事件（见 Q1）。这是本需求唯一需要先确认的语义分叉。

### 3.3 过滤必须放在 RecordWriter

**结论：放在 `RecordWriter::push`，不能放在 `DanmakuHub::fan_out`。**

原因：`DanmakuHub` 同时服务观看端和录制端。消息进入 `ingest` 后先调 `conn.fan_out(&message)`（`danmaku.rs:597`），紧接着 `batch.push(message)`，最后由 `flush` 发给观看端（`:601-610`）。如果在 `fan_out` 之前或 `ingest` 里按 kind 过滤，观看端的 batch 也会少消息，出现「用户关掉礼物录制，结果看直播也看不到礼物」。所以过滤只能放在 writer 内部，不能上移到连接层。这是最容易被误实现的一处。

推荐结构：

```rust
#[derive(Clone, Copy)]
pub struct RecordRules {
    gift: bool,
    super_chat: bool,
    guard: bool,
}

impl RecordRules {
    fn allows(&self, kind: &str) -> bool {
        match kind {
            "gift" => self.gift,
            "super_chat" => self.super_chat,
            "guard" => self.guard,
            // chat 和未来新增 kind 默认放行，避免升级后静默丢数据
            _ => true,
        }
    }
}
```

`RecordWriter::new(path, rules)` 保存一份**不可变**规则；`push` 第一行 `if !self.rules.allows(&message.kind) { return; }`。每个录制会话在开录时从 `Settings` 生成规则，录制中改设置不影响本场。

> 实现命名说明：评审时叫 `DanmakuFilter`，落地为 `RecordRules`（`src-tauri/src/danmaku.rs`），字段与判断逻辑一致。

未知 kind 放行是刻意选择：以后加「进场」「关注」等事件时，老版本不会因为不认识就丢掉；要过滤再显式加分支。

### 3.4 设置页落点

**结论：只加一个入口，建议新增「弹幕录制」页，放在「录制与媒体」组。**

理由：

- 录制页已经有 6 个 Section（流、观看画质、分割、并发、监控、后处理），再加 4 行会把「后处理」挤到很下面；独立页更清楚。
- 弹幕录制和「录制与观看」强相关，放同一组，不新增顶级分类。
- **不要**在录制页再放一份相同开关，也不要在每个房间卡片上放房间级开关；那就是「多余入口」。

页面结构：

```text
设置
  账号
  录制与媒体
    录制与观看
    存储
    弹幕录制   ← 新增
  应用
    通知
    外观
    系统
    关于
```

页面内容：

- Section「录制范围」：Switch「录制弹幕」，说明「关闭后本场不生成弹幕文件，也不自动导出 ASS」。
- Section「事件」：
  - Switch「礼物消息」，说明「B 站、斗鱼、虎牙、抖音」；
  - Switch「醒目留言（SC）」，说明「仅 B 站」；
  - Switch「上舰消息」，说明「仅 B 站；当前只记录新开通，续舰暂不记录」。
- 底部提示：「修改后对下一场录制生效，正在录制的场次保持不变。」
- 总开关关闭时，三个子 Switch 设 `disabled`，但保留原值；不要清零。

i18n 英文统一用「Danmaku」，与现有 `en-US.json` 一致；不要新造「bullet chat」。

### 3.5 Windows / macOS 兼容性

**结论：没有平台专属代码，但必须两边各跑一次。**

- 过滤是纯 Rust 字符串匹配，不涉及系统 API；设置仍然写同一个 SQLite 的 `app_setting` 表。
- 不调用 shell、不新增依赖，也不碰路径分隔符；JSONL 路径仍由视频路径 `with_extension("jsonl")` 得到。
- 唯一需要留意的是 Windows 的文件占用：录制中如果用户用编辑器打开 JSONL，可能影响删除/改名（取决于编辑器的共享模式）。当前收尾是 `finish` 取走并关闭文件后再清理 0 字节文件，不会自己锁自己。
- Windows 验收至少覆盖：四个开关保存后重启仍在、开录生成 JSONL、关闭总开关不生成、路径含中文/空格时正常。

1. `Settings` 结构体加 4 个字段（camelCase 序列化自动生效）；
2. `settings.rs` 加 4 个 key 常量、`defaults()`、`load()`、`save()`；
3. `settings.rs:628` 附近的 `Settings` 结构体字面量补 4 个字段；

5. 设置页的 `patch` 走全量 `settingsUpdate`，新字段自动带上，不需要单独命令。

## 5. 运行时改造点

### 5.1 开录门禁

`recorder.rs:1022-1031` 原来无条件 `attach_record`，现在总开关与平台支持一起决定是否挂载：

```rust
let danmaku = self
    .danmaku
    .as_ref()
    .filter(|_| settings.record_danmaku && crate::danmaku::supports(room))
    .and_then(|hub| {
        hub.attach_record(
            room,
            &danmaku_path,
            crate::danmaku::RecordRules::new(
                settings.record_danmaku_gift,
                settings.record_danmaku_super_chat,
                settings.record_danmaku_guard,
            ),
        )
    });
let danmaku_path_text = danmaku.as_ref().map(|_| danmaku_path.display().to_string());
```

注意 `settings` 是 `recorder.rs:925` 已加载的那一份，不要在这里重新 `load`，否则同一场会出现「视频用旧设置、弹幕用新设置」的撕裂。`danmaku_path_text` 同时用于建会话与 `Active`，无 writer 时必为 `None`。

### 5.2 收尾路径修正（必须一起做）

现在 `recorder.rs:1098` 无条件写：

```rust
danmaku_path: Some(danmaku_path.display().to_string()),
```

总开关关闭、或 `attach_record` 失败时，这里会留下一个不存在的路径；`:2087-2093` 在 detach 失败/无 writer 时又回退 `active.danmaku_path`，最终 `:2107` 把它写进 DB。后果是 DB 里留下假路径：导出命令会报「这段录像没有弹幕文件」，按路径清理/定位的逻辑也会空跑。媒体库因为 `danmakuCount=0` 不会显示导出按钮，所以问题更隐蔽。

修正三处：

1. 建会话时用 `danmaku.as_ref().map(|_| danmaku_path.display().to_string())`，无 writer 时写 `None`；
2. 收尾的 `(Some(hub), Some(writer))` 分支里，`detach_record` 返回 `None` 时用 `(None, 0)`，不回退任何旧路径；
3. `detach_record` 在 `count == 0` 时删除 JSONL 并返回 `None`，避免 0 字节文件进入媒体库。

**实际实现进一步删掉了 `Active.danmaku_path` 字段**：收尾既然只信 `detach_record` 的返回值，就没有任何地方需要这条缓存；留着只会诱使后来的人再写回假路径。

### 5.3 顺手修 attach 的引用泄漏

`danmaku.rs:186-210` 先 `retain`，如果 `RecordWriter::new` 失败直接 `return None`，没有 `release`；`:204` 取不到 `conn` 时也会 `?` 返回，同样泄漏。每失败一次，房间引用计数就多 1，停录后 WS 不关闭。

建议：

- `RecordWriter::new` 失败：`self.release(&room.id)` 后返回 `None`；
- 取不到 `conn`：先释放 `rooms` 锁，再 `self.release(&room.id)`，返回 `None`（不要在持有 `rooms` 锁时调用 `release`，会死锁）。

这是既有问题，但本次要改 `attach_record` 签名，顺手修掉成本最低。

## 7. 测试与验收

### 7.1 单测

- `RecordRules::allows`：全开、单关礼物、单关 SC、单关舰长、未知 kind 放行、`chat` 永远放行。

## 11. 实施记录（v1.0）

### 11.1 设置与兼容

- `Settings` 新增四个布尔字段：`recordDanmaku`、`recordDanmakuGift`、`recordDanmakuSuperChat`、`recordDanmakuGuard`（`src-tauri/ipc-types/src/lib.rs`）。
- 持久化 key：`record.danmaku`、`record.danmaku_gift`、`record.danmaku_super_chat`、`record.danmaku_guard`。
- 默认值全 `true`；旧库没有这些键时 `load()` 回落默认，不做 schema 迁移。新增 `danmaku_defaults_to_on_for_missing_keys` 锁住这个兼容行为。
- `save()` 每次都写四个键；前端保存走现有全量 `settingsUpdate`，无需新 IPC。

### 11.2 开录门禁与收尾

- 开录时只有 `settings.record_danmaku && danmaku::supports(room)` 才调用 `attach_record`；四个平台支持判断未改。
- 传给 writer 的 `RecordRules` 来自开录瞬间的设置快照，录制中改设置只影响下一场。
- 无 writer 时建会话写 `danmaku_path = NULL`，`Active` 不再保存该字段；收尾只信 `detach_record` 的返回值，绝不回退旧路径。
- 自动 ASS 仍只在 `danmaku_count > 0` 且路径存在时触发，因此总开关关闭不会自动生成 ASS。

### 11.3 写入器过滤

- `RecordRules { gift, super_chat, guard }` 的 `allows()` 只过滤这三个 kind；`chat` 与未知 kind 默认保留。
- 过滤发生在 `RecordWriter::push` 第一行，位于 `fan_out` 之后；观看端仍收到全部事件，只有录像 JSONL 少事件。
- `finish()` 在 `count == 0` 时删除 JSONL；`detach_record` 对 0 条返回 `None`，DB 不会登记空文件。
- `attach_record` 在创建 writer 失败、取不到房间连接两条路径都会 `release`，修复原有 WS 引用计数泄漏。

### 11.4 设置页

- 「录制与媒体」组新增「弹幕录制」页，侧栏、页面标题、搜索索引各一处入口，无房间级/平台级开关。
- 总开关关闭时三个事件开关置灰但保留原值，重新打开总开关不会丢配置。
- 文案明确：只影响之后开始的录制、观看实时弹幕不受影响、礼物含免费/连击、SC/舰长仅 B 站、v1 只消费 `GUARD_BUY`。
- i18n 中英各新增 16 个 key；`check:i18n` 为 597 keys。

### 11.7 已知限制

- **只对下一场生效**：录制中改开关不会重建 writer，本场 JSONL 保持开录时的规则。
- **续舰未接入**：只消费 B 站 `GUARD_BUY`；续舰若走其它事件（如 `USER_TOAST_MSG`）不会出现在录像里。
- **礼物不聚合**：免费礼物与连击逐条记录，长直播可能让 JSONL 偏大；P2 再考虑合并。
- **ASS 跟随 JSONL**：关掉的事件不会进自动 ASS；这是「录像保存哪些事件」的自然结果。
- **崩溃残留**：优雅停录会删 0 字节 JSONL；应用被强杀/断电时仍可能留下空文件，启动清扫未纳入 v1。
- **Windows 未真机**：过滤是纯 Rust，路径仍走 `with_extension`，但只做了编译级验证，未在 Windows 实际录制。
