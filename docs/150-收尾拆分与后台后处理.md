# 150 · 收尾拆分与后台后处理

> 范围：`src-tauri/src/recorder.rs` 的停录收尾链路（`finalize` / `finalize_active` / `FinalizeGuard`）。
> 结论：**封口（合并分片、切片段、结算房间级状态、摘弹幕）完成后立即释放 `finalizing`，后处理在释放之后继续跑；同一房间可以在旧场后处理还没结束时开新场。**
> 时间：2026-11-13；基线：`9e2713d` + 本次改动。

---

## 1. 旧问题

旧实现里 `finalize_active` 从头到尾都在 `FinalizeGuard` 的生命周期内：

```text
finalize
  └─ 插入 finalizing
      └─ finalize_active
          ├─ 合并分片 / 切片段
          ├─ 跑后处理（转封装 / 自定义 ffmpeg，可能几分钟）
          ├─ 写 DB、切弹幕、导出 ASS、缩略图
          └─ Drop FinalizeGuard → 移除 finalizing
```

后处理是这里最慢的一步。它没结束时，同一房间：

- `start_checked` 会看到 `is_finalizing(room_id)`，自动录制被拒；
- 手动开录也被同一条检查拦住；
- 监控每个 tick 继续尝试，形成「上一场正在收尾」的连续失败；
- 下播后很快重开、或画质升级换容器时，新场要等旧场编码完才能开始，直接丢开头几分钟。

后处理本身并不需要「占用房间」：它只操作已经落盘的源文件，不读直播流，也不改这个房间的采集状态。把房间锁在后处理上是用错了临界区。

---

## 2. 新的边界

`finalize_active` 现在明确分成两段：

| 阶段 | 是否持有 `finalizing` | 做什么 |
| --- | --- | --- |
| 封口 | 是 | 按 `ClipPlan` 合并分片 / 切出片段；记录 `PreparedClip`；写 split manifest；0 字节改判；`mark_ended`；未确认结束与硬失败计数；摘弹幕 writer；清连续失败冷却 |
| 后处理 | 否 | 逐片段跑 `post::run`；写 DB（首段 `finish_session_with_post`、后续 `create_clip`）；切 JSONL；导出 ASS；缩略图；保留策略；通知 |

封口结束、`drop(finalizing_guard)` 之后打一条：

```text
INFO 封口完成，释放收尾标记并转入后台后处理 room_id=... session_id=... clips=...
```

后处理仍在原来的 `finalize_active` 任务里串行执行，没有另起一个游离任务；区别只是它不再持有 `finalizing`。这样既能让新场立刻开始，又保留原来的顺序、取消作用域与崩溃恢复入口。

### 2.1 为什么房间级副作用要提前到释放前

这些状态描述的是「这一场直播已经结束」，不是「文件已经处理完」：

- `mark_ended`：房间的 `live_started_at` 要清掉，否则新场会被当成同一场；
- `note_hard_failure` / `clear_failure` / `clear_hard_failure`：连续失败冷却与硬失败计数按「场」结算；
- `detach_record`：弹幕 writer 必须在这场结束时摘掉，不能等编码完；
- `empty_recording_failure`：0 字节要在封口后立刻判定，不能因为后处理失败而掩盖。

如果在释放后再做，新场可能已经插入 active，旧场的收尾会误改新场的房间状态。因此这些副作用统一在封口阶段、释放之前完成。

### 2.2 后处理失败不再影响房间可用性

封口阶段已经把「这场录到了什么」定下来。后处理失败只会让该片段的 `post_state=failed`、保留源封装母带，并在 DB/媒体库里显示失败原因；不会重新把房间锁住，也不会回滚已完成的封口。

## 4. 已知限制

1. **旧场在后处理全部结束前仍显示为录制中。** DB 写入仍在后处理之后，期间 `record_session.status=recording`、`file_path` 为空；媒体库看不到这一场。崩溃恢复依赖 split manifest，能在下次启动补完。若要让媒体库更早看到，需要把 DB 写入再前移成「先登记 processing、后处理完再更新」，这是下一步可做的优化。
2. **后处理仍串行。** 同一场的多个片段逐个跑；不同场共用自动后处理槽位，本次实测第二场先拿到槽位、第一场 clip1 排队 10 分钟才开跑。新场开录不受影响，但编码队列可能变长；排队时间不计入自定义超时，只有真正开始编码后、连续 600 秒未退出才会超时。
3. **退出仍会等后处理。** `shutdown_all` 逐会话 `await finalize`（包含后处理），退出时可能等当前编码结束；这与本次拆分无关。
4. **崩溃恢复窗口变大。** 封口完成后、DB 写入前如果进程退出，靠 manifest 恢复；manifest 在封口阶段已经写好，恢复逻辑沿用原路径。

## 5. 类似问题审计

| 位置 | 是否同类 | 结论 |
| --- | --- | --- |
| 画质升级换容器 | 否 | 已经是「先开新会话，再 `spawn` 收旧场」，不等待旧场后处理 |
| `recheck_quality` / `upgrade_locks` | 部分 | 持锁跨网络与重启，但只串行同一房间的升级请求，不阻塞普通开录；未改 |
| `shutdown_all` | 是（退出路径） | 逐会话等待 finalize（含 post），退出会慢；属于可接受的退出语义 |
| `recover_split_manifest` | 是（恢复路径） | 启动时逐片段重跑 post，可能拖慢启动后的可用性；失败会保留 manifest 等下次再试 |
| `post::run` 槽位等待 | 否 | 等待槽位不持有房间 `finalizing`；新场可开录 |

本次只改日常停录收尾的临界区，不扩大改动范围。

## 7. 改动清单

- `src-tauri/src/recorder.rs`
  - `FinalizeGuard` 变量改为可显式 `drop` 的 `finalizing_guard`；
  - 新增 `PreparedClip`；
  - `finalize_active` 拆为封口 / 后处理两段；
  - 房间级副作用提前到封口段；
