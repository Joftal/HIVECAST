# 任务中心历史虚拟化、时间线窗口与跨 Run 检索导出

> 状态：实现、单测、release 构建与真机验收完成（2026-11-22）。承接 [189-任务中心事件分页与历史压力](189-任务中心事件分页与历史压力.md)。
> 本轮范围：收口 189 第 5 节剩余的四项——历史 1000 行虚拟化、事件时间线按 200 条窗口化、跨 Run 事件检索与 CSV 导出、并发收尾重试的真实互斥证据。

## 1. 结论

四项都已完成。历史表只渲染视口附近的 8 行左右，加载 1000 场后 app RSS 仍为 30,560 KB、CPU 0.4%；事件时间线在 200 条一页之外再加 200 条窗口，2100 条事件翻到最早也不会一次渲染全部；跨 Run 检索能查到不在历史窗口内的场次，CSV 导出按当前筛选条件写全部命中（上限 50,000 条），房间号列已从内部主键改为平台房号；收尾重试锁补了两线程同时抢锁的单测。

| 项目 | 本轮之前 | 本轮之后 |
| --- | --- | --- |
| 历史 1000 行 | 1000 个 tr 全部挂载 | 按 420px 视口 + 上下各 8 行 overscan 只渲染可见行 |
| 时间线翻页 | 200 条一页，翻到 2000 条时整段渲染 | 每页仍 200 条，但只渲染当前 200 条窗口，提供「较新 / 加载更早」 |
| 跨 Run 检索 | 只能看当前屏/history 窗口 | 独立检索 dialog，按消息/阶段/主播/标题查全库 |

| 收尾重试锁 | 单测覆盖同线程与不同清单 | 增加两线程 Barrier 抢同一清单，断言只有 1 个成功 |

## 2. 历史虚拟列表

实现位置：src/features/tasks/TasksPage.tsx。

- 常量：HISTORY_PAGE = 100、HISTORY_MAX = 1_000、HISTORY_VIEWPORT = 420、HISTORY_ROW = 56、HISTORY_OVERSCAN = 8。
- historyStart = max(0, floor(scrollTop / 56) - 8)，historyEnd = min(len, ceil((scrollTop + 420) / 56) + 8)，visibleHistory = historyRuns.slice(start, end)。
- 表格前用一个高度 historyStart * 56 的空 tr 占位，表格后再用一个 (len - end) * 56 的空 tr 占位，滚动条长度与真实 1000 行一致。
- 滚动容器 max-h-[420px] overflow-auto，表头 sticky top-0。
- 「加载更多历史」仍是每次 +100、最多 1000；达到 1000 后按钮换成「最多显示最近 1000 场」。

真机：加载到 1000 场后，表格只渲染当前视口约 7 行；用 agent-desktop mouse-wheel 从 11/21 08:08 滚到 11/20 18:42，行内容连续无空白；应用 RSS 30,560 KB、CPU 0.4%。

## 3. 事件时间线窗口化

- 数据仍走 189 的 task_event_page：200 条一页、(at,id) 游标向前翻。
- 新增 timelinePage 与 TIMELINE_PAGE_SIZE = 200：已加载事件按 200 条切页，只渲染当前页，顶部提供「加载更早的事件」（继续向后端取一页）与「较新 / 更早」（在本地区间翻页）。
- 计数文案从「第 1–200 条 · 共 200 条」改为「第 1–200 条 · 已加载 200 条」，避免把已加载数量误当成真实总数。
- 窗口只影响渲染，不丢数据；已加载 2100 条时仍可逐页回看，DOM 中最多 200 条事件。

真机：event-head 2100 条事件初次显示 #1900..#1904 和「第 1–200 条 · 已加载 200 条」；点「加载更早的事件」变为 400 条、#1700..#1704；点「较新」回到 #1900..#1904，计数变为「第 201–400 条 · 已加载 400 条」。连续点 10 次可翻到 #0，无重复、无断档。

## 4. 跨 Run 检索与 CSV 导出

### 4.1 检索

src-tauri/src/db.rs:1783 task_event_search(query, only_failed, platform, limit)：

- 联表 task_event、record_session、room，因此能带出平台、房号、主播、标题；
- 查询词对消息、阶段、任务类型、主播、直播间标题做 LIKE，并转义百分号、下划线、反斜杠，避免用户输入被当成通配符；
- only_failed 同时匹配 failed/interrupted；
- 结果按 at DESC, id DESC 返回，页面只显示最近 200 条，但总数单独返回。

前端 EventSearchDialog 提供平台筛选、仅失败/中断开关、250ms 防抖搜索和「录制文件」跳转。真机输入 注入事件 #123 得到 11 条（#1239、#1238...），与 2100 条总库中的子串命中一致。

### 4.2 导出

src-tauri/src/commands.rs:3157 task_events_export：

- 按当前查询、平台、仅失败条件重新查库，上限 50,000 条，不导出 UI 当前 200 条；
- 文件带 UTF-8 BOM，Excel 直接打开中文表头不乱码；
- 列：时间、平台、房间号、主播、直播间标题、阶段、状态、进度、消息、任务、Run；
- 房间号优先 TaskEventHit.room_key（平台房号），为空才回退 room_id（本地主键）。本轮修复了此前导出 fixture-room 而不是 888888 的问题；
- 超过 50,000 条时写 warn 日志，只导出最近 50,000 条。

真机：搜索 注入事件 #123 → 导出 CSV，文件 2,100 B、12 行（1 行表头 + 11 行数据），表头与预期一致，房间号列为 888888，主播 我不是来吐槽，消息 注入事件 #1239...。

## 5. 并发收尾重试

原锁 FINALIZE_RETRYING 以 manifest 字符串为 key，acquire_finalize_retry 返回 FinalizeRetryLease，Drop 释放。新增单测 recorder::tests::finalize_retry_lock_serializes_two_threads：

- 两个线程用 Arc<Barrier> 同时起跑抢同一 manifest；
- 抢到的线程持有 100ms 再释放；
- 断言两个线程中恰好 1 个成功。

结果：437 tests 全部通过，该用例通过。

真机边界：任务页的 busyId 在第一次点「重试收尾」后会把所有重试按钮置灰，所以单窗口 UI 无法同时触发两次；顺序点第二个按钮会得到 TIMEOUT ... live enabled state is false，这正说明产品层也在串行保护。因此本轮不能声称「真机同时并发」，只能给出「UI 串行 + 两线程单测互斥」的证据。跨进程同时开两个 app 不在当前单实例设计内，锁是进程内的。

## 7. 边界与未做

1. 历史仍是最近 1000 场上限；更早的场次只能靠检索事件或直接查库，没有「历史全量」入口。
2. 单场事件仍要逐页加载，2100 条需点 10 次「加载更早的事件」；每次约 1–4 秒，没有跳页或按时间定位。
3. 检索页只展示最近 200 条命中，导出最多 50,000 条；没有检索结果分页。
4. 收尾锁是进程内锁，不防两个 app 进程同时操作同一 manifest；应用未声明单实例。
5. 时间线窗口只减少 DOM，不减少已加载到内存的事件数；超长任务（>2000 条）仍需用户主动翻页。
6. 历史虚拟化的行高固定 56px；若以后卡片支持多行备注，需要同步调整 HISTORY_ROW。
