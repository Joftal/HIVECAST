# 03 · 架构对比与设计取舍

> 目的：把三个参考项目（bililive-go / streamlink / biliLive-tools）的"同一个问题、不同解法"摆在一起，明确 HIVECAST 抄什么、不抄什么、为什么。
> 三者逐项对照的完整体检表在 `18-三项目横向对照速查`；biliLive-tools 的实现细节在 `17`。本文只保留与决策相关的部分。

## 1. 一句话定位差异

| | bililive-go | streamlink | biliLive-tools |
| --- | --- | --- | --- |
| 形态 | 常驻服务 + Web UI（也有 CLI 模式） | 库 + 一次性 CLI | Electron 桌面应用 + 内嵌本地 Koa 服务 |
| 生命周期 | 长期运行，轮询、重连、定时分段 | 一次调用，取到流就交给播放器/文件 | 长期运行，随桌面应用存活 |
| 关注点 | **状态**：谁在播、录没录、文件在哪、后处理到哪一步 | **数据**：怎么把 m3u8/mpd/直链变成字节流 | **闭环**：取流→录制→弹幕→转码→上传/同步全链路 |
| 扩展方式 | 平台适配器（`live.Live` 实现 + `init()` 注册） | 站点插件（`Plugin` 子类 + matcher） | 平台解析器（`PlatformParser`）+ 录制器（`RecorderProvider`），两层分开 |
| 语言/生态 | Go 单二进制，依赖 FFmpeg | Python，依赖 FFmpeg（可选） | TypeScript/pnpm monorepo，Electron + Vue3，依赖 FFmpeg |
| 许可 | MIT | BSD-2-Clause | **GPL-3.0-only**（只读设计，不拷代码） |

HIVECAST 是**桌面端**：既要 bililive-go 的"状态与编排"，也要 streamlink 的"取流与缓冲"，产品形态上则与 biliLive-tools 最接近。所以文档按"编排 / 取流 / 桌面闭环"三段组织。

## 2. 逐项对照

### 2.1 平台适配

| 维度 | bililive-go | streamlink | HIVECAST 取舍 |
| --- | --- | --- | --- |
| 匹配 | 域名 → builder（`live.Register(domain, b)`），`map[string]Builder` | 正则 matcher 列表 + 优先级 | **正则 matcher + 优先级**（同域名多形态，如 `live.bilibili.com`/`b23.tv`/`live.bilibili.com/blanc/`） |
| 输出 | `GetInfo()` + `GetStreamInfos()` 两个方法，返回结构化清晰度列表 | `_get_streams()` 返回 `{name: Stream}`，不区分"信息"与"取流" | 两者都要：**房间信息**与**流候选**分离（UI 需要展示封面/标题/分区，即使不录制）；候选可为 `Deferred`（懒解析直链） |
| 清晰度 | 平台自定义字符串 + `AttributesForStreamSelect` 打分 | `stream_weight` 统一成数值 | **统一数值权重 + 平台附加属性**，UI 展示原名、排序用权重 |
| 失败语义 | `ErrRoomNotExist`/`ErrPlatformToolsNotReady` 等哨兵错误 | `NoStreamsError`/`PluginError` | 定义统一错误枚举：`RoomNotFound / RoomClosed / Offline / NeedAuth / RateLimited / ToolMissing / Network` |

### 2.2 请求节流

- bililive-go：`WrappedLive` 装饰器，同房间串行 + 缓存 + waiter 共享 + 指数退避 + 平台级令牌桶 + 工具就绪轮询。
- streamlink：几乎不做（一次性调用），只有 `http-timeout` 与重试选项。

**取舍**：HIVECAST 必须有 bililive-go 这一套。桌面端同时监听几十个房间时，没有平台级限流一定会被风控。

### 2.3 下载与缓冲

- bililive-go：把 URL 交给 ffmpeg 子进程，自己几乎不碰字节流（native-flv 是例外）。优点是实现简单、兼容性好；缺点是"无法在下载中做任何决策"（不能过滤分片、不能换 CDN、不能算精确进度）。
- streamlink：自己拉分片、自己解密、自己缓冲，ffmpeg 只在"音视频分离需要合流"时介入。

**取舍**：HIVECAST 采用**双层策略**：
- 默认 `direct` 模式（ffmpeg/自研 FLV 直写）——覆盖 90% 平台，CPU 占用最低；
- 平台需要解密/过滤/多 CDN 时切 `segmented` 模式（自研 HLS 下载器，带 RingBuffer）；
- 两者对上层暴露同一个 `Recorder` 接口，按平台能力自动选择。

### 2.4 分段/切片

- bililive-go：按 **时间**（`MaxDuration`）、**大小**（`MaxFileSize`）、**改名**（`OnRoomNameChanged`）切；切段是 Recorder 内部重启，共享 pipeline 状态。
- streamlink：按 **时长**（`stream-segmented-duration`）、**分片边界**（`check_sequence_gap`）、**无新分片超时**。

**取舍**：两者都要。分段点必须落在"分片边界"上（HLS）或"关键帧"上（FLV），否则文件开头会花屏。HIVECAST 的 `SegmentPolicy` 要同时支持 `ByDuration/BySize/ByRoomName/ByDiscontinuity`。

### 2.5 后处理

- bililive-go：完整的阶段流水线 + 任务队列 + 持久化 + 从指定阶段重试。
- streamlink：无（交给用户/播放器）。

**取舍**：全盘采用 bililive-go 的模型，但阶段执行器要支持**取消**与**进度上报**（桌面端要画进度条）。

### 2.6 配置

- bililive-go：YAML 三层覆盖（全局 → 平台 → 房间），`OverridableConfig` 用指针表达"未设置"，`ResolvedConfig` 为解析结果。
- streamlink：扁平选项表（`Options` 描述符），CLI/配置文件/插件参数合并。

**取舍**：桌面端面向普通用户，**不能让用户编辑 YAML**。采用"三层覆盖"的语义（数据模型照抄），但存储为 SQLite + JSON 列，UI 里以"继承自全局/平台"的形式展示覆盖关系。

### 2.7 实时推送

- bililive-go：SSE（`/api/sse`），广播录制状态、弹幕、日志、FFmpeg 状态、内存告警。
- streamlink：无。

**取舍**：桌面端用 IPC 事件通道（Tauri event / Electron IPC），语义与 SSE 一致：**单向、可丢、按房间分频道**。日志量大的频道要限流（丢弃 + "已省略 N 条"）。

### 2.8 biliLive-tools（第三个参考，2025 新增）

它是三者中**唯一把桌面端做完整**的：Electron + 本地 Koa 服务 + SQLite + 任务队列 + 弹幕链路 + 上传同步。对 HIVECAST 的价值不在"产品功能列表"，而在三处工程决策：

| 维度 | biliLive-tools | HIVECAST 取舍 |
| --- | --- | --- |
| 平台抽象 | **两层**：`StreamGet.PlatformParser`（无状态取流） + `RecorderProvider`（有状态录制） | 合并为一层 `PlatformAdapter` + 独立的 `RecordingProfile`（我们没有"第三方注入 provider"的需求，两层是过度设计） |
| 流候选 | 按**线路（CDN）分组**：`SourceInfo{name, streams}`，"主线/备线1/备线2" | **采纳**（见 `04` §2.3）——扁平列表会丢掉备线切换能力 |
| 错误模型 | 5 个 `code`：`UNSUPPORTED_PLATFORM/ROOM_NOT_FOUND/NOT_LIVING/NETWORK_ERROR/PARSE_ERROR` | 采纳并扩到 9 个（补 `RoomClosed/NeedAuth/RateLimited/ToolMissing`） |
| 轮询调度 | **每 provider 一个 `setTimeout` 循环** + 每 provider 独立的 `maxThreadCount=3` 线程池 | **不采纳**：5 个平台 = 5 条互不知情的定时器，暂停/改配置/恢复容易漏。用单调度器 + 每房间"下次检查时间"最小堆 |
| 录制门禁 | 顺序固定：标题关键词 → 付费/加密/大航海/密码房 → 清晰度可满足 → 时间段 → 手动禁录场次 | 采纳顺序，但抽成独立 `RecordGate` 模块，每条规则返回可展示的 `skip reason` |
| 下载器 | `IDownloader` 接口 + ffmpeg/mesio/bililive 三种实现 | 采纳接口形状，只保留 ffmpeg + 自研 segmented 两种 |
| 文件安全 | 先写临时名，段结束 rename；fmp4 抗损坏参数 | **采纳**（见 `08` §7.1、§9） |
| 弹幕 | WS 客户端 + XML 每 10s 批量追加 + DanmakuFactory 转 ASS | 采纳"批量追加 + 强 flush"，但落盘格式改为 JSONL 旁挂、XML/ASS 作导出 |
| 桌面外壳 | Electron 内嵌 Koa，渲染进程走 `http://127.0.0.1:port` + `passKey` | **不采纳**：桌面端直接 IPC，不引入本地 HTTP 层（除非以后要 CLI/远程） |
| 工程组织 | 15 个包 + awilix DI + pnpm workspace | **不采纳**：单包 + 目录分层，依赖手工装配 |

**许可**：biliLive-tools 是 **GPL-3.0-only**。读设计、按同样参数自己实现没问题；**拷源码进 HIVECAST 会传染 GPL**。这一点在 `18` §1 也有标注。

## 3. 关键设计决策（ADR 摘要）

| 编号 | 决策 | 理由 | 备选与否决原因 |
| --- | --- | --- | --- |
| ADR-01 | 平台适配层与录制引擎解耦，接口为 `resolve_info / resolve_streams / open_stream` | 平台差异集中在适配层，引擎可测（mock 平台） | 若每个平台自带下载逻辑，则弹幕/切片/后处理都要重复实现 |
| ADR-02 | 统一清晰度权重（数值）+ 保留平台原名与属性 | UI 需要跨平台排序，但用户认的是"原画/蓝光" | 只用字符串 → 无法排序；只保留权重 → 用户看不懂 |
| ADR-03 | 请求层必须有平台级限流 + 房间级串行 + 指数退避 | 桌面端并发监听数量远大于单房间调试场景 | 无 |
| ADR-04 | 录制内核双模式：`direct`（ffmpeg/FLV 直写）与 `segmented`（自研分片） | 兼容性 vs 可控性的折中 | 全用 ffmpeg → 无法过滤广告分片/解密/统计；全自研 → 工作量大且 FLV 兼容性差 |
| ADR-05 | 状态机单线程驱动 + 同步事件，异步事件只做通知 | 规避 bililive-go 注释里描述的"新 LiveStart 与旧 ListenStop 乱序"竞态 | 全异步事件 → 状态机可重入，难调试 |
| ADR-06 | 后处理失败保留全部中间文件 | 宁可留垃圾不能丢录像 | 失败即清理 → 用户投诉 |
| ADR-07 | 配置三层覆盖（全局/平台/房间），存储为结构化 | 多房间场景下逐条配置不可维护 | 单一全局配置 → 无法给单个房间设清晰度/画质 |
| ADR-08 | 数据库与录制产物分离目录，产物按模板落盘 | 用户要能直接拿文件，也要能备份数据库 | 全部塞数据库 → 大文件不可行 |
| ADR-09 | 流候选按"线路"分组，组内再按清晰度排序 | 备线切换是抗断流最有效的一招；UI 也能让用户选线路 | 扁平列表 → 主线坏了只能重启任务（biliLive-tools 的 `SourceInfo` 证明分组可行） |
| ADR-10 | 桌面端不内嵌本地 HTTP 服务，UI 直接走 IPC | 少一层攻击面、少一次序列化、无需 passKey 与端口管理 | 内嵌 Koa（biliLive-tools）→ 要处理鉴权/端口冲突/同机监听，收益只在"同时提供 CLI/远程访问"时才成立 |

## 4. 明确"不采用"的部分

1. **不采用 bililive-go 的 YAML 作为主配置源**：桌面端用 SQLite + 导入/导出 YAML（兼容老用户），避免"改配置要重启/文件被覆盖"。
2. **不采用 streamlink 的 Python 插件沙箱**：HIVECAST 的平台适配器是编译期代码，不做运行期脚本加载（安全与性能）。
3. **不采用"外部 Chromium + CDP"**：桌面端直接用内嵌 WebView 完成登录与取 cookie。
4. **不采用 bililive-go 的 `/tools/`、`/scheduler/` 反向代理子 UI**：桌面端没有"另一个 Web UI"的概念，工具状态直接在设置页展示。
5. **不采用 biliLive-tools 的"Electron 内嵌 Koa + passKey"**：它这么做是为了同时支持 Docker/CLI；HIVECAST 是纯桌面应用，IPC 足够，多一层 HTTP 只增加攻击面与调试成本。
6. **不采用 biliLive-tools 的"每平台一个 npm 包 + awilix 容器"**：15 个包的 monorepo 适合多人协作与独立发布，对单人项目是纯负担。

## 5. 需要自研/重点验证的风险点

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 平台风控 | 斗鱼签名、B 站风控、抖音 x-bogus | 限流 + 复用浏览器 UA/cookie + 设备号固定 |
| 长时间稳定性 | 连续录制 12h+ 内存/句柄泄漏 | 环形缓冲固定容量、子进程回收、定期自检（内存/句柄/磁盘） |
| 分段边界 | FLV 中途切断导致花屏 | 优先在关键帧/分片边界切；否则后处理 `fix_flv` 修时间戳 |
| 磁盘写满 | 录制中写失败 | 预留空间检查 + 低空间告警 + 自动停止策略 |
| 弹幕时间轴 | 断流重连后时间偏移 | 以"录制开始的单调时钟"为基准，重连不清零 |
| 跨平台路径 | Windows 非法字符、macOS 大小写不敏感 | 统一 `filename_filter` + 长度截断 + 保留名检查 |
