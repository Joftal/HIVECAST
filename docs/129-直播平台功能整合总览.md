# 129 · 直播平台功能整合总览（2026-11 复核）

> 目的：把 `bililive-go`、`biliLive-tools`、`streamlink` 三个成熟项目里与「取流 / 录制 / 登录 / 弹幕」有关的实现，压缩成 HIVECAST 可以直接查阅、对照、取舍的一层文档。

> 口径：参考实现结论都带仓库相对路径与行号；HIVECAST 结论以当前 `main` 实现为准，不沿用设计期文档里的旧路径。

## 1. 三个参考源怎么分工

| | bililive-go | biliLive-tools | streamlink |
| --- | --- | --- | --- |
| 语言/形态 | Go 常驻服务 | TypeScript / Electron 桌面应用 | Python CLI / 库 |
| 强项 | 监听与录制状态机、阶段化后处理、下载器抽象、ASS 弹幕 | 平台取流的统一契约、按线路分组、可录性门禁、任务与文件生命周期 | HLS/DASH 分片、缓冲与重连、插件匹配、流权重 |
| 弱项 | 平台协议老、抖音靠外部进程 | 包体巨大、GPL、平台实现与 UI 耦合 | 完全没有弹幕、没有长驻状态 |
| 对 HIVECAST 的用法 | 抄「状态机与失败恢复」 | 抄「取流结果形状与门禁顺序」 | 抄「分片层与超时参数」 |
| 许可 | MIT | **GPL-3.0-only，只借设计不复制代码** | BSD-2-Clause（部分插件例外） |

一句话：**取流结果形状学 biliLive-tools，录制生命周期学 bililive-go，分片与超时学 streamlink。**

## 2. 一条直播从 URL 到文件的统一链路

```text
用户输入 URL / 房间号
        │
        ▼
[1] resolve        纯本地：匹配平台、抽 room_key、规范化 URL        （不联网）
        │
        ▼
[2] room_info      平台接口：在播？标题/主播/封面/开播时间/特殊状态
        │
        ▼
[3] gate           可录性：付费/加密/大航海/密码房/关键词/时段/画质
        │
        ▼
[4] stream_plan    一次解析：线路组 × 画质档 × 格式 × 编码 × 直链
        │
        ▼
[5] pick           画质 rank → 编码 rank → 格式 rank → 码率/权重
        │
        ▼
[6] record         ffmpeg/分片下载器 → 分段文件 → 收尾合并
        │
        ├──▶ 弹幕客户端（独立连接，失败不阻断视频）
        └──▶ 事件/DB（开始、进度、结束、失败原因）
```

三段职责必须分开，这是三个项目共同验证过的边界：

1. **平台层不下载**：只返回候选直链与请求头，不建长连接、不写文件。
2. **取流与录制解耦**：biliLive-tools 的 `getStreams` 与 downloader 分开；streamlink 的 `Stream` 与 `StreamWriter` 分开。
3. **弹幕与视频解耦**：bililive-go 弹幕启动失败只 Warn，视频继续录（`src/recorders/recorder.go:702-761`）。

## 3. 四个平台能力矩阵（当前实现）

| 能力 | B 站 | 斗鱼 | 虎牙 | 抖音 |
| --- | --- | --- | --- | --- |
| 房间信息 | `room/v1/Room/get_info` | `betard/{id}` | 房间页 HTML | `webcast/room/web/enter` |
| 结构化线路 | ✅ host 分组 | ✅ cdn 逐条请求 | ✅ sCdnType 分组 | ✅ FLV/HLS 两组 |
| 画质档位 | qn 表 + accept_qn | multirates → rate | antiCode ratio / HEVC qn | origin/uhd/hd/sd/ld |
| 需要签名 | WBI（弹幕） | auth + did | antiCode | abogus + ttwid |
| 扫码登录 | ✅ 已有 | 参考项目有，HIVE 无 | ❌ | ❌ |
| Cookie 续期 | 30 分钟复验 | 参考项目有 LTP0，HIVE 无 | ❌ | ❌ |
| 弹幕 | WS + WBI | TCP 8601 | WS + Tars | WS + protobuf/gzip |
| 主要坑 | 付费/加密/大航海 | 匿名流约 5 分钟被切 | 每次取流重算签名 | 签名 UA 必须一致 |

> 画质与线路的真实性已在 `122`–`127` 用真实 Cookie 验证过；本文只描述协议与取舍，不重复截图。

## 4. 三个项目最值得借的十件事

1. **按线路分组的结果形状**：`SourceInfo{name, streams}`（`biliLive-tools/packages/StreamGet/src/types.ts`）。HIVECAST 的 `StreamGroup` 已是这个形状。
2. **可录性门禁先于取流**：付费标记、DRM、空 stream、密码房（`BilibiliRecorder/src/stream.ts` 的 `getInfo`）。HIVE 目前缺这一层。
3. **懒解析候选**：`ListStreamCandidates` + `ResolveStreamCandidate`（`bililive-go/src/live/lives.go:272-284`）。适合把「列画质」与「取直链」拆开。
4. **短录制→换备线**：<12s 连续 2 次则下次优先另一条流（`liveManager/src/manager.ts:80-82, 468-500`）。
5. **录制中断立即重查**：非手动停止且已录 ≥60s，1s 后重查，单场最多 10 次（`manager.ts:503-545`）。
6. **请求头必须放在 `-i` 前且合并成一个 `-headers`**（`bililive-go/src/pkg/parser/ffmpeg/ffmpeg.go:324-365`）。这是 HIVECAST 当前最值得先补的工程细节。
7. **SPS/PPS 变化作为换源/断流信号**（`native/flv/tag_video.go:71-77`）。比只看进程退出更早。
8. **ASS 宁可重叠也不推迟时间戳**（`danmaku/ass.go:419-458`）。排队会把时间轴越推越歪。
9. **分片失败只告警、不整体失败**（`streamlink/src/streamlink/stream/segmented/segmented.py:251-259`）。
10. **开流预读判空**：先读 8192 字节，避免把错误页当视频（`streamlink_cli/main.py:366-395`）。

## 5. 明确不要照搬的十件事

- biliLive-tools 的 GPL 源码、15 包 monorepo、awilix DI、Koa + passKey 本地服务。
- bililive-go 的 ffmpeg 只能写 `q` + 3 秒强杀（`ffmpeg.go:414-449`），HIVE 应使用进程组/信号与超时双层收尾。
- bililive-go 的两套 FLV 代理并存（StreamProbe 与旧 flvproxy）。
- 斗鱼签名失败直接 panic（`douyu.go:115-137`）。
- 抖音内嵌 485KB `sign.js` 每次建连都起 JS 运行时；HIVE 的 `douyin_sign.rs` 已有独立实现，保持。
- streamlink 的 TLS 跳过 hostname 校验、session 级全局 headers、无 jitter 重试。
- streamlink 的清晰度魔法权重（k/2.8、p+fps），HIVE 继续用显式 rank。
- biliLive-tools 的固定 `-c copy` 到 ts/m4s/flv 后再转 MP4 的双链路；HIVE 的 ffmpeg 分段 + 收尾合并更适合桌面端。
- 把 Cookie 塞进候选 headers；HIVE 按域名在 HTTP 层注入，避免 CDN 收到登录态。
- 用「页面解析失败」静默当作未开播；必须区分 Parse 与 NotLive。

## 8. 实测方法与边界

- 需要验证平台接口时使用 **ego-browser**，Cookie 从项目根 `Cookie.txt` 读取；不要把 Cookie 写进文档、日志或提交。
- 参考仓库只读：不修改、不复制 GPL 代码、不把其依赖引入 HIVECAST。
- 文档中的「确认」= 代码/接口实测；「推测」= 仅从代码推断，需实测后再升级为结论。
- 平台接口随时会变；新结论优先写进对应专题文档，并在本文 §6 更新差距表。

## 9. 2026-11 复核结论

1. 04–09 的分层设计仍然成立，但**路径与错误模型已落后于实现**：实际代码在 `src-tauri/src/platform/`，`PlatformError` 只有 7 类。
2. 三个参考项目里，**biliLive-tools 的取流契约最接近 HIVECAST 需要的形状**；bililive-go 的监听/录制状态机最完整；streamlink 只适合借分片层。
3. HIVECAST 已经从「能取到流」进入「要解释为什么没录、为什么断」的阶段，下一轮重点应是**门禁、请求头、失败原因、重连语义**，而不是继续加平台。
4. 弹幕四平台协议已经齐全，剩余工作主要是**去重、落盘一致性、ASS 时间轴**，不需要再参考 streamlink（它没有弹幕）。
