# 73-日志功能审查与测试报告

> 版本：v2.2（2026-11-07，移除单日上限 + 脱敏/转义/退出收尾加固）
> 审查对象：`src-tauri/src` 全模块日志覆盖、异常路径记录、日志设置与前端错误上报
> 对应实现：[72-日志功能实现](72-日志功能实现.md)；初版报告：[70-日志设置与日志体系评审](70-日志设置与日志体系评审.md)
> 结论：写盘主链路通过；本轮把日志点扩展到 29 个模块、约 360 处，补齐启动/退出、命令层、账号、本地回放、回环服务、托盘等静默链路，修复 1 个真实的子进程异常处理缺陷，并把每 200ms 一批的弹幕日志改为 60 秒汇总。v2.2 进一步移除单日 64 MiB 上限，日志按 16 MiB 无限续段，不再因容量丢日志；同时补 URL path 脱敏、字段换行转义和退出 2 秒超时。Windows 与磁盘满/断电等边界仍未真机覆盖。

## 1. 结论

1. **写盘核心可信**：目录选择、本地日切、16 MiB 无限续段、同日重启追加、保留清理、运行中换目录、目录失效回落、退出 flush 均已有单测或真机证据；v1.0 记录的 11 个写盘缺陷全部修复并有回归测试，v2.2 又移除了唯一会因当天容量上限丢日志的路径。
2. **全功能链路可追溯**：从进程启动、监控检测、自动/手动录制、观看、本地回放、弹幕、账号、媒体库、后处理、托盘、设置到退出，每个用户可感知的状态变化都有 INFO，每个可恢复异常都有 WARN，每个不可恢复失败都有 ERROR；高频路径用 DEBUG，弹幕批次日志按 60 秒汇总，4 路同时观看也不刷屏。
3. **异常处理审查有实际收获**：本轮发现并修复 `process::send_graceful` 在 SIGINT 发送失败时直接返回、既不报错也不兜底强杀的问题；同时把 `wait_exit` 的等待错误从“等同超时”改为显式 WARN，并修掉每 200ms 一批的弹幕 DEBUG 日志（D15）。v2.2 再修 URL path 脱敏、字段换行注入与退出 `join` 无超时（D17–D19），并统一 `dropped` 语义、去掉重复的凭据加载日志（D20/D21）。另有 12 类原本静默的失败点补上了日志。
4. **不再因容量丢日志**：移除 `MAX_SEGMENTS=4` 后，单日分段可无限续写，单条超过 16 MiB 也能写入空分段；`dropped` 只保留给 channel 满、pending 溢出和写失败等内存/故障保护，并每 60 秒最多 WARN 一次。新增日志全部走同一 tracing 管道。
5. **日志不是业务正确性的替代**：本次仍发现若干业务层风险（如删除文件后再删库失败会留下悬空记录），已在第 8 节列出，不在本次日志改造范围内擅自改变事务语义。

最终验证：`cargo fmt --check` 通过；`cargo check --all-targets` 0 警告；`cargo test --lib` 204 passed / 0 failed / 14 ignored（总 218）；`cargo build` 通过；`pnpm build`、`pnpm check:i18n`（479 keys）、`pnpm check:docs`（74 files）通过。

## 2. 审查范围与判定标准

| 维度 | 判定标准 |
| --- | --- |
| 可追溯 | 用户动作、状态翻转、后台任务开始/结束能按 `room_id` / `session_id` / `slot` / `platform` 串起来 |
| 异常可见 | 失败不能只 `let _ =` 或只返回错误；至少一条 WARN/ERROR，且不重复刷屏 |
| 安全 | 不记录 Cookie、URL token、密码；URL 走 `redact_url`（含 path 中的 token/UUID/长哈希）；回环 token 不落明文；字段换行统一转义 |
| 噪声控制 | 高频缓存命中、轮询中间态用 DEBUG；同一原因只在变化时 WARN |
| 一致性 | 成功与失败成对；开始与结束成对；错误字段带上下文（路径、房间、平台、错误文本） |

方法：逐文件静态审查 + 调用链追踪 + 关键路径故障注入单测 + debug 二进制真机运行 + 对既有日志做“是否可定位”复核。所谓“所有情况”无法穷举，本报告按**失败面矩阵**覆盖：启动失败、目录/数据库不可用、平台请求失败与冷却、录制拉起/退出/续录、观看重连、回环拒绝、本地回放超时、账号过期、设置保存被拒、清理失败、退出被任务拦截等。

统计口径：`grep -c 'tracing::'`，只代表日志点数量，不代表质量；`logging.rs` 自身只有 2 处是刻意的——写日志的代码不能再递归写日志。

| 账号 | `account.rs`(21)、`credential.rs`(2)、`secret.rs`(1) | 扫码阶段迁移、保存/删除、启动复验、过期通知失败；不记录 Cookie |

## 5. 异常处理审查结果

### 5.1 本轮修掉的真实缺陷

| # | 缺陷 | 影响 | 修法 |
| --- | --- | --- | --- |
| D12 | `process::send_graceful` 用 `let _ = libc::kill(...)` 后直接 return | SIGINT 发送失败时既不记录也不 `start_kill`，调用方只能等 2–4 秒超时，录制尾部和观看收尾被拖慢 | 检查返回值；非 0 时 WARN 带 errno 并立即 `start_kill`；无 pid 时 DEBUG 后强杀 |
| D13 | `wait_exit` 把 `try_wait` 的 Err 当作超时返回 `None` | 日志会误报“2 秒未退出，强制结束”，真实错误被吞 | 单独 WARN“等待子进程退出失败”，再返回 `None` |
| D14 | `recorder::shutdown_all` 对空会话也打“开始/完成” | 退出流程重入（SIGTERM handler + RunEvent::Exit）时重复两遍空收尾，掩盖真实会话数 | 空会话 DEBUG 后直接返回；有会话才 INFO 汇总 |
| D15 | `danmaku::flush` 每个 200ms 批次打一条 DEBUG | 每房间最多 5 条/秒；4 路观看约 172–247 MiB/天，64 MiB 额度 6–9 小时写满，当天后半段日志全部丢弃 | 新增 `BatchMeter`，每 60 秒汇总一条（batches/messages/dropped_total）；4 路同时观看约 0.6 MiB/天 |
| D16 | `MAX_SEGMENTS=4`，当天第 5 段起直接丢弃 | 每天最多 64 MiB；高频日志或长时间运行会把当天后半段日志全部丢掉，只剩 `dropped` 计数，事后无法追溯 | 删除 `MAX_SEGMENTS`；`open_from` 找第一个未满分段，没有就继续 `checked_add(1)` 开新段；单条超过 16 MiB 写入空分段；空间交给保留天数清理。回归：`full_segments_continue_into_a_new_segment_without_fallback` |
| D17 | `redact_url` 只处理 query/userinfo/fragment | `/live/<token>`、`/api/<uuid>` 等 path 中的 token/签名会原样落盘 | 新增 `SENSITIVE_PATH_KEYS` 与 `looks_like_secret`，对敏感 `key=` 段、UUID、长 hex/Base64 样式段打码；解析失败的 URL 走 `redact_raw_url`。回归：`path_tokens_and_long_hashes_are_redacted`、`path_uuids_and_prefixed_tokens_are_redacted`、`multiple_path_parameters_are_all_redacted`、`unparsable_urls_redact_path_after_an_at_sign` |
| D18 | 字段值中的换行/控制字符未转义 | 恶意房间名、URL 或平台响应可伪造日志行，干扰排查与审计 | 文件 layer 使用 `SanitizedFields`：`\n`→`\\n`、`\r`→`\\r`、`\t`→`\\t`，其他控制字符转 `\\u{...}`；控制台保持原样。回归：`log_field_values_escape_newlines_and_controls` |
| D19 | `logging::shutdown` 对写线程 `join` 无超时 | 网络盘、卡死 I/O 或写线程 panic 时退出可能被永久拖住 | `try_send(Shutdown)` 不阻塞；`join` 放到 `hivecast-log-join` 旁路线程，主线程 `recv_timeout(2s)`，超时 eprintln 并分离线程 |
| D20 | `dropped` 在状态、i18n、`LogStatus` 注释里被说成“条数” | 实际按写入批次计数，用户会误以为等于丢失的日志行数 | 状态文案改为“日志片段（按写入批次计，不是行数）”，`LogStatus.dropped` 注释同步 |
| D21 | state 与 `account::revalidate` 各调一次 `credential::load_from_db` | 每次启动出现两条“已加载账号凭据”，属噪声 | 新增 `load_from_db_quiet`，复验路径不再打 INFO；启动路径保留一条 |

### 5.2 保留的 11 个写盘缺陷修复（v1.0）

满段误回落、dropped 漏计、删除目录/文件后写 unlinked inode、0644 权限、路径绕过与 probe 截断、清理中断、URL 解析失败泄露 userinfo、前端去重 Map 无界、默认目录删后永久停写、shutdown 丢启动 pending、换目录丢剩余 pending——逐条根因、修法与回归测试见 v1.0 第 4 节，本轮复核仍通过。

### 5.3 审查中确认“行为正确”的关键点

- 日志字段里的 URL 统一走 `redact_url`；Cookie 只在 `credential` 内存表，账号日志只打平台/账号名。
- 回环 token 校验失败只记 session/path，不记 token 值；Origin/Host 拒绝原因可定位但不泄露凭据。
- 同一自动开录失败只在原因变化时 WARN，重复失败降为 DEBUG，避免 10 秒一条。
- 保留策略删除失败不再计入释放空间，避免磁盘统计虚高。
- 缩略图事件发送失败不再阻断后续任务。

## 8. 残余风险与未覆盖项

1. **Windows 未真机**：路径分隔符、杀毒占用、文件锁、`LOCALAPPDATA` 重定向、ACL 继承（`0600` 只在 Unix 有测试）仍可能在打包机暴露。
2. **磁盘满/只读卷/断电**：写入失败会 `dropped` 并尝试回落，但没有 fsync，断电可能丢最后一段缓冲。
3. **保留清理依赖每日巡检**：日志不再有日上限，若保留清理连续失败或用户把保留天数设得很大，磁盘占用会持续增长；`last_error` 能提示，但没有配额告警。
4. **fallback 只留最近一次**：连续切换时设置页可能只看到最后一次。
5. **`dropped` 是块计数**：单条日志被拆分写入时会多计，不等于日志行数。
6. **无 24 小时 soak 与多实例压测**：本轮以故障注入和短时真机为主。
7. **平台适配器无独立日志**：请求与结果由 HTTP 层和 broker 记录；若需要定位“同一响应解析差异”，还要临时加 DEBUG。
8. **业务事务风险（非日志缺陷）**：`media_delete` 先删文件再删库，若删库失败会留下指向已删文件的记录；当前只记录 WARN，未改成可回滚流程。
9. **无日上限后的磁盘回归风险**：日志量 × 保留天数就是磁盘占用；当前弹幕批次已治理为 60 秒汇总，后续若新增每帧/每请求/每轮询 DEBUG，需要按保留窗口重新评估总量。

## 11. 验收结论

- **可以交付**：日志主链路、全功能链路关键节点、异常路径与退出收尾均有日志点、单测或真机证据。
- **交付前建议**：Windows 打包机补目录/权限/占用测试；如需长期运行，补 24 小时 soak，并观察保留清理失败时的磁盘增长。
- **后续可选**：把 `media_delete` 改成“先标记删除、成功后删文件”的可恢复流程；为日志总量加可选的磁盘水位告警。
