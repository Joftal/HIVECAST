# 任务中心复查与边界收口

> 状态：复查、修复、单测与真机验收完成（2026-11-21）。承接 [185-任务中心历史增量加载与部分完成](185-任务中心历史增量加载与部分完成.md)。
> 本轮范围：重新完整复查任务中心的数据聚合、Run 状态机、四段链路、异常动作、历史分页、详情抽屉与周边入口；只处理本轮确认的缺陷，不改数据库结构语义。

## 1. 结论

任务中心的主链路没有回归：录制中的 Run 会实时更新时长和体积，停止后按「录制 → 收尾 → 后处理 → 入库」推进；失败与中断会进入「需要处理」，收尾失败、后处理失败、登录失效、监控退避各自有动作；历史分页、平台筛选、详情时间线和录制文件入口均可正常使用。

本轮修掉的主要是**边界状态**，不是主流程：

| 边界 | 修复前 | 修复后 |
| --- | --- | --- |
| 上次退出打断录制（无产物） | 后处理/入库一直显示「等待中」 | 后处理「已跳过」、入库直接「失败」 |
| 上次退出打断录制（有产物） | 入库一直「等待中」 | 入库「部分完成」 |
| 已收尾完成的场次残留旧 finalize 失败 | 仍给「重试收尾」，点了只报错 | 不再显示重试，异常动作改为「查看任务」 |
| 无清单时点「重试收尾」 | 先建 job，再报错，留下常驻失败任务 | 校验在创建 job 之前，直接给用户文案 |
| 上次退出打断的后处理任务 | 只显示「已中断」，没有重试入口 | 异常卡给出「重试后处理」 |
| 监控退避异常 | 详情直接显示内部枚举 `failed/retry/throttled` | 显示本地化说明 |
| 需要处理超过 8 条 | 被硬截断成 8 条，计数与列表不一致 | 计数与列表一致，不再丢弃异常 |
| 连续双击「加载更多历史」 | 可能一次推进两页 | ref 单飞，第二次点击被忽略 |

## 2. 当前实现

### 2.1 数据聚合

入口仍是 `commands::task_center` → `task_center::build`。一次构建会读取：

- `record_session`：录制场次、分片、文件、后处理、弹幕与分组；
- 内存中的 `Jobs`：正在运行/排队中的任务，以及 `task_history` 的最近历史；
- `task_event`：Run 详情的阶段时间线；
- `credential`：登录失效异常；
- 监控状态与运行时健康：监控退避、ffmpeg、磁盘。

### 2.2 Run 怎么分组

- 有 `session_id` 的任务挂到 `session:<group_id>` 的 Run；同一场直播的分割片段共享 `group_id`，因此在任务页只出现一行。
- 收尾任务（`finalize`）不单独成 Run，只把阶段推进到「收尾」。
- 合并、单独导出弹幕等没有 session 的任务，各自成为 `task:<id>` 的独立 Run。
- 历史按分组倒序取，先统计分组再截断；多读一组只用于回答 `history_has_more`。

### 2.3 状态与阶段

Run 状态优先级：**收尾中 → 录制中 → 处理中 → 排队 → 失败/部分失败 → 中断 → 取消 → 完成**。四段链路固定为：

1. 录制：`active/done/failed/skipped`；
2. 收尾：`active/done/failed/skipped`；
3. 后处理：`active/done/failed/skipped/pending`；
4. 入库：`done/partial/failed/pending`。

`partial` 表示「有产物、但没有完整入库」，例如磁盘满导致的分片中断；它不会被当成完整成功。

### 2.4 页面

- 顶部：平台态势、统计卡（房间/直播/录制/排队/24 小时失败）。
- 进行中：录制中与排队中的 Run。
- 需要处理：按严重度排序的异常，动作包括打开直播间、打开账号、查看任务、重试后处理、重试收尾。
- 最近完成：历史表，首屏 100 场，底部「加载更多历史」，最多 1000 场。
- 详情抽屉：四段链路、阶段时间线、任务、上下文、复制诊断、录制文件。

## 3. 本轮修复

### 3.1 `app_exit` 中断不再永远等待

`/Library/dshproject/HIVECAST/src-tauri/src/task_center.rs`：

- `build_stages` 的后处理状态在 `interrupted_abort && all_ended` 时返回 `skipped`（:823）。
- `normal_commit` 从只处理 `abnormal_abort` 扩为 `abnormal_abort || interrupted_abort`（:834）：有文件或 `file_size > 0` → `partial`，否则 `failed`。
- `commit_state` 的最终态分支同步扩展（:856），不再落入「等待中」。

新增测试：

- `interrupted_without_product_fails_commit_instead_of_waiting`：无产物时后处理 `skipped`、入库 `failed`；
- `aborted_on_app_exit_is_interrupted_not_failed` 增加 `post=skipped`、`commit=partial` 断言。

### 3.2 陈旧收尾失败不再提供无效重试

问题：场次已经 `finished`，但 `task_history` 还留着上一轮 `finalize` 失败记录。旧逻辑只按任务状态判断，仍显示「重试收尾」；实际清单已被消费，点击只会失败并再留下一条失败任务。

修复：

- `/Library/dshproject/HIVECAST/src-tauri/ipc-types/src/lib.rs:948` 的 `RunView` 新增 `pub finalize_retry_ready: bool`，由 `task_center.rs:681` 计算：
  `finalize stage == failed && 同组存在 status != finished 的片段`。
- `build_incidents` 的动作改为：`finalize` 且 `finalize_retry_ready` 才给 `retry_finalize`；否则给 `open_task`（:1035）。
- 前端 `/Library/dshproject/HIVECAST/src/features/tasks/TasksPage.tsx:212` 的 `failedFinalizeTask` 首行判断 `run.finalizeRetryReady`，不满足就不渲染按钮。

新增测试 `stale_finalize_failure_on_finished_session_is_not_retryable`：同一失败任务落在 `finished` 场次上为 `false`，落在 `failed` 场次上为 `true`。

### 3.3 重试收尾先校验，再创建任务

`/Library/dshproject/HIVECAST/src-tauri/src/commands.rs:1514` 的 `finalize_retry` 现在按顺序校验：

1. 场次不存在 → `这段录像不存在，可能已被清理`；
2. `status == "recording"` → `这段还在录制，先停下再重试收尾`；
3. `split_manifest_for` 为空或文件不存在 → `这段录像没有待恢复的收尾清单，可能已经收尾完成`；
4. 全部通过后才 `jobs.begin_for("finalize", ...)`。

这样失败点击不会留下 `finalize` 失败任务，也不会在「需要处理」里生成常驻异常。

### 3.4 中断的后处理任务也能重试

- `task_center.rs:1009` 的 `build_incidents` 现在接受 `interrupted` 的 `post/remux/finalize` 任务，仍拒绝把「录制任务中断」当成后处理失败。
- 前端 `failedTask` 条件从 `state === "failed"` 扩为 `failed || interrupted`，且限定 `post/remux`（`TasksPage.tsx:212`）。

新增测试 `interrupted_postprocessing_becomes_a_retryable_incident`：`app_exit` 中断的后处理生成 `task_failed` 异常，动作为 `retry_post`。

### 3.5 监控退避不再暴露内部枚举

监控退避的 `incident.detail` 来自 `last_outcome`，可能是 `failed/retry/throttled`。`TasksPage.tsx:535` 新增 `backoffDetail`：只有 detail 不是这三个内部值时直接展示，否则用 `tasks.incidentMonitorBackoffDetail` 的本地化说明。

### 3.6 「需要处理」不再截断

`task_center.rs` 删除了 `incidents.truncate(8)`（原 :1142 附近）。此前计数按全部异常算，列表只显示 8 条，用户会以为已经处理完。本轮真机注入后「需要处理 10」全部展开。

### 3.7 加载更多的双击保护

`TasksPage.tsx:882` 新增 `loadingMoreRef`；`loadMore`（:929）在计算下一页之前先检查并置位，`finally` 中释放。连续双击时第二次直接返回，不会把上限一次推进两页。

该保护以代码审查为主：真实夹具只有约 130 场，一次加载就到末尾，无法用数据量区分「一页」和「两页」；单次「加载更多」已在 185 真机验证。

### 3.8 历史容量与启动收尾

- `/Library/dshproject/HIVECAST/src-tauri/src/db.rs:1829` 的 `task_history` 读取上限从 `clamp(1, 500)` 提到 `clamp(1, 2_000)`，与前端最多 1000 场留出余量。
- `db.rs:1845` 的启动清理从只处理 `running` 扩为 `running/queued`：排队任务在进程退出后不可能再执行，留在 `queued` 又会被 `task_history` 的过滤条件排除，导致 Run 被误判为「完成」。
- `db.rs:47` 的 schema 增加 `idx_record_session_started`，任务中心按 `started_at DESC` 扫全表时不再临时排序。

新增测试：

- `task_history_keeps_more_than_five_hundred_for_task_center`：写入 600 条，读取 600 条；
- `queued_tasks_are_interrupted_on_startup`：`running/queued` 都被标记 `interrupted`，`done` 不变。

## 4. 真机验收

环境：macOS release bundle **33.15 MiB**；窗口 1166×749 @ (70,30)，截图 2332×1498；真实 DB 测试前为空库，备份 `/tmp/hivecast-before-task-review2.db`。

| 场景 | 夹具 | 结果 |
| --- | --- | --- |
| 退出中断、无产物 | `s-run-record`（aborted/app_exit） | 详情「已中断」；录制完成、收尾已跳过、后处理已跳过、入库失败；不再等待 |
| 已完成场次残留收尾失败 | `s-finalizing`（finished + finalize interrupted） | 详情仍显示收尾失败，但底部无「重试收尾」；异常动作「查看任务」 |
| 有效收尾重试 | `s-fin-valid`（真实 1 秒 FLV + 清单） | 重试后 session `finished`、清单删除、任务 `收尾 完成 100%`、详情四段全绿 |
| 分组部分失败 | `s-partial-g1` + `s-partial-g2` | 详情「部分完成」；重试后两段 `post_state=done`，旧失败任务隐藏 |
| 中断的后处理 | `s-post-run` | 详情「已中断」，异常卡提供「重试后处理」 |
| 需要处理数量 | 10 条异常 | 筛选页 10 条全部展开，不再截断为 8 |
| 历史与平台筛选 | 250 片同组 + 平台筛选 | 跨页仍聚合为一行；平台筛选后列表、统计卡、异常全部归零 |
| 正常录制回归 | `https://live.bilibili.com/6` | 自动开录、手动停止、分片合并、后处理 `done`、历史首行「完成」 |

补充说明：直接向 `task_history` 插入一条 `state=queued` 的假任务不会出现在任务中心，因为 `task_history` 的 SQL 明确 `WHERE state NOT IN ('running','queued')`；真正的排队任务存在于内存 `Jobs` 中。这不是缺陷，测试夹具已删除。

## 5. 仍需完善

1. **收尾并发仍只有单测**：`FINALIZE_RETRYING` 按 manifest 互斥、不同清单并行、lease 释放已覆盖；没有真机同时点两个片段的重试。
2. **异常列表没有分页**：取消 8 条截断后，如果积累大量失败任务，页面会一次渲染全部异常；目前只有 10 条量级，尚未量化上百条时的性能。
3. **旧阶段事件会保留**：重试成功后，上次失败留下的 5% 时间线仍会显示，作为历史事件可以接受，但详情会较长。
4. **大数据量仍只到 5000 行**：`load_sessions` 超过 5000 行会截断并告警；任务页最多 1000 场，尚未测试 1000 场全量渲染。
5. **监控退避详情未真机注入**：监控状态在内存中，没有可写入的公开入口；本轮只做了代码修正，未构造真实 `last_outcome`。
6. **真机收尾成功样本依赖合成清单**：`s-fin-valid` 的清单是人工构造的，但 FLV 是真实 ffmpeg 产物；真实录制中「录制成功、收尾失败」路径仍建议后续用断网/磁盘满再验一次。
