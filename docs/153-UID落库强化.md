# 153 · UID 落库强化

> 范围：`src-tauri/src/monitor.rs` 的成功检查写库判断、`src-tauri/src/db.rs` 的房间更新语句，以及 B 站单房间/批量监控的衔接。
> 结论：**平台返回 UID 时，成功检查一定会把它写回 `room.platform_uid`，不再依赖标题/封面等字段是否同时变化。** 缺 UID 的存量房间在下一次成功检查后即可进入 B 站批量状态接口。
> 时间：2026-11-13；基线：`148f65f` + 本次改动。

---

## 1. 问题

B 站批量状态接口按主播 UID 查询，`monitor.rs:191` 的 `is_batchable` 要求：

- `platform == "bilibili"`；
- `platform_uid` 非空（去空白后非空）。

缺 UID 的房间会退回单房间 `room_info` 请求。单查本身不会漏检，但房间多时请求量会被放大：238 个房间约 47.6 请求/秒，1000 个房间约 200 请求/秒。

单查结果进入 `apply_room_info` 后，旧逻辑只在「结构性字段」变化时整行写库：

```rust
let structural = info.is_live != room.is_live
    || info.room_name != room.title
    || info.host_name != room.host_name
    || info.avatar_url != room.avatar_url
    || info.cover_url != room.cover_url
    || info.area_name != room.area_name
    || info.started_at != room.started_at;
```

UID 不在比较范围内。若房间的标题、主播、封面、开播状态都没变，只缺 UID，就会走 `touch_room_throttled`：

```sql
UPDATE room SET online = ?, last_checked_at = ? WHERE id = ?
```

这条语句不写 `platform_uid`。结果就是：平台这次明明返回了 UID，日志也显示检查成功，数据库里的 `platform_uid` 仍是 `NULL`，下一拍继续单查，形成长期退化。

典型来源：

- 早期版本导入/重建的房间；
- 手工迁移或从备份恢复、UID 列被清空的房间；
- 历史 `insert_room` 没有拿到 UID、后来平台才补上的房间。

---

## 2. 修复

### 2.1 UID 纳入写库判断

`monitor.rs:943` 新增 `needs_room_write`，在原有结构性字段之后增加：

```rust
|| crate::db::platform_uid_of(info)
    .is_some_and(|uid| room.platform_uid.as_deref() != Some(uid.as_str()))
```

`platform_uid_of`（`db.rs:2261`）只接受正整数，兼容 `"50329118"`、`50329118`、带空白的字符串；`"0"`、空串、缺失都返回 `None`。因此：

- 平台返回有效 UID 且与本地不同 → 视为结构性变化；
- 平台没返回 UID → 不触发 UID 写库，保留本地旧值，避免每拍把 UID 冲成空；
- 平台返回的 UID 与本地相同 → 不产生额外整行 UPDATE。

### 2.2 复用已有的整行更新

`apply_room_info`（`monitor.rs:958`）在 `structural == true` 时调用 `db.update_room_info`。该语句（`db.rs:528`）本来就写 UID：

```sql
platform_uid = COALESCE(?11, platform_uid)
```

所以不需要新增 SQL，也不需要额外请求：UID 差异会把这次检查提升为整行写库，`COALESCE` 再把有效 UID 落盘。若平台这次没给 UID，`?11` 为 `NULL`，旧值保持不变。

### 2.3 覆盖的链路

| 链路 | UID 来源 | 本次改动后 |
| --- | --- | --- |
| 添加房间 | `room_info` → `insert_room` | 原本就写；已有分支走 `update_room_info` |
| 关注导入 | 导入结果/`room_info` | 原本就写；已有房间走 `update_room_info` |
| 单房间监控 | `room_info` | 缺 UID 或 UID 变化时整行写库 |
| B 站批量监控 | 批量状态 → `batch_room_info` | 批量结果也带 `extra.uid`；UID 差异同样触发写库 |
| 重新添加/短号归一 | `room_info` | 原本就写，保留 |

注意：批量路径只处理「已经有 UID」的房间；缺 UID 的房间仍要先走单查拿到 UID，这是 `is_batchable` 的设计，不是本次要绕过的限制。

## 3. 具体行为举例

### 例 1：存量房间补 UID

房间 `room_key=7734200`，数据库 `platform_uid=NULL`，其他字段与平台一致。下一拍单查拿到 `uid=50329118`：

1. `needs_room_write` 比较 `None != Some("50329118")` → `true`；
2. `update_room_info` 写入标题、主播等字段，并把 `platform_uid` 写成 `50329118`；
3. 再下一拍 `is_batchable` 返回 `true`，房间进入 B 站批量状态。

只多一次整行 UPDATE，没有额外网络请求。

### 例 2：只有 UID 变化

数据库 `platform_uid='42'`，平台返回 `43`，其他字段全部相同：

- 旧逻辑：`structural=false` → `touch_room_throttled`，UID 仍是 `42`；
- 新逻辑：UID 差异令 `structural=true` → 写库为 `43`。

### 例 3：平台没返回 UID

数据库 `platform_uid='42'`，平台这次 `extra.uid` 缺失或为 `0`：

- `platform_uid_of` 返回 `None`；
- 不触发 UID 写库；
- `update_room_info` 若因其他字段变化被调用，`COALESCE(NULL, platform_uid)` 仍保留 `42`。

不会出现「平台偶尔没给 UID，本地就被清空」的抖动。

### 例 4：离线房间

房间当前离线，但平台 `room_info` 正常返回 UID，且本地 UID 为空：

- `is_live` 相同、标题相同，UID 差异仍令 `structural=true`；
- 离线状态也会补 UID；
- 下次开播时可以直接走批量，不必再等一轮单查。

## 5. 边界与不做什么

1. **平台不返回 UID 时不会凭空生成。** 只能等下一次成功检查或重新添加；日志仍会显示单查。
2. **写库失败不会阻塞监控。** `update_room_info` 失败只记 WARN，下一拍仍会因 UID 差异重试。
3. **暂停监控的房间不会主动补。** 没有检查就没有新 UID；恢复监控后的第一次成功检查补写。
4. **没有新增启动回填任务。** 不为缺 UID 的房间额外发请求；避免启动时对几百个房间制造请求尖峰。
5. **没有改 `touch_room_throttled`。** UID 差异已经走整行更新；让节流语句也写 UID 会造成两条写路径，反而难排查。

---

## 6. 验收结论

- 成功检查只要平台返回有效 UID，`platform_uid` 就会落库，与标题/封面是否变化无关；
- 平台不返回 UID 时保留旧值，不会把已有 UID 冲掉；
- 单房间与批量路径共用同一判断，避免两条链路行为分叉；
- 新增单测覆盖「缺失补写 / 相同不写 / 变化改写 / 空值不写」与真实 SQL 持久化；
- 303 tests 通过，0 警告。
