# 130 · 取流与线路：四平台实现对照

> 适用范围：从用户输入 URL 到拿到「可交给 ffmpeg 的直链 + 请求头」这一段。
> 不包含：录制进程管理（见 131）、登录态获取（见 132）、弹幕（见 133）。
> 参考基线：bililive-go（MIT）、biliLive-tools（GPL，只借设计）、streamlink（BSD-2-Clause）。

---

## 1. 职责边界

平台适配层只做四件事，任何一件之外的事情都不应出现在 `src-tauri/src/platform/`：

1. `matches` / `resolve`：纯本地把输入变成 `RoomRef`，不联网。
2. `room_info`：一次请求拿房间状态与展示信息。
3. `stream_plan`：一次请求拿全部线路/画质/格式/直链。
4. 把平台错误翻译成统一的 `PlatformError`。

**不要**在适配层里下载、探测码率、起 ffmpeg、写文件、重试整场录制。三个参考项目都遵守这条边界：bililive-go 的 `Live` 只返回 `StreamInfo`；biliLive-tools 的 Recorder 只返回 `sources/streams`；streamlink 的 Plugin 只返回 `Stream` 对象。

## 2. 统一数据模型

当前 HIVECAST 的类型定义在 `src-tauri/src/platform/mod.rs`：

```rust
pub struct RoomRef {
    pub platform: String, pub room_key: String,
    pub canonical_url: String, pub input: String,
}
pub struct RoomInfo {
    pub host_name: String, pub room_name: String,
    pub avatar_url: Option<String>, pub cover_url: Option<String>,
    pub area_name: Option<String>, pub is_live: bool,
    pub started_at: Option<i64>, pub online: Option<u64>,
    pub extra: serde_json::Value,
}
pub struct StreamCandidate {
    pub id: String, pub name: String, pub weight: f64,
    pub format: StreamFormat, pub codec: Option<Codec>,
    pub width: Option<u32>, pub height: Option<u32>, pub fps: Option<f32>,
    pub bitrate_kbps: Option<u32>, pub url: Option<String>,
    pub headers: BTreeMap<String, String>,
    pub attrs: BTreeMap<String, String>,
}
pub struct StreamGroup { pub name: String, pub priority: u32, pub candidates: Vec<StreamCandidate> }
pub struct StreamPlan { pub groups: Vec<StreamGroup>, pub qualities: Vec<QualityInfo> }
```

与 biliLive-tools 的对应关系（`packages/StreamGet/src/types.ts`）：

| HIVECAST | biliLive-tools | 说明 |
| --- | --- | --- |
| `StreamGroup` | `SourceInfo` | 一条线路/CDN，组名给用户看 |
| `StreamCandidate` | `StreamInfo` | 一档画质 + 一种格式 |
| `weight` | 无（用数组顺序） | 组内比较：B 站 qn、斗鱼码率、虎牙码率、抖音档位 |
| `attrs` | 可扩展字段 | 放 qn/协议/编码原名，不参与展示排序 |

**关键取舍**：不把「线路」拍平成候选数组。拍平后无法回答「这条 CDN 挂了还有哪条」，也无法做备线切换。

## 3. 解析顺序与错误

```text
resolve(input) ──失败──▶ InvalidInput
   │
room_info(ref) ──HTTP 4xx/5xx──▶ Upstream / Throttled
   │           ──房间不存在──▶ RoomNotFound
   │           ──明确下播────▶ NotLive（room_info 返回 is_live=false）
   ▼
stream_plan(ref) ──无候选──▶ NoStream
   │             ──需要登录/付费──▶ NeedAuth（建议新增）
   ▼
pick(candidates) ──全部不可用──▶ NoStream
```

三个参考项目的错误分类可以直接借：

- biliLive-tools `packages/StreamGet/src/errors.ts`：`UNSUPPORTED_PLATFORM / ROOM_NOT_FOUND / NOT_LIVING / NETWORK_ERROR / PARSE_ERROR`。
- bililive-go 的 `RoomNotFound` / `Status=false` 两态（虎牙页面文案判断，`src/live/huya/huya.go`）。
- HIVECAST 现有 `PlatformError`：`Unsupported / RoomNotFound / NotLive / Upstream{code,message} / Network / Parse / Throttled{retry_after}`；没有独立的 `NoStream`，建议补 `NeedAuth / RoomClosed / ToolMissing`。

**不要**把「页面结构变了」当成 `NotLive`。前者是 Parse（要报警、要修代码），后者是正常业务状态（不报警）。

## 4. B 站

### 4.1 调用链

1. `GET https://api.live.bilibili.com/room/v1/Room/get_info?room_id={rid}`
   - `room_id` 支持短号，返回真实 `room_id`、`live_status`、`title`、`user_cover`、`live_time`。
   - `live_time` 可能是文本或数字，HIVE 在 `bilibili.rs` 做了双解析。
2. `GET https://api.live.bilibili.com/live_user/v1/UserInfo/get_anchor_in_room?roomid={rid}`
   - 拿 `info.uname` 与 `info.face`；失败不应阻断取流。
3. `GET https://api.live.bilibili.com/xlive/web-room/v2/index/getRoomPlayInfo`
   - 固定 query（bililive-go `bilibili.go:164`）：
     `room_id, protocol=0,1, format=0,1,2, codec=0,1,2, qn=10000, platform=web, ptype=8, dolby=5, panorama=1`。
   - `codec=2` 会带回 AV1；观看可用，录制侧会在选流时过滤（见 §4.6）。
   - 返回 `playurl_info.playurl.stream[]`，三层结构：stream(`protocol_name`) → format(`format_name`) → codec(`codec_name`) → `url_info[]`。

### 4.2 URL 与画质

- 每个 `url_info`：`url = host + base_url + extra`。
- `accept_qn` 是这一路编码实际支持的画质集合；HIVE 用它反推「每档画质有哪些编码」，用于 MSE 门禁。
- 展示名取 `g_qn_desc[current_qn]`，`weight = current_qn`；这样「请求 10000、实际 250」会显示为超清，而不是原画。

B 站 qn 表（bililive-go / biliLive-tools 一致）：

| qn | 含义 | 备注 |
| --- | --- | --- |
| 30000 | 杜比 | 需要 `dolby=5`，多数录制器不支持；B 站接口最高档 |
| 25000 | 原画真彩 | 登录账号常见高档，FLV/H.264 可录 |
| 20000 | 4K | 需要登录 + 大会员 |
| 15000 | 2K | 页面 `g_qn_desc` 会返回；需权限/编码门禁 |
| 10000 | 原画 | 旧默认请求值 |
| 400 | 蓝光 | 旧档位 |
| 250 | 超清 | 未登录常见上限 |
| 150 | 高清 | |
| 80 | 流畅 | |

### 4.2.1 最高哨兵与能力探测

- 应用层 40000 = 「最高可用」；`request_qn(40000)` 映射成 B 站 `QN_MAX=30000`，不直接把 40000 发给平台。
- **线路**按用户目标档位请求；**能力清单**另发一次 `qn=30000` 探测。不能拿请求 10000 的响应判断 2K/4K/杜比：登录账号请求 10000 时 `current_qn` 会被封在 10000，菜单会把高档全标灰。
- 高档探测成功：`granted_qn = max(current_qn)`，`quality_available = accepted.contains(qn) && qn <= granted_qn`。
- 高档探测失败：回退 base 清单，`probed_high=false`，沿用旧规则（`granted>=10000 || qn<=granted`），不把未知高档直接标灰。
- `build_qualities` 合并 `g_qn_desc` 与 `accept_qn`，按 qn 降序；`quality_hint` 让「杜比」优先于 HEVC/AV1。
- 实测房间 `22637261`：granted=25000，菜单出现 25000「原画真彩」，30000/20000 标灰，15000 因房间 `accept_qn` 不含而标灰。详见 [142](142-B站画质档位与高档探测修复.md)。

### 4.3 格式优先级

biliLive-tools `BilibiliRecorder/src/stream.ts` 的排序可直接借：

```text
http_stream/flv/avc  9
http_hls/fmp4/avc    8
http_hls/ts/avc      7
http_stream/flv/hevc 6
http_hls/fmp4/hevc   5
http_hls/ts/hevc     4
```

理由：FLV/AVC 对 ffmpeg 最稳、可边录边播；HEVC 只有在用户明确要「更小体积」时才优先。HIVE 当前按「格式 rank + 编码 rank」组合，等价于这张表。

### 4.4 请求头

- 页面/接口：`User-Agent` + `Referer: https://live.bilibili.com/{rid}` + 登录 Cookie。
- 直链（CDN）：至少 `User-Agent` + `Referer: https://live.bilibili.com/{rid}`。
- **不要**把 `SESSDATA` 发给 CDN；HIVE 在 `credential.rs` 按域名白名单注入，直链域名不在白名单内。
- 现状：`bilibili.rs:24` 的 `REFERER` 是首页常量，直链 headers 直接复用；应改成 `https://live.bilibili.com/{rid}`，否则部分 CDN 会 403 或降档（见 129 §6 P0-1）。

### 4.5 可录性门禁（HIVE 缺失）

biliLive-tools 在取流前判四类：

| 类型 | 判据 | 处理 |
| --- | --- | --- |
| 付费 | `room_init.is_sp==1` 或 `special_type==1` | 标 `paid`，提示需购买 |
| DRM | `all_special_types` 含 `203` | 不录，提示加密 |
| 大航海 | 有 `playurl_info` 但 `stream` 为空 | 标 `guard`，提示需上舰 |
| 密码房 | 房间信息带密码标记 | 提示输入密码 |

取流接口异常时按 `normal` 放行，避免因接口抖动漏录——这一点值得保留。

### 4.6 AV1 录制门禁

`codec=0,1,2` 后 B 站可能返回 AV1。观看侧走 MSE，有编码能力门禁；录制侧不能把 AV1 直接 `-c copy` 进 MPEG-TS/Matroska 分片，否则 ffmpeg 报 `Output file does not contain any stream`，产物 0 字节。

- `best_in_group` 过滤 `Codec::Av1`；
- 整份 plan 只有 AV1 时，开录返回「当前直播只提供 AV1 编码，录制链路暂不支持 AV1」，不笼统报「没有可用的线路」；
- 若未来 ffmpeg 支持 AV1 直封装，可去掉过滤并补真实录制验收。

## 5. 斗鱼

### 5.1 房间信息

`GET https://www.douyu.com/betard/{rid}`：

- `room.show_status == 1` 且 `room.videoLoop == 0` 才算直播。
- `room.owner_name` / `room.room_name` / `room.room_pic`。
- 只认 `videoLoop==0` 是为了排除「录播循环」伪装成直播。

### 5.2 签名

斗鱼没有可直接拼的公开 play 接口，需要两步：

1. `GET https://www.douyu.com/swf_api/homeH5Enc?rids={rid}`
   返回一段 JS（`ub98484234`），里面含 `enc_time`、`key`、`is_special` 等常量。
2. 生成 `auth`：
   ```text
   f = 随机串
   重复 enc_time 次：f = md5(f + key)
   suffix = is_special == 1 ? "" : rid + 服务器时间戳
   auth = md5(f + key + suffix)
   ```

- `tt` 用**服务器 `Date` 响应头**，不是本机时间；本机时钟偏差会导致签名过期。
- 参考实现差异：bililive-go 用 goja 执行页面 JS（失败 panic）；streamlink 用纯 Python md5 链；biliLive-tools 用纯 JS md5 链。**HIVE 应采用纯 Rust md5 链**，不引入 JS 运行时。

### 5.3 取流

`POST https://www.douyu.com/lapi/live/getH5PlayV1/{rid}`，`application/x-www-form-urlencoded`：

```text
enc_data, tt, did, auth, cdn, rate, hevc, fa, ive
```

- 返回 `rtmp_url` + `rtmp_live`，拼成 FLV 直链；HIVE 会把 `http://` 升级为 `https://`。
- `multirates[]` 给出所有码率档：`name`（原画/蓝光/超清…）、`rate`、`bit`。HIVE 用 `bit` 做排序，用 `rate` 请求。
- 线路：对返回的 `cdnsWithName` 逐条再请求，形成多个 `StreamGroup`。

### 5.4 did

- 参考实现：streamlink 固定 `10000000000000000000000000001501`；bililive-go 优先 Cookie 里的 `dy_did/acf_did/acf_devid`，否则 UUID 去横线并固定生命周期。
- HIVE 当前：`md5(机器名)`。问题：同一台机器多实例相同、换机就变、卸载重装也变。
- 建议：首次生成 UUIDv4，去横线，落库到 `app_setting`，所有请求复用。

### 5.5 登录态与 CDN

bililive-go 实测：下载请求带登录 Cookie 可避免 CDN 约每 5 分钟把连接切成匿名流（`douyu.go:504-511`）。因此斗鱼直链**需要**带登录 Cookie，这点与 B 站相反。HIVE 的域名白名单要包含斗鱼 CDN 域（`*.douyucdn.cn` 等）。

## 6. 虎牙

### 6.1 房间信息

没有稳定公开 API，抓房间页 HTML：

- `var hyPlayerConfig = {...}` 或 `window.HyPlayerConfig`；可能是裸 JSON，也可能 base64。
- 字段：`stream: "base64(json)"`、`nick`、`isOn`、`liveTime`。
- 错误页文案： 「哎呀，虎牙君找不到这个主播」→ `RoomNotFound`；「该主播涉嫌违规，正在整改中」→ 在播但不可用。
- HIVE 当前用正则提取 `nick/isOn/stream`；建议加一层「JSON 优先、正则兜底」，减少页面小改就 Parse 失败。

### 6.2 antiCode

虎牙直链必须带 `wsSecret/wsTime/seqid/uid/fs` 等参数，算法：

```text
uid      = 随机数 + 1200000000000
seqid    = 当前毫秒 + uid
t        = 100
ver      = 1
sv       = 2405220949（参考实现固定值，会随页面变）
codec    = 264
ss       = md5(seqid | ctype | t)
fm       = base64(ss) 后做 $0-$3 替换（把 base64 里的 + / = 换成 _ -）
wsSecret = md5(fm)
wsTime   = hex(now_seconds)
```

- `ctype` 是流名（如 `huya_live`），`fs` 是流地址里的 hash。
- 参考实现里 `t=100` 表示「常亮/回看」；直播也用 100，不要改成 0。
- streamlink 的 `convert_uid` 变体：`((uid << 8) | (uid >> 24)) & 0xFFFFFFFF`，用于旧版 antiCode；HIVE 当前按 bililive-go 的公式，遇到 403 时再切。
- **每次取流都要重算**：`wsTime` 与 `seqid` 都带时间，缓存直链会在几分钟后 403。

### 6.3 线路与编码

- `gameStreamInfoList[]` 每条含 `sCdnType`（线路名）、`sStreamName`、`sFlvUrl`、`sFlvUrlSuffix`、`sHlsUrl`。
- HIVE 按 `sCdnType` 分组，组内按 `vMultiStreamInfo` 的画质档生成候选。
- `vMultiStreamInfo[]` 含 `iBitRate`、`sDisplayName`，以及 H.265 的 `iHEVCBitRate`；HEVC 只在客户端支持且用户允许时启用。
- 画质与码率不是线性映射：同一个 `ratio` 在不同主播可能对应不同码率，**用返回的码率排序，不要用档位名猜**。

### 6.4 请求头

- 页面：正常浏览器 UA + Referer。
- 直链：`User-Agent` + `Referer: https://www.huya.com/{room}`；部分 CDN 还要 `Origin`。
- 虎牙对 UA 与签名的一致性敏感：签名时的 UA 与下载时的 UA 必须相同，否则 403。

## 7. 抖音

### 7.1 调用链

1. 先访问 `https://live.douyin.com/{rid}` 预热，拿 `ttwid`（Set-Cookie）与页面 `__ac_nonce`。
2. 用 `abogus` 对 `webcast/room/web/enter` 的 query 签名，带 `ttwid` 请求。
3. `data.data[0].status == 2` 为直播中；`status == 4` 为已结束。
4. 直链在 `data.data[0].stream_url`：`flv_pull_url` 与 `hls_pull_url_map`，档位 `FULL_HD1/HD1/SD2/SD1`。

### 7.2 abogus

- 算法：SM3 双层 + RC4(UA) + 自定义 base64；HIVE 在 `src-tauri/src/platform/douyin_sign.rs` 有独立 Rust 实现。
- 输入包含 query、UA、当前时间、`__ac_nonce`；**UA 必须与后续下载一致**，否则签名失效。
- 未登录还需要 `__ac_signature`；HIVE 当前只在登录态下稳定，匿名场景建议直接提示「请先登录抖音」。
- 不要引入 biliLive-tools 的 485KB `sign.js` 或每次建连起 JS 运行时。

### 7.3 档位与格式

| 档位 | 含义 | 备注 |
| --- | --- | --- |
| FULL_HD1 | 原画/蓝光 | 通常最高 |
| HD1 | 高清 | |
| SD2 | 标清 | |
| SD1 | 流畅 | |

- 抖音只保证 FLV 可用；HLS 有时是同一路转封装，优先 FLV（延迟低、ffmpeg 稳）。
- 直链有效期短（约几分钟），且带签名参数；**每次录制/重连都重新取流**，不要缓存超过 5 分钟。

## 8. 候选选择策略

HIVE 的选择顺序（建议固化为函数并写单测）：

```text
1. 过滤：format/codec 不被前端 MSE 支持；画质低于用户下限；url 为空
2. 画质：按 StreamPlan.qualities 选中目标 QualityInfo，再筛 attrs.qn/id 对应的候选
3. 组内：weight 降序；同 weight 时 bitrate_kbps 高者优先
4. 线路：用户指定线路优先，否则组 priority 升序 / 上次成功线路
5. 编码：avc > hevc（用户开启 HEVC 时反转）
6. 格式：flv > hls/fmp4 > hls/ts（B 站另有 9/8/7/6/5/4 表）
```

HIVE 的 `weight` 已经是平台原生尺度：B 站是 `current_qn`，斗鱼/虎牙是码率，抖音是档位权重。**不要跨平台比较 weight**，它只在同一线路组内有意义。

反面教材：streamlink 的 `stream_weight` 把 `720p60` 算成 `720+60=780`，与 `1080p` 的 `1080` 比较，结果 720p60 低于 1080p30 却高于 1080p？实际是 780 < 1080，看似合理，但 `4k` 与 `4320p` 又会打架。**显式 rank 表更可控**。

## 9. 请求头与下载需求（HIVE 当前最大缺口）

ffmpeg 的 `-headers` 有两个硬约束（bililive-go `ffmpeg.go:324-365`）：

1. 必须放在 `-i` **之前**，否则 ffmpeg 忽略。
2. `-headers` 是整体赋值，多次出现只有最后一个生效；必须合并成一个字符串，行分隔用 `\r\n`。

建议新增统一函数（录制与观看共用）：

```rust
pub struct DownloadRequirements {
    pub headers: Vec<(String, String)>, // UA / Referer / Origin / Cookie（按域）
    pub user_agent: String,
    pub referer: Option<String>,
}
fn download_requirements(platform: PlatformId, room: &RoomRef) -> DownloadRequirements
```

规则：

- B 站：UA + `Referer: https://live.bilibili.com/{rid}`；不带 Cookie 给 CDN。
- 斗鱼：UA + `Referer: https://www.douyu.com/{rid}` + 登录 Cookie（CDN 需要）。
- 虎牙：UA + `Referer: https://www.huya.com/{rid}` + `Origin`。
- 抖音：UA（与签名一致）+ `Referer: https://live.douyin.com/{rid}` + `ttwid`。

**现状问题**：候选里的 `headers` 只由平台适配层填，B 站只填了首页 Referer，抖音为空；录制与观看都直接使用候选 headers，导致部分场景 403 或静默降档。修复应落在「下载需求」这一层，而不是在每个平台里补字符串。

## 10. 反模式清单

- 把 Cookie 无条件透传给 CDN（B 站/虎牙不需要，泄露登录态）。
- 用本机时间做斗鱼 `tt`（时钟漂移 → 签名过期）。
- 缓存虎牙/抖音直链超过 5 分钟（签名过期 → 403）。
- 把「请求 qn=10000」当成「实际拿到原画」（要看 `current_qn` 与 `g_qn_desc`）。
- 取流失败一律 `NotLive`（用户会以为主播没开播，实际是接口/签名坏了）。
- 对同一房间并发调用 `room_info` 与 `stream_plan`（虎牙会抓两次页面，风控面翻倍）。
- 把线路拍平后只留第一条（CDN 挂了无法切换）。

## 11. 实测清单（用 ego-browser + Cookie.txt）

对每个平台至少验证：

1. 未登录：能拿到哪些画质？是否 403？
2. 登录：画质是否提升？直链是否带登录态？
3. 断网/改错 Referer：错误是否归为 `Upstream` 而不是 `NotLive`？
4. 直链 5 分钟后是否还能播？（验证签名有效期）
5. 同一直链换 UA 是否 403？（验证 UA 一致性）
6. 线路组数量与顺序是否稳定？
7. 录制 60s 的 ffmpeg 日志里，是否真的带上了 `Referer`？
