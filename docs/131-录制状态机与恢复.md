# 131 · 录制状态机与恢复

> 适用范围：从「决定开始录」到「文件收尾、入库、可播放」这一段。
> 参考：bililive-go 的监听/重启循环、biliLive-tools 的 liveManager、streamlink 的分片写入。
> 结论先行：**录制不是一个 while(true) 里起 ffmpeg，而是「场次 + 尝试 + 分片」三层状态机。**

---

## 1. 三层状态模型

```text
场次 Session（一场直播）
  └── 尝试 Attempt（一次 ffmpeg 进程）
        └── 分片 Segment（一个 mpegts 文件）

Session:  waiting → recording → ending → done | failed | cancelled
Attempt:  starting → running → exited(0) | failed(code) | stalled | killed
Segment:  open → closed → merged
```

三个参考项目的映射：

| 层 | bililive-go | biliLive-tools | HIVECAST |
| --- | --- | --- | --- |
| 场次 | `Live` 的一次开播周期 | `channelId-liveId` | `record_session` 行 |
| 尝试 | `recorder.start()` 的每次重启 | downloader 的每次 ffmpeg | ffmpeg 子进程 |
| 分片 | ffmpeg `-f segment` / native flv 分片 | ffmpeg/mesio 分段 | mpegts 300s 分片 |

**为什么必须分三层**：只有场次层，无法区分「同一场重连 3 次」与「开了 3 场」；只有尝试层，无法在崩溃后恢复；只有分片层，无法向用户解释「为什么这场是失败的」。

## 2. HIVECAST 当前常量

实现位于 `src-tauri/src/recorder.rs` 与 `src-tauri/src/segment.rs`。这些值是行为契约，改动必须同步文档与单测：

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `EARLY_EXIT` | 12s | 进程在 12s 内退出视为「起播失败」，不计为正常结束 |
| `FAILURE_COOLDOWN` | 60s | 单次失败后的基础退避 |
| `MAX_RESTARTS` | 3 | 同一场次最多自动重启次数 |
| `MAX_STALL_RESTARTS` | 2 | 因「无数据/卡住」重启的上限 |
| `STALL_TIMEOUT` | 60s | 无新分片/无输出增长多久判定卡住 |
| `ENDED_BLOCK` | 600s | 平台确认下播后，多久内不再尝试 |
| `MAX_EOF_RETRIES` | 2 | 正常 EOF 后的重连次数 |
| `FAILED_STREAK_LIMIT` | 3 | 连续失败多少场后进入冷却 |
| `FAILED_STREAK_COOLDOWN` | 300s | 连续失败冷却时长 |
| `START_FAILURE_LIMIT` | 3 | 起播连续失败次数上限 |
| `START_FAILURE_COOLDOWN` | 300s | 起播连续失败冷却 |
| `HEALTHY_RESET` | 30min | 稳定录制多久后清零失败计数 |
| `PLATFORM_RECHECK_DELAY` | 20s | 失败后回到平台复查的延迟 |
| 分片时长 | 300s | mpegts 单片时长（`segment.rs:17`） |

参考阈值对照：

- biliLive-tools：短录制 12s、同场连续 2 次失败切备流、立即重试 10 次且要求已录 ≥60s、检测间隔 60s、3 线程。
- bililive-go：fastFail 5s；重试 5s 起翻倍，本场从未拉流过上限 60s、拉过流上限 15s。
- streamlink：分片失败只告警继续；HLS 以 live-edge 为准，固定节拍扣 fetch 耗时。

**取舍**：HIVE 的 60s 退避比 bililive-go 的「5s 翻倍」更保守，适合桌面端少打扰；但应加 jitter（±20%），避免多房间同时重连打爆平台。

## 3. 状态流转

### 3.1 开始录制

```text
用户点录制 / 自动录制命中
        │
        ▼
检查门禁：已在下播？付费/加密？磁盘够？ffmpeg 存在？
        │ 失败 → 记录原因，Session=failed，UI 显示可读原因
        ▼
创建 Session（platform, room_key, title, started_at, output_dir）
        │
        ▼
Attempt #1：取流（重新 stream_plan）→ 起 ffmpeg
        │
        ├── 12s 内退出 → Attempt=failed，按退避重试
        ├── 正常运行   → Attempt=running，开始写分片
        └── 60s 无增长 → Attempt=stalled，杀掉并重试
```

### 3.2 重试决策表

| 情况 | 判定 | 动作 |
| --- | --- | --- |
| ffmpeg 非 0 退出，且本场从未出过分片 | 起播失败 | 退避 5s/10s/20s（上限 60s），最多 `START_FAILURE_LIMIT` 次 |
| 已出分片后非 0 退出 | 中途断流 | 20s 后重取流，最多 `MAX_RESTARTS` 次 |
| 60s 无新分片/无增长 | 卡住 | 杀进程，最多 `MAX_STALL_RESTARTS` 次 |
| ffmpeg 正常退出（EOF） | 流结束/被切 | 先复查平台是否仍在播；在播则最多 `MAX_EOF_RETRIES` 次 |
| 平台明确 `is_live=false` | 下播 | 收尾，不再重试；600s 内不重复检查 |
| 用户手动停止 | 取消 | 立即收尾，不重试，不进入连续失败计数 |

**关键细节**：手动停止必须与失败区分。bililive-go 用 `stopFlag`；biliLive-tools 用 `manualStop` 并写 `tempBanObj`。HIVE 应记录 `stop_reason` 枚举，而不是只写一个布尔。

### 3.3 收尾

```text
停止写入 → 关闭当前分片 → 合并（或保留分片）
        → 探测时长/大小 → 生成缩略图 → 写 DB → 触发后处理
```

收尾必须幂等：崩溃恢复时再次执行不能产生重复文件或重复 DB 行。建议用 `session_id + state` 做幂等键。

## 4. 分片与文件

### 4.1 为什么用 mpegts 分片

- ffmpeg `-f segment -segment_format mpegts` 崩溃时最多丢最后一个分片，前面可播。
- 合并时直接 `concat`，不需要转码。
- 代价：mpegts 有 188 字节包开销，体积略大于 flv；收尾可转封装为 mp4/mkv（见 10 后处理文档）。

### 4.2 命名

建议延续 bililive-go 的可读模板，但把「场次」放进去：

```text
{platform}/{anchor}/{yyyy-MM-dd HH-mm-ss} {title} [{room_key}]/
    part-000.ts
    part-001.ts
    cover.jpg
    danmaku.jsonl
    session.json
```

- 文件名必须过滤 `/ : * ? " < > |` 与系统保留名；长度按字节截断，不要按字符截断（bililive-go 在长标题上踩过）。
- 同一场重启不新建目录；只有「新场次」才新建。

### 4.3 崩溃恢复

启动时扫描未收尾的 `record_session`：

1. 目录存在且有分片 → 标记 `interrupted`，后台合并并入库。
2. 目录不存在/空 → 标记 `failed`，附原因。
3. 有 `.part` 临时文件 → 删除或忽略，不能当成正式分片。

## 5. ffmpeg 参数

推荐形态（HIVE 当前实现以此为基础）：

```text
ffmpeg -hide_banner -nostdin -y
  -headers "User-Agent: ...\r\nReferer: ...\r\n"
  -i <url>
  -c copy
  -f segment -segment_format mpegts -segment_time 300
  -reset_timestamps 1
  -segment_start_number 0
  part-%03d.ts
```

要点：

1. `-headers` 必须在 `-i` 前，且只出现一次（见 130 §9）。
2. `-c copy` 不转码；平台给 HEVC 就录 HEVC，后处理再决定是否转 H.264。
3. `-reset_timestamps 1` 让每个分片从 0 开始，合并更稳。
4. `-nostdin` 防止 ffmpeg 抢终端输入。
5. 不要用 `-t` 或 `-fs` 做业务分段；业务分段应由 `-f segment` 或应用层控制。
6. 进程要用进程组启动，停止时先 `SIGINT`，超时再 `SIGKILL`；只杀父进程会留下子进程。

biliLive-tools 的 fMP4 参数 `-movflags faststart+frag_keyframe+empty_moov -min_frag_duration 10000000` 适合「边录边播」，但 HIVE 已有独立播放链路，不必照搬。

## 6. 失败原因与用户可见文案

不要只存 ffmpeg 退出码。建议枚举：

| 原因 | 触发 | 文案（中文示例） |
| --- | --- | --- |
| `start_failed` | 12s 内退出 | 起播失败，可能是线路不可用 |
| `stream_ended` | EOF + 平台下播 | 直播已结束 |
| `network` | 连接重置/超时 | 网络中断，正在重试 |
| `forbidden` | 403/401 | 需要登录或权限不足 |
| `no_data` | 60s 无增长 | 流无数据，正在切换线路 |
| `disk_full` | 写入失败 ENOSPC | 磁盘空间不足 |
| `user_stopped` | 手动停止 | 已手动停止 |
| `cancelled` | 任务取消 | 已取消 |

这些原因要同时出现在：任务中心、录制详情、日志、DB。UI 不应把 `forbidden` 显示成「主播未开播」。

## 7. 与参考实现的差异

| 能力 | bililive-go | biliLive-tools | HIVECAST 现状 | 建议 |
| --- | --- | --- | --- | --- |
| 场次 ID | 无稳定 ID | `md5(channelId-startTime)` | `record_session.id` | 保持自增 + 平台场次键 |
| 短录制换线 | 无 | 有（<12s 两次） | 无 | 加 `prefer_alt_line` |
| 立即重查 | 有（5s 翻倍） | 有（≥60s，10 次） | 有（20s 平台复查） | 补 jitter |
| 卡住检测 | 看进程/日志 | frame 连续不变 35/18 | 60s 无增长 | 可再加「码率突降」 |
| 分片 | ffmpeg `-fs` / native flv | ffmpeg/mesio | mpegts 300s | 保持 |
| 崩溃恢复 | 有（临时文件清理） | 有（任务表） | 有（扫描 session） | 保持并加单测 |

## 8. 单测与真机验收

单测（不依赖网络）：

1. 状态机：起播失败 → 退避 → 达到上限 → `failed`。
2. 手动停止不增加失败计数。
3. 连续 3 场失败 → 冷却 300s；第 4 场手动开始可绕过。
4. 60s 无增长 → 杀进程 → 切备线。
5. 崩溃恢复：只有 1 个分片时也能合并；空目录标记 failed。

真机（用 ego-browser + Cookie.txt）：

1. 录 70s 后手动停：文件可播、DB 有 session、缩略图存在。
2. 录制中拔网 30s：应出现 `network`，恢复后继续同一场。
3. 录制中关掉主播（或换到无流房间）：应收尾为 `stream_ended`，不无限重试。
4. 录 6 分钟：应产生 ≥2 个分片，合并后时长连续。
5. 强杀 app：重启后未收尾场次应被修复，不产生重复记录。

## 9. 反模式

- 用 `while true { spawn ffmpeg }` 且不区分退出原因。
- 失败后立即重试，没有退避/jitter。
- 手动停止也计入「连续失败」，导致用户被冷却。
- 只杀 ffmpeg 父进程，留下僵死子进程继续写文件。
- 用文件大小判断「还在录」，但平台码率波动会导致误判；应看「新分片/输出增长」。
- 收尾时删除源分片却没有成功合并；必须先校验输出再删。
- 把「平台下播」和「取流失败」都写成同一个 `failed`。
