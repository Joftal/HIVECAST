### 1.1 未确认收尾为什么不再静默

`finalize` 现在分三层：

1. **先算归类**：`stop_reason` 存在或平台确认离线才算 `stream_ended`；否则即使退出码是 0 也只是「干净收尾」。
2. **再算惩罚**：`unconfirmed_end(final_status, reason, confirmed_end)` 为真时走 `note_hard_failure`，第 3 次打「连续未确认收尾，暂停自动重试 5 分钟」，与「连续失败」共用同一套冷却。
3. **最后才清理**：只有 `failed_streak == 0` 才清失败计数与硬失败，避免刚记上的惩罚被同一次收尾的「成功」分支抹掉；缩略图照做。

这样「秒退循环」和「平台真下播」在数据库里都还是 `finished/stream_ended`，但后者有 `confirmed_end` 凭据，前者没有——通知、静默、冷却全部以后者为准。

## 3. 真机验收

环境同 58：macOS 27.0.1 arm64、ffmpeg 9.0.2、DB `~/Library/Application Support/com.hivecast.desktop/hivecast.db`、测试房间 douyu 9999（真实在播，DB id `rm-audit-b` / `rm-audit-c`）。

### 3.1 B1/B3/B4：伪造 ffmpeg 秒退（PATH 前置 `/tmp/fakebin`）

假 ffmpeg 收到 `part%04d.ts` 参数就写 200 KB、0.3 秒后 `exit 0`，平台侧完全真实（斗鱼 9999 在播）。

| 时间 | 事件 |
| --- | --- |
| 23:32:29 | 开始录制（会话 1） |
| 23:32:33 / 37 / 42 | 断流后续录 restarts=1/2/3（每次间隔 3 秒，符合预期） |
| 23:32:43 | WARN「续录次数用尽」→ WARN「续录失败，按平台状态收尾 confirmed=false」→ 录制结束 `finished/stream_ended` |
| 23:32:43 | WARN「未能确认平台已下播，本次收尾不弹结束通知 failed_streak=1 confirmed_end=false」 |
| 23:32:59 | 监控重新开录（16 秒后，不是 600 秒） |
| 23:33:13 / 23:33:26 | 第 2、3 次同样收尾，failed_streak=2、3 |
| 23:33:40 | WARN「连续未确认收尾，暂停自动重试 5 分钟」 |

与 58 的 T9 对比：当时同一条路径记 `finished/stream_ended` 后立刻写 600 秒静默，期间不重开；现在每个会话结束 15 秒左右就由监控重开，且从不发「直播已结束」。

3 GiB 稀疏 APFS 卷 + `HIVECAST_MEDIA_DIR=/Volumes/HIVECASTTEST/Recording`，录到一半 `dd` 写 2050 MiB，把剩余压到 789 MiB（红线 1 GiB）。

## 4. 常量与行为变化

| 项 | 之前 | 现在 |
| --- | --- | --- |
| 离线确认窗口 | 180 秒内两次（间隔 >180 秒永远不确认） | 无窗口，连续两次成功检查（中间在播即清零） |
| 停录幂等 | 每次调用都重发 SIGINT 并打 INFO | 同理由忽略；仅用户停录可覆盖磁盘红线 |
| 续录后的退避 | `invalidate` 清共享冷却 | 只丢地址缓存，保留 failures |
| 未确认收尾 | 发通知 + 静默 600 秒 | 不通知、不静默、计入连续失败（3 次冷却 5 分钟） |
| 设置/房间读取 | 每拍各一次 | 2 秒 TTL |
| 刷新自动开录 | `start()`，绕过所有闸门 | `start_checked()`，与监控同条件 |

## 5. 验收结论

- 58 的 B1–B9 全部落地，B1 的真机复现路径已从「丢 10 分钟 + 误报下播」变成「只记未确认收尾 + 十几秒后重开 + 3 次冷却」。
- 磁盘红线不再每秒重发停止请求，SIGTERM 收尾没有回归。
- 仍有 6 项靠单测/代码审查保障（见 §3.3），其中 B2 与 B9 建议下次有 UI 自动化时补真机用例。
