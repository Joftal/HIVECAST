# 122-三平台画质与线路真实性与映射修复

> 状态：v1 已实施（2026-11-09）；已用 bilibili / 斗鱼 / 虎牙 的真实接口数据核对，并修复画质、线路链路上的映射与重启问题。
> 范围：观看页画质/线路、`room_lines`、`view_set_quality`、bilibili / douyu / huya 适配器。

## 0. 结论速览

- 画质和线路都是真实功能，不是占位：
  - B 站 `getRoomPlayInfo` 返回按 CDN host 分组的 `url_info`，并给出 `accept_qn` / `g_qn_desc`。
  - 斗鱼 `getH5PlayV1` 返回 `multirates` 与 `cdnsWithName`，线路是真实 CDN 列表。
  - 虎牙页面里的 `stream` JSON 返回 `gameStreamInfoList`（sCdnType 线路）与 `vMultiStreamInfo`（画质档位）。
- 本轮修复了 6 个真实问题：自动画质取错线路档、斗鱼 qn↔rate 错位、虎牙码率映射错位、B 站 40000 哨兵、错误态切画质不重启、线路失效时仍显示旧选中项。
- 现在的映射以平台真实档位名称为准：斗鱼 rate2 高清 / rate3 超清 / rate4 蓝光4M，虎牙 500 流畅 / 900 高清 / 2000 超清 / 4000 蓝光4M / 0 蓝光10M。
- `cargo check`、`cargo test --lib --no-run`、`tsc`、`build`、i18n 735 keys、docs 123 files 通过。

## 1. 真实接口抽查

### Bilibili

抽查 `getRoomPlayInfo`（room 6 与首页多个直播间）：

| 字段 | 结果 |
| --- | --- |
| `g_qn_desc` | 30000 杜比、20000 4K、15000 2K、10000 原画、400 蓝光、250 超清、150 高清、80 流畅 |
| `accept_qn` | 常见为 [15000, 10000, 400, 250, 150] |
| 线路 | 每次请求返回 5–7 个 CDN host，如 `d1--cn-gotcha08.bilivideo.com`、`cn-sdqd-cu-01-11.bilivideo.com` |
| 格式/编码 | flv、ts、fmp4；avc、hevc |
| 访客限制 | 官方赛事等房间即使请求 10000/20000，`current_qn` 仍可能被压到 250 |

结论：线路是真实 CDN 分组；画质的 qn 体系与 B 站一致，但访客权限会限制实际档位。

### 斗鱼

用与适配器相同的签名流程调用 `getH5PlayV1`（房间 138243）：

| rate | 平台名称 | 码率 |
| --- | --- | --- |
| 0 | 原画1080P60 | 约 15 Mbps |
| 4 | 蓝光4M | 4000 |
| 3 | 超清 | 2000 |
| 2 | 高清 | 900 |

- `cdnsWithName` 返回「线路7（hw-h5）」「线路13（hs-h5）」，是真实可切换 CDN。
- 请求 rate0 时，如果原画档不可用，服务端会返回 rate4（蓝光4M），需要在 UI 中体现降级。
- 请求 rate1 也会回落到 rate2（高清），说明该房间没有独立「流畅」档。

### 虎牙

抽查 `huya.com/660000` 页面内 `stream` JSON：

| 线路 | sCdnType |
| --- | --- |
| 阿里云 | AL、AL13 |
| 腾讯云 | TX、TX15 |
| 华为云 | HS、HS24 |

- H.264 画质：蓝光10M（0）、蓝光4M（4000）、超清（2000）、流畅（500）。
- 另有 4K/2K/HDR 条目，但 `iCodecType=1`，当前适配器只选 H.264（codec 0），避免录制/浏览器兼容问题。

结论：线路与画质均真实；HDR/4K 不在当前 H.264 兼容路径内。

## 2. 已修复问题

### 2.1 自动画质时线路列表用错档位

`WatchPage` 之前调用 `roomLines(roomId, requestedQn || undefined)`：自动画质 `requestedQn=0` 被转成 `undefined`，后端 `room_lines` 于是回退到**录制画质** `effective_record_qn`。观看和录制档位不同时，菜单里的线路不是当前观看流实际使用的线路。

修复：始终传 `requestedQn`，包括 `0`；后端 `Some(0)` 会按平台自动档位取线路。

### 2.2 斗鱼 qn 与 rate 整体错位一档

旧映射：

| 请求 qn | 旧 rate | 平台实际名称 |
| --- | --- | --- |
| 80 流畅 | 2 | 高清 |
| 150 高清 | 3 | 超清 |
| 250 超清 | 4 | 蓝光4M |
| 400 蓝光 | 8 | 不存在时回落到蓝光4M |

这会让「超清」实际拿蓝光4M，却把 actual_qn 记成 250；「蓝光」拿到蓝光4M 反而显示降级。

修复后的映射：

| qn | rate | rate 反推 qn |
| --- | --- | --- |
| 80 流畅 | 1 | 1 → 80 |
| 150 高清 | 2 | 2 → 150 |
| 250 超清 | 3 | 3 → 250 |
| 400 蓝光 | 8 | 4/8 → 400 |
| 10000 原画 | 0 | 0 → 10000 |

rate8 不存在时服务端返回 rate4，仍归为蓝光，不再误报降级。

### 2.3 虎牙码率映射错位

旧逻辑把 250 映射到 4000（蓝光4M），把 400 映射到 8000（没有该档，回落到 4000），并把 4000 反推成 250，导致「蓝光」显示降级、「超清」实际拿蓝光4M。

修复：

| qn | 目标码率 | 说明 |
| --- | --- | --- |
| 80 流畅 | 500 | 流畅 |
| 150 高清 | 1000 | 有 900 高清档则取 900 |
| 250 超清 | 2000 | 超清 |
| 400 蓝光 | 4000 | 蓝光4M |
| 10000 原画 | 0 | 蓝光10M / 源码率 |

`qn_for_bitrate` 同步改为：0/≥10M 原画、≥4M 蓝光、≥2M 超清、≥900K 高清、其余流畅。

### 2.4 B 站 40000 是应用层哨兵，不是 B 站 qn

B 站没有 qn 40000；`g_qn_desc` 最高常规档是 30000 杜比 / 20000 4K / 10000 原画。旧代码把 40000 直接发给 B 站，依赖平台回退。

修复：`BilibiliAdapter` 在请求前把 40000 归一化为 10000（原画），斗鱼/虎牙仍把 40000 视为最高可用。

### 2.5 出错后切画质不会重新拉起管线

`view.set_line` 在监督循环已退出时会重新 spawn，`view.set_quality` 不会。结果是出错态（`alive=false`）下改画质没有任何反应。

修复：`set_quality` 也返回 `needs_spawn`，必要时调用 `restart_supervisor`；同档位重选也会在 dead 状态下重新拉起。

### 2.6 手选线路消失时仍显示为已选

线路列表刷新后，如果 `preferredLine` 已不存在，前端会补一条同名假选项并把它勾上，但实际播放使用的是回退线路。

修复：线路列表确认加载完成后，若首选线路不存在，菜单选中实际使用的 `session.line`，不再伪造选项；加载中仍保留首选线路作为临时显示。

## 3. 保留的已知限制

- 画质选项仍是跨平台统一 qn 集合，没有按 B 站 `accept_qn` 动态生成；不支持 2K/4K/杜比等平台专有档位。
- 菜单没有“每条线路的完整画质列表”接口；后端只暴露线路组，组内 candidates 未返回给前端。
- B 站访客权限、斗鱼原画权限都可能让服务端主动降级；UI 用「↓ 实际画质」提示，不会假装成功。
- 虎牙 HDR/4K 条目是 H.265，当前兼容路径只取 H.264。
- 换线路仍保留当前画质请求；新线路缺档时由后端回退，入口标签仍显示请求值，降级由标题栏提示。
